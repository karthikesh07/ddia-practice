6.0 · The setup

Breaking up on purpose

Terminology guard

Partitioning, as discussed in this chapter, is a way of intentionally breaking a large database down into smaller ones. It has nothing to do with network partitions (netsplits) — faults in the network between nodes, which Chapter 8 covers. Same word, unrelated problem.

Chapter 5 gave us replication: multiple copies of the same data on different nodes. But for very large datasets or very high query throughput, replication alone isn’t enough — you need to break the data up into partitions, also known as sharding. And every system renamed it:

What everyone calls it

Shard in MongoDB, Elasticsearch, SolrCloud · region in HBase · tablet in Bigtable · vnode in Cassandra and Riak · vBucket in Couchbase. “Partitioning” is the most established term, so the book — and this site — uses it.

Definition — partition

Partitions are defined so that each piece of data (record, row, document) belongs to exactly one partition, and each partition is a small database of its own — though the database may support operations touching several at once.

The primary reason is scalability: in a shared-nothing cluster, partitions sit on different nodes, so a large dataset spreads across many disks and the query load across many processors. Partitioned databases were pioneered in the 1980s by products like Teradata and Tandem NonStop SQL, then rediscovered by NoSQL databases and Hadoop-based warehouses — some systems target transactional workloads, others analytics, but the fundamentals apply to both.

Partitioning and replication, together

Partitioning is usually combined with replication: copies of each partition live on multiple nodes, so a record belongs to exactly one partition and may still be stored on several nodes for fault tolerance. With leader–follower replication, each partition’s leader sits on one node and its followers on others — and each node is the leader for some partitions and a follower for others, spreading the load nicely. Everything from Chapter 5 applies to replication of partitions; the choice of partitioning scheme is mostly independent of the replication scheme.

Each partition has one leader and its followers on other nodes; each node leads some partitions and follows others. (A node may also hold more than one partition.)

The chapter’s route: approaches for partitioning large datasets, how secondary indexes interact with partitioning, rebalancing when nodes come and go, and how requests get routed to the right partition.

6.1 · Which record on which node?

Partitioning of key-value data

You have a large amount of data and want to partition it — how do you decide which records go on which nodes? The goal: spread data and query load evenly. If every node takes a fair share, 10 nodes should handle 10× the data and 10× the read/write throughput of a single node. When the split is unfair:

Skew
The partitioning is unfair — some partitions have more data or queries than others. Skew makes partitioning much less effective.
Hot spot
A partition with disproportionately high load. Extreme case: all the load lands on one partition, 9 of your 10 nodes sit idle, and the bottleneck is the single busy node.

The simplest approach — assign records randomly — distributes the data quite evenly, but to read any item you have no idea which node holds it, so you’d query all nodes in parallel. Useless. Assume instead a simple key-value model, always accessed by primary key — like an old-fashioned paper encyclopedia, where you look up an entry by title and everything is alphabetically sorted. Two ways to do it:

6.1.1 — Partitioning by key range

Assign a continuous range of keys (some minimum to some maximum) to each partition, like the volumes of a paper encyclopedia. If you know the boundaries, you know which partition contains a key; if you know which node has that partition, you send the request straight there (or pull the right volume off the shelf).

Figure 6-2 (recreated) · An encyclopedia, partitioned by key range

Volume 1 covers A–B, volume 12 covers six letters: one-volume-per-two-letters would make some volumes much bigger than others. Boundaries are chosen by an administrator or automatically, and adapt to the data.

Systems using key ranges: Bigtable, HBase, RethinkDB, and MongoDB before version 2.4. The payoff: within each partition, keys are kept in sorted order (SSTables, Chapter 3), so range scans are easy, and you can treat the key as a concatenated index to fetch several related records in one query.

The sensor example — range scans’ best friend, worst enemy

Say the key is the measurement timestamp (year-month-day-hour-minute-second) from a network of sensors. Range scans make it trivial to fetch all readings from a particular month. But the partitions are ranges of time — one per day, say — and since measurements are written as they happen, all writes land on the same partition: the one for today, which melts while the others idle. The workaround: prefix each timestamp with the sensor name, partitioning first by sensor, then by time — writes spread across sensors. The cost: fetching multiple sensors within a time range now takes a separate range query per sensor.

6.1.2 — Partitioning by hash of key

Because of skew and hot-spot risk, many distributed datastores hash the key to pick the partition. A good hash function takes skewed data and makes it uniform: a 32-bit string hash returns a seemingly random number in 0 to 2³² − 1, and even very similar inputs hash to evenly spread values. It needn’t be cryptographically strong — in practice:

  • Cassandra and MongoDB use MD5; Voldemort uses Fowler–Noll–Vo.
  • Your language’s built-in hash is probably unsuitable: Java’s Object.hashCode() and Ruby’s Object#hash can give the same key a different hash in different processes.

Each partition then owns a range of hashes rather than a range of keys: every key whose hash falls in the range lives in that partition. Boundaries can be evenly spaced or chosen pseudorandomly — the latter is what’s sometimes called consistent hashing (next section).

Figure 6-3 (recreated) · Partitioning by hash of key

Good at distributing keys fairly. Bad at anything involving order: adjacent keys scatter across partitions, so range queries are gone.

6.1.3 — “Consistent hashing”

As defined by Karger et al., consistent hashing evenly distributes load across an internet-wide system of caches (a CDN), using randomly chosen partition boundaries to avoid central control or distributed consensus. Note carefully: “consistent” here has nothing to do with replica consistency (Chapter 5) or ACID consistency (Chapter 7) — it describes an approach to rebalancing.

The term to avoid

This particular approach doesn’t actually work very well for databases, so it is rarely used in practice — and database documentation that still says “consistent hashing” is often inaccurate. Because it’s so confusing, the book’s advice is: avoid the term and just say “hash partitioning.”

The price of hashing: range queries

Hash partitioning loses key-range partitioning’s nice property — efficient range queries — because keys that were once adjacent are now scattered and their sort order is destroyed. Concretely: with MongoDB’s hash-based sharding mode, any range query must be sent to all partitions; range queries on the primary key are not supported at all by Riak, Couchbase, or Voldemort.

Cassandra’s compromise — the compound primary key

A Cassandra table can declare a compound primary key of several columns: only the first part is hashed to pick the partition, and the remaining columns form a concatenated index that sorts data within Cassandra’s SSTables. You can’t range-search the first column — but if you fix it, you get efficient range scans over the rest. Classic use: a social site where one user posts many updates, keyed (user_id, update_timestamp) — each user’s updates live sorted by timestamp on one partition, so “all of this user’s updates in this time interval” is one efficient scan, while different users spread across partitions.

6.1.4 — Skewed workloads and relieving hot spots

Hashing reduces hot spots but can’t eliminate them: if all reads and writes target the same key, every request still routes to the same partition. On a social media site, a celebrity with millions of followers can cause a storm of activity — a huge volume of writes to one key (the celebrity’s user ID, or the ID of the thing everyone’s commenting on). Hashing doesn’t help: the hash of two identical IDs is still the same.

3% Of Twitter’s servers, dedicated to Justin Bieber Samuel Axon, Mashable, September 7, 2010 — one user, three percent of the fleet

Today, most data systems cannot automatically compensate for such highly skewed workloads — reducing the skew is the application’s job. The technique: add a random number to the beginning or end of the key. A two-digit decimal random number splits the writes to one hot key evenly across 100 different keys, which then land on different partitions. The trade-offs:

  • Reads must now read all 100 keys and combine the results.
  • It demands bookkeeping: only hot keys should be split — for the vast majority of low-write keys it’s pure overhead, and you need a way to track which keys are being split.

Perhaps future data systems will detect and compensate for skew automatically; for now, you think through the trade-offs for your own application.

6.2 · The awkward tenant returns

Partitioning and secondary indexes

Everything so far assumed a key-value model: records reached only via their primary key, so the key determines the partition and routes the request. Secondary indexes complicate it. A secondary index usually doesn’t identify a record uniquely — it’s a way of searching for occurrences of a value: find all actions by user 123, all articles containing “hogwash”, all cars whose color is red. They are the bread and butter of relational databases, common in document databases, avoided by key-value stores like HBase and Voldemort for implementation complexity (though Riak added them out of usefulness) — and the raison d’être of search servers like Solr and Elasticsearch.

The core problem — and a DIY warning

Secondary indexes don’t map neatly to partitions. There are two approaches (below). And if your database only supports key-value, you might build your own index as a value→document-ID mapping in application code — in which case take great care to keep it consistent: race conditions and partial write failures easily desynchronize index from data (Chapter 7’s multi-object transactions exist for exactly this).

6.2.1 — Partitioning secondary indexes by document (local indexes)

The used-car website example: each listing has a unique document ID; the database is partitioned by document ID (IDs 0–499 in partition 0, 500–999 in partition 1, and so on). Users search by color and make — secondary indexes. If you declare the index, the database maintains it automatically: whenever a red car is added, the partition holding it adds the document to its list for color:red.

Each partition is completely separate: it maintains its own secondary index covering only the documents in that partition, caring nothing about other partitions. A document-partitioned index is also called a local index.

The read cost — scatter/gather

Nothing says all red cars live in the same partition — red cars appear in partition 0 and partition 1. So a search for red cars goes to all partitions, and the results are combined. This is scatter/gather, and it makes secondary-index reads quite expensive: even querying partitions in parallel, it’s prone to tail latency amplification (Chapter 1) — the query is as slow as the slowest partition.

Figure 6-4 (recreated) · Local (document-partitioned) secondary index

Every partition has red cars, so the query scatters to all and gathers the combination — as slow as the slowest partition. Used by MongoDB, Riak, Cassandra, Elasticsearch, SolrCloud, and VoltDB; most vendors recommend structuring partitioning so index queries hit one partition — but that’s not always possible, especially when combining multiple secondary indexes in one query (color and make).

6.2.2 — Partitioning secondary indexes by term (global indexes)

The alternative: build a global index covering data in all partitions. But we can’t store it on one node — it would be a bottleneck that defeats the purpose of partitioning. So the global index is itself partitioned, and it can be partitioned differently from the primary key: the color index might put colors starting A–R in partition 0 and S–Z in partition 1, while the make index splits between F and H. It’s called term-partitioned because the term you’re looking for determines the index partition — a term like color:red; the name “term” comes from full-text indexes, where the terms are all words occurring in a document.

Figure 6-5 (recreated) · Global (term-partitioned) secondary index

The index is partitioned by term: all color:red entries — from every document partition — live together. A read hits one partition; a write to one document may update several index partitions (every term in it may live elsewhere).

The index itself can be partitioned by the term or by a hash of the term: partitioning by the term supports range scans (e.g., over a numeric property like asking price); hashing the term spreads load more evenly.

The trade, flipped

Reads are efficient — the client asks only the partition containing the term. Writes are slower and more complicated — one document write may now touch several index partitions (each term on a different node). Ideally the index would always be up to date, but that would require a distributed transaction across all affected partitions, which not all databases support (Chapters 7 and 9). So global index updates are usually asynchronous: read the index right after your write and your change may not be reflected yet. Amazon DynamoDB says its global secondary indexes update within a fraction of a second normally, but with longer propagation delays during infrastructure faults. Used by Riak’s search feature and Oracle’s data warehouse (which lets you choose local or global); revisited in Chapter 12.

6.3 · Nodes come and go

Rebalancing partitions

Over time, things change: query throughput increases (you want more CPUs), the dataset grows (more disks and RAM), a machine fails (others take over). All of these force data and requests to move between nodes — rebalancing. Whatever the partitioning scheme, it must meet three requirements:

i.

Fair share

After rebalancing, load (storage, reads, writes) is shared fairly between the nodes.

ii.

Stay up

While rebalancing happens, the database continues accepting reads and writes.

iii.

Move no more than necessary

Only as much data as needed moves between nodes — fast rebalancing, minimal network and disk I/O.

6.3.1 — Four strategies (one anti-strategy)

How not to do it: hash mod N

With hash partitioning, hash(key) mod 10 looks like an easy way to spread keys over ten nodes. The problem: if N changes, most keys move. Watch one key, hash(key) = 123456:

mod 10 → 6Ten nodes123456 mod 10 = 6 — key lives on node 6
mod 11 → 3Eleven nodesthe key must move to node 3
mod 12 → 0Twelve nodesand again to node 0 — most keys shuffle on every change

Frequent moves make rebalancing excessively expensive. We need approaches that don’t move data around more than necessary.

Strategy 1 — fixed number of partitions

Create many more partitions than nodes from the outset — a 10-node cluster might split into 1,000 partitions, ~100 per node. When a node joins, it steals a few partitions from every existing node until the distribution is fair again; removal runs the same process in reverse. Crucially, only entire partitions move: the number of partitions never changes, and neither does the assignment of keys to partitions — only partition-to-node assignment changes. The change isn’t immediate (transferring data takes time), so the old assignment serves reads and writes during the transfer. A bonus: on mismatched hardware, assign more partitions to more powerful nodes and they take a greater share of the load.

Figure 6-6 (recreated) · New node steals partitions

The new node steals one partition from each existing node. Used by Riak, Elasticsearch, Couchbase, and Voldemort.

The fixed-partitions dilemma

The partition count is usually chosen at setup and never changed — splitting and merging is possible but operationally simpler to skip, so many fixed-partition databases don’t implement it. The number you pick is the maximum number of nodes you can ever have (choose high enough for growth), yet each partition has management overhead (don’t choose too high). And since each partition holds a fixed fraction of the total data, its size grows proportionally to the dataset: too large → expensive rebalancing and failure recovery; too small → too much overhead. “Just right” is hard to hit when the dataset size varies.

Strategy 2 — dynamic partitioning

For key-range databases, fixed boundaries would be terrible: get them wrong and all the data sits in one partition, and reconfiguring by hand is tedious. So key-range databases like HBase and RethinkDB create partitions dynamically: when one grows beyond a configured size — HBase’s default split threshold is 10 GB — it splits in two, roughly half the data on each side; if lots of data is deleted, small partitions can be merged with neighbors. It’s the same dynamic as B-tree page splitting at the top level (Chapter 3). As with fixed partitions, each partition is assigned to one node, and after a split, one half can move to another node to balance the load — HBase transfers partition files via HDFS, its underlying distributed filesystem.

The advantage: partition count adapts to total data volume — small data, few partitions, small overhead; huge data, per-partition size still capped. The caveat: an empty database starts with a single partition (no prior information about boundaries), so until the first split, all writes hit one node while the rest idle. Mitigation — pre-splitting: HBase and MongoDB can configure an initial set of partitions on an empty database, but with key-range partitioning that requires already knowing the key distribution. And dynamic partitioning isn’t key-range-only: it works equally well for hash-partitioned data — MongoDB since 2.4 supports both and splits dynamically in either case.

Strategy 3 — partitioning proportionally to nodes

Contrast: with dynamic partitioning the number of partitions is proportional to dataset size; with fixed partitions, per-partition size is proportional to dataset size. In both, the partition count is independent of the node count. The third option (Cassandra, and the Ketama library): make partitions proportional to the number of nodes — a fixed number of partitions per node (Cassandra’s default: 256). A larger dataset generally means more nodes, so partition size stays fairly stable: it grows with the dataset while the node count is unchanged, and shrinks again when nodes are added. When a new node joins, it randomly chooses a fixed number of existing partitions to split, taking ownership of one half of each and leaving the other half in place. Randomization can produce unfair splits, but averaged over many partitions (256 per node), the new node ends up taking a fair share. (Cassandra 3.0 introduced an alternative rebalancing algorithm that avoids the unfair splits.) One requirement: picking boundaries randomly needs hash-based partitioning — this corresponds most closely to the original consistent hashing; newer hash functions achieve the same effect with lower metadata overhead.

6.3.2 — Automatic or manual rebaling?

Who decides when partitions move? A spectrum: fully automatic (the system rebalances with no administrator interaction) through the middle ground (Couchbase, Riak, and Voldemort generate a suggested partition assignment automatically but require an administrator to commit it) to fully manual (assignment changes only when explicitly reconfigured).

Automatic rebalancing is convenient — less operational work — but can be unpredictable. Rebalancing is expensive: it reroutes requests and moves a large amount of data, and if done carelessly it can overload the network or nodes and harm performance of other requests while it runs. The danger scenario:

Automatic rebalancing + automatic failure detection = cascade

(1) One node is overloaded and responds slowly. (2) Other nodes conclude it’s dead. (3) They automatically rebalance the cluster to move load away from it. (4) Which puts more load on the overloaded node, the other nodes, and the network — making things worse, potentially causing a cascading failure. Having a human in the loop for rebalancing is slower than fully automatic, but it helps prevent operational surprises.

6.4 · Finding the node

Request routing

A client wants to make a request — which node does it connect to? As partitions rebalance, partition-to-node assignment changes, and somebody must stay on top of it to answer: “to read or write key ‘foo’, which IP address and port do I connect to?” This is the general problem of service discovery — not limited to databases; any network-accessible software aiming for high availability has it, and many companies have built (and open-sourced) their own tools.

6.4.1 — Three approaches

Figure 6-7 (recreated) · Three ways to route a request

(1) Clients contact any node (e.g. via round-robin load balancer); it handles the request if it owns the partition, otherwise forwards it and relays the reply. (2) All requests go through a routing tier that forwards each to the right node. (3) Partition-aware clients connect directly with no intermediary.

In all three, the routing decision-maker — a node, the routing tier, or the client — must learn about changes in partition assignment. Everyone must agree, or requests go to wrong nodes and go unhandled. There are protocols for consensus in distributed systems, but they’re hard to implement correctly — that’s Chapter 9’s story.

6.4.2 — The coordination service: ZooKeeper

Figure 6-8 (recreated) · ZooKeeper tracks partition assignment

Each node registers itself in ZooKeeper; ZooKeeper maintains the authoritative mapping of partitions to nodes; the routing tier (or a partitioning-aware client) subscribes, and gets notified whenever a partition changes ownership or a node joins or leaves.

In practice: LinkedIn’s Espresso uses Helix for cluster management (which relies on ZooKeeper) with a routing tier; HBase, SolrCloud, and Kafka use ZooKeeper directly to track partition assignment. MongoDB has a similar architecture but relies on its own config server implementation and mongos daemons as the routing tier. Cassandra and Riak take the other path: a gossip protocol among nodes disseminates changes in cluster state, requests can be sent to any node (approach 1), and the model puts more complexity in the database nodes but avoids the external coordination-service dependency. Couchbase doesn’t rebalance automatically (which simplifies the design) and is normally configured with a routing tier called moxi, which learns routing changes from the cluster nodes.

And the IPs?

Even with a routing tier or send-to-any-node, the client still needs some IP address to connect to. Those change far less often than partition assignments, so plain DNS is often sufficient.

6.5 · Beyond single-key requests

Parallel query execution

This chapter has focused on very simple queries — read or write a single key, plus the scatter/gather of document-partitioned secondary indexes. That’s about the level most NoSQL distributed datastores support. Massively parallel processing (MPP) relational products, typically used for analytics, go much further.

A typical data warehouse query contains several join, filtering, grouping, and aggregation operations. The MPP query optimizer breaks that complex query into a number of execution stages and partitions, many of which execute in parallel on different nodes of the cluster — queries that scan over large parts of the dataset benefit most. Fast parallel execution of warehouse queries is a specialized, commercially important topic; techniques are covered in Chapter 10.

6.6 · Pulling it together

Summary

The chapter in one card

Partitioning is necessary when data outgrows a single machine; the goal is to spread data and load evenly, avoiding hot spots. Key-range partitioning: keys sorted, a partition owns a range — efficient range queries, but hot-spot risk from clustered access; rebalanced dynamically by splitting ranges. Hash partitioning: a partition owns a range of hashes — even load, but ordering destroyed; commonly a fixed number of partitions created in advance and moved whole between nodes (dynamic splitting also possible). Hybrids exist: a compound key, one part identifying the partition, another defining the sort order. Secondary indexes also need partitioning: document-partitioned (local) indexes write to one partition but read via scatter/gather; term-partitioned (global) indexes read from one partition but write to several (usually asynchronously). Routing ranges from partition-aware load balancing to full MPP engines. By design every partition operates mostly independently — that’s what scales — but operations writing to several partitions are hard to reason about: what if one write succeeds and another fails? That’s Chapter 7’s door.

Glossary

partition (a.k.a. shard)
A logical subdivision of the database; each record belongs to exactly one partition. Renamed shard (MongoDB/Elasticsearch/SolrCloud), region (HBase), tablet (Bigtable), vnode (Cassandra/Riak), vBucket (Couchbase).
key-range partitioning
A partition owns a continuous range of keys; sorted within the partition → efficient range scans; risk: hot spots from sequential access patterns.
hash partitioning
A partition owns a range of hash values; even load, destroyed ordering — range queries fan out to all partitions or aren’t supported.
consistent hashing
Karger et al.’s randomly-chosen-boundaries scheme for CDN caches; “consistent” refers to rebalancing, not replica/ACID consistency — and it doesn’t work well for databases. Prefer “hash partitioning” as a term.
skew / hot spot
Skew: unfair partitioning — some partitions get more data or queries. Hot spot: a disproportionately loaded partition; worst case, all load on one node.
rebalancing
Moving load between nodes. Requirements: fair sharing, reads/writes continue throughout, and minimal data movement.
hash mod N
hash(key) mod N assignment; changing N moves most keys (123456: mod 10→6, mod 11→3, mod 12→0). The anti-pattern.
fixed number of partitions
Many more partitions than nodes (1,000 on 10 nodes); new nodes steal whole partitions. Key→partition never changes. Riak, Elasticsearch, Couchbase, Voldemort.
dynamic partitioning
Split when too big (HBase: 10 GB), merge when too small — like B-tree page splitting at the top level. Works for key-range and hash.
pre-splitting
Configuring initial partitions on an empty database — required because empty DBs start with one partition; needs key-distribution foreknowledge.
partitions per node
Cassandra/Ketama: partition count proportional to node count (Cassandra default 256); new nodes split random partitions and take half of each.
secondary index
An index on a value other than the primary key, for searching occurrences (“all red cars”); doesn’t map neatly to partitions.
local index
Document-partitioned: each partition indexes only its own documents. One-partition writes, scatter/gather reads.
global index
Term-partitioned: the index is partitioned by the searched term (or its hash), covering all partitions. One-partition reads, multi-partition (usually asynchronous) writes.
scatter/gather
Send the query to all partitions, combine the results — prone to tail latency amplification.
compound primary key
Cassandra’s multi-column key: first column hashed for the partition, the rest a concatenated sort index within it — per-user time ranges without giving up spread.
service discovery
The general problem of finding the right address/port for a service — of which partition routing is one instance.
routing tier
A partition-aware load balancer that forwards requests to the right node without handling any itself (mongos in MongoDB, moxi in Couchbase).
ZooKeeper
Coordination service holding the authoritative partition→node mapping; nodes register, routing tiers subscribe. Used (directly or via Helix) by HBase, SolrCloud, Kafka, Espresso.
gossip protocol
Nodes exchange cluster state among themselves (Cassandra, Riak) — any node can forward requests; no external coordination dependency.
MPP
Massively parallel processing: analytic relational databases whose optimizers break joins/filters/aggregations into parallel stages across nodes.
