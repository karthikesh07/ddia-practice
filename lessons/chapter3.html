3.0 · The setup

The 3 AM mystery

Story time

It’s 3 AM. A page jolts you awake: the session cache is gone. All of it. The Redis box kept everything in memory — and memory is fast but volatile: ~100 nanoseconds per access, and the moment power blinks, it forgets everything you ever told it.

Meanwhile the ancient Postgres box, chugging along on spinning disks, didn’t lose a row. Disk is slow but durable: ~10 milliseconds per access — roughly 100,000× slower than RAM — but it remembers.

So here’s the mystery: if disk is 100,000× slower than memory, how do databases get away with trusting it? This chapter is the answer. You’re probably not going to write a storage engine, but you will select and tune one — and the difference between engines optimized for transactional workloads and those optimized for analytics is enormous. Two families dominate:

Log-structured engines

Only permit appending to files and deleting obsolete files — never update a file in place. We build up to them from the simplest possible database.

Page-oriented engines

Treat the disk as a set of fixed-size pages that can be overwritten. The B-tree is the giant of this family.

3.1 · Two shell functions

The simplest database that works

Chapter 2 looked at data models from the developer’s view; now look from the database’s internal view. Start embarrassingly small — a key-value store in bash:

#!/bin/bash db_set () { echo "$1,$2" >> database } db_get () { grep "^$1," database | sed -e "s/^$1,//" | tail -n 1 }

Append a key,value line on write; on read, grep for the key, strip the prefix, and take the last match (so the most recent value wins). Watch it work — including the part where updates append rather than overwrite:

$ db_set 123456 '{"name":"London","attractions":["Big Ben","London Eye"]}' $ db_set 42 '{"name":"San Francisco","attractions":["Golden Gate Bridge"]}' $ db_get 42 {"name":"San Francisco","attractions":["Golden Gate Bridge"]} $ db_set 42 '{"name":"San Francisco","attractions":["Exploratorium"]}' $ db_get 42 {"name":"San Francisco","attractions":["Exploratorium"]} $ cat database 123456,{"name":"London","attractions":["Big Ben","London Eye"]} 42,{"name":"San Francisco","attractions":["Golden Gate Bridge"]} 42,{"name":"San Francisco","attractions":["Exploratorium"]}

The performance split is the whole chapter in miniature: db_set is fast (appending to a file is very efficient), but db_get is terrible — it greps the entire file, so a lookup costs O(n): double the records, double the lookup time. Real databases keep the append-only idea (internally it’s called a log — an append-only sequence of records, not necessarily human-readable) and add back the missing machinery: concurrency control, reclaiming disk space, handling errors and partially written records.

The index trade-off — remember this forever

An index is an additional structure derived from the primary data — a signpost that helps locate it. Well-chosen indexes speed up reads, but every index slows down writes, because each write must update every index too. That’s why databases don’t index everything by default: you pick indexes for your query patterns and pay for them at write time. There is no free signpost.

3.2 · From log to lookup

Hash indexes

Key-value data is the most common shape, and in memory it lives in a hash map. So keep it there: an in-memory hash map mapping every key to a byte offset in the data file. On write, append and update the map; on read, seek to the offset and read. Figure 3-1:

Struck-through entries are superseded — the log keeps them, the hash map just points at the latest offset per key. Each key maps to the byte offset of its most recent value; one disk seek per read.

This is essentially Bitcask, the default storage engine of Riak: high-performance reads and writes, on one condition — all keys must fit in memory. The values can exceed memory, loaded from disk in one seek (or none, if that file region is in the OS page cache). It shines when each key’s value is updated frequently — say, key = URL of a cat video, value = play counter — many writes, but not too many distinct keys.

Compaction and segment merging

An append-only file eventually eats the disk, so: break the log into segments (close a segment at a certain size, start a new one), and run compaction — throw away duplicate keys, keeping only the most recent value per key. Compacted segments shrink dramatically, and merging several segments at once is natural. Segments are never modified after being written — the merged output goes to new files — so compaction can run in a background thread while reads and writes continue against the old segments; when the merge finishes, reads switch over and the old segments are deleted. Each segment has its own hash map; lookups check the newest first, then older — and merging keeps the number of segments (and hash maps) small.

The five practical issues

i.

File format

CSV isn’t the best log format. A binary format — length of a string in bytes, then the raw string, no escaping needed — is faster and simpler.

ii.

Deleting records

Append a special deletion record — a tombstone — so the merging process knows to discard previous values for that key.

iii.

Crash recovery

Restart loses the in-memory hash maps; replaying whole segments to rebuild them is slow. Bitcask stores a snapshot of each segment’s hash map on disk for fast reload.

iv.

Partially written records

The DB can crash mid-append. Bitcask files include checksums to detect and ignore torn parts of the log.

v.

Concurrency control

Writes are appended in a strictly sequential order — the common choice is a single writer thread. Segments are immutable, so many reader threads can read them concurrently.

Two hard limits

1 — the hash table must fit in memory. A hash map on disk needs lots of random-access I/O, is expensive to grow when full, and hash collisions require fiddly logic. 2 — range queries are dead. You cannot scan all keys between kitty00000 and kitty99999 — you’d have to look up each key individually. Fixing these two limits is the next idea’s job.

3.3 · Sort the diary

SSTables and LSM-trees

Change one thing about the format: a Sorted String Table (SSTable) is a log-structured segment where key-value pairs are sorted by key, and each key appears once per merged segment. Three big advantages fall out:

i.

Merging is mergesort

Read segments side by side, compare first keys, copy the lowest to the output — the classic merge, efficient even when files exceed memory, and the output is sorted too. Duplicate keys across segments? Keep the value from the most recent segment.

ii.

Sparse in-memory index

You don’t need every key in memory. Looking for handiwork with offsets known only for handbag and handsome? It must sit between them — jump to handbag’s offset and scan. One index entry per few kilobytes of segment file is enough.

iii.

Block compression

Since range reads scan many consecutive records anyway, group records into blocks and compress them — each sparse-index entry points at the start of a compressed block. Less disk space and less I/O bandwidth.

Constructing and maintaining SSTables

Writes arrive in any order but segments must be sorted — so sort in memory first. The workflow of an LSM storage engine:

  1. Writes go into an in-memory balanced tree (red-black or AVL), called the memtable.
  2. When the memtable exceeds a threshold (typically a few megabytes), write it out as an SSTable — cheap, since the tree is already sorted. Meanwhile, new writes go to a fresh memtable.
  3. Reads check the memtable, then the most recent on-disk segment, then older ones.
  4. Background merging and compaction periodically combine segments and discard overwritten or deleted values.

Crash recovery: writes sitting only in the memtable would be lost, so every write also goes immediately to a separate log on disk — unsorted, because its only job is restoring the memtable after a crash; it’s discarded once the memtable is flushed.

A name worth knowing

This algorithm is what LevelDB and RocksDB implement (LevelDB can back Riak as a Bitcask alternative); similar engines power Cassandra and HBase, inspired by Google’s Bigtable paper — which introduced the terms SSTable and memtable. The original description is Patrick O’Neil et al.’s Log-Structured Merge-Tree (LSM-tree), which gives the whole family its name: LSM storage engines.

Lucene — the indexing engine behind Elasticsearch and Solr — uses the same idea for full-text search’s term dictionary: key = word, value = the postings list of all document IDs containing it, kept in SSTable-like sorted files merged in the background.

Performance optimizations

  • Bloom filters: a read for a nonexistent key would otherwise check the memtable and every segment back to the oldest. A Bloom filter is a memory-efficient set approximation that can say “definitely not here” — skipping most of those disk reads.
  • Size-tiered compaction (HBase): successively merge newer, smaller SSTables into older, larger ones.
  • Leveled compaction (LevelDB, RocksDB — hence the name): split the key range into smaller SSTables and move older data into separate “levels,” compounding more incrementally and using less disk space. Cassandra supports both.

The summary of what LSM buys: works well even when the dataset is far bigger than memory, range queries work (it’s sorted), and writes are sequential — remarkably high write throughput.

3.4 · The library catalog

B-trees

The most widely used indexing structure in the world: introduced in 1970, called “ubiquitous” less than a decade later, still the standard in almost all relational databases and many nonrelational ones. Like SSTables, B-trees keep key-value pairs sorted for lookups and range queries — but the philosophy is the opposite.

Log-structured indexes break the database into variable-size segments written sequentially. B-trees break it into fixed-size blocks or pages — traditionally 4 KB — read or written one page at a time, matching how disks are physically arranged. Each page has an address, so pages can refer to each other like pointers on disk.

Figure 3-6 (recreated) · Looking up key 251 in a B-tree

Start at the root; each page contains keys and references to child pages, each child responsible for a continuous key range. Key 251 follows the >200 reference, narrows into the 200–300 range, and lands in a leaf page holding the value (inline or by reference). Branching factor here: three; in practice several hundred.

How they grow

An update finds the leaf page and rewrites it. An insert that doesn’t fit splits the page into two half-full pages and updates the parent to account for the subdivision (Figure 3-7) — which is what keeps the tree balanced: a B-tree with n keys always has depth O(log n).

4 KB Traditional B-tree page size matching the disk’s own fixed-size blocks
~500 Typical branching factor “several hundred” — limited by page size and key boundaries
256 TB Capacity of a 4-level tree 4 KB pages × branching factor 500: most databases fit in 3–4 levels

Crash safety: the WAL

Here is the B-tree’s Achilles heel: the basic write operation overwrites a page on disk — magnetic hard drive: move the head, wait for the platter, overwrite the sector; SSD: erase and rewrite large blocks of the chip. And some operations (a page split) must overwrite several pages at once: the two halves and the parent. Crash after only some of those writes, and you have a corrupted index — say, an orphan page that is no child of any parent.

The write-ahead log (WAL, a.k.a. redo log)

Every B-tree modification is first appended to an append-only write-ahead log, then applied to the tree’s pages. After a crash, the WAL is replayed to restore the tree to a consistent state. Note the rhyme with the memtable’s recovery log from the LSM side — same trick, opposite engines. Concurrency, meanwhile, needs latches (lightweight locks) so threads never see the tree half-modified; log-structured engines get this for free by doing merges in the background and swapping segments atomically.

Five real-world optimizations

  • Copy-on-write B-trees (e.g. LMDB): write the modified page to a different location, and create a new version of parent pages pointing there — no WAL needed, and handy for concurrency.
  • Key abbreviation: interior pages only need enough key to act as a range boundary; abbreviating keys packs more per page → higher branching factor → fewer levels.
  • Leaf page ordering: try to lay out leaves sequentially on disk so range scans don’t seek per page — hard to maintain as the tree grows (LSM merges make it easier).
  • Sibling pointers: leaves point left and right, so a scan walks the key range without returning to parent pages. (This common variant is the B+ tree.)
  • Fractal trees borrow log-structured ideas to reduce disk seeks (nothing to do with fractals).

3.5 · Diary vs. library

Comparing B-trees and LSM-trees

Rule of thumb: LSM-trees are typically faster for writes; B-trees are thought to be faster for reads (an LSM read must check several structures and SSTables at various compaction stages — read amplification). Benchmarks are inconclusive and workload-sensitive: test with yours.

Write amplification deserves the definition: one write to the database becoming multiple writes to disk over its lifetime — a particular concern on SSDs, which can only overwrite blocks a limited number of times before wearing out.

Verdict: B-trees are deeply ingrained and consistently good for many workloads; log-structured indexes are increasingly popular in new datastores. No quick and easy rule — test empirically.

3.6 · Beyond the two giants

Other indexing structures

Secondary indexes, heap files, clustered and covering indexes

Everything so far indexed the primary key (one row, one document, one vertex). Secondary indexes — CREATE INDEX — are crucial for joins; they’re easy to build from a key-value index once you handle keys that aren’t unique: make each value a list of matching row identifiers (like a postings list), or append the row identifier to make each key unique. Both B-trees and LSM-trees work as secondary indexes.

Then: does the index store the row, or a reference to it? The reference approach keeps rows in a heap file — unordered storage that avoids duplicating data across multiple secondary indexes. In-place update works if the new value fits; otherwise the row moves and all indexes update, or a forwarding pointer is left behind. At the other extreme, a clustered index stores the row within the index: MySQL InnoDB’s primary key is always clustered (secondary indexes there refer to the primary key), and SQL Server allows one clustered index per table. In between sits the covering index (“index with included columns”) — some of a table’s columns stored in the index, so some queries are answered by the index alone: it covers them. Trade-offs: faster reads, more storage, more write overhead.

Multi-dimensional indexes

A restaurant finder needs all restaurants within the map rectangle the user is viewing — a two-dimensional range query:

SELECT * FROM restaurants WHERE latitude > 51.4946 AND latitude < 51.5079 AND longitude > -0.1162 AND longitude < -0.1004;

A standard B-tree or LSM index can’t answer it: it can give all restaurants in a latitude range at any longitude, or in a longitude range anywhere pole-to-pole — not both at once. The fixes: a space-filling curve translating 2-D positions into one number (then a regular B-tree), or specialized R-trees — PostGIS implements geospatial indexes as R-trees on PostgreSQL’s Generalized Search Tree. And it’s not just maps: e-commerce (an RGB color range: a three-dimensional index) or weather observations (all 2013 temperatures between 25 and 30 °C: a two-dimensional index on (date, temperature) narrows both simultaneously, where a one-dimensional index would force scanning all of one dimension).

Full-text search and fuzzy indexes

All the indexes so far assume exact keys. Full-text search expands a word to synonyms, ignores grammatical variation, finds words near each other in a document — and Lucene can search for words within a given edit distance (edit distance 1 = one letter added, removed, or replaced). Internally: LevelDB’s in-memory index is a sparse collection of keys; Lucene’s is a finite-state automaton over the characters — like a trie — transformable into a Levenshtein automaton that efficiently matches within an edit distance.

Keeping everything in memory

All of this is a response to disk’s awkwardness. Disk keeps two advantages — durability and lower cost per gigabyte — but RAM keeps getting cheaper and many datasets aren’t that big. Hence in-memory databases: Memcached for cache-only use; VoltDB, MemSQL, Oracle TimesTen (relational, durable via log/snapshot/replication); RAMCloud (log-structured, in memory and on disk); Redis and Couchbase (weak durability via asynchronous disk writes).

The counterintuitive part

The performance advantage of in-memory databases is not about avoiding disk reads. A disk-based engine with enough memory never reads from disk either — the OS caches recently used blocks. The real win: avoiding the overhead of encoding in-memory data structures into a form that can be written to disk. Plus data models disks can’t do well — Redis exposes priority queues and sets because keeping everything in memory makes the implementation simple.

Research on anti-caching extends the architecture to datasets larger than memory — evict least-recently-used records to disk, reload on access (like OS swap, but at record granularity rather than whole pages), with indexes still fully in memory (the Bitcask constraint). And watch non-volatile memory (NVM): it may force yet another rethink of storage engine design.

3.7 · Two very different jobs

Transaction processing or analytics?

Early databases served commerce, so a “transaction” was literally making a sale. The word stuck as databases grew beyond money: a group of reads and writes forming a logical unit (not necessarily ACID — that’s Chapter 7). Two access patterns emerged:

OLTP (online transaction processing): interactive applications look up a small number of records by key via an index, inserting and updating from user input. OLAP (online analytic processing): analytic queries scan huge numbers of records, read a few columns, and compute aggregates — “What was each store’s January revenue?”, “How many extra bananas did the promotion sell?”, “Which baby food is bought together with brand X diapers?” — written by business analysts feeding business intelligence reports.

Data warehousing

At first the same database did both — SQL was flexible enough. Then, in the late 1980s / early 1990s, came the shift: stop running analytics on OLTP systems. The reasoning: an enterprise has dozens of transaction systems (website, point-of-sale, inventory, supplier management…), each highly available and latency-critical; DBAs rightly refused to let analysts run ad hoc queries that scan large parts of the dataset and damage concurrent transactions. So build a data warehouse: a separate, read-only database that analysts can query to their hearts’ content — fed by ETL (extract–transform–load) from all the OLTP systems: periodic dumps or continuous update streams, transformed into an analysis-friendly schema, cleaned up, loaded.

Warehouses exist in almost all large enterprises and are almost unheard of in small companies — small companies have less data and fewer OLTP systems; a conventional SQL database or even a spreadsheet suffices. What the big guys get for their trouble: a database optimized for analytic access patterns, where the internals look completely different from OLTP despite both speaking SQL.

Commercial warehouses

Teradata, Vertica, SAP HANA, ParAccel — and Amazon Redshift, a hosted version of ParAccel.

SQL-on-Hadoop

Apache Hive, Spark SQL, Cloudera Impala, Facebook Presto, Apache Tajo, Apache Drill — young but competing with the commercial systems; some based on Google’s Dremel.

3.8 · The formula for facts

Stars and snowflakes

Analytics doesn’t have data-model diversity — most warehouses use one formulaic style, the star schema (a.k.a. dimensional modeling): a central fact table where each row is an event — a purchase, a click, a page view — with columns for attributes (sale price, supplier cost for margin math) and foreign keys into dimension tables representing the who/what/where/when/how/why: dim_product (SKU, description, brand, category, fat content, package size), dim_store (services offered, square footage, opening date, distance from the highway…), even date as a dimension so holidays are queryable. Capture events individually for maximum analytical flexibility, and the fact table becomes extremely large — Apple, Walmart, or eBay may hold tens of petabytes of transaction history, most of it fact tables.

Why “star”? The fact table sits in the middle with dimensions around it — the connections look like the rays of a star. The snowflake schema is the variation where dimensions break into subdimensions (separate brand and category tables, referenced by foreign key): more normalized, but star schemas are usually preferred for being simpler for analysts. Either way, tables run wide: fact tables often exceed 100 columns, sometimes several hundred.

3.9 · Flip it sideways

Column-oriented storage

Fact tables have 100+ columns; a typical warehouse query touches 4 or 5 of them (SELECT * is rare in analytics). But OLTP storage is row-oriented — all values of one row adjacent, as in document stores. Example 3-1, a representative query:

SELECT dim_date.weekday, dim_product.category, SUM(fact_sales.quantity) AS quantity_sold FROM fact_sales JOIN dim_date ON fact_sales.date_key = dim_date.date_key JOIN dim_product ON fact_sales.product_sk = dim_product.product_sk WHERE dim_date.year = 2013 AND dim_product.category IN ('Fresh fruit', 'Candy') GROUP BY dim_date.weekday, dim_product.category;

Every fruit-or-candy purchase in 2013 — a huge number of rows — but only three columns of fact_sales: date_key, product_sk, quantity. Row storage must still load each 100+ column row from disk, parse it, and discard most of it. The fix: store all values from each column together.

Each column file keeps rows in the same order — row 23 is the 23rd entry of every column file, which is how you reassemble a whole row. Parquet, the columnar format for document data models, descends from Google’s Dremel.

Column compression

Columns are repetitive, which compresses beautifully. A retailer may have billions of sales but only 100,000 distinct products: take a column with n distinct values and turn it into n separate bitmaps — one per value, one bit per row (1 = the row has that value). Small n (a country column: ~200 values) means one bit per row, already tiny; bigger n makes sparse bitmaps, which run-length encode down to remarkably little.

Bitmaps compute your WHERE clause

WHERE product_sk IN (30, 68, 69) → load three bitmaps and bitwise OR them. WHERE product_sk = 31 AND store_sk = 3 → load two bitmaps and bitwise AND — valid because columns share row order, so the kth bit of one column’s bitmap is the same row as the kth bit of another’s.

CPU, sort order, and writes

Beyond disk bandwidth, column layouts make CPU cycles go further — vectorized processing: compressed column chunks fit in the CPU’s L1 cache and iterate in a tight loop, no function calls, with bitwise operators working directly on compressed data (also avoiding branch mispredictions; using SIMD instructions). Since rows must stay in the same order across columns, you sort entire rows at a time by chosen sort keys — date_key first means last-month queries scan only that range, and the first sort column compresses hardest (long runs of the same value → run-length encoding to a few KB even over billions of rows). C-Store/Vertica’s extension: store the data replicated in several sort orders at once — like multiple secondary indexes, but without pointers, since column stores hold values only. One more thing Cassandra/HBase readers trip on: their column families (inherited from Bigtable) are not column orientation — all columns of a row are stored together, row key attached, no column compression; mostly row-oriented.

Writes are the cost: update-in-place is impossible in compressed, sorted columns (inserting mid-table rewrites every column file). So use the LSM move — writes go to an in-memory store, and bulk-merge into column files later. Queries check both; the optimizer hides the split. That is essentially what Vertica does.

Materialized views and data cubes

Warehouse queries aggregate constantly — COUNT, SUM, AVG, MIN, MAX. A materialized view is a table-like object whose contents are the results of a query, written to disk (unlike a virtual view, which is just a query shortcut expanded on the fly). It’s a denormalized copy that must be updated when underlying data changes — expensive writes, which is why OLTP rarely uses them and read-heavy warehouses might. The special case: a data cube (OLAP cube) — a grid of aggregates grouped by dimensions; with two dimensions (date × product), each cell holds the SUM of facts for that combination, and row/column totals give one-dimension summaries. Precomputed answers — “total sales per store yesterday” is a lookup, not a scan of millions. The catch: cubes lack the raw data’s flexibility — if price isn’t a dimension, you can’t ask what share of sales came from items over $100 — so warehouses keep the raw data and use cubes as a speed boost.

3.10 · Pulling it together

Summary

The chapter in one card

Storage engines split by workload. OLTP: user-facing, huge request volume, few records per query, index-driven — disk seek time is the bottleneck. Analytics/warehouse: fewer but brutally demanding queries over millions of rows — disk bandwidth is the bottleneck, and column-oriented storage is the rising answer. On the OLTP side, two schools: the log-structured school (Bitcask, SSTables, LSM-trees, LevelDB, Cassandra, HBase, Lucene) systematically turns random writes into sequential ones; the update-in-place school (B-trees, in all major relational databases) overwrites fixed-size pages, giving each key exactly one home. Knowing these internals won’t make you an expert tuner of any one engine, but it gives you the vocabulary to read its documentation and reason about what the knobs do.

Glossary

An append-only sequence of records — in the general sense, not application logs; may be binary.
index
A structure derived from primary data that acts as a signpost; speeds reads, slows writes — the storage trade-off.
Bitcask
Riak’s default engine: in-memory hash map of every key → byte offset in an append-only file; all keys must fit in memory.
segment / compaction
A closed chunk of the log; compaction discards duplicate keys, keeping the most recent value per key.
tombstone
A deletion record appended to the log, telling the merger to drop previous values for that key.
SSTable
Sorted String Table — a segment where key-value pairs are sorted by key and each key appears once.
memtable
The in-memory sorted tree that receives writes before flushing them out as an SSTable; restored from a log after a crash.
LSM-tree
Log-Structured Merge-Tree: a cascade of SSTables merged in the background (O’Neil et al.); LevelDB, RocksDB, Cassandra, HBase, Bigtable lineage.
size-tiered vs. leveled compaction
Merge smaller SSTables into bigger ones vs. split key ranges into incremental “levels” (LevelDB/RocksDB, hence the names).
B-tree
The ubiquitous page-oriented index: fixed-size pages (traditionally 4 KB), balanced by page splits, depth O(log n).
branching factor
The number of child-page references in one B-tree page — several hundred in practice.
WAL / redo log
Write-ahead log: every B-tree modification appended there before touching the pages; replayed after a crash.
latches
Lightweight locks protecting B-tree structures for concurrent access.
write amplification
One database write becoming multiple disk writes over its lifetime (WAL + page + splits; or repeated compaction) — a wear concern on SSDs.
heap file
Unordered row storage that indexes point into, avoiding data duplication across secondary indexes.
clustered index
Stores the row within the index (InnoDB primary keys, SQL Server’s one-per-table allowance).
covering index
Stores some columns in the index so some queries never leave it — it “covers” them.
concatenated index
Multi-column index combining fields into one key — like a phone book sorted (lastname, firstname).
R-tree / space-filling curve
Multi-dimensional (e.g. geospatial) indexing; PostGIS uses R-trees, curves flatten 2-D to a sortable number.
Levenshtein automaton
Lucene’s fuzzy-search structure: match words within a given edit distance.
anti-caching
Evict least-recently-used records from memory to disk, reload on access — OS swap at record granularity.
OLTP / OLAP
Small indexed reads/writes for interactive apps vs. aggregate scans over huge history for analysts.
data warehouse / ETL
A separate read-only analytic copy of an organization’s OLTP data, fed by extract–transform–load.
star / snowflake schema
Fact table (events) surrounded by dimension tables (who/what/where/when); snowflake further normalizes dimensions.
column-oriented storage
All values of each column stored together; query reads only needed column files (Parquet descends from Dremel).
bitmap index / run-length encoding
One bitmap per distinct value, one bit per row; AND/OR bitmaps evaluate WHERE clauses; RLE compresses sparse runs.
vectorized processing
Tight loops over compressed column chunks that fit in L1 cache — also SIMD-friendly.
materialized view / data cube
Query results written to disk; a cube is the dimension-grid special case — precomputed aggregates as a speed boost.
