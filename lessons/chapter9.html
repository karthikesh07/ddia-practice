9.0 · The setup

Consistency guarantees

Lots of things can go wrong in distributed systems — Chapter 8 was the catalog. The simplest response is to let the whole service fail and show the user an error. When that’s not acceptable, you need ways of tolerating faults: keeping the service correct even while some internal component is broken. This chapter assumes the full Chapter 8 disaster menu is on the table: packets lost, reordered, duplicated, or arbitrarily delayed; clocks approximate at best; nodes pausing (a garbage collection stop, say) or crashing whenever they like.

The winning strategy, as with transactions in Chapter 7, is to find general-purpose abstractions with useful guarantees, implement them once, and let applications lean on the guarantee. A transaction lets the application pretend there are no crashes (atomicity), no concurrent access (isolation), and perfectly reliable storage (durability) — the abstraction absorbs the mess. The distributed-systems equivalents do the same for replication and coordination. The most important of them is consensus: getting all the nodes to agree on something. That sounds trivial. It is not — many broken systems exist because their builders assumed it was. One immediate use: in a single-leader database whose leader dies, the survivors can use consensus to elect a replacement, avoiding split brain (two self-appointed leaders, and usually data loss).

But before the algorithms, we need the map of what guarantees even exist, and where the hard limits are — some things are possible in the face of faults, and some provably are not. Researchers have explored these limits for decades; this chapter scratches the surface with informal intuitions, leaving the formal models and proofs to the literature.

9.0.1 — Eventual consistency is very weak

Look at two replicas of the same database at the same instant and you’ll likely see different data, because writes arrive at different nodes at different times — no matter whether replication is single-leader, multi-leader, or leaderless. Most replicated databases therefore offer at least eventual consistency: stop writing, wait an unspecified length of time (assuming faults are eventually repaired), and eventually all reads return the same value. Convergence would honestly be a better name — the replicas do eventually settle.

The weakness is the word eventually: nothing is promised about when. Before convergence, reads can return anything or nothing. Write a value and immediately read it back, and you might not see your own write if the read hits a lagging replica. This is painful for developers precisely because it contradicts everything a variable in a normal single-threaded program teaches you: assign, read back, expect your value. A database looks like a big readable/writable variable, but its real semantics are far stranger. With only weak guarantees, you must constantly keep the limitations in mind and avoid assuming too much — and the bugs are subtle, because the application works fine most of the time. The edge cases only surface during a fault (a network interruption) or under high concurrency.

Stronger models exist and don’t come free — they can cost performance and fault tolerance — but they are easier to use correctly. There’s a resemblance to the hierarchy of isolation levels from Chapter 7, and some overlap, but the two are mostly independent concerns: transaction isolation is about avoiding race conditions between concurrently executing transactions; distributed consistency is about coordinating the state of replicas in the face of delays and faults.

9.1 · The illusion of one machine

Linearizability

In an eventually consistent database, two replicas asked the same question at the same moment can disagree. Wouldn’t it be simpler if the database could pretend there is only one replica? Then every client sees the same view, and replication lag stops being the application’s problem. That is the idea behind linearizability (also called atomic consistency, strong consistency, immediate consistency, or external consistency): make the system appear as if there is only one copy of the data, and every operation on it is atomic.

Concretely: as soon as one client successfully completes a write, every client reading the database must be able to see that value — not a stale cache, not a lagging replica. Linearizability is a recency guarantee. To see why that phrase needs care, start with a system that fails it.

Figure 9-1 (recreated) · A nonlinearizable sports site

If Alice and Bob had refreshed simultaneously, different answers would be unremarkable — neither knows exactly when the server processed each request. But Bob knows he pressed reload only after hearing Alice exclaim the result, so he expects his answer to be at least as recent as hers. Getting a stale score anyway is the violation. (Had Alice said nothing, Bob would simply have refreshed again a few seconds later and never noticed — keep that thought for the cross-channel discussion below.)

9.1.1 — What makes a system linearizable

To pin the idea down, the literature uses a register — in practice, one key in a key-value store, one row of a relational table, or one document. Clients issue read(x) ⇒ v, write(x, v) ⇒ r, and sometimes atomic cas(x, vold, vnew) ⇒ r — compare-and-set, which succeeds only if the current value equals vold. The client’s request is a bar on a timeline: the bar starts when the request is sent and ends when the response comes back; the database processed it at some point in between. (Pretending a global clock exists for analysis is fine as long as the algorithm itself can’t see it — it only gets the mangled quartz-and-NTP approximation.)

Figure 9-2 (recreated) · Reads concurrent with a write may return either value — once

Client C writes x = 1; A and B poll. A’s first read finishes before the write begins — it must return 0. A’s last read begins after the write completes — it must return 1. Reads overlapping the write window may return either value, because we can’t know exactly when the write took effect. The extra constraint that makes it linearizable: imagine the value flips atomically from 0 to 1 at some instant inside the write’s window. Once any read returns 1 — even while C’s write bar is still open — every later read must also return 1. B’s read starts just after A’s read returned the new value, so B must see 1, write still in flight or not. It’s the Alice-and-Bob rule in miniature. (A register where concurrent reads may see old or new is called a regular register; linearizability adds the no-flip-back rule.)

A richer diagram in the book adds compare-and-set operations and marks, inside each request bar, the single point where the operation appears to take effect; joining those marks in order must produce a valid register history, and the marks must always move forward in time. Two subtleties from it are worth remembering: a read can legitimately return a value whose write hasn’t yet been acknowledged (the response may just be slow in the network — the value itself was already written), and reads at different points can see different values because writes genuinely happen in between. What’s never allowed is a read returning a value older than one another client has already seen. The formal definition builds on exactly this intuition, and while testing a history for linearizability is computationally expensive, it can be done by recording request timings and checking whether they arrange into a valid sequential order.

9.1.2 — Linearizability is not serializability

The two words sound like the same promise — “can be arranged in some sequential order” — but they are quite different, and confusing them causes real design mistakes:

Serializability isolation

An isolation property of transactions. Every transaction may read and write multiple objects (rows, documents, records), and the guarantee is that transactions behave as if executed in some serial order — each running to completion before the next starts. That serial order doesn’t have to match the order transactions actually ran in.

Linearizability recency

A recency guarantee on reads and writes of a single register (an individual object). It has no notion of grouping operations into transactions, so on its own it prevents neither write skew nor phantoms — unless you add measures like materializing conflicts.

A database can offer both at once — that combination is called strict serializability (or strong one-copy serializability, strong-1SR). Serializable implementations based on two-phase locking or actual serial execution are typically linearizable too. But serializable snapshot isolation is not linearizable, by design: SSI serves reads from a consistent snapshot precisely to avoid lock contention, and a snapshot by definition excludes more-recent writes — so those reads aren’t linearizable.

9.1.3 — Where linearizability is genuinely needed

A sports score a few seconds stale is harmless. Three areas where it is not:

1.

Locking and leader election

Single-leader replication must ensure there really is only one leader — split brain must be impossible. One approach is a lock: on startup, every node tries to acquire it, and the winner becomes leader. Whatever the implementation, the lock must be linearizable — all nodes must agree on who holds it, or it’s useless. Coordination services like ZooKeeper and etcd implement exactly this on top of consensus; libraries like Apache Curator add higher-level recipes. Fencing subtleties from Chapter 8 still apply. At the granular end, Oracle RAC takes a linearizable lock per disk page across nodes sharing one storage system — with locks on the transaction critical path, RAC deployments usually run a dedicated cluster interconnect.

2.

Constraints and uniqueness

A username or email address must identify exactly one user; a file path can name only one file. Enforcing that at write time — one of two concurrent claimants gets an error — requires linearizability. It’s really the lock again: registering a username is “acquiring a lock on the name,” or an atomic compare-and-set setting the username to a user’s ID if it’s still null. The same applies to never-negative balances, stock counts, and not double-booking a seat: all need one up-to-date value all nodes agree on. Real systems sometimes treat these loosely (an overbooked flight becomes compensation and an apology) — but a hard uniqueness constraint, like the classic relational kind, needs linearizability. Foreign key and attribute constraints don’t.

3.

Cross-channel timing

Bob only noticed the stale read because Alice’s voice was a second communication channel. Systems have those too. A photo site: the web server writes the full image to file storage, then drops a “resize this” instruction on a message queue (photos are too big for broker messages). If the file storage isn’t linearizable, the queue can beat the storage’s internal replication — the resizer fetches an old version or nothing, and the stored full-size and thumbnail images are permanently inconsistent. Linearizability is the simplest fix; if you control the extra channel, you can also coordinate it explicitly, at the price of complexity.

9.1.4 — Which replication methods can be linearizable

The obvious “implementation” of one-copy semantics — actually keeping one copy — has no fault tolerance: the node dies, the data is gone. So compare the Chapter 5 replication architectures:

Single-leader potentially

Reads from the leader, or from synchronously updated followers, can be linearizable. But not every single-leader database actually is — snapshot isolation breaks it, and so do concurrency bugs. And it hinges on knowing for sure who the leader is: a delusional node that still believes it’s the leader will happily violate linearizability, and with asynchronous replication, failover can even lose committed writes. (Partitioning a single-leader database doesn’t hurt linearizability — it’s a single-object guarantee; cross-partition transactions are a separate matter.)

Consensus algorithms yes

They resemble single-leader replication but add measures that prevent split brain and fence off stale replicas. ZooKeeper and etcd are built this way — this is how they implement linearizable storage safely.

Multi-leader no

Multiple nodes accept writes concurrently and replicate asynchronously — conflicting writes needing resolution are the direct artifact of there being no single copy. Not linearizable.

Leaderless (Dynamo-style) probably not

Even with strict quorums (w + r > n) it fails: with n = 3, w = 3, r = 2, a reader can see the new value from one node while another reader, starting later, hits a different quorum of two and gets only the old value — the Alice-and-Bob violation, quorum condition satisfied. LWW on time-of-day clocks (Cassandra) is ruled out by clock skew alone; sloppy quorums ruin it too. It is possible to fix — synchronous read repair before returning, and writers reading quorum state first — but Riak skips the synchronous repair for performance, Cassandra does it yet loses to LWW on concurrent writes, and a linearizable compare-and-set is impossible this way entirely: it requires consensus. Safest assumption: not linearizable.

9.1.5 — The CAP theorem, stated properly

Picture a multi-datacenter deployment with multi-leader replication; the inter-datacenter link breaks, but each datacenter’s internal network and its clients are fine. Multi-leader keeps both sides working — writes queue up and sync when the link returns. Single-leader doesn’t: only the datacenter hosting the leader can take writes and linearizable reads; clients of the other datacenters are stuck with stale reads or errors. And this isn’t about replication style or geography — any linearizable database behaves this way, even within one datacenter, because the argument is general:

  • If you require linearizability and a network problem cuts some replicas off from the rest, those replicas can’t process requests while disconnected — they must wait or return errors. Either way: unavailable.
  • If you don’t require linearizability, each replica can keep processing requests independently (multi-leader style). The system stays available through the network problem — but its behavior is not linearizable.

That is the CAP theorem, named by Eric Brewer in 2000, though database designers knew the trade-off as far back as the 1970s. As a rule of thumb it did real cultural good — it pushed engineers beyond the then-dominant linearizable shared-storage clusters and toward the shared-nothing design space that fed the NoSQL explosion. (The two sides are sometimes labeled CP and AP; the classification has enough flaws that it’s best avoided.)

“Pick 2 of 3” is the wrong way to read CAP

A network partition isn’t a feature you choose — it’s a fault, and it will happen whether you like it or not. A perfectly reliable network is a fantasy. When the network is healthy, a system can provide both consistency (linearizability) and full availability; when a partition occurs, you must choose. So the honest phrasing is either Consistent or Available when Partitioned. The formal theorem is also narrow — it covers exactly one consistency model (linearizability) and one fault type (live-but-disconnected nodes), and says nothing about network delays, dead nodes, or other trade-offs. The term “availability” itself has contradictory definitions in CAP discussions, and many genuinely fault-tolerant systems fail CAP’s idiosyncratic version of it. Superseded by more precise results, CAP is of mostly historical interest — but the underlying choice during a partition is forever.

9.1.6 — The cost of linearizability: it’s slow all the time

Here’s the surprise: surprisingly few real systems are linearizable, and the reason usually isn’t CAP. Consider RAM on a modern multi-core CPU — a thread on one core writes a memory address, a thread on another core reads it shortly after, and it is not guaranteed to see the written value (absent a memory barrier or fence). Each core has its own cache and store buffer; updates reach main memory asynchronously, so there are several asynchronously-updated copies — linearizability is lost, in exchange for speed. Nobody invokes CAP to justify the multi-core memory model: within one computer you assume reliable communication, and a core can’t keep running if disconnected from the machine anyway. The reason to drop linearizability here is performance, not fault tolerance. The same motive drives many distributed databases.

And no cleverer implementation can rescue it: a result by Attiya and Welch shows that if you want linearizability, the response time of reads and writes is at least proportional to the uncertainty of network delays. On networks with highly variable delay — meaning most computer networks — linearizable operations are inevitably slow, not just during faults but always. Weaker consistency models can be much faster, which matters enormously for latency-sensitive systems. Chapter 12 returns to getting correctness without paying this tax.

9.2 · Cause before effect

Ordering guarantees

A linearizable register’s operations execute in some well-defined order — we drew it as the timeline of effect-markers. Ordering has been quietly everywhere in this book, which suggests it’s fundamental. Recap of its cameo appearances: the leader in single-leader replication exists mainly to determine the order of writes in the replication log (no single leader → concurrent-operation conflicts); serializability is transactions behaving as if executed in some sequential order; and Chapter 8’s timestamp tricks were attempts to impose order on which write happened later. Ordering, linearizability, and consensus turn out to be deeply connected.

9.2.1 — Ordering and causality

One big reason ordering recurs is that it preserves causality. You’ve already met the pattern many times:

1.

Answers before questions

Chapter 5’s consistent-prefix-reads anomaly: an observer of a chat saw the reply before the question it answered. Confusing because it violates cause and effect — whoever answered must have seen the question first. There’s a causal dependency from question to answer.

2.

Updates before creations

The three-leader replication example where writes could overtake each other, so a replica saw an update to a row that didn’t exist yet. Causality says: the row must be created before it can be updated.

3.

Happens-before

The Chapter 5 definition: two operations are concurrent when neither happened before the other — where “A happened before B” means B might have known about, built upon, or depended on A. That is causality in its purest form.

4.

Consistent snapshots

What “consistent” means in snapshot isolation is consistent with causality: if the snapshot contains an answer, it also contains the question. It shows all effects of operations causally before the snapshot point, and none from after. Read skew is reading in a state that violates causality.

5.

Write skew

Alice goes off call believing Bob is on, and vice versa: each decision causally depends on an observation. SSI catches write skew by tracking exactly these causal dependencies between transactions.

6.

Alice and Bob

Bob hearing the result from Alice is causally downstream of the score announcement and Alice’s read of it — so Bob’s stale result was a causality violation too. The image-resizer race is the same shape with different actors.

Causality imposes an ordering — cause before effect, message sent before message received, question before answer — and the chains multiply: one node reads and writes as a result, another reads that and writes in turn. Those chains of dependent operations define the causal order: what happened before what. A system that obeys this ordering is causally consistent. Snapshot isolation is one example: if you can see some data, you can also see everything that causally precedes it (barring later deletion).

9.2.2 — The causal order is a partial order

A total order lets you compare any two elements — 5 and 13, and 13 is greater. Mathematical sets aren’t like that: is {a, b} greater than {b, c}? Neither contains the other, so they’re incomparable — sets are only partially ordered. The distinction maps straight onto consistency models:

Linearizability total order

One single copy, every operation atomic at one point in time, so for any two operations you can always say which happened first. In a linearizable datastore there are no concurrent operations at all — every request is handled at a single instant along a single timeline. Concurrent would mean the timeline branches and merges, and operations on different branches would be incomparable.

Causality partial order

Two events are ordered if causally related; incomparable if concurrent. Some operations relate, others don’t — a partial order, which is exactly what the happens-before arrows of Chapter 5’s diagrams drew. Git users already live in one: version histories are causal-dependency graphs — often a straight line, sometimes branches of concurrent commits, rejoined by merges.

Relationship between the two: linearizability implies causality — any linearizable system preserves causal order automatically, across all communication channels, with no extra work (no timestamps passed between components). That automatic causality is a large part of why linearizable systems are pleasant to reason about. But it’s not the only way to get it. You can be causally consistent without linearizability — and crucially, the CAP theorem does not apply to causal consistency: it is the strongest consistency model that does not slow down under network delays and remains available in the face of network failures. Many systems that seem to need linearizability really only need causal consistency, which is cheaper; researchers are building databases on that insight, with eventual-consistency-like performance, though little of it has reached production yet.

What does it take? A replica processing an operation must first have processed everything causally preceding it; to know that, the system must track what each node has “seen” — the same did-the-CEO-know-about-X-when-deciding-Y logic as Chapter 5’s concurrent-write detection, generalized from one key to the whole database. Version vectors generalize; writes carry back the version the application read (as in the Figure 5-13 pattern), and SSI-style conflict detection is a cousin.

9.2.3 — Sequence number ordering

Tracking all causal dependencies explicitly can be impractical — clients read lots of data before writing, and it’s unclear which reads the write depends on; the bookkeeping would be huge. The better way: attach sequence numbers or timestamps to operations. These need not come from a time-of-day clock (Chapter 8 showed how treacherous those are) — a logical clock just increments a counter per operation. Sequence numbers are compact (a few bytes) and totally ordered — every operation gets a unique number, and comparing two numbers tells you which came later.

The goal is a total order consistent with causality: if A causally precedes B, then A gets a lower number than B. Concurrent operations may be numbered arbitrarily. (A total order that ignores causality is easy but useless — random UUIDs compared lexicographically form a valid total order that tells you nothing about what actually happened first.) In a single-leader database this is natural: the replication log is a causality-consistent total order, and the leader just increments a counter per operation; any follower applying the log in order stays causally consistent, however far behind it lags.

Without a single leader — multi-leader, leaderless, or partitioned databases — three generators are common in practice, and all three are subtly broken:

1.

Per-node numbering

Node one emits odd numbers, node two even (or reserve bits of the number for a node ID, guaranteeing uniqueness). But nodes process operations at different rates — the even counter can lag the odd or vice versa, so an odd-numbered and an even-numbered operation tell you nothing reliable about which causally came first.

2.

Wall-clock timestamps

Attach a time-of-day clock reading — high resolution might suffice to order operations (this is the LWW mechanism). But clock skew makes timestamps inconsistent with causality, exactly as in Chapter 8’s Figure 8-3, where the causally-later write got the earlier timestamp. (Spanner can make clock timestamps causality-consistent by waiting out the uncertainty interval before committing — but most clocks can’t report that uncertainty.)

3.

Preallocated blocks

Node A claims 1–1,000, node B claims 1,001–2,000, each allocates a new block as needed. Scalable — but a causally-earlier operation can land in block 1,001–2,000 while its causally-later successor gets a number from 1–1,000.

9.2.4 — Lamport timestamps

There is a simple generator consistent with causality, published by Leslie Lamport in 1978 — one of the most-cited papers in distributed systems. A Lamport timestamp is the pair (counter, node ID): each node keeps its own counter of operations processed, and the node ID breaks ties when counters match. The comparison rule is purely lexicographic: greater counter wins; equal counters, greater node ID wins.

So far that’s just the odd/even scheme again. The causality-preserving trick is one rule: every node and every client tracks the maximum counter value it has ever seen, includes it in every request, and a node that receives a maximum greater than its own counter immediately jumps its counter to that value. In the book’s figure: a client receives counter 5 from node 2 and carries that 5 to node 1, whose counter was only 1 — node 1 immediately moves to 5, so its next operation gets 6. Carrying the maximum along every operation guarantees that each causal dependency produces a strictly greater timestamp.

Lamport timestamps vs version vectors — a classic mix-up

They look similar but do different jobs. Version vectors can distinguish concurrent from causally-dependent operations; Lamport timestamps always impose a total order, and from that order alone you cannot tell whether two operations were concurrent or causally related. The compensation: Lamport timestamps are more compact.

9.2.5 — What timestamp ordering can’t do

Even a causality-consistent total order isn’t enough for many real problems. Take username uniqueness again: two users concurrently register the same name; one should win. With total-order timestamps the tiebreak is easy — lower timestamp wins, and the comparison is always valid. And it genuinely works after the fact: collect all the registration operations in the system, compare timestamps, done.

The failure is the moment of decision. A node has just received a registration request and must decide right now whether it succeeds. At that instant, it has no idea whether another node is concurrently creating the same username, or what timestamp that node will assign. To be sure no one can slip a lower-timestamped claim in ahead of you, you’d have to check every other node — and if one has failed or is unreachable, the whole system grinds to a halt. Not fault tolerant.

The diagnosis: a total order over operations only exists once you have collected all the operations. Unknown operations from other nodes may still need to be inserted at various positions. To enforce something like a uniqueness constraint you need not just a total order — you need to know when that order is finalized, so that no other node can prepend a claim ahead of yours. That idea is captured by total order broadcast.

9.2.6 — Total order broadcast

On a single CPU core the total order of operations is just the order the core executed them. In a distributed system, getting all nodes to agree on the same total order is the hard part. In the research literature this problem is total order broadcast (also atomic broadcast — a confusing name, unrelated to ACID atomicity; total order multicast is another synonym). It is usually described as a message-exchange protocol with two safety properties that must always hold:

  • Reliable delivery: no messages are lost — if a message is delivered to one node, it is delivered to all nodes.
  • Totally ordered delivery: messages are delivered to every node in the same order.

These must survive node and network faults — during an interruption, messages wait and retry, and once the network recovers they still must arrive in the correct order. A third property matters just as much, informally: the order is fixed at delivery time — a node may not retroactively insert a message into an earlier position once later messages have been delivered. That finality is what makes total order broadcast stronger than timestamp ordering.

Why it’s useful:

1.

State machine replication

If every message is a database write and every replica applies the same writes in the same order, replicas stay consistent (modulo temporary lag). This is the state machine replication principle — and it’s exactly what ZooKeeper and etcd implement, which hints at the deep link between total order broadcast and consensus.

2.

Serializable transactions

Let each message be a deterministic stored-procedure transaction; every node processes the same messages in the same order, and partitions and replicas stay in lockstep.

3.

Locks with fencing tokens

Append lock-acquisition requests to the log; messages are numbered sequentially, and that sequence number is a monotonically increasing fencing token. ZooKeeper calls it zxid.

A useful lens: total order broadcast is a log. Delivering a message is appending to the log; every node reads the same sequence. One caveat from partitioned databases — a single leader per partition typically maintains order only within each partition, so cross-partition guarantees (consistent snapshots, foreign keys) don’t come free; total ordering across partitions needs extra coordination.

Building linearizable storage on top of the log

Linearizability and total order broadcast are close but not identical — the broadcast is asynchronous (guaranteed order, no delivery deadline), while linearizability is a recency guarantee. Still, you can build the second from the first. The username claim becomes: (1) append a message tentatively claiming the username; (2) read the log and wait until your own message is delivered back to you; (3) if the first claim for that username in the log is yours, commit and acknowledge; otherwise abort. Because everyone sees the same order, all nodes agree on who came first — the equivalent of a linearizable compare-and-set. The same recipe gives serializable multi-object transactions over a log. The procedure’s writes are linearizable; its plain reads aren’t necessarily (reading an asynchronously updated local copy can be stale — this is formally sequential consistency, a bit weaker). To fix reads: send the read through the log too (etcd’s quorum reads work somewhat this way), or fetch the latest log position linearizably and wait for entries up to it (the idea behind ZooKeeper’s sync()), or read from a synchronously updated replica (chain replication).

Turning it around: the log from linearizable storage

Assume a linearizable integer register with an atomic increment-and-get (compare-and-set works too). For each message: increment-and-get, attach the returned value as the message’s sequence number, send to all nodes (resending any lost messages), and every recipient delivers messages strictly in sequence-number order. Unlike Lamport timestamps, these numbers have no gaps: a node that delivered message 4 and receives message 6 knows message 5 must arrive first and waits for it. That gaplessness is precisely what timestamp ordering lacks.

And how hard can a linearizable increment-and-get register be? If nothing failed, it’s a variable on one node. The trouble is handling interrupted connections and restoring state when that node dies — think hard enough about linearizable sequence-number generators and you inevitably reinvent a consensus algorithm. That’s no accident: a linearizable compare-and-set (or increment-and-get) register and total order broadcast are each formally equivalent to consensus — solve one and you can transform it into the others. A genuinely profound result, and the bridge into the rest of the chapter.

9.3 · Agreeing to commit

Distributed transactions and consensus

Consensus is among the most fundamental problems in distributed computing, and on the surface it’s trivial: get several nodes to agree on something. Many broken systems exist because their builders believed that. The subtleties run deep — even the research community took decades to converge on a correct understanding, with misunderstandings along the way. With replication, transactions, system models, linearizability, and total order broadcast behind us, we can finally tackle it head-on. Two situations where agreement is essential:

Leader election

All nodes must agree on which node is the leader. A contested election under a network fault invites split brain: two leaders, both accepting writes, data diverging and getting lost.

Atomic commit

A transaction spanning several nodes or partitions may fail on some nodes and succeed on others. Preserving ACID atomicity means all nodes agree on the outcome: all abort, or all commit.

9.3.1 — The impossibility of consensus (and its escape hatches)

You may have heard of the FLP result — Fischer, Lynch, and Paterson — proving that no algorithm can always reach consensus if there is a risk a node may crash. Since we must assume nodes crash, reliable consensus is impossible. Yet here we are, about to discuss consensus algorithms. The resolution: FLP is proved in the asynchronous system model — deterministic algorithms, no clocks, no timeouts. Allow timeouts or some other way of suspecting crashed nodes (even sometimes wrongly), and consensus becomes solvable; even just permitting random numbers escapes the impossibility. So FLP is of great theoretical importance while real distributed systems reach consensus routinely in practice.

9.3.2 — From single-node to distributed atomic commit

Recall why atomicity exists: a transaction ends in a clean commit (all writes durable) or a full abort (all writes discarded), so failed transactions don’t litter the database with half-finished state — especially critical for multi-object transactions and secondary indexes, where the index is a separate structure that must stay consistent with the primary data.

On a single node, the storage engine handles it: writes go to the write-ahead log, then a commit record is appended to the log on disk. Crash mid-way, and recovery replays from the log: if the commit record made it to disk, the transaction is committed; if not, its writes roll back. The pivotal instant is the moment the disk finishes writing that commit record — before it, abort is still possible; after it, the transaction is committed even if the database crashes immediately. One device — that disk controller, attached to that node — makes the commit atomic. Order matters too: data first, commit record second.

Across multiple nodes (a partitioned multi-object transaction, or a term-partitioned secondary index whose entries live on other nodes), simply sending a commit request to everyone fails in three characteristic ways: some nodes detect a constraint violation and must abort while others commit; some commit requests are lost to the network (timing out to abort) while others get through; some nodes crash before fully writing the commit record and roll back on recovery while others commit. Any of these leaves the nodes inconsistent — and a commit cannot be retracted after the fact, because once committed, data is visible to other transactions that may already rely on it (the foundation of read committed isolation). A later compensating transaction can undo the effects, but that’s a separate transaction, and any cross-transaction correctness is the application’s problem. The conclusion: a node may only commit when it is certain every other node will too.

9.3.3 — Two-phase commit

2PC is the most common algorithm for atomic commit across nodes — a classic of distributed databases, implemented internally in databases and exposed to applications as XA transactions (for example through the Java Transaction API) or WS-AtomicTransaction for SOAP services. (Don’t confuse 2PC with 2PL, two-phase locking — the serializable-isolation mechanism from Chapter 7. Entirely different things; the name collision is pure misfortune.)

2PC introduces a component absent from single-node transactions: the coordinator (transaction manager) — often a library inside the application process requesting the transaction, sometimes a separate process. Examples: Narayana, JOTM, BTM, MSDTC. The database nodes involved are the participants. The application reads and writes on the participants as normal; when it wants to commit, the coordinator splits the decision into two phases. It resembles a wedding ceremony: the officiant asks each participant individually whether they will commit; only after every “I do” does the officiant pronounce the transaction committed and announce it to everyone. One “no” aborts the ceremony.

The full happy path. Note where durability is forced to disk: participants write their transaction data before voting yes, and the coordinator writes its decision before announcing it.

Figure 9-4 (recreated) · 2PC — the abort path

Abort is cheap for the coordinator to decide and hard for participants to argue with: any no vote, failed prepare, or timeout in phase 1 settles it.

9.3.4 — Why it works: a system of promises

From the pictures, it’s not obvious why 2PC achieves atomicity while a one-phase “everyone commit now” doesn’t — prepare and commit requests can be lost just as easily. The step-by-step shows where the strength hides:

1.

Get a global transaction ID

The application requests a globally unique transaction ID from the coordinator and attaches it to the single-node transaction started on each participant. Any failure here — crash, timeout — lets the coordinator or any participant abort.

2.

Prepare

The coordinator sends a prepare request (tagged with the ID) to every participant. Any failure or timeout aborts the transaction.

3.

The “yes” vote is a point of no return

Before voting yes, a participant makes certain it could commit under all circumstances: all transaction data written to disk (a crash, power failure, or full disk is not an acceptable excuse later), all conflicts and constraints checked. By voting yes it surrenders the right to abort unilaterally — without yet committing.

4.

The commit point

Once all votes are in, the coordinator makes a definitive decision — commit only if every participant said yes — and writes that decision to its transaction log on disk. That disk write is the single moment the outcome is settled.

5.

The decision is irrevocable

The coordinator then sends commit/abort to everyone, retrying forever on failure. If a participant crashed after voting yes, it commits on recovery — it cannot refuse. Single-node atomic commit collapses points 3 and 4 into one event: writing the commit record.

Back to the wedding: before “I do,” either party can call it off; after saying it, fainting through the pronouncement changes nothing — you can query the officiant for your transaction’s status when you come to, or wait for the next retry of the commit request, which will have continued throughout your unconsciousness. The two “points of no return” — the participant’s vote and the coordinator’s logged decision — are what make 2PC atomic.

9.3.5 — Coordinator failure: the blocking problem

Participant or network failures are handled: failed prepares abort; failed commit/abort requests retry forever. The coordinator is the weak point. If it fails before sending prepares, participants can safely abort. But once a participant has voted yes, it can no longer decide anything alone — it must wait for the coordinator’s verdict. A transaction in that state is in doubt (or uncertain).

Figure 9-5 (recreated) · The coordinator crashes after the votes

In principle the participants could talk among themselves and work out how everyone voted — but that’s not part of the 2PC protocol. Without the coordinator, an in-doubt participant is stuck: it holds locks (shaded regions in the earlier figures) that it cannot release until the outcome is settled. On recovery the coordinator reads its log and resolves every in-doubt transaction — any transaction with no commit record in the log is aborted. The commit point of 2PC is, in the end, a regular single-node atomic commit on the coordinator.

9.3.6 — Three-phase commit, and why nobody uses it

2PC is called a blocking atomic commit protocol precisely because it can get stuck waiting for the coordinator. An alternative, three-phase commit (3PC), has been proposed — but it assumes a network with bounded delay and nodes with bounded response times, and in most real systems (unbounded delays, process pauses — all of Chapter 8) it cannot guarantee atomicity. In general, nonblocking atomic commit requires a perfect failure detector — a reliable way to tell whether a node has crashed — and with unbounded network delays, a timeout is not one: a request can time out from network trouble while every node is healthy. So 2PC persists, coordinator-shaped warts and all.

9.3.7 — Distributed transactions in practice: XA

Distributed transactions have a mixed reputation: a real safety guarantee that is hard to get any other way, and simultaneously criticized for operational pain, killed performance, and promising more than they deliver — enough that many cloud services skip them entirely. MySQL’s distributed transactions have been reported at more than 10× slower than single-node ones; much of the cost is the extra disk forcing (fsync) for crash recovery plus the extra network round-trips. Before dismissing them, be precise about which kind you mean:

Database-internal

All participants run the same database software (VoltDB, MySQL Cluster’s NDB storage engine). Free to use any protocol and vendor-specific optimizations — these often work quite well.

Heterogeneous

Participants are different technologies — databases from different vendors, or non-databases like message brokers. Atomic commit must span systems that share nothing under the hood. Much harder, and the interesting case.

The killer app for heterogeneous transactions is exactly-once message processing: acknowledge a message from a queue if and only if the database transaction that processed it committed, by committing the acknowledgment and the writes atomically. If either fails, both abort and the broker can safely redeliver — a few retries still add up to effectively-once processing. The catch: every system touched must support the same atomic commit protocol. A side effect that emails a receipt can still be sent twice if the email server doesn’t participate.

X/Open XA (eXtended Architecture, 1991) is the standard for 2PC across heterogeneous technologies — supported by PostgreSQL, MySQL, DB2, SQL Server, and Oracle, plus message brokers including ActiveMQ, HornetQ, MSMQ, and IBM MQ. XA is not a network protocol: it’s a C API for talking to a transaction coordinator, with bindings elsewhere — in Java EE, the Java Transaction API implements it over JDBC database drivers and JMS broker drivers. Driver-level XA support means the coordinator can ask a participant to prepare, commit, or abort through callbacks.

The standard doesn’t say how to build the coordinator, and in practice it’s usually a library loaded into the application process itself, keeping its log on the application server’s local disk. If that process or machine dies, the coordinator dies with it — and every prepared-but-uncommitted participant transaction is stuck in doubt until the server is restarted and the coordinator library recovers its log. The database can’t contact the coordinator directly; all communication goes through the client library.

9.3.8 — In-doubt transactions hold locks

Why is “stuck in doubt” so bad? Can’t the rest of the system just work around it? No — because of locking. Transactions take row-level exclusive locks on modified rows (to prevent dirty writes), and under two-phase locking for serializability, shared locks on rows read too. Those locks cannot be released until commit or abort — so an in-doubt transaction holds its locks the entire time it waits. A coordinator that takes 20 minutes to restart means 20 minutes of blocked rows; a lost coordinator log means locks held until a human intervenes. While those locks sit, no other transaction can modify (and depending on the database, even read) that data — large parts of the application can grind to a halt.

Reboots don’t save you: a correct 2PC implementation must preserve an in-doubt transaction’s locks across restarts, or it would risk breaking atomicity. Orphaned in-doubt transactions — whose outcome the coordinator genuinely cannot decide, say from a lost or corrupted log — do occur in practice, and they sit forever holding locks. The only escape is an administrator manually inspecting the participants, figuring out whether anything committed or aborted, and applying that outcome everywhere — probably under stress, during a production outage (otherwise the coordinator wouldn’t be in such a state). Many XA implementations offer an emergency hatch, heuristic decisions: a participant unilaterally commits or aborts an in-doubt transaction without the coordinator’s verdict. “Heuristic” is a euphemism for probably breaking atomicity — for catastrophes only, never routine use.

The coordinator is itself a database — treat it like one

XA solves a real problem, but its operational cost comes from a realization: the coordinator stores transaction outcomes, which makes it a kind of database, and it deserves the same care. Four structural problems: (1) A single-machine coordinator is a single point of failure for the whole system — surprisingly many implementations aren’t highly available by default. (2) It breaks statelessness: apps that kept all state in the database suddenly have crucial durable state in the coordinator’s log — those application servers are no longer interchangeable. (3) XA must be a lowest common denominator: no cross-system deadlock detection (no standard protocol for exchanging lock-wait information), no SSI (no protocol for cross-system conflict identification). (4) Even database-internal transactions amplify failures: 2PC needs all participants to respond, so any broken part breaks the transaction — the opposite of fault tolerance. Chapters 11 and 12 return to ways of keeping systems consistent without this pain.

9.3.9 — Fault-tolerant consensus

Formally: one or more nodes may propose values, and the algorithm decides on one of them. Several customers race for the last airplane seat; each node proposes the customer it’s serving; the decision says who flies. A consensus algorithm must satisfy:

1.

Uniform agreement

No two nodes decide differently.

2.

Integrity

No node decides twice.

3.

Validity

If a node decides value v, then v was proposed by some node. (Rules out the trivial “always decide null” algorithm, which would satisfy the first two.)

4.

Termination

Every node that does not crash eventually decides some value. This is the fault-tolerance property — and the liveness one; the first three are safety properties.

Without fault tolerance, the first three are trivial: hardcode one node as dictator and let it decide everything. But when the dictator fails, the system stops deciding — which is exactly what 2PC’s coordinator looks like. The consensus system model assumes a crashed node vanishes forever — the datacenter-destroyed-by-landslide model, not the software-crash model — so any algorithm that must wait for a node to recover fails termination, and 2PC does not meet termination’s requirements. The provable limit: any consensus algorithm requires a majority of nodes functioning correctly to assure termination — that majority can form a quorum, just like Chapter 5. Within that assumption, good implementations keep the safety properties (agreement, integrity, validity) even when a majority fails or the network is badly broken: a massive outage can stop the system from processing, but cannot corrupt it into invalid decisions. Byzantine faults are assumed away here (a node not following the protocol can break safety); BFT variants exist if fewer than a third of nodes are Byzantine.

The best-known algorithms are Viewstamped Replication (VSR), Paxos, Raft, and Zab (ZooKeeper’s). They differ in detail but share high-level ideas — and implementing one yourself is inadvisable; it’s hard, with a poor historical success record. Most don’t decide a single value anyway: they decide a sequence, which makes them total order broadcast engines — consensus is repeated rounds of proposing and deciding the next message. The mapping is exact: agreement → all nodes deliver the same messages in the same order; integrity → messages are not duplicated; validity → messages aren’t corrupted or fabricated from thin air; termination → messages aren’t lost. VSR, Raft, and Zab implement total order broadcast directly; in Paxos this optimization is Multi-Paxos.

Now the apparent circularity: single-leader replication already looks like total order broadcast — why didn’t Chapter 5 need consensus? Because the leader was chosen by hand. A human-configured leader is a dictatorship that satisfies agreement, integrity, and validity but not termination — progress requires human intervention. Automatic failover gets closer, but correct leader election needs all nodes to agree who the leader is… and consensus algorithms are total order broadcast, which is like single-leader replication, which needs a leader. To elect a leader we must first elect a leader. The way out is these algorithms’ actual trick.

9.3.10 — Epoch numbering and quorums

Every well-known consensus protocol uses a leader internally — but none guarantees a unique leader at all times. Instead each defines an epoch number (the ballot in Paxos, view number in VSR, term in Raft) and guarantees: within each epoch, the leader is unique. Whenever the current leader is believed dead, nodes vote to elect a new leader with an incremented epoch number — so epochs are totally ordered and monotonically increasing, and when two leaders from different epochs conflict (the old one wasn’t dead after all), the higher epoch wins.

Before deciding anything, a leader must confirm it hasn’t been ousted. A node can’t trust its own judgment here — believing you’re the leader doesn’t make the others agree (Chapter 8’s majority-defined truth). So the leader collects votes from a quorum — typically, though not always, a majority of nodes — for every decision: send the proposal out, wait for a quorum to respond in favor. A node votes in favor only if it knows of no leader with a higher epoch. That gives two rounds of voting: once to choose the leader, once on each of its proposals. The key insight is that the two quorums must overlap: if a proposal vote succeeds, at least one node that voted for it also participated in the most recent leader election — so if the proposal vote surfaces no higher epoch, no higher-epoch election has happened, and the leader can safely decide.

Figure 9-6 (recreated) · An epoch change, survived safely

Compare with 2PC, which this voting superficially resembles. The differences are everything: in consensus the coordinator is itself elected; only a majority of nodes must vote yes, not every participant; and there is a defined recovery process that brings nodes to a consistent state after a new leader takes over, keeping the safety properties intact through the transition.

9.3.11 — The limitations of consensus

Consensus algorithms are a genuine breakthrough — concrete safety properties in an uncertain world, progress guaranteed while a majority survives. But the benefits have prices:

1.

Synchronous-replication cost

The pre-decision voting is a form of synchronous replication. Databases often choose async and accept possible data loss on failover for better performance — consensus systems don’t get to make that trade.

2.

Strict majority required

At least 3 nodes to tolerate 1 failure (2 of 3 form a majority), 5 to tolerate 2 (3 of 5). If a network fault cuts off part of the cluster, only the majority side makes progress; the rest is blocked — the cost-of-linearizability argument again.

3.

Fixed membership

Most algorithms assume a fixed set of voting nodes — you can’t just add or remove nodes at will. Dynamic-membership extensions exist but are much less well understood than the static versions.

4.

Timeout-sensitivity

Failure detection relies on timeouts. With highly variable network delays — especially geographically distributed systems — nodes sometimes falsely believe the leader died. Safe, but frequent elections wreck performance: the system can spend more time choosing leaders than doing work.

Some consensus algorithms are particularly sensitive to weird network behavior: Raft has demonstrated unpleasant edge cases where a single consistently unreliable link — while the rest of the network is fine — makes leadership bounce between nodes or forces the current leader to resign endlessly, so the system effectively never progresses. Other algorithms have similar problems, and designing consensus that is robust to unreliable networks remains open research.

9.4 · Outsourced agreement

Membership and coordination services

Projects like ZooKeeper and etcd are often described as “distributed key-value stores” or “coordination and configuration services” — their APIs look like a database’s (read and write the value for a key, iterate over keys). So why do they bother implementing a consensus algorithm? What makes them different from any other database?

As an application developer you’ll rarely use ZooKeeper directly — it’s poorly suited as a general-purpose database. More likely you rely on it indirectly: HBase, Hadoop YARN, OpenStack Nova, and Kafka all depend on ZooKeeper running in the background. What do they get from it?

ZooKeeper and etcd are designed to hold small amounts of data that fit entirely in memory (still written to disk for durability) — not your application data. That small dataset is replicated to every node with a fault-tolerant total order broadcast algorithm — the same primitive that keeps database replicas consistent when every message is a write. ZooKeeper is modeled on Google’s Chubby lock service and layers several features on top that turn out to be exactly what distributed systems need:

9.4.1 — The feature set

1.

Linearizable atomic operations

An atomic compare-and-set implements a lock: several nodes race to perform the same operation, exactly one wins — guaranteed atomic and linearizable by the consensus protocol even if a node fails or the network breaks mid-operation. Distributed locks are usually built as leases with an expiry time, so a dead client can’t hold one forever.

2.

Total ordering of operations

Chapter 8’s fencing lesson: a resource protected by a lease needs a fencing token that increases monotonically on every acquisition. ZooKeeper totally orders all operations and stamps each with a monotonically increasing transaction ID (zxid) and version number (cversion) — either works as a fencing token.

3.

Failure detection via sessions

Clients hold long-lived sessions with the ZooKeeper servers, maintained by periodic heartbeats. A connection can be briefly interrupted or a ZooKeeper node fail without killing the session; but if heartbeats cease for longer than the session timeout, the session is declared dead. Locks held by a session can be configured to auto-release on expiry — ZooKeeper calls these ephemeral nodes.

4.

Change notifications (watches)

A client can watch another client’s locks and values — find out when someone joins the cluster (they wrote a value) or fails (their session timed out and their ephemeral nodes vanished) — without polling. One client reads what another wrote, and subscribes to changes.

Of these, only the linearizable atomic operations genuinely require consensus — the rest are useful layering. The combination is what makes ZooKeeper so handy for coordination.

9.4.2 — Allocating work to nodes

Two canonical tasks suit this model. First: several instances of a service, one of which must be the leader or primary, with a fast takeover when the leader fails — single-leader databases, job schedulers, stateful systems generally. Second: a partitioned resource (database, message streams, file storage, distributed actor system) where partitions must be assigned to nodes — and reassigned as nodes join, leave, or fail, like Chapter 6’s rebalancing. Judicious combinations of atomic operations, ephemeral nodes, and notifications let applications recover from faults without human intervention. It isn’t easy — Apache Curator exists to wrap the tricky recipes — but it beats implementing consensus from scratch, an endeavor with a poor success record.

Scale note: an application might grow to thousands of nodes, and running majority votes across that many would be terribly inefficient. ZooKeeper instead runs on a fixed number of nodes — usually three or five — performing its majority votes among those while serving many thousands of clients. It effectively outsources consensus, operation ordering, and failure detection to a small dedicated cluster. The data it manages is slow-changing — “the node at 10.1.1.23 is the leader for partition 7” changes on a timescale of minutes or hours, not thousands of times per second. For fast-changing runtime state, other tools (Apache BookKeeper) are the better fit.

9.4.3 — Service discovery

ZooKeeper, etcd, and Consul are also used for service discovery: finding which IP address to connect to for a given service. In cloud datacenters, VMs come and go, so services register their endpoints in a service registry at startup and others look them up. Interestingly, service discovery doesn’t actually need consensus — DNS, the traditional answer, layers caches for performance and availability, is absolutely not linearizable, and everyone is fine with slightly stale results; what matters there is reliable availability and robustness to network interruptions. But leader election does need consensus — so if your consensus system already knows who the leader is, exposing that knowledge to other services is cheap. Some systems add read-only replicas: they receive the decision log asynchronously and serve non-linearizable reads, expanding read capacity without voting.

9.4.4 — Membership services

ZooKeeper and friends continue a research line going back to the 1980s (important for systems like air traffic control): membership services, which determine which nodes are currently active, live members of the cluster. Chapter 8 showed that unbounded network delays make reliable failure detection impossible on your own — but couple failure detection with consensus, and nodes can agree on who is alive and who is not. A node can still be incorrectly declared dead while actually alive — but having the system-wide agreement is what makes it useful: “pick the lowest-numbered current member as leader” only works if everyone agrees on the member list.

9.5 · Pulling it together

Summary

Linearizability makes replicated data appear to be a single copy with atomic operations — a database that behaves like a variable in a single-threaded program. Its cost: it’s slow, especially with large network delays, and during a partition you choose between it and availability. Causality is the cheaper ordering — what happened before what, with branching-and-merging histories like Git’s — and causal consistency has neither the coordination overhead of linearizability nor its sensitivity to network problems. But even captured causality (say, with Lamport timestamps) can’t implement things like username uniqueness: a node accepting a registration needs to know no other node is concurrently claiming the same name, and a total order is only final once all operations are in. That is what led to consensus: deciding something so all nodes agree on it, irrevocably.

A remarkable cluster of problems turns out to be equivalent to consensus — a solution to any one can be transformed into a solution for the rest:

1.

Linearizable CAS registers

The register must decide atomically whether to set its value, based on what the current value is.

2.

Atomic transaction commit

The database must decide commit or abort for a distributed transaction.

3.

Total order broadcast

The messaging system must decide the order of message delivery.

4.

Locks and leases

With clients racing to acquire, the lock must decide who got it.

5.

Membership / coordination

Given a failure detector (timeouts), the system must decide which nodes are alive and which are dead.

6.

Uniqueness constraints

With concurrent conflicting records, the constraint must decide which one passes.

All of these are straightforward with a single decision-maker — which is exactly what a single-leader database does: power vested in the leader buys linearizable operations, uniqueness constraints, a totally ordered replication log. But if that leader fails or becomes unreachable, the system stops making progress. Three ways to respond:

1.

Wait for recovery

Accept blocking while the leader is down. Many XA/JTA coordinators take this road. It does not satisfy termination — if the leader never returns, the system is blocked forever.

2.

Manual failover

Humans choose a new leader and reconfigure. Many relational databases do this — consensus by “act of God,” limited by the speed of humans.

3.

Automatic election

Use a proven consensus algorithm that handles adverse network conditions correctly. Strongly advised over inventing your own.

There’s a sense in which a single-leader database only “kicks the can down the road”: it still needs consensus for leadership changes, just less frequently. ZooKeeper-style tools provide the outsourced consensus, failure detection, and membership service — not easy to use well, but far better than rolling your own against everything Chapter 8 threw at you. And not every system needs consensus at all: leaderless and multi-leader systems skip it and live with the conflicts — which may be fine; maybe we simply cope without linearizability and learn to work with branching, merging version histories. That closes Part II: replication (Ch 5), partitioning (Ch 6), transactions (Ch 7), the failure model (Ch 8), and finally consistency and consensus. Glossary

linearizability
The illusion of a single copy of the data with atomic operations: as soon as one client’s write completes, every client must see that value. A recency guarantee on an individual register — also called atomic, strong, immediate, or external consistency.
serializability
An isolation property of transactions: they behave as if executed in some serial order. Orthogonal to linearizability — a DB can offer either, both (strict serializability / strong-1SR), or neither. SSI is serializable but not linearizable (snapshot reads exclude recent writes by design).
CAP theorem
Named by Brewer (2000), known since the 1970s: if a linearizable system’s replicas are cut off by a network partition, they must refuse requests; a non-linearizable system can stay available. Honest phrasing: consistent or available when partitioned — a perfectly reliable network is a fantasy, so the P isn’t optional.
causality / causal order
The happened-before chains of operations: cause before effect, message sent before received, question before answer. Defines a partial order — concurrent operations are incomparable.
happens-before
A happened before B if B might have known about, depended on, or built upon A. Neither happens before the other → concurrent. Physical timing is irrelevant; knowledge is what counts.
sequence number / logical clock
A compact totally ordered identifier for operations, from an incrementing counter rather than a quartz clock. Best when the total order is consistent with causality.
Lamport timestamp
The pair (counter, node ID). Each node and client tracks the maximum counter seen and carries it on every request; a node seeing a higher maximum immediately jumps its own counter to it. Total order consistent with causality — but cannot distinguish concurrent from causally related, and the order is only final after all operations are collected.
total order broadcast
Protocol guaranteeing reliable delivery (no losses) and totally ordered delivery (same order everywhere), with the order fixed at delivery time. Equivalent to consensus. Powers state machine replication, serializable transactions, fencing tokens.
state machine replication
If every message in the log is a write and every replica applies the same writes in the same order, replicas stay consistent — the principle behind ZooKeeper, etcd, and single-leader replication done properly.
atomic commit
Getting all participants of a distributed transaction to agree on one outcome — all commit or all abort — so no half-finished state survives. Formally a close cousin of consensus; nonblocking atomic commit is actually harder than consensus.
2PC (two-phase commit)
Coordinator sends prepare to all participants; if all vote yes, the coordinator writes its decision to disk and sends commit, else abort. Atomic — and blocking: a consensus algorithm, but not a good one.
coordinator (transaction manager)
2PC’s extra component, often a library in the application process (Narayana, JOTM, BTM, MSDTC). Its transaction log is effectively a database — a single point of failure if not replicated.
in-doubt (uncertain) transaction
A participant’s state after voting yes but before hearing the verdict. It can neither commit nor abort alone, and it holds locks the whole time — potentially forever if the coordinator’s log is lost.
XA transactions
X/Open XA (1991): a standard C API (JTA in Java) for 2PC across heterogeneous systems — supported by PostgreSQL, MySQL, DB2, SQL Server, Oracle, and several message brokers. Not a network protocol.
heuristic decision
An XA emergency hatch: a participant unilaterally commits or aborts an in-doubt transaction without the coordinator. A euphemism for probably breaking atomicity — catastrophes only.
FLP impossibility
Fischer–Lynch–Paterson: no deterministic consensus algorithm can always terminate in the asynchronous model if a node might crash. Escaped in practice via timeouts/failure detectors or even just randomness.
consensus
Nodes propose values; the algorithm decides one, satisfying uniform agreement, integrity, validity (safety — always held) and termination (liveness — needs a live majority). Equivalent to total order broadcast and to linearizable CAS registers.
epoch (ballot / term / view)
A monotonically increasing number identifying each leadership era. The leader is unique within an epoch; when epochs conflict, the higher one wins. Raft calls it term, Paxos ballot, VSR view number.
quorum
The minimum set of nodes whose votes a leader needs — typically a majority. Two rounds of voting (leader election, then proposals) with overlapping quorums are what make stale leaders harmless: 2f+1 nodes tolerate f failures.
leader election
Choosing the leader by vote when the old one is suspected dead, starting a new epoch. Needs consensus to avoid split brain — which is why a single-leader database “kicks the can down the road.”
fencing (tokens)
Making a stale leader harmless by number: every grant carries a monotonically increasing token, and the resource rejects writes carrying older tokens than the highest processed. In ZooKeeper, zxid or cversion serves.
ZooKeeper / etcd
Coordination services holding small in-memory datasets, replicated via total order broadcast (Zab / Raft). Offer linearizable CAS, zxid-ordered fencing tokens, sessions with heartbeats, ephemeral nodes, and watches. Run on 3–5 nodes, serve thousands of clients. HBase, YARN, OpenStack Nova, and Kafka have all depended on ZooKeeper.
session
A client’s long-lived, heartbeat-maintained connection to ZooKeeper. Survives brief interruptions and node failures; declared dead after the session timeout expires, at which point its ephemeral nodes vanish and its locks release.
watch
A one-time notification a client registers on a znode/key — how ZooKeeper clients learn about other clients joining, writing, or dying, without polling.
ephemeral node
A ZooKeeper node tied to a session’s lifetime: it disappears automatically when the session times out — automatic lock release, membership tracking, and failure signaling in one primitive.
membership service
Determines which nodes are currently live members of the cluster — unreliable detection made trustworthy by consensus agreement on the list. Research lineage back to the 1980s.
