4.0 · The setup

Rolling upgrades and the two compatibilities

Chapter 1 introduced evolvability: build systems that make change easy. Applications inevitably change — features are added, requirements understood better, business circumstances shift — and a change to features usually means a change to the data they store: a new field, a new record type, an old thing presented in a new way.

The catch: in a large application, code changes can’t happen instantaneously. Server-side, you want rolling upgrades (staged rollouts) — deploy the new version to a few nodes at a time, check it’s running smoothly, and work through the fleet gradually: no downtime, more frequent releases, less risk. Client-side, you’re at the mercy of users who may not install the update for a long time. Either way, old and new versions of the code, and old and new data formats, coexist in the system at the same time — so the system must maintain compatibility in both directions:

Backward compatibility

Newer code reads data written by older code. Normally the easy one — as the author of the new code, you know the old format and can handle it explicitly.

Forward compatibility

Older code reads data written by newer code. Trickier — requires old code to ignore additions made by newer versions of itself.

Relational databases assume all data conforms to one schema (changeable via ALTER, but exactly one in force at a time); schema-on-read “schemaless” databases allow a mixture of formats written at different times (Chapter 2). This chapter looks at how encoding formats — JSON, XML, Protocol Buffers, Thrift, Avro — handle schema change, and then at the three places encoded data flows: databases, services (REST/RPC), and asynchronous message passing.

4.1 · Objects to bytes

Formats for encoding data

Programs hold data in two representations. In memory: objects, structs, lists, arrays, hash tables, trees — optimized for CPU access, typically via pointers. To write it to a file or send it over the network: a self-contained sequence of bytes — a pointer is meaningless to any other process, so the byte form looks nothing like the in-memory form. The translation between them:

Encoding
In-memory → bytes. Also called serialization or marshalling. (Nothing to do with encryption; and the book says “encoding” rather than “serialization” to avoid a collision with Chapter 7’s transaction sense of the word.)
Decoding
Bytes → in-memory. Also called parsing, deserialization, unmarshalling.

Language-specific formats

Most languages ship built-in encoders — Java’s java.io.Serializable, Ruby’s Marshal, Python’s pickle, third-party Kryo for Java. Convenient, but four deep problems:

i.

Language lock-in

Reading the data from another language is very difficult — you’ve committed to your current language for potentially a very long time.

ii.

Security holes

Restoring objects requires the decoder to instantiate arbitrary classes — an attacker who can feed your app an arbitrary byte sequence can often remotely execute code.

iii.

Versioning as afterthought

Designed for quick-and-easy encoding; forward and backward compatibility are neglected.

iv.

Efficiency as afterthought

Java’s built-in serialization is notorious for bad performance and bloated output.

Verdict: don’t use your language’s built-in encoding for anything beyond very transient purposes.

JSON, XML, and CSV

The standardized, many-language formats. Widely known, widely supported, almost as widely disliked — XML too verbose and complicated, JSON popular mainly via built-in browser support and relative simplicity, CSV less powerful. Beyond the syntax complaints, subtler problems:

  • Numbers are ambiguous. XML and CSV can’t distinguish a number from a digit-string without an external schema; JSON distinguishes strings and numbers but not integers from floats, and specifies no precision. Integers greater than 2⁵³ can’t be exactly represented in an IEEE 754 double — so Twitter’s API returns each 64-bit tweet ID twice, as a JSON number and as a decimal string, to survive JavaScript parsing.
  • No binary strings. Both handle Unicode text well but have no byte-sequence type. The workaround — Base64-encode and mark it in the schema — works but increases data size by 33%.
  • Schemas are optional and heavy. XML/JSON schema languages are powerful, complicated to learn and implement; XML schemas are widespread, many JSON tools don’t bother. Without a schema, apps hardcode the encoding logic — and the correct interpretation of numbers and binary strings depends on the schema.
  • CSV has no schema at all — the app defines the meaning of every row and column, and handles new columns manually. It’s vague (what if a value contains a comma or newline?), and although RFC 4180 formalized the escaping, not all parsers implement it correctly.

Good enough anyway — especially as data interchange between organizations, where the difficulty of getting different organizations to agree on anything outweighs prettiness and efficiency. Internally, at terabyte scale, you can do better.

Binary variants and the Example 4-1 record

Binary encodings of JSON/XML exist in profusion (MessagePack, BSON, BJSON, UBJSON, BISON, Smile; WBXML, Fast Infoset) — niche adoption only, because they keep the JSON/XML data model and thus must repeat every field name inside the encoded data. The record we’ll encode six ways:

{ "userName": "Martin", "favoriteNumber": 1337, "interests": ["daydreaming", "hacking"] }

MessagePack (Figure 4-1) encodes it in 66 bytes — barely less than the 81 bytes of whitespace-free textual JSON. How it reads the first bytes: 0x83 = an object (top nibble 0x80) with 3 fields (bottom nibble 0x03); 0xa8 = a string (top nibble 0xa0) of 8 bytes; then the ASCII userName — no terminator or escaping needed, since the length was declared. A 33% space saving that costs you human-readability is a debatable trade.

Thrift and Protocol Buffers

Apache Thrift (from Facebook) and Protocol Buffers (from Google) — both open-sourced 2007–08 — are binary encodings that require a schema. The Example 4-1 record in Thrift’s interface definition language:

struct Person { 1: required string userName, 2: optional i64 favoriteNumber, 3: optional list<string> interests }

And the equivalent protobuf schema:

message Person { required string user_name = 1; optional int64 favorite_number = 2; repeated string interests = 3; }

Both ship code generation: the schema compiles to classes in your language of choice. And both replace field names with field tags — the 1, 2, 3 in the schemas — which is where the savings come from:

  • Thrift BinaryProtocol: 59 bytes. Each field has a type annotation and, where needed, a length; strings in ASCII/UTF-8 like MessagePack — but no field names, just the tags.
  • Thrift CompactProtocol: 34 bytes — packs field type and tag into one byte, and encodes integers as variable-length integers (varints): numbers between –64 and 63 take one byte, –8192 to 8191 take two, and so on — the top bit of each byte says whether more bytes follow. 1337 fits in two bytes, not eight.
  • Protocol Buffers: 33 bytes, the same ideas with slightly different bit packing. (Thrift also has a DenseProtocol — C++-only, so not cross-language — and two JSON-based formats.)

One nuance: required vs. optional makes no difference to the encoding — nothing in the bytes says which a field was. required just enables a runtime check that fails if the field is unset — useful for catching bugs.

Field tags and schema evolution

An encoded record is a concatenation of fields, each identified by its tag number and annotated with a datatype. From this, all the evolution rules follow:

  • You can rename fields freely — the encoded data never mentions names. You can never change a tag — that instantly invalidates all existing encoded data.
  • Adding a field is forward compatible: give it a new tag; old code that doesn’t recognize it just skips that many bytes (the datatype annotation tells it how many).
  • Adding a field must not make it required: new code reading old data (which lacks the field) would fail the runtime check — so every field added after initial deployment must be optional or defaulted. That’s backward compatibility.
  • Removing is the mirror image: you can only remove an optional field, and you can never reuse its tag number — old data out there still carries it, and it must be ignorable forever.
  • Datatype changes are risky: 32-bit → 64-bit integer works for new-code-reads-old (pad with zeros), but old code reading new data truncates values that no longer fit in 32 bits.

A curious protobuf detail: no list datatype, just a repeated marker — the same tag appears multiple times in a record. This buys you a free evolution: an optional (single-valued) field can become repeated — new code reading old data sees a list of zero-or-one elements; old code reading new data sees only the last element. Thrift’s dedicated list datatype can’t do this, but does support nested lists.

Avro: the schema is the message

Apache Avro (started 2009 as a Hadoop subproject, after Thrift proved a poor fit for Hadoop’s use cases) also uses a schema — in two languages, a human-editable Avro IDL and a machine-friendly JSON representation:

record Person { string userName; union { null, long } favoriteNumber = null; array<string> interests; }

No tag numbers anywhere. The Example 4-1 record encodes in 32 bytes — the most compact of all, because the bytes contain nothing to identify fields or datatypes at all: just values concatenated together, a string is a length prefix plus UTF-8 bytes, an integer is a varint. You can only decode the bytes by walking the fields in schema order with the schema telling you each one’s type. Which raises the obvious question — whose schema?

Writer’s schema vs. reader’s schema

The writer’s schema is whatever version the encoding application knows (say, compiled into it). The reader’s schema is what the decoding application expects (its own compiled-in version). Avro’s key idea: they don’t have to be the same — only compatible. At read time, the Avro library resolves the differences: fields matched by name (order irrelevant); writer fields the reader doesn’t know are ignored; reader fields the writer didn’t write are filled with declared defaults.

Evolution rules: you may only add or remove a field that has a default value. Add without a default → new readers can’t read old writers (breaks backward compatibility). Remove without a default → old readers can’t read new writers (breaks forward). Nullability is also explicit: Avro won’t let you default anything to null unless null is a branch of a union type (union { null, long }) — more verbose than everything-nullable-by-default, but it prevents bugs (Tony Hoare called null references “the billion dollar mistake”). Datatype changes work when Avro can convert; field renames use aliases (backward compatible, not forward); new union branches likewise.

But how does the reader know the writer’s schema?

You can’t embed the whole schema per record — it would dwarf the data. Three contexts, three answers:

i.

Big files

Millions of records, one writer: include the writer’s schema once at the head of the file — Avro’s object container files do exactly this. The Hadoop case.

ii.

Database with per-record writes

Records written at different times by different schema versions: store a small version number at the start of each record, keep a database of schema versions, look up the writer’s schema on read (how LinkedIn’s Espresso works).

iii.

Network connections

Two processes on a bidirectional connection negotiate the schema at connection setup and use it for the connection’s lifetime — the Avro RPC protocol’s approach.

A database of schema versions is worth keeping anyway — it documents your formats and lets you check compatibility before deploying a change.

Why no tags turns out to be a feature

Dynamically generated schemas. Dump a relational database to a file: generate an Avro record per table, one field per column — and when the database schema changes (a column added, a column dropped), just generate the new schema and export again; the fields match by name, so readers keep working. With Thrift/Protobuf, field tags would have to be assigned by hand — and never reused — because dynamic schemas were never their design goal. Avro also makes code generation optional: useful for statically typed languages (type checking, IDE help), pointless or annoying for dynamically typed ones (JavaScript, Ruby, Python) — and a positive obstacle when the schema itself is generated at runtime. Open an object container file with Apache Pig and analyze it without ever thinking about schemas — the file is self-describing.

The merits of schemas — four points

Binary schema-driven formats (1) are more compact than binary-JSON variants (field names omitted); (2) make the schema documentation that can’t drift, since decoding requires it; (3) allow compatibility checking before deployment via a schema registry; (4) enable code generation and compile-time type checking for statically typed languages. ASN.1 (1984) did tags-and-evolution first — it still encodes SSL certificates — but is complex, badly documented, and a poor choice for new applications.

4.2 · Flow #1

Dataflow through databases

In a database, the writing process encodes; the reading process decodes. Sometimes that’s one process — in which case writing to the database is sending a message to your future self, and backward compatibility is clearly required, or your future self can’t read what you wrote.

But usually several processes access the database at once, and during a rolling upgrade, some run newer code and some run older. A value written by newer code may be read by older code a moment later — so databases need forward compatibility too.

Figure 4-7 (recreated) · How old code silently deletes new data

The snag: decode into application model objects, re-encode on write-back, and any field the old code didn’t know about can be dropped in translation. Formats can preserve unknown fields, but you sometimes have to take care at the application level — it’s not a hard problem, just one you must remember exists.

The other deep property of databases: data outlives code. You replace your application’s old version within minutes of deploying the new one, but a database contains values written five milliseconds ago and five years ago — still in the original encoding, unless you rewrote it. Rewriting (migrating) is possible but expensive, so databases avoid it: most add a column with a NULL default and fill the gap at read time; LinkedIn’s Espresso uses Avro, inheriting its schema-evolution rules — the whole database appears to be in one schema even though storage holds many historical versions. And when you archive or snapshot, you copy anyway — so dump consistently in the latest schema, into immutable Avro object container files, or an analytics-friendly column format like Parquet.

4.3 · Flow #2

Dataflow through services: REST and RPC

The most common network arrangement: servers expose an API; clients connect to make requests — a service. The web itself works this way (browsers GET/POST against servers via standardized protocols); so do native mobile apps, and in-browser JavaScript apps via XMLHttpRequest (the Ajax technique) — except the responses are JSON for code to process, not HTML for humans. A server can itself be a client of another service (a web app server is a client of its database), and decomposing a large application into services by functionality — one service requesting from another — is service-oriented architecture (SOA), lately refined and rebranded as microservices.

Services are like databases with training wheels: both let clients submit and query data, but services expose an application-specific API permitting only what the business logic allows — a useful encapsulation. And the key design goal of microservices: independently deployable, independently evolvable services — each owned by a team releasing frequently without coordinating — which means old and new versions of clients and servers run simultaneously, and the encodings must be compatible across API versions. Exactly this chapter’s problem.

When HTTP underlies the service, it’s a web service — a slight misnomer, since it’s used in three quite different contexts: (1) client apps on user devices talking to services over the public internet; (2) one service talking to another inside the same organization, same datacenter (the software supporting this is sometimes called middleware); (3) services of different organizations exchanging data via the internet — public APIs like credit-card processing or OAuth.

REST and SOAP

Two popular approaches, philosophically almost opposite. REST is not a protocol but a design philosophy built on HTTP’s principles: simple data formats, URLs identifying resources, HTTP features for cache control, authentication, and content negotiation. An API built this way is RESTful; REST has been gaining popularity, especially for cross-organizational integration, and is often associated with microservices. SOAP is an XML-based protocol that aims to be independent of HTTP (avoiding most of its features) and brings a sprawling framework of WS-* standards; its APIs are described in WSDL (XML), which enables code generation — useful in statically typed languages, less so in dynamic ones, and not human-readable or hand-constructible: SOAP users live in tooling. Despite being ostensibly standardized, SOAP interop between vendors’ implementations often causes problems. It survives in large enterprises; smaller companies have moved on. RESTful APIs favor simpler approaches with less generated code — description formats like OpenAPI/Swagger for documentation.

The problems with RPC

Web services are the latest in a long line of technologies for making API requests over a network — and many were seriously flawed. EJB and Java RMI (Java-only), DCOM (Microsoft-only), CORBA (excessively complex, no compatibility guarantees). All based on the remote procedure call — around since the 1970s — whose ambition is location transparency: a network request that looks like a local function call. The approach is fundamentally flawed, because a network request is a different animal:

i.

Unpredictability

A local call succeeds or fails based on parameters you control; a network request can be lost, slowed, or the remote machine unavailable — entirely outside your control. Retries become mandatory.

ii.

Timeouts

A local call returns, throws, or hangs. A network request has a fourth outcome: returns without a result due to timeout — and you have no idea whether the request got through.

iii.

Retries aren’t free

If only the responses are getting lost, a retry performs the action multiple times — you need deduplication (idempotence) in the protocol. Local calls never needed that.

iv.

Wild latency

A local call takes roughly the same time every time; a network request varies from under a millisecond to many seconds for identical work under congestion.

v.

Parameters must be bytes

Locally you pass pointers; over the wire, everything must be encoded — fine for numbers and strings, painful for large objects.

vi.

Cross-language types

Client and service may use different languages; translating datatypes between them gets ugly — recall JavaScript’s 2⁵³ problem.

Moral: don’t make a remote service look too much like a local object — it’s a different thing. Part of REST’s appeal is that it doesn’t pretend otherwise. Yet RPC isn’t going away: gRPC (Protocol Buffers), Finagle (Thrift), and Rest.li (JSON over HTTP) all build RPC on this chapter’s encodings — and the new generation is honest about the difference: Finagle and Rest.li use futures (promises) for async-possibly-failing actions and easy parallel fan-out; gRPC supports streams (many requests and responses over time); several add service discovery (which IP:port serves which service). Custom binary RPC can beat generic JSON-over-REST on performance — but REST wins on experimentation (curl, browsers), universal language support, and its enormous tooling ecosystem. Hence REST’s dominance for public APIs, with RPC mostly for same-organization, same-datacenter traffic.

Evolvability of service APIs

The simplifying assumption for services: servers upgrade first, clients second — so you need backward compatibility on requests and forward compatibility on responses (inherited from whatever encoding carries them). But across organizations you don’t control clients and can’t force upgrades: compatibility must hold for a long time, perhaps indefinitely — and breaking changes mean running multiple API versions side by side. No consensus exists on versioning: version in the URL, in the HTTP Accept header, or (Stripe-style) per-client API keys with server-side version selection.

4.4 · Flow #3

Message-passing dataflow

Asynchronous message passing sits between RPC and databases: like RPC, a client’s message is delivered to another process with low latency; like a database, it goes through an intermediary that stores it — a message broker (message queue, message-oriented middleware) rather than a direct network connection. (Commercially: TIBCO, IBM WebSphere, webMethods; open source: RabbitMQ, ActiveMQ, HornetQ, NATS, Apache Kafka.)

Five things a broker buys you over direct RPC

(1) Buffers if the recipient is unavailable or overloaded — reliability. (2) Automatic redelivery to a process that crashed — no lost messages. (3) The sender doesn’t need the recipient’s IP:port — valuable in cloud deployments where VMs come and go. (4) One message to several recipients. (5) Logical decoupling of sender from recipient — the sender just publishes.

Usage: one process sends to a named queue or topic; the broker delivers to one or more consumers/subscribers; many producers and consumers can share a topic. It’s normally one-way — a sender doesn’t expect a reply (a reply can ride a separate reply queue if needed, chaining topics into request/response flows). Brokers enforce no data model — a message is just bytes with metadata — so any encoding works, and with a backward-and-forward-compatible one, publishers and consumers can be changed and deployed independently, in any order. (Careful when a consumer republishes to another topic: preserve unknown fields, or Figure 4-7 strikes again.)

Distributed actor frameworks

The actor model is a single-process concurrency model: instead of wrangling threads (races, locks, deadlock), logic lives in actors, each typically representing one client or entity, holding private local state, communicating only via asynchronous messages — delivery not guaranteed; messages can be lost. Each actor processes one message at a time, so no threads to worry about, and the framework schedules actors independently.

Distributed actor frameworks scale the model across nodes: same message-passing, whether sender and recipient are on the same machine or not — across nodes the message is transparently encoded, sent, and decoded. Location transparency works better here than in RPC, because the actor model already assumed messages may be lost even in-process — less fundamental mismatch between local and remote. A distributed actor framework is essentially a message broker and the actor model fused into one framework — but rolling upgrades still require forward and backward compatibility of the message encodings. The three big frameworks:

Akka

Java-built-in serialization by default — no forward/backward compatibility. Swap in Protocol Buffers and rolling upgrades become possible.

Orleans

Custom encoding by default, no rolling upgrades — you stand up a new cluster and move traffic over. Pluggable serialization, like Akka.

Erlang OTP

Rolling upgrades possible but carefully planned — record schema changes are surprisingly hard, despite the system’s high-availability pedigree. The maps datatype (Erlang R17, 2014) may make it easier.

4.5 · Pulling it together

Summary

Encoding details affect not just efficiency but the architecture of applications and deployment options. Rolling upgrades — gradual, no-downtime, low-risk, and thus frequent — demand that all data flowing through the system be readable by both old and new code:

Dataflow modeWho encodes / decodesCompatibility needed
DatabasesWriting process encodes; reading process decodes — possibly a later version of yourself; during rolling upgrades, mixed old/new processes share the storeBackward and forward; beware re-encoding dropping unknown fields
Services (REST/RPC)Client encodes request → server decodes; server encodes response → client decodesBackward compat on requests, forward compat on responses (servers upgrade first)
Message passingSender encodes, broker stores, recipient decodes — independently deployable in any orderWhatever the encoding provides — compatible encoding = maximum freedom

And the formats themselves: language-specific encodings (single language, weak compatibility), textual JSON/XML/CSV (widespread; vague about datatypes — mind the numbers), and binary schema-driven Thrift/Protobuf/Avro (compact, clearly defined compatibility semantics, schemas as documentation and codegen source; the cost: bytes aren’t human-readable). With a bit of care, backward/forward compatibility and rolling upgrades are quite achievable. May your application’s evolution be rapid and your deployments be frequent.

Glossary

encoding / decoding
In-memory → bytes, and back. A.k.a. serialization/marshalling and parsing/deserialization — the book says “encoding” to dodge the transaction sense of “serialization”.
backward compatibility
Newer code can read data written by older code — usually the easy direction.
forward compatibility
Older code can read data written by newer code — requires ignoring unknown additions.
rolling upgrade / staged rollout
Deploying a new version a few nodes at a time — no downtime, less risk, more frequent releases.
data outlives code
Databases hold values written years ago in the original encoding, long after the writing code was replaced.
field tag
Numeric alias for a field in Thrift/Protobuf — its stable identity across schema versions; renamable names, unchangeable tags, never reused.
varint
Variable-length integer: –64…63 in one byte, –8192…8191 in two, etc.; the top bit announces more bytes. How 1337 shrinks to 2 bytes.
writer’s / reader’s schema
Avro’s two schemas: the one the data was encoded with, and the one the application expects — they need only be compatible, resolved by field name with defaults.
object container file
Avro’s file with the writer’s schema once at the head — self-describing; ideal for big immutable dumps.
dynamic schemas
Avro’s superpower: schemas generated on the fly (e.g., from a database’s tables) and matched by field name — no hand-assigned tags to keep stable.
location transparency
The RPC abstraction that pretends a remote call is a local one — fundamentally flawed because networks fail unpredictably.
REST / RESTful
A design philosophy on HTTP’s principles: URLs as resources, HTTP for caching/auth/negotiation. “RESTful” = an API so designed.
SOAP / WSDL
XML-based protocol with the WS-* framework, described in WSDL for codegen; interop problems, fading outside enterprises.
SOA / microservices
Decomposing an application into services by functionality, independently deployable and evolvable; microservices = the rebrand.
idempotence
Retrying a request doesn’t perform the action twice — mandatory once timeouts force retries.
futures / promises
Encapsulation of async, possibly-failing actions; enables parallel requests to multiple services (Finagle, Rest.li).
service discovery
Letting a client learn which IP:port currently serves a given service.
message broker
Intermediary storing messages temporarily: buffers, redelivers, hides locations, fans out, decouples — RabbitMQ, Kafka, etc.
actor model
Concurrency via private-state actors passing async, lossy messages one at a time; distributed frameworks extend it across nodes (Akka, Orleans, Erlang OTP).
ASN.1
1984 schema-definition language with tag-based evolution; still encodes SSL certificates, poor choice for new apps.
