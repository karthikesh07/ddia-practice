5.0 · The setup

Why keep copies at all?

Replication means keeping a copy of the same data on multiple machines that are connected via a network. People do it for three reasons:

Latency

Keep data geographically close to your users, so they interact with it faster.

Availability

Keep the system working even if some of its parts have failed.

Read throughput

Scale out the number of machines that can serve read queries.

The scope assumption for this chapter: the dataset is small enough that each machine can hold a copy of the entire thing. (Datasets too big for one machine get partitioned — that’s Chapter 6.) And the key insight that drives the whole chapter: if the data never changed, replication would be trivial — all the difficulty lies in handling changes to replicated data.

Three popular algorithms for replicating changes, and almost every distributed database uses one of them:

i.

Single-leader

Each change is processed by one node, which sends it on to the others.

ii.

Multi-leader

Several nodes accept writes and forward them to each other.

iii.

Leaderless

Any replica accepts writes directly from clients; quorums sort out the truth.

A terminology warning before we start: “hot, warm, and cold standby” mean different things to different people. In PostgreSQL, a hot standby accepts reads from clients, while a warm standby processes changes from the leader but doesn’t serve queries. And a historical note for humility: replication is an old topic — the principles haven’t changed much since the 1970s, because the fundamental constraints of networks haven’t either.

5.1 · One node in charge

Leaders and followers

Each node that stores a copy of the database is a replica. The core problem: every write must be processed by every replica, or they stop being copies of the same thing. Leader-based replication (also known as active/passive or master–slave) solves it with a designated writer:

1.

The leader writes first

One replica is designated the leader (master, primary). All client writes go to it, and it writes new data to its local storage first.

2.

The log fans out

The other replicas are followers (read replicas, slaves, secondaries, hot standbys). The leader sends every data change to all of them as part of a replication log or change stream. Each follower applies the writes in the same order the leader processed them.

3.

Reads go anywhere

Clients can query the leader or any follower — but writes are only accepted on the leader. Followers are read-only from the client’s point of view.

Figure 5-1 (recreated) · Leader-based (master–slave) replication

All writes through one node; the log fans out; reads can go anywhere. It’s not a new idea — PostgreSQL (since 9.0), MySQL, Oracle Data Guard, SQL Server’s AlwaysOn Availability Groups, MongoDB, RethinkDB, Espresso, Kafka, RabbitMQ’s highly available queues, and replicated block devices like DRBD all work this way.

5.1.1 — Synchronous vs. asynchronous replication

The next question is whether the log fan-out happens synchronously or asynchronously — in relational databases it’s often a configurable option; other systems hardcode one or the other.

Figure 5-2 (recreated) · One synchronous follower, one asynchronous

Synchronous: the leader waits for the follower to confirm the write before reporting success — that follower is guaranteed consistent with the leader, and survives leader failure with the data intact. Asynchronous: the leader sends the message and moves on — if the leader dies unrecoverably, any writes not yet replicated are lost, even ones already confirmed to the client.

< 1 s Normal replication delay most database systems apply changes to followers in less than a second — when healthy
minutes+ How far an async follower can fall behind recovering from failure, near capacity, network problems — no upper bound

The trade-off in one breath: synchronous replication gives you consistency but a single dead follower blocks all writes (the leader must block and wait); asynchronous gives you availability but a confirmed write isn’t guaranteed durable. Weakening durability sounds like a bad deal, yet fully asynchronous configurations are widely used anyway — especially with many followers or geographically distributed ones.

Semi-synchronous — the common middle ground

In practice, “synchronous replication” usually means one follower is synchronous and the rest are asynchronous. If that follower becomes unavailable or slow, one of the async followers is promoted to synchronous. The guarantee: an up-to-date copy of the data exists on at least two nodes — the leader and its sync follower. A related variant, chain replication, has been used successfully in systems such as Microsoft Azure Storage. And there’s a deep connection between replication consistency and consensus (getting several nodes to agree on a value) — Chapter 9’s territory.

5.1.2 — Setting up new followers

Sometimes you need new followers — to increase replica count or replace failed nodes. Just copying the data files doesn’t work: clients are constantly writing, so a file copy would see different parts of the database at different points in time. And locking the database for a consistent copy defeats the point of high availability. The procedure instead:

1.

Take a consistent snapshot

Of the leader’s database at some point in time, without locking everything if possible. Most databases support this (it’s needed for backups too); for MySQL you may need a third-party tool like innobackupex.

2.

Copy it to the new follower

Standard file copy — the snapshot is frozen, so timing doesn’t matter here.

3.

Connect and catch up

The follower requests all changes since the snapshot. This needs the snapshot tied to an exact position in the leader’s replication log — PostgreSQL calls it the log sequence number, MySQL calls it the binlog coordinates.

4.

Stream live changes

Once the backlog is processed, the follower has caught up and continues applying changes as they happen.

How automated this is varies wildly by database — from fully automatic to an arcane multi-step workflow an administrator performs by hand.

5.1.3 — Handling node outages

Any node can go down — unexpectedly from a fault, or just as likely for planned maintenance like a kernel security patch reboot. The goal is to keep the system running through it.

Follower failure is the easy case — catch-up recovery. Each follower keeps a log of the changes it has received from the leader. On restart or after a network interruption, it knows from its log the last transaction it processed before the fault, connects to the leader, and requests everything it missed. Caught up, business as usual.

Leader failure is the hard case — failover. One of the followers must be promoted to be the new leader, clients must be reconfigured to send writes to it, and other followers must start consuming changes from it. Failover can happen manually (an administrator takes the steps) or automatically, and the automatic version has three stages:

1.

Determine the leader has failed

Crashes, power outages, network issues — there’s no foolproof detection, so most systems use a timeout: nodes bounce messages back and forth, and a node that doesn’t respond for some period — say, 30 seconds — is assumed dead. (Planned maintenance doesn’t need the guessing.)

2.

Choose a new leader

By election (a majority of remaining replicas agrees) or appointment by a previously elected controller node. The best candidate is usually the replica with the most up-to-date data from the old leader, to minimize data loss. Getting all nodes to agree is a consensus problem — Chapter 9.

3.

Reconfigure the system

Clients send writes to the new leader. And if the old leader comes back, it might still believe it is the leader — the system must ensure it steps down and becomes a follower.

Failover is fraught — four ways it bites

1. Discarded writes. With async replication the new leader may not have all the old leader’s writes; if the old leader rejoins, its unreplicated writes are usually discarded — violating durability expectations clients were given.

2. Coordinated external state. The GitHub/MySQL incident below: discarded writes poisoned another storage system too.

3. Split brain. Two nodes both believe they are the leader, both accept writes, and with no conflict resolution, data is lost or corrupted. Safety catches exist — fencing, or more emphatically Shoot The Other Node In The Head (STONITH) — but poorly designed, you can end up with both nodes shut down.

4. The timeout dilemma. Too long a timeout means slow recovery; too short means unnecessary failovers — a load spike or network glitch can push response times past the threshold, and an unnecessary failover on a struggling system makes things worse, not better.

Case study: the GitHub primary-key collision

In one incident at GitHub, an out-of-date MySQL follower was promoted to leader. The database used an autoincrementing counter to assign primary keys to new rows — but the new leader’s counter lagged behind the old leader’s, so it reused primary keys that the old leader had already handed out. Those keys were also used in a Redis store, and the reuse created inconsistency between MySQL and Redis — which caused private data to be disclosed to the wrong users. Discarding writes is bad enough inside the database; it’s especially dangerous when other systems are coordinated with the database’s contents.

There are no easy solutions here. Node failures, unreliable networks, and the trade-offs between replica consistency, durability, availability, and latency are fundamental distributed systems problems — which is why some operations teams prefer to perform failovers manually even when the software supports automatic ones. Chapters 8 and 9 go deeper.

5.1.4 — How replication logs actually work

Under the hood, four different replication methods are used in practice:

Method 1 — Statement-based

The leader logs every write request it executes and ships that statement log to followers: every INSERT, UPDATE, or DELETE is parsed and executed by each follower as if a client had sent it. Three ways this breaks:

  • Nondeterministic functions — NOW() and RAND() likely generate different values on each replica.
  • Order dependence — statements using autoincrementing columns or depending on existing data (UPDATE … WHERE) must execute in exactly the same order everywhere, which is limiting under concurrency.
  • Side effects — triggers, stored procedures, and UDFs may fire differently on each replica unless absolutely deterministic.

Workarounds exist (the leader can replace nondeterministic calls with fixed values when logging). MySQL before 5.1 used statement-based replication; it now switches to row-based by default if there’s any nondeterminism, but statement-based survives because it’s compact — and VoltDB makes it safe by requiring transactions to be deterministic.

Method 2 — Write-ahead log (WAL) shipping

From Chapter 3: storage engines append every write to a log — the log is the storage in log-structured engines, and B-trees write a WAL to restore index consistency after crashes. Either way, the log is an append-only sequence of bytes containing all writes, and the exact same log can build a replica: the leader sends it across the network, and followers processing it build identical data structures. Used by PostgreSQL and Oracle, among others.

The coupling cost

A WAL describes data at a very low level — which bytes changed in which disk blocks — so replication is closely coupled to the storage engine. If the database changes its storage format between versions, leader and followers typically can’t run different versions. That kills the nice zero-downtime upgrade path (upgrade followers first, failover to one, upgrade the rest) — with WAL shipping, upgrades need downtime.

Method 3 — Logical (row-based) log replication

Decouple the replication log from the storage engine’s physical format. A logical log records writes at the granularity of a row: for an inserted row, the new values of all columns; for a deleted row, enough to identify it (usually the primary key, or all old column values if there isn’t one); for an updated row, the identifier plus the new values. A multi-row transaction produces several such records followed by a commit record. MySQL’s binlog in row-based mode works this way.

The payoffs: the log stays backward compatible across database versions and even storage engines, and external applications can parse it easily — feeding a data warehouse, building custom indexes and caches. That technique is called change data capture, and it returns in Chapter 11.

Method 4 — Trigger-based

When you need to replicate a subset of the data, cross database engines, or run custom conflict-resolution logic, the built-ins won’t do. Options: tools like Oracle GoldenGate that read the database log from application code, or triggers — register custom code that fires on every data change and logs it to a separate table, from which an external process reads and applies whatever logic you like. Examples: Databus for Oracle, Bucardo for Postgres. The price: more overhead than built-in replication, and more prone to bugs and limitations — but sometimes the flexibility is worth it.

5.2 · The lag trilogy

Problems with replication lag

Surviving node failures is only one reason to replicate. Scalability (more read capacity than one machine) and latency (replicas near users) are the others — and for read-heavy web workloads, the standard architecture is many followers with reads spread across them, removing load from the leader and serving reads from nearby replicas.

The catch: this only realistically works with asynchronous replication. Synchronously replicating to all followers means a single node failure or network outage makes the whole system unwritable — and the more nodes you have, the likelier one is down. So the followers lag, and if your application reads from a lagging follower, it sees stale data.

This inconsistency is temporary: stop writing, wait, and the followers catch up — hence eventual consistency. (The term was coined by Douglas Terry et al. and popularized by Werner Vogels; it became the battle cry of NoSQL, but async-replicated relational followers have exactly the same characteristics.) “Eventually” is deliberately vague — in general there is no limit to how far a replica can fall behind. Normally the lag is a fraction of a second and nobody notices; near capacity or with network trouble, it’s seconds to minutes.

Three classic anomalies follow — each with a guarantee that fixes it.

5.2.1 — Reading your own writes

A user submits data (a profile update, a comment) and then views it. The write goes to the leader; the read goes to a follower. If the write hasn’t reached that follower yet, it looks to the user like their data was lost.

Figure 5-3 (recreated) · A stale replica eats the user’s own write

The fix is read-after-write consistency (also known as read-your-writes): if the user reloads the page, they will always see any updates they submitted themselves. No promises about other users — those may lag — but your own input is safe.

How to implement it, in escalating complexity:

1.

Read your own data from the leader

When reading something the user might have modified, read from the leader; everything else from a follower. Works when you can know what’s editable without querying — e.g., a social profile is only editable by its owner: always read your own profile from the leader, everyone else’s from a follower.

2.

Time-based criteria

If most things are editable, the above negates read scaling. Instead: track the time of the last update, and for one minute after it, route all that user’s reads to the leader. Or monitor replication lag per follower and refuse queries to any follower more than a minute behind.

3.

The client remembers a timestamp

The client remembers the timestamp of its most recent write; the system ensures the replica serving reads has caught up to at least that point — otherwise route to another replica or wait. The timestamp can be logical (a log sequence number) or a wall clock (in which case clock synchronization becomes critical — Chapter 8).

4.

Multi-datacenter complications

Any leader-served request must be routed to the datacenter containing the leader. And cross-device read-after-write (enter on desktop, view on phone) adds more: timestamp memory must be centralized across devices, devices may route to different datacenters on different network paths, and reads-from-leader may require pinning all a user’s devices to one datacenter.

5.2.2 — Monotonic reads

The second anomaly: a user can see time go backward — if they make several reads from different replicas. User 2345 queries twice while refreshing a page whose requests are load-balanced randomly: the first query hits a fresh follower and returns the comment user 1234 just added; the second hits a lagging follower and returns nothing. The comment appears, then disappears — the second query observes the system at an earlier point in time than the first. (It wouldn’t be so bad if the first query had returned nothing — the user would never know. Seeing something and then un-seeing it is the confusing part.)

Figure 5-4 (recreated) · Time running backward across two followers

Monotonic reads is the guarantee that this doesn’t happen: lesser than strong consistency, stronger than eventual consistency. Fix: each user always reads from the same replica — e.g., chosen by a hash of the user ID rather than randomly. Different users can use different replicas. If that replica fails, the user’s queries must be rerouted.

5.2.3 — Consistent prefix reads

The third anomaly violates causality itself. The book’s example dialog:

Mr. Poons and Mrs. Cake

Mr. Poons: How far into the future can you see, Mrs. Cake?
Mrs. Cake: About ten seconds usually, Mr. Poons.

Mrs. Cake’s answer causally depends on the question — she heard it and replied. Now a third party listens through followers: Mrs. Cake’s words come through a follower with little lag, Mr. Poons’s through one with much more. The observer hears:

Mrs. Cake: About ten seconds usually, Mr. Poons.
Mr. Poons: How far into the future can you see, Mrs. Cake?

To the observer, Mrs. Cake answers the question before it was asked. Such psychic powers are impressive, but very confusing.

Consistent prefix reads: if a sequence of writes happens in a certain order, anyone reading them sees them in that order. This is particularly a problem in partitioned databases (Chapter 6), where different partitions operate independently — no global ordering of writes exists, so a reader can see parts of the database in an older state and parts in a newer one. If the database always applies writes in the same order, the anomaly can’t happen — but in many distributed databases it doesn’t. The fixes: ensure causally related writes go to the same partition (not always efficient), or explicitly track causal dependencies — which is exactly where this chapter ends up, with happens-before and version vectors.

5.2.4 — What to do about lag

When working with an eventually consistent system, ask how the application behaves if replication lag climbs to minutes or even hours. If the answer is “no problem,” great. If it’s a bad user experience, design in a stronger guarantee like read-after-write. Pretending replication is synchronous when it’s actually asynchronous is a recipe for problems down the line.

You can provide stronger guarantees in application code — leader reads, timestamp tracking — but it’s complex and easy to get wrong. It would be better if developers could just trust the database to do the right thing. That’s why transactions exist: a way for a database to provide stronger guarantees so the application can be simpler. Single-node transactions have existed for a long time; many distributed systems abandoned them claiming transactions are too expensive and eventual consistency is inevitable at scale — there’s some truth in that, but it’s overly simplistic. Chapters 7 and 9 develop the nuanced view.

5.3 · More than one writer

Multi-leader replication

Leader-based replication’s one major downside: there’s a single leader, and all writes must go through it — if you can’t reach it, you can’t write. The natural extension: allow more than one node to accept writes. Each leader simultaneously acts as a follower to the other leaders. Also called master–master or active/active replication. (If the database is partitioned, each partition has one leader — different partitions may live on different nodes, but each partition has exactly one leader node.)

It rarely makes sense within a single datacenter — the benefits rarely outweigh the added complexity. Three situations where it does make sense:

5.3.1 — Three use cases

Use case 1: multi-datacenter operation

Replicas in several datacenters — to tolerate a whole datacenter failing, or to be near your users. With single-leader, every write must travel to the datacenter hosting the leader; with a leader in each datacenter, writes stay local and replicate asynchronously between datacenters.

Single-leaderMulti-leader
PerformanceEvery write crosses the internet to the leader’s datacenter — significant write latency that can defeat the purpose of having multiple datacentersEvery write processed in the local datacenter, replicated asynchronously across — inter-datacenter delay hidden from users
Datacenter outage toleranceThe leader’s datacenter failing requires failover to promote a follower in another datacenterEach datacenter keeps operating independently; replication catches up when the failed one returns
Network problem toleranceVery sensitive to inter-datacenter link problems, because writes go synchronously over that public-internet linkAsync replication tolerates network problems — a temporary interruption doesn’t block writes

Some databases support multi-leader natively, but it’s often bolted on with external tools: Tungsten Replicator for MySQL, BDR for PostgreSQL, GoldenGate for Oracle. The key downside: the same data can be concurrently modified in two datacenters, and those conflicts must be resolved.

Dangerous territory

Multi-leader replication is a somewhat retrofitted feature in many databases, with subtle configuration pitfalls and surprising interactions — autoincrementing keys, triggers, and integrity constraints can all misbehave. It’s often considered a last resort, to be avoided if possible.

Use case 2: clients with offline operation

Apps that must work while disconnected — calendar apps on your phone and laptop. You need to read and enter meetings whether or not you’re online, and changes sync when connectivity returns. Architecturally this is multi-leader replication taken to the extreme: every device is a “datacenter” with a local database acting as a leader, and an extremely unreliable network between them. Replication lag may be hours or even days. As the rich history of broken calendar sync implementations demonstrates, multi-leader replication is a tricky thing to get right. CouchDB is designed for exactly this mode of operation.

Use case 3: collaborative editing

Real-time collaborative editing (Etherpad, Google Docs): several people editing a document simultaneously. One user’s changes apply instantly to their local replica and replicate asynchronously to the server and other editors. If you demand no editing conflicts, the application must lock the document before editing — equivalent to single-leader replication with transactions on the leader, and everyone else waits. For faster collaboration, make the unit of change small — a single keystroke — and skip locking: multiple users edit at once, and all of multi-leader replication’s challenges, including conflict resolution, come along for the ride.

5.3.2 — Handling write conflicts

The biggest problem with multi-leader replication: write conflicts. Two users edit the same wiki page at the same time — user 1 changes the title from A to B, user 2 changes it from A to C. Each change succeeds on its local leader; when the changes replicate asynchronously, a conflict is detected — too late to ask the users. In a single-leader database the second write would simply block or abort. You could make conflict detection synchronous — wait for the write to reach all replicas before confirming — but then you’ve lost the entire point of multi-leader, and might as well use single-leader.

Figure 5-7 (recreated) · Two leaders, one title, no winner

If each replica just applied writes in the order it saw them, the final value would be C on leader 1 and B on leader 2 — unacceptable. Every replication scheme must converge: all replicas arrive at the same final value once everything has replicated.

Conflict avoidance — the simplest strategy

Ensure all writes for a particular record go through the same leader, and conflicts cannot occur. Since many multi-leader implementations handle conflicts quite poorly, avoidance is the frequently recommended approach — route each user to a “home” datacenter and use its leader for reads and writes; from any one user’s view, the system is single-leader. It breaks down the moment you need to reroute — a failed datacenter, a user who moved — and concurrent writes on different leaders become possible again.

Convergent conflict resolution — four approaches

1.

Last write wins

Give each write a unique ID (timestamp, long random, UUID, hash) and the highest ID wins; the losers are discarded. With timestamps this is LWW — popular, and dangerously prone to data loss (more below).

2.

Replica precedence

Give each replica a unique ID; writes from a higher-numbered replica always win. Also implies data loss.

3.

Merge the values

Order them alphabetically and concatenate — the wiki title might become “B/C”.

4.

Record the conflict

Preserve all the information in an explicit structure and resolve later — perhaps by prompting the user.

Custom conflict resolution logic

Because the right resolution is application-specific, most multi-leader tools let you write it: on write — the handler fires as soon as the database detects a conflict in the replication log (Bucardo lets you write a snippet of Perl; it can’t prompt a user and must execute quickly), or on read — conflicting writes are all stored, and the next read returns the multiple versions for the application (or the user) to resolve and write back. CouchDB works this way. Note that conflict resolution usually applies at the level of an individual row or document, not a whole transaction — each write in a multi-write transaction is considered separately.

Case study: the Amazon shopping cart

For some time, Amazon’s shopping cart conflict resolution preserved items added to the cart but not items removed — so customers would sometimes see deleted items reappear in their carts. A vivid reminder that custom resolution logic can quietly do the wrong thing.

Automatic conflict resolution — three research lines

CRDTs

Conflict-free replicated datatypes — sets, maps, ordered lists, counters — that can be concurrently edited by multiple users and automatically resolve conflicts in sensible ways. Implemented in Riak 2.0.

Mergeable persistent data structures

Track history explicitly, like Git, and merge with three-way merge functions (CRDTs use two-way merges).

Operational transformation

The conflict resolution behind Etherpad and Google Docs — designed for concurrent editing of an ordered list of items, like the characters in a document.

Implementations are still young, but automatic resolution could make multi-leader sync much simpler to deal with in the future.

What even counts as a conflict?

Some conflicts are obvious (two writes to the same field). Some are subtle: a meeting room booking system must ensure no room is double-booked — the application can check availability before each booking, but two bookings made on different leaders can still conflict. There’s no quick ready-made answer; Chapter 7 sees more conflict examples, and Chapter 12 discusses scalable detection and resolution.

5.3.3 — Replication topologies

A replication topology describes the communication paths along which writes propagate. With two leaders there’s only one plausible topology: each sends everything to the other. With more, options open up:

All-to-all

The most general: every leader sends its writes to every other leader.

Circular

Each node receives writes from one node and forwards them (plus its own) to the next. MySQL supports only this by default.

Star

A designated root forwards writes to all others; generalizable to a tree. (Not to be confused with a star schema.)

In circular and star topologies a write may pass through several nodes before reaching every replica, so nodes must forward changes they receive — and to prevent infinite replication loops, each write is tagged with the identifiers of all nodes it has passed through; a node ignores any change already tagged with its own ID. The weakness: if just one node fails, it interrupts the flow of replication messages between other nodes until fixed — reconfiguration is usually manual. Densely connected topologies like all-to-all tolerate faults better, since messages can travel different paths. But all-to-all has its own problem: some network links are faster than others, so replication messages can overtake each other.

The overtaking scenario: client A inserts a row on leader 1, and client B updates that row on leader 3 — but leader 2 receives the update first (an update to a row it doesn’t have) and only later the insert that should have preceded it. That’s the causality problem from consistent prefix reads again. Attaching timestamps doesn’t fix it — clocks can’t be trusted to be sufficiently in sync (Chapter 8) — but version vectors, coming up in 5.4, can.

Read the fine print

Conflict detection is poorly implemented in many multi-leader systems: PostgreSQL BDR does not provide causal ordering of writes; Tungsten Replicator for MySQL doesn’t even try to detect conflicts. If you run multi-leader, read the documentation carefully and test that the guarantees you believe in actually exist.

5.4 · No leaders at all

Leaderless replication

The third approach abandons the leader entirely: any replica directly accepts writes from clients. Some of the earliest replicated data systems were leaderless, the idea was forgotten during the relational era, and it came back into fashion after Amazon used it for its in-house Dynamo system — inspiring Riak, Cassandra, and Voldemort (“Dynamo-style” databases). (Confusingly, AWS’s hosted DynamoDB uses a completely different architecture: single-leader replication.)

In some implementations the client sends writes to several replicas directly; in others, a coordinator node does it — but unlike a leader, the coordinator enforces no particular ordering of writes.

5.4.1 — Writing when a node is down

Three replicas, one unavailable (rebooting for a system update). In a leader-based configuration you might need a failover. In a leaderless configuration, failover does not exist:

  • The client sends the write to all three replicas in parallel; the two available ones accept it, the unavailable one misses it.
  • Two out of three acknowledgements is enough — the client considers the write successful and simply ignores the fact that one replica missed it.
  • When the node comes back, clients reading from it would get stale values — so reads are also sent to several nodes in parallel, and version numbers determine which response is newer.

5.4.2 — Read repair and anti-entropy

How does a returned node catch up? Two mechanisms, often combined:

1.

Read repair

When a client reads from several nodes and detects a stale response (version 6 from replica 3, version 7 from replicas 1 and 2), it writes the newer value back to the stale replica. Works well for frequently-read values.

2.

Anti-entropy

A background process constantly looks for differences between replicas and copies missing data from one to another. Unlike a leader’s replication log, it copies in no particular order and may lag significantly.

Not all systems have both — Voldemort has no anti-entropy process, so rarely-read values may simply be missing from some replicas, with reduced durability.

5.4.3 — Quorums for reading and writing

If 2 of 3 is enough, how far can we push it? The general scheme — there are n replicas, every write must be confirmed by w nodes, every read must query at least r nodes — and the key condition:

The quorum condition

As long as w + r > n, the set of nodes you wrote to and the set you read from must overlap in at least one node — so at least one of the r responses is up to date. Reads and writes obeying r and w are called quorum reads and writes; think of r and w as the minimum votes required for the operation to be valid.

Figure 5-11 (recreated) · Why w + r > n forces an overlap

The overlap node — n3 here — carries the latest value into every read. With w + r ≤ n there is no guaranteed overlap, and stale reads become much more likely (though latency and availability improve).

In Dynamo-style databases, n, w, and r are typically configurable. A common choice: n odd (typically 3 or 5) and w = r = (n + 1) / 2 rounded up — a majority. A read-heavy workload might set w = n and r = 1: faster reads, but a single failed node stops all writes. The tolerance math:

n=3 · w=2 · r=2 Tolerates one unavailable node writes and reads both continue with 2 of 3
n=5 · w=3 · r=3 Tolerates two unavailable nodes majorities still overlap: 3 + 3 > 5

It works in reverse too: w < n lets writes proceed when a node is down; r < n does the same for reads. If fewer than w (or r) nodes respond, the operation returns an error — and the reason a node didn’t respond doesn’t matter: crashed, disk full, network interruption. Only the successful response counts. One subtlety: there may be more than n nodes in the cluster, but any given value is stored on only n of them — which is what allows the dataset to be partitioned (Chapter 6).

Four settings of n, w, r. The pattern to internalize: w + r > n buys freshness; w + r ≤ n buys latency and availability — you trade one for the other, deliberately.

5.4.4 — The limitations of quorum consistency

With w + r > n you can generally expect every read to return the latest value — but only generally. r and w are often majorities (more than n/2) because that guarantees overlap while tolerating up to n/2 failures, but quorums need not be majorities — only overlap matters, which allows flexibility in designing distributed algorithms. And if you set w + r ≤ n, you’re more likely to read stale values but gain lower latency and better availability: the database only becomes unavailable when reachable replicas drop below w (for writes) or r (for reads).

Even with w + r > n, stale reads remain possible — six documented edge cases:

1.

Sloppy quorums

The w writes may land on different nodes than the r reads (see below) — no guaranteed overlap.

2.

Concurrent writes

Two concurrent writes have no defined order; the only safe resolution is merging — and picking a timestamp winner (LWW) can lose writes to clock skew.

3.

Concurrent write + read

The write may be reflected on only some replicas when the read happens — old value, new value, undetermined.

4.

Partial write failure

A write that succeeded on some replicas but overall failed (fewer than w) is not rolled back where it succeeded — later reads may or may not see it.

5.

Restoration from a stale replica

If the node carrying a new value fails and is restored from a replica holding an old value, the number of replicas with the new value can fall below w.

6.

Unlucky timing

Even with everything working correctly, edge-case timings can still return stale values (revisited with linearizability, Chapter 9).

So quorums appear to guarantee freshness but don’t quite. Dynamo-style databases are optimized for use cases that tolerate eventual consistency; w and r tune the probability of stale reads, not an absolute guarantee. In particular, quorums do not give you read-your-writes, monotonic reads, or consistent prefix reads — the lag anomalies from 5.2 can still occur. Stronger guarantees require transactions or consensus (Chapters 7 and 9).

Monitoring staleness

Operationally, you need to know whether your database returns up-to-date results, and to be alerted when it falls behind. Leader-based: writes apply in the same order everywhere and each node has a position in the log, so lag is measurable — subtract the follower’s position from the leader’s. Leaderless: no fixed order of writes; with only read repair there’s no limit to how old an infrequently-read value can be. Research exists on measuring and predicting stale-read rates from n, w, and r, but it isn’t yet common practice — “eventual” deserves to be quantified.

5.4.5 — Sloppy quorums and hinted handoff

Quorums tolerate node failures and slow nodes — but a network interruption can cut a client off from many alive nodes. In a large cluster, the client may be able to reach some database nodes, just not the ones its quorum needs. The choice: return errors for every request that can’t reach w or r of the right nodes, or accept writes anyway and put them on reachable nodes that aren’t among the value’s designated n “home” nodes?

A sloppy quorum still requires w and r successful responses — but those responses may come from outside the home nodes. The book’s analogy: lock yourself out of your house, and you may knock on the neighbor’s door and ask to sleep on their couch temporarily. Once the network heals, the writes a node temporarily accepted on another’s behalf are sent to the appropriate home nodes — hinted handoff. (Once you find your keys, your neighbor politely asks you to get off their couch and go home.)

A “quorum” that isn’t one

Sloppy quorums increase write availability — as long as any w nodes are reachable, writes proceed. But even with w + r > n, you can no longer be sure to read the latest value: it may be sitting on nodes outside n. A sloppy quorum is only an assurance of durability — the data is on w nodes somewhere — with no guarantee that a read of r nodes will see it until hinted handoff completes. It’s optional in all common Dynamo implementations: enabled by default in Riak, disabled by default in Cassandra and Voldemort.

Leaderless multi-datacenter

Leaderless replication also suits multi-datacenter operation — it’s designed to tolerate conflicting concurrent writes, network interruptions, and latency spikes. Two styles: Cassandra and Voldemort keep n spanning all datacenters (you configure how many replicas per datacenter); each write goes to all replicas, but the client waits only for a quorum in its local datacenter, so cross-datacenter delay doesn’t hurt; remote writes replicate asynchronously. Riak keeps client-to-node communication local to one datacenter (n counts within it) and replicates between clusters asynchronously in the background — a style similar to multi-leader replication.

5.4.6 — Detecting concurrent writes

Dynamo-style databases allow several clients to concurrently write the same key, so conflicts occur even with strict quorums — during read repair and hinted handoff too. The core problem: events may arrive in a different order at different nodes, because of variable network delays and partial failures.

Figure 5-12 (recreated) · No well-defined ordering

Two clients, A and B, concurrently write the same key. If each node simply overwrote on arrival, node 2 would end at B while nodes 1 and 3 end at A — permanently inconsistent. Replicas must converge, and most implementations won’t do it for you: to avoid losing data, you need to know a lot about your database’s conflict handling internals.

Last write wins (discarding concurrent writes)

One route to eventual convergence: each replica keeps only the most “recent” value. Quotes because it’s misleading — in the example above, neither client knew about the other, so “which happened first” has no answer; the writes are concurrent and their order is undefined. You can force an arbitrary order anyway — timestamp each write, keep the biggest, discard the rest. That’s last write wins: the only supported method in Cassandra, optional in Riak.

LWW trades durability for convergence

If several concurrent writes hit the same key — even if every one was reported successful to its client (they each reached w replicas) — only one survives; the rest are silently discarded. LWW can even drop writes that aren’t concurrent, thanks to clock skew. For caches, maybe acceptable; if losing data isn’t acceptable, LWW is a poor choice. The only safe way to use an LWW database: write each key once and treat it as immutable — e.g., use a UUID as the key, so every write gets a unique one and no concurrent updates to the same key can exist.

The “happens-before” relationship and concurrency

How do we decide whether two operations are even concurrent? The key definition: an operation A happens before an operation B if B knows about A, depends on A, or builds upon A in some way. Two operations are concurrent if neither happens before the other — neither knows about the other. So for any A and B there are exactly three possibilities: A happened before B, B happened before A, or they’re concurrent. If one happened before the other, the later can safely overwrite; if concurrent, there’s a conflict to resolve.

Two intuitions from the chapter: in the multi-leader overtaking example, B’s update builds on A’s insert (it increments the value A inserted) — causally dependent, not concurrent. In the three-node example above, neither client knew about the other — concurrent, no causal dependency.

Concurrency, time, and relativity

“At the same time” is not the test — with unreliable clocks (Chapter 8), it’s genuinely hard to tell whether two things happened at exactly the same time, and for defining concurrency, exact time doesn’t matter. Two operations are concurrent if they are both unaware of each other, regardless of the physical time at which they occurred. People connect this to special relativity, where information can’t travel faster than light, so sufficiently-close-in-time distant events can’t affect each other. In computer systems, operations can be concurrent even when light had time — a slow or broken network prevented one from knowing about the other, which is all “concurrent” means.

Capturing happens-before: the shopping cart

Start with a single replica (extend to many afterwards). Two clients concurrently edit a shopping cart — initially empty. Five writes, and the server tags every value with a version number it increments per key:

Client 1Client 2Server state & response
Write 1adds milk → sends [milk]first write to the key: stores it as version 1, echoes the value + version back to client 1
Write 2adds eggs → sends [eggs] (unaware of milk)stores version 2 = [eggs], keeps [milk] as a separate value — returns both values + version 2
Write 3wants milk + flour → sends [milk, flour] with version number 1version 1 tells it this write supersedes [milk] but is concurrent with [eggs] → stores version 3 = [milk, flour], keeps [eggs], returns both
Write 4unaware of flour; merges the two values it saw ([milk], [eggs]), adds ham → sends [eggs, milk, ham] with version number 2version 2 overwrites [eggs], concurrent with [milk, flour] → keeps v3 = [milk, flour] and v4 = [eggs, milk, ham]
Write 5merges what it last saw ([milk, flour] and [eggs]), adds bacon → sends [milk, flour, eggs, bacon] with version number 3overwrites v3; concurrent with v4 → final siblings: v4 = [eggs, milk, ham] and v5 = [milk, flour, eggs, bacon]

The clients are never fully up to date — there’s always another concurrent operation — but old versions get overwritten eventually, and no writes are lost. The final siblings, [eggs, milk, ham] and [milk, flour, eggs, bacon], merge to [milk, flour, eggs, bacon, ham] without duplicates.

The version-number algorithm

The server decides concurrency purely from version numbers — it never interprets the value, which can be any data structure:

  • The server keeps a version number per key, incrementing it on every write and storing it with the value.
  • Reads return all un-overwritten values plus the latest version number. A client must read a key before writing it.
  • A write must include the version number from the prior read and must merge all values it received in that read.
  • On receiving a write with version v, the server overwrites all values with version ≤ v (they were merged into the new value) but keeps all values with a higher version (those are concurrent).
  • A write without a version number is concurrent with everything — it overwrites nothing and just becomes one more value on subsequent reads.

Merging siblings — and tombstones

No data is silently dropped, but clients do extra work: concurrent values must be cleaned up afterwards by merging. Riak calls the concurrent values siblings, and merging them is the same problem as multi-leader conflict resolution. For a shopping cart, merging can be the union — but note that milk and eggs appear in both final siblings even though each was written only once, and a pure union goes wrong once removal exists: an item removed in only one sibling reappears in the union. The fix: a removal can’t just delete the item — the system must leave a marker with an appropriate version number, a tombstone (last seen in Chapter 3’s log compaction). Because manual merging is complex and error-prone, Riak’s datatype support uses CRDTs that merge automatically — including preserving deletions.

Version vectors

Everything above used a single replica. With multiple replicas and no leader, a single version number per key isn’t enough — you need a version number per replica as well as per key. Each replica increments its own counter on a write and tracks the version numbers it has seen from every other replica; that collection of numbers is a version vector. The most interesting variant is the dotted version vector, used in Riak 2.0. Like the single-replica numbers, version vectors go to clients on reads and come back on writes (Riak encodes them as a string it calls the causal context), and they let the database distinguish overwrites from concurrent writes. They also make it safe to read from one replica and write to another — siblings may be created, but no data is lost as long as they’re merged correctly. A version vector is sometimes also called a vector clock, though they’re not quite the same thing — the difference is subtle, and for comparing the state of replicas, version vectors are the right data structure.

5.5 · Pulling it together

Summary

Replication serves four purposes: high availability (keep running through machine or datacenter failures), disconnected operation (keep working through network interruptions), latency (data geographically close to users), and scalability (more read volume than one machine can handle). Despite the simple goal, it’s a remarkably tricky problem requiring careful thought about concurrency and every way things can go wrong.

ApproachHow it worksThe trade
Single-leaderAll writes go to one node, which streams changes to followers; reads from any replicaEasy to understand, no conflict resolution to worry about — but a leader outage means failover, and followers’ reads may be stale
Multi-leaderEach of several leaders accepts writes and streams changes to the others and to followersRobust to faults and network interruptions — but write conflicts must be resolved, and implementations are often fragile
LeaderlessWrites go to several nodes directly; reads query several in parallel and correct the stale onesTolerates node failures and conflicts without failover — but quorums give probabilistic, not absolute, freshness

Replication can be synchronous, semi-synchronous, or asynchronous (and usually is the last). Failover is fraught: data loss, split brain, misconfigured timeouts. Replication lag creates the illusion anomalies — read-your-writes, monotonic reads, consistent prefix reads — and the escape is stronger guarantees, ideally via transactions. And when several nodes accept writes concurrently, conflicts need convergent resolution — LWW is easy but lossy; CRDTs and version vectors are safe but more work.

Glossary

replication / replica
Keeping a copy of the same data on multiple networked machines; each node storing a copy is a replica.
leader-based replication
One replica (leader/master/primary) handles all writes and sends a replication log to the followers, who apply it in order. a.k.a. active/passive, master–slave.
synchronous replication
The leader waits for follower confirmation before reporting success — guaranteed consistency, but a dead follower blocks all writes.
asynchronous replication
The leader sends changes without waiting — available, but a confirmed write can be lost if the leader dies unrecoverably.
semi-synchronous
One follower synchronous, the rest async; guarantees an up-to-date copy on at least two nodes.
failover
Promoting a follower to leader when the leader fails, reconfiguring clients, and repointing the other followers. Three stages: detect (timeout), elect, reconfigure.
split brain
Two nodes both believing they are the leader and both accepting writes — dangerous without conflict resolution.
fencing / STONITH
A safety catch that shuts down one node when two leaders are detected — “Shoot The Other Node In The Head”; badly designed, it can shut down both.
statement-based replication
Shipping the SQL statements themselves; breaks on nondeterministic functions, ordering, and side effects.
WAL shipping
Replicating the storage engine’s write-ahead log; fast but tightly coupled to the storage engine’s format and version.
logical (row-based) log
A replication format decoupled from storage internals — row-level insert/delete/update records; enables change data capture.
change data capture
Using the logical log to send database changes to external systems — warehouses, caches, indexes (Chapter 11).
trigger-based replication
Application code fired by triggers logs changes to a separate table for an external process — flexible, but more overhead and more bugs.
replication lag
The delay between a write on the leader and its reflection on a follower — fraction of a second normally, minutes or worse when degraded.
eventual consistency
The promise that replicas will catch up once writes stop. “Eventually” is deliberately vague — there is no bound on how far behind a replica can fall.
read-after-write / read-your-writes
A user always sees their own updates on reload. Implementations: own data from the leader, time windows, client-remembered timestamps.
monotonic reads
A user never sees time go backward — no older data after newer data. Fix: pin each user to one replica (hash of user ID).
consistent prefix reads
If writes happen in an order, readers see them in that order — causality preserved (the Mrs. Cake guarantee).
multi-leader replication
Several nodes accept writes, each acting as a follower to the others. a.k.a. master–master, active/active.
write conflict / convergence
Concurrent writes to the same data on different leaders; every scheme must guarantee replicas arrive at the same final value.
last write wins (LWW)
Conflict resolution by keeping the highest-timestamp write and discarding the rest — convergent but dangerously prone to data loss.
CRDT
Conflict-free replicated datatype — merges concurrent edits automatically and sensibly (sets, maps, counters; Riak 2.0).
operational transformation
The merge algorithm behind Etherpad and Google Docs, built for concurrent edits of ordered lists.
replication topology
The communication paths for write propagation between leaders: circular (MySQL default), star, or all-to-all.
leaderless (Dynamo-style) replication
Any replica accepts client writes directly; Riak, Cassandra, and Voldemort are the open-source descendants of Amazon’s Dynamo.
quorum reads and writes
Writes confirmed by w of n replicas, reads querying r of n; the w + r > n condition forces the sets to overlap.
sloppy quorum
Accepting w responses from nodes outside a value’s home set — an availability boost that reduces the quorum to a durability assurance.
hinted handoff
After the network heals, temporarily-accepted writes are forwarded to their proper home nodes — the neighbor’s couch, vacated.
read repair
A reader that detects stale values among parallel responses writes the newer value back to the stale replica.
anti-entropy process
A background process that continuously compares replicas and copies missing data — unordered and potentially slow.
happens-before
A happens before B if B knows about, depends on, or builds upon A. Two operations are concurrent if neither happens before the other.
version vector
A collection of per-replica version numbers distinguishing overwrites from concurrent writes without trusting clocks; dotted variant in Riak 2.0.
siblings
Concurrent values returned by the server (Riak’s term) that the application — or a CRDT — must merge.
tombstone
A deletion marker left in place of removed data so sibling merges don’t resurrect it.
