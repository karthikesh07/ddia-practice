11.0 · The setup

The unbounded input

Batch processing reads a set of files and produces new files — derived data, recreatable by running the process again. But everything in Chapter 10 rested on one assumption: the input is bounded, of known and finite size, so the process knows when it has finished reading. The sorting at the heart of MapReduce is the purest example — it must read its entire input before producing any output, because the very last record might carry the lowest key and need to come out first.

In reality, much data is unbounded because it arrives gradually over time: your users produced data yesterday and today, and they will produce more tomorrow. Unless you go out of business, the process never ends, and the dataset is never “complete” in any meaningful way. Batch processors cope by artificially dividing the data into chunks of fixed duration — a day’s worth at the end of every day, an hour’s worth at the end of every hour. The problem with daily batch processes: changes in the input are only reflected in the output a day later, which is too slow for many impatient users. Run it more frequently — a second’s worth at the end of every second — or abandon fixed time slices entirely and process every event as it happens. That is stream processing.

In general, a stream is data that is incrementally made available over time. The concept appears in many places: the stdin and stdout of Unix, lazy lists in programming languages, filesystem APIs like Java’s FileInputStream, TCP connections, audio and video delivered over the internet. This chapter treats event streams as a data management mechanism: how they are represented, stored, and transmitted; what they have to do with databases; and how to process them continually.

11.0.1 — What is an event?

In a batch job, the first step is parsing a file into records. In a stream, a record is more commonly known as an event — essentially the same thing: a small, self-contained, immutable object containing the details of something that happened at some point in time. An event usually carries a timestamp indicating when it happened, according to a time-of-day clock (Chapter 8’s warnings about those clocks will matter later in this chapter).

  • A user action — viewing a page, making a purchase, typing a search query.
  • A machine measurement — a periodic temperature-sensor reading, a CPU utilization metric.
  • A line in a web server log — every line of the nginx access log from Chapter 10 is an event.

An event may be encoded as a text string, JSON, or a binary form (Chapter 4), which lets you store it — append it to a file, insert it into a relational table, write it to a document database — or send it over the network to another node for processing. An event is generated once by a producer (also known as a publisher or sender) and then potentially processed by multiple consumers (subscribers or recipients); related events are usually grouped into a topic or stream, the streaming analogue of a filename.

In principle, a file or database is enough to connect producers and consumers: the producer writes every event, and each consumer periodically polls for events since it last ran — essentially what a daily batch process does. But moving toward continual processing with low delays, polling becomes expensive: the more often you poll, the lower the percentage of requests that return new events, and the higher the overheads. It is better for consumers to be notified when new events appear. Databases have traditionally supported this badly — relational triggers can react to a change, but they are very limited and something of an afterthought in database design. Instead, specialized tools have been developed for delivering event notifications: messaging systems.

11.1 · Moving events around

Transmitting event streams

A direct communication channel like a Unix pipe or TCP connection between producer and consumer would be a simple messaging system, but pipes and TCP connect exactly one sender with one recipient. A proper messaging system allows multiple producer nodes to send messages to the same topic, and multiple consumer nodes to receive messages in a topic. Within this publish/subscribe model, systems take a wide range of approaches, and two questions do most of the separating.

11.1.1 — Two questions for any messaging system

1.

What if producers send faster than consumers can process?

Broadly three options: drop messages, buffer them in a queue, or apply backpressure (also known as flow control — blocking the producer from sending more). Unix pipes and TCP use backpressure: a small fixed-size buffer, and if it fills up, the sender is blocked until the recipient takes data out. If messages are buffered, it matters what happens as the queue grows — does the system crash when it no longer fits in memory, does it write to disk, and how does that disk access affect performance?

2.

What if nodes crash or go offline — are messages lost?

As with databases, durability may require some combination of writing to disk and replication, which has a cost; if you can afford to sometimes lose messages, you can get higher throughput and lower latency on the same hardware. Whether loss is acceptable depends on the application: for periodically transmitted sensor readings and metrics, an occasional missing data point is perhaps not important, since an updated value arrives shortly anyway (though beware: if a large number of messages are dropped, it may not be apparent that the metrics are wrong). If you are counting events, reliable delivery matters more — every lost message means incorrect counters.

One thing to envy about Chapter 10’s batch systems: a strong reliability guarantee — failed tasks automatically retried, partial output of failed tasks automatically discarded, and the output the same as if no failures had occurred. That simplifies the programming model enormously, and the second half of this chapter is about providing the same guarantee in a streaming context.

11.1.2 — Direct messaging, without a middleman

Some messaging systems use direct network communication between producers and consumers, with no intermediary nodes:

  • UDP multicast — widely used in the financial industry for streams such as stock market feeds, where low latency is important. UDP itself is unreliable, but application-level protocols can recover lost packets (the producer must remember the packets it has sent so it can retransmit them on demand).
  • Brokerless libraries — ZeroMQ and nanomsg take a similar approach, implementing publish/subscribe messaging over TCP or IP multicast.
  • UDP metrics — StatsD and Brubeck use unreliable UDP messaging to collect metrics from all machines on a network. In the StatsD protocol, counter metrics are only correct if all messages are received — using UDP makes the metrics at best approximate.
  • Webhooks — if the consumer exposes a service on the network, producers can make a direct HTTP or RPC request to push messages to it: a callback URL of one service is registered with another, which requests that URL whenever an event occurs.

These work well for what they were designed for, but they generally require the application code to be aware of the possibility of message loss, and the faults they tolerate are limited: even if the protocols detect and retransmit lost packets, they generally assume producers and consumers are constantly online. If a consumer is offline, it misses messages sent while it was unreachable. Some protocols let the producer retry failed deliveries — but that breaks down if the producer crashes, losing the buffer of messages it was supposed to retry.

11.1.3 — Message brokers

The widely used alternative: send messages via a message broker (also known as a message queue), essentially a kind of database optimized for handling message streams. It runs as a server, with producers and consumers connecting as clients: producers write messages to the broker, and consumers receive them by reading from the broker. Centralizing the data in the broker makes it easy to tolerate clients that come and go — connect, disconnect, crash — and the durability question moves to the broker: some brokers keep messages only in memory; others (depending on configuration) write them to disk so they survive a broker crash. Faced with slow consumers, they generally allow unbounded queueing rather than dropping messages or applying backpressure.

A consequence of queueing is that consumers are generally asynchronous: when a producer sends a message, it normally waits only for the broker to confirm the message is buffered, not for it to be processed by consumers. Delivery happens at some undetermined future point — often within a fraction of a second, sometimes significantly later if there is a queue backlog. Some message brokers can even participate in two-phase commit protocols using XA or JTA (Chapter 9), which makes them quite similar in nature to databases — but important practical differences remain.

11.1.4 — Message brokers versus databases

1.

Deletion policy

Databases usually keep data until it is explicitly deleted; most message brokers automatically delete a message when it has been successfully delivered. Such brokers are not suitable for long-term data storage.

2.

Working-set assumptions

Because they delete messages quickly, most brokers assume their working set is fairly small — the queues are short. If the broker needs to buffer a lot because consumers are slow (perhaps spilling to disk when memory runs out), each message takes longer to process and overall throughput may degrade.

3.

Selection mechanism

Databases support secondary indexes and various ways of searching for data; brokers support some way of subscribing to a subset of topics matching some pattern. The mechanisms differ, but both are ways for a client to select the portion of the data it wants to know about.

4.

Snapshots vs notifications

A database query result is based on a point-in-time snapshot — if another client subsequently writes something that changes the result, the first client doesn’t find out unless it repeats the query. Brokers don’t support arbitrary queries, but they do notify clients when data changes — when new messages become available.

This traditional view of message brokers is encapsulated in standards like JMS and AMQP, and implemented in software like RabbitMQ, ActiveMQ, HornetQ, Qpid, TIBCO Enterprise Message Service, IBM MQ, Azure Service Bus, and Google Cloud Pub/Sub.

11.1.5 — Multiple consumers: load balancing and fan-out

When multiple consumers read messages in the same topic, two main patterns are used — and they can be combined: two separate groups of consumers each subscribe to a topic, such that each group collectively receives all messages, but within each group only one node receives each message.

Load balancing divide the work

Each message is delivered to one of the consumers, so the consumers share the work of processing the topic; the broker may assign messages arbitrarily. Useful when messages are expensive to process and you want to add consumers to parallelize. In AMQP you get it by having multiple clients consume from the same queue; in JMS it is called a shared subscription.

Fan-out deliver to all

Each message is delivered to all consumers, allowing several independent consumers to each “tune in” to the same broadcast without affecting each other — the streaming equivalent of several different batch jobs that read the same input file. JMS provides this via topic subscriptions; AMQP via exchange bindings.

11.1.6 — Acknowledgments and redelivery

Consumers may crash at any time, so a broker might deliver a message that the consumer never processes, or only partially processes before crashing. To ensure the message is not lost, brokers use acknowledgments: a client must explicitly tell the broker when it has finished processing a message, so the broker can remove it from the queue. If the connection to a client is closed or times out without an acknowledgment, the broker assumes the message was not processed and delivers it again — to another consumer. (Note that the message might actually have been fully processed with only the ack lost in the network; handling that case properly requires an atomic commit protocol — Chapter 9 again.)

Combined with load balancing, redelivery has an interesting effect on ordering. Suppose consumer 2 crashes while processing message m3, at the same time as consumer 1 is processing m4. The unacknowledged m3 is redelivered to consumer 1 — which now processes the order m4, m3, m5. Even if the broker otherwise preserves message order (as both the JMS and AMQP standards require), the combination of load balancing with redelivery inevitably reorders messages. To avoid it, use a separate queue per consumer — i.e., don’t use load balancing. Reordering is harmless when messages are completely independent, but it matters greatly when there are causal dependencies between messages, as we shall see.

11.1.7 — Partitioned logs: the durable hybrid

Sending a packet over a network is normally a transient operation that leaves no permanent trace. Message brokers inherit that mindset: even those that durably write messages to disk quickly delete them again after delivery. Databases and filesystems take the opposite approach: everything written is expected to be permanently recorded, at least until someone explicitly deletes it. The mindset difference matters for derived data. A key feature of batch processes is that you can run them repeatedly, experimenting, without risk of damaging the read-only input. That is impossible with AMQP/JMS-style messaging: receiving a message is destructive if the acknowledgment deletes it from the broker — you cannot run the same consumer twice and get the same result. Add a new consumer to such a system and it typically only sees messages sent after it registered; all prior messages are gone. Why not have a hybrid — the durable storage of databases combined with the low-latency notification of messaging? That is the idea behind log-based message brokers.

A log is an append-only sequence of records on disk — Chapter 3’s storage engines and Chapter 5’s replication both ran on one. It makes a natural broker: a producer sends a message by appending it to the end of the log, and a consumer receives messages by reading the log sequentially, waiting at the end for notification of a new append. The Unix tool tail -f, which watches a file for appended data, essentially works like this. To scale beyond a single disk’s throughput, the log can be partitioned (in Chapter 6’s sense): partitions hosted on different machines, each a separate log that can be read and written independently, and a topic defined as a group of partitions that all carry messages of the same type. Within each partition the broker assigns a monotonically increasing sequence number, or offset, to every message. Offsets make sense because a partition is append-only, so messages within a partition are totally ordered — but there is no ordering guarantee across different partitions.

Figure 11-3 (recreated) · A partitioned log with consumer groups and offsets

The whole log-based model in one picture. Reading a message does not delete it, so fan-out is trivial — any number of independent consumer groups — and load balancing is coarse-grained: entire partitions are assigned to nodes in a consumer group. The offset mechanism is the same idea as the log sequence number in single-leader replication: the broker behaves like a leader database, the consumer like a follower reconnecting after a disconnection and resuming without skipping writes. Kafka, Amazon Kinesis Streams, and Twitter’s DistributedLog work this way; Google Cloud Pub/Sub is architecturally similar but exposes a JMS-style API rather than a log abstraction. Even though these brokers write all messages to disk, they achieve throughput of millions of messages per second by partitioning across machines, and fault tolerance by replicating messages.

11.1.8 — Log-based brokers versus traditional messaging

The log-based approach trivially supports fan-out, because several consumers can independently read the log without affecting each other — reading doesn’t delete. For load balancing, rather than assigning individual messages to consumer clients, the broker assigns entire partitions to nodes in the consumer group, and each node then consumes all messages in its partitions sequentially, in a straightforward single-threaded manner. That coarse-grained balancing has two downsides:

1.

Parallelism ceiling

The number of nodes sharing the work of consuming a topic can be at most the number of log partitions in that topic, because messages within the same partition are delivered to the same node. (You can split a partition’s work between two consumers by even/odd offsets, or spread processing over a thread pool — but both complicate offset management; more partitions is the usual answer.)

2.

Head-of-line blocking

A single message that is slow to process holds up the processing of all subsequent messages in that partition — head-of-line blocking, Chapter 1’s acquaintance, in queue clothing.

So the fit is clear: when messages may be expensive to process, you want to parallelize message by message, and ordering is not so important — the JMS/AMQP style is preferable. When message throughput is high, each message is fast to process, and message ordering matters — the log-based approach works very well.

11.1.9 — Consumer offsets

Consuming a partition sequentially makes it easy to tell what has been processed: all messages with an offset less than a consumer’s current offset are done; all greater offsets are unseen. The broker therefore doesn’t need to track acknowledgments per message — it only periodically records consumer offsets. The reduced bookkeeping and the opportunities for batching and pipelining help log-based systems reach high throughput. The offset is the close cousin of the log sequence number in single-leader database replication: there, it lets a follower reconnect after a disconnection and resume replication without skipping writes — exactly the same principle here. If a consumer node fails, another node in the consumer group takes over its partitions and starts from the last recorded offset. If the failed consumer had processed messages past its recorded offset, those messages will be processed a second time on restart. Hold that thought — it becomes the exactly-once problem at the end of this chapter.

11.1.10 — Disk space: the log as a big ring buffer

If you only ever append, you eventually run out of disk. The log is divided into segments, and from time to time old segments are deleted or moved to archive storage. A consumer that falls so far behind that its offset points into a deleted segment will miss those messages — effectively the log implements a bounded-size buffer that discards old messages when full, also known as a circular buffer or ring buffer. But since the buffer is on disk, it can be quite large:

11 hrs Of buffering on one typical drive a 6 TB hard drive writing at 150 MB/s takes ~11 hours to fill — and the ratio stays the same even across many drives and machines
days–weeks Practical retention deployments rarely use full disk write bandwidth, so the log typically keeps several days’ or even weeks’ worth of messages
constant Throughput regardless of retention every message is written to disk anyway — unlike memory-first brokers that are fast with short queues and slow down badly when they start spilling to disk

Return to the original three choices — drop, buffer, or backpressure: the log-based approach is buffering with a large but fixed-size buffer, limited by disk space. A consumer that falls behind past what is retained effectively has old messages dropped — but only that consumer is affected; it does not disrupt the service for other consumers. That is a big operational advantage: you can monitor how far a consumer lags the head of the log and alert, and because the buffer is large, a human operator has time to fix a slow consumer before it starts missing messages. You can even experimentally consume a production log for development, testing, or debugging without much worry about disrupting production — and when a consumer shuts down, the only thing left behind is its offset. Traditional brokers are the opposite: you must carefully delete queues whose consumers have been shut down, or they keep accumulating messages and take memory away from active consumers.

11.1.11 — Replaying old messages

With AMQP/JMS-style brokers, processing and acknowledging messages is destructive — it causes them to be deleted. In a log-based broker, consuming messages is more like reading from a file: a read-only operation that does not change the log. The only side effect is the consumer offset moving forward — and the offset is under the consumer’s control, so it can be manipulated: start a copy of a consumer with yesterday’s offsets and write the output to a different location, and you have reprocessed the last day’s worth of messages. Repeat any number of times, varying the processing code.

Why replay matters

This is what makes log-based messaging the streaming sibling of Chapter 10’s batch processes: derived data clearly separated from input data through a repeatable transformation process. It allows more experimentation, easier recovery from errors and bugs, and it is a good tool for integrating dataflows within an organization. It is also the foundation Chapter 12 builds its entire finale on.

11.2 · The database, turned outward

Databases and streams

We compared brokers and databases and found them less unlike than tradition claims — log-based brokers already took ideas from databases and applied them to messaging. Now go in reverse: take ideas from messaging and streams, and apply them to databases. The bridge is an observation easy to miss: an event is a record of something that happened at some point in time — a user action, a sensor reading, or a write to a database. A write is an event that can be captured, stored, and processed, so the connection between databases and streams runs deeper than the physical storage of logs on disk. A replication log is a stream of database write events, produced by the leader as it processes transactions; followers apply that stream and end up with an accurate copy of the same data. Even the state machine replication principle from Chapter 9 is just another case of event streams: if every event represents a write, and every replica processes the same events in the same order (deterministically), the replicas end up in the same final state.

11.2.1 — Keeping systems in sync

There is no single system that can satisfy all data storage, querying, and processing needs, so most nontrivial applications combine several technologies: an OLTP database to serve user requests, a cache to speed up common requests, a full-text index to handle search queries, a data warehouse for analytics. Each holds its own copy of the data in its own representation, optimized for its own purposes — so the copies must be kept in sync. With data warehouses this is usually ETL — a full copy, transformed, bulk-loaded: a batch process. If periodic full database dumps are too slow, the alternative people reach for is dual writes: the application code explicitly writes to each system when data changes — first the database, then the search index, then the cache invalidation (or even concurrently). Dual writes have serious problems, and the first is a race condition.

11.2.2 — The dual-writes race

Two clients concurrently update item X: client 1 wants to set the value to A, client 2 to B. Both write to the database first, then to the search index. With unlucky timing the requests interleave: the database first sees client 1’s write (A), then client 2’s (B) — final database value B. The search index first sees client 2’s write, then client 1’s — final index value A. The two systems are now permanently inconsistent with each other, even though no error occurred.

Figure 11-4 (recreated) · The dual-writes race, on a timeline

The root cause: there is no single leader. The database may have a leader and the index may have a leader, but neither follows the other — so conflicts occur, exactly like multi-leader replication in Chapter 5, just one level up. And unless you have an additional concurrency-detection mechanism like the version vectors of Chapter 5, you will not even notice the concurrent writes: one value simply, silently overwrites the other. The situation would be better if there really were only one leader — the database — and if the search index could be made a follower of the database. That is precisely what change data capture arranges.

11.2.3 — Change data capture

The problem with most databases’ replication logs is that they have long been considered an internal implementation detail, not a public API — clients are supposed to query through the data model and query language, not parse replication logs. For decades many databases had no documented way of getting the log of changes written to them, making it hard to replicate changes to a different storage technology. Hence the growing interest in change data capture (CDC): the process of observing all data changes written to a database and extracting them in a form in which they can be replicated to other systems. CDC is especially interesting when changes are made available as a stream, immediately as they are written.

Capture the changes and continually apply them — in the same order — to a search index, and the index’s data will match the database’s. The search index and any other derived data systems are just consumers of the change stream: the data in the index and the warehouse is another view onto the data in the system of record. Essentially, CDC makes one database the leader (the one changes are captured from) and turns the others into followers — the fix the dual-writes race wanted. A log-based message broker is well suited to transporting the change events, because it preserves message ordering, avoiding the redelivery-reordering issue.

11.2.4 — Implementing CDC: triggers or the replication log?

Triggers flexible, fragile

Register triggers that observe all changes to data tables and add corresponding entries to a changelog table (trigger-based replication, Chapter 5). You decide exactly what gets logged. But triggers tend to be fragile, and they have significant performance overheads.

Replication log robust, low-level

Parse the database’s own replication log. More robust, and the order of writes extracted from the database matches the order in which they were actually written — which is precisely what kills the dual-writes race. The challenges are mechanical: handling schema changes, for instance. And the application writing to the database does not need to be aware that CDC is occurring.

Real deployments, at large scale: LinkedIn’s Databus, Facebook’s Wormhole, Yahoo!’s Sherpa. Tooling by database: Bottled Water implements CDC for PostgreSQL using an API that decodes the write-ahead log; Maxwell and Debezium do something similar for MySQL by parsing the binlog; Mongoriver reads the MongoDB oplog; GoldenGate provides similar facilities for Oracle. Like message brokers, CDC is usually asynchronous: the system of record does not wait for the change to be applied to consumers before committing. Operationally nice — adding a slow consumer does not affect the source database too much — but it means all the issues of replication lag from Chapter 5 apply to your derived systems.

11.2.5 — The initial snapshot

If you had the log of all changes ever made, you could reconstruct the entire state by replaying it. But keeping all changes forever takes too much disk space and replaying takes too long, so the log needs to be truncated — and building a new full-text index, for example, requires a full copy of the entire database: a log of recent changes alone would miss items that were not recently updated. Without the entire history, you need to start from a consistent snapshot, the same problem as setting up a new follower in Chapter 5. The snapshot must correspond to a known position or offset in the change log, so you know exactly where to start applying changes after processing it. Some CDC tools integrate this snapshot facility; others leave it as a manual operation.

11.2.6 — Log compaction

If you can only keep limited log history, you need the snapshot process every time you add a new derived data system. Log compaction is the better alternative. We met it in Chapter 3’s hash indexes: the storage engine periodically looks for log records with the same key, throws away duplicates, and keeps only the most recent value. An update with a special null value — a tombstone — indicates a key was deleted and causes it to be removed during compaction. As long as a key is not overwritten or deleted, it stays in the log forever, and the disk space of the compacted log depends only on the current contents of the database, not the number of writes that have ever occurred.

Now apply it to CDC: if every change has a primary key and every update for a key replaces the previous value, it is sufficient to keep just the most recent write for each key. Whenever you want to rebuild a derived system — say, a search index — start a new consumer at offset 0 of the log-compacted topic and sequentially scan all messages: the log is guaranteed to contain the most recent value for every key in the database (and maybe some older values). A full copy of the database contents, no snapshot needed. Kafka supports log compaction for exactly this purpose — it allows the message broker to be used for durable storage, not just transient messaging.

11.2.7 — API support for change streams

Databases are increasingly supporting change streams as a first-class interface rather than the retrofitted, reverse-engineered CDC efforts: RethinkDB allows queries to subscribe to notifications when the results change; Firebase and CouchDB provide data synchronization based on a change feed that is also made available to applications; Meteor uses the MongoDB oplog to subscribe to data changes and update the user interface. VoltDB allows transactions to continuously export data as a stream: the database represents an output stream in the relational model as a table that transactions can insert tuples into but that cannot be queried — the stream consists of the log of tuples committed transactions wrote to this special table, in commit order, and external consumers can use it to update derived data systems. And Kafka Connect integrates change data capture tools for a wide range of databases with Kafka, so the change events can feed derived systems and stream processors alike.

11.2.8 — Event sourcing

There are strong parallels between all this and event sourcing, a technique developed in the domain-driven design (DDD) community. Event sourcing also involves storing all changes to application state as a log of change events — the biggest difference is the level of abstraction:

1.

CDC — mutable database, low-level log

The application uses the database in a mutable way, updating and deleting records at will. The log of changes is extracted at a low level (parsing the replication log), which ensures the extracted write order matches the actual write order — avoiding Figure 11-4’s race. The application writing to the database does not need to know CDC is occurring.

2.

Event sourcing — immutable events, application level

The application logic is explicitly built on immutable events written to an event log. The event store is append-only; updates and deletes are discouraged or prohibited. Events reflect things that happened at the application level, rather than low-level state changes.

Why it is a powerful technique for data modeling: from an application’s point of view it is more meaningful to record the user’s actions as immutable events than to record the effects of those actions on a mutable database. Storing “student cancelled their course enrollment” expresses the intent of a single action neutrally; the side-effect phrasing — “one entry was deleted from the enrollments table, and one cancellation reason was added to the student feedback table” — embeds assumptions about how the data will later be used. If a new feature arrives (“the place is offered to the next person on the waiting list”), event sourcing lets the new side effect chain off the existing event. It makes applications easier to evolve, helps debugging by making it easier to understand after the fact why something happened, and guards against application bugs. Event sourcing is similar to the chronicle data model, and an event log has similarities to the fact table of a star schema (Chapter 3). Specialized databases like Event Store exist, but the approach is independent of any particular tool — a conventional database or a log-based message broker works too.

11.2.9 — Deriving current state from the event log

An event log by itself is not very useful: users generally expect to see the current state of a system, not its history of modifications — the current contents of their cart, not an append-only list of every change they ever made to it. Applications using event sourcing must transform the log (the way data is written) into application state suitable for showing to a user (the way data is read). The transformation can use arbitrary logic, but it should be deterministic, so running it again derives the same state from the same log. Like CDC, replaying the log reconstructs current state — but log compaction must be handled differently:

  • CDC: an update event typically contains the entire new version of the record, so the current value for a primary key is entirely determined by the most recent event for that key — log compaction can discard previous events for the same key.
  • Event sourcing: events are modeled at a higher level, expressing the intent of a user action rather than the mechanics of the state update. Later events typically do not override prior ones, so you need the full history of events to reconstruct the final state — compaction is not possible in the same way.

Event-sourced applications typically have some mechanism for storing snapshots of the current state derived from the log, so they don’t repeatedly reprocess everything — but that is only a performance optimization, to speed up reads and recovery from crashes. The intention is that the system can store all raw events forever and reprocess the full event log whenever required.

11.2.10 — Commands versus events

Event sourcing carefully distinguishes events from commands. When a request from a user first arrives, it is initially a command: at this point it may still fail, for example because some integrity condition is violated. The application must first validate that it can execute the command — the username is not already taken, the seat is not already booked. If validation succeeds and the command is accepted, it becomes an event: durable and immutable.

At the point the event is generated, it becomes a fact. Even if the customer later changes or cancels the reservation, the fact remains true that they formerly held a reservation for that seat — the change or cancellation is a separate event added later. This has a hard architectural consequence: a consumer of the event stream is not allowed to reject an event — by the time the consumer sees it, it is already an immutable part of the log, and it may already have been seen by other consumers. Any validation must therefore happen synchronously, before the event exists — for example via a serializable transaction that atomically validates the command and publishes the event. Alternatively, split the request into two events — a tentative reservation, then a separate confirmation once validated — which allows the validation to take place asynchronously.

11.2.11 — State, streams, and immutability

Chapter 10 benefited from the immutability of input files; the same principle is what makes event sourcing and CDC so powerful. We normally think of databases as storing current state — optimized for reads, the most convenient representation for serving queries. The nature of state is that it changes, which is why databases support updating and deleting. But here is the reframe: whenever you have state that changes, that state is the result of the events that mutated it over time. Your list of available seats is the result of the reservations processed; the current account balance is the result of the credits and debits; the response-time graph is an aggregation of the response times of all requests that occurred. Even as things are done and undone, the fact remains true that those events occurred. Mutable state and an append-only log of immutable events do not contradict each other — they are two sides of the same coin. The changelog represents the evolution of state over time.

If you are mathematically inclined: application state is what you get when you integrate an event stream over time, and a change stream is what you get when you differentiate the state by time. The analogy has limits (the second derivative of state does not seem meaningful), but it is a useful starting point. Store the changelog durably and the state becomes reproducible; treat the log as the system of record and all mutable state as derived from it, and dataflow through a system becomes much easier to reason about:

“The truth is the log”

“Transaction logs record all the changes made to the database. High-speed appends are the only way to change the log. From this perspective, the contents of the database hold a caching of the latest record values in the logs. The truth is the log. The database is a cache of a subset of the log. That cached subset happens to be the latest value of each record and index value from the log.” — Pat Helland. Log compaction is one way of bridging the distinction between log and database state: it retains only the latest version of each record and discards overwritten versions.

Why is immutability worth this trouble? Accountants have used it for centuries: when a transaction occurs, it is recorded in an append-only ledger — essentially a log of events describing money, goods, or services that changed hands — and the accounts (profit and loss, the balance sheet) are derived by adding up the ledger. If a mistake is made, accountants don’t erase or change the incorrect entry; they add a compensating transaction, and the incorrect entry remains forever for auditing; if wrong figures were published, the next accounting period includes a correction. Entirely normal in accounting — and beneficial well beyond finance: if you accidentally deploy buggy code that writes bad data, recovery is much harder when the code can destructively overwrite good data; with an append-only log of immutable events, diagnosing and recovering is far easier. Immutable events also capture more information than current state: the customer who added an item to their cart and then removed it — for order fulfillment the events cancel out, but for analytics, knowing they considered the item and decided against it is real signal, which a database that deletes on removal would have lost.

11.2.12 — Several views from one log: CQRS

Separating mutable state from the immutable event log lets you derive several different read-oriented representations from the same log — multiple stream consumers again: the analytic database Druid ingests directly from Kafka this way; Pistachio is a distributed key-value store that uses Kafka as a commit log; Kafka Connect sinks export from Kafka to various databases and indexes. An explicit translation step from event log to database also makes applications easier to evolve: a new feature presenting existing data in a new way is just a new read-optimized view built from the log and run alongside the old systems — no complicated schema migration in a live system. Once the old view is no longer needed, shut it down and reclaim its resources.

Storing data is straightforward if you don’t have to worry about how it will be queried; many of the complexities of schema design, indexing, and storage engines exist to serve particular access patterns. So you gain flexibility by separating the form in which data is written from the form in which it is read, and by allowing several read views — an idea known as command query responsibility segregation (CQRS). It dissolves the classic normalization debates: it is entirely reasonable to denormalize data in read-optimized views, because the translation process is the mechanism keeping them consistent with the event log. Twitter’s home timelines from Chapter 1 are exactly this: highly denormalized read-optimized state — your tweets duplicated into all your followers’ timelines — kept manageable because the fan-out service continuously syncs the duplicated state with new tweets and new following relationships.

11.2.13 — Concurrency control

The biggest downside of event sourcing and CDC is that consumers of the event log are usually asynchronous: a user may write to the log, then read from a log-derived view and find the write not yet reflected — the read-your-own-writes problem from Chapter 5, back again. One solution: update the read view synchronously with appending the event, which requires a transaction to combine the writes atomically — so either the event log and read view live in the same storage system, or you need a distributed transaction across them. The Chapter 9 approach of implementing linearizable storage via total order broadcast is another route.

But deriving current state from an event log also simplifies parts of concurrency control. Much of the need for multi-object transactions (Chapter 7) stems from a single user action requiring data changes in several different places. With event sourcing, you can design the event as a self-contained description of the user action, so the action requires only a single write — appending the event to the log — which is easy to make atomic. Better: if the event log and the application state are partitioned the same way (an event for a customer in partition 3 only requires updating partition 3 of the state), then a straightforward single-threaded log consumer needs no concurrency control for writes at all — by construction it only processes one event at a time, like Chapter 7’s actual serial execution. The log removes the nondeterminism of concurrency by defining a serial order of events in a partition. Events touching multiple state partitions require more work — which is Chapter 12’s territory.

11.2.14 — The limits of immutability

Many systems that don’t use event sourcing still rely on immutability: databases internally use immutable data structures or multi-version data to support point-in-time snapshots; version control systems like Git, Mercurial, and Fossil preserve immutable file history. To what extent is it feasible to keep an immutable history of all changes forever? It depends on churn. Workloads that mostly add data and rarely update or delete are easy to make immutable. Workloads with high rates of updates and deletes on a comparatively small dataset make the immutable history grow prohibitively large; fragmentation becomes an issue, and the performance of compaction and garbage collection becomes crucial for operational robustness.

And beyond performance, there are circumstances where data must be deleted for administrative reasons — privacy regulations may require deleting a user’s personal information after they close their account; data protection legislation may require erroneous information removed; a leak of sensitive information may need containing. In those cases it is not enough to append an event saying “consider this deleted” — you actually want to rewrite history as if the data had never been written. Datomic calls this feature excision; the Fossil version control system has a similar concept called shunning. Truly deleting data is surprisingly hard, since copies can live in many places: storage engines, filesystems, and SSDs often write to new locations rather than overwriting in place, and backups are often deliberately immutable. Deletion is more a matter of “making it harder to retrieve the data” than “making it impossible.” Nevertheless, sometimes you have to try — Chapter 12 returns to this with the ethics of retention.

11.3 · The operators

Processing streams

We know where streams come from (user activity events, sensors, writes to databases) and how they travel (direct messaging, brokers, event logs). What remains is what you do with one. Broadly, three options:

1.

Write it to a storage system

Database, cache, or search index, from where other clients can query it — the streaming equivalent of Chapter 10’s batch outputs, and a good way to keep the store in sync with the rest of the system, especially if the stream consumer is the only client writing to it.

2.

Push it to people

Email alerts, push notifications, streaming events into a real-time dashboard where they are visualized. A human is the ultimate consumer of the stream.

3.

Produce derived streams

Process one or more input streams to produce one or more output streams, possibly through a pipeline of several processing stages before ending at option 1 or 2. A piece of code that does this is an operator or a job — closely related to the Unix processes and MapReduce jobs of Chapter 10, with the same dataflow shape: consume input read-only, write output append-only somewhere else.

The rest of this chapter is about option 3. Partitioning and parallelization work like MapReduce and the dataflow engines, and basic mapping operations (transform, filter) are the same. The one crucial difference: a stream never ends. That changes everything about the hard parts — sorting does not make sense with an unbounded dataset, so sort-merge joins cannot be used (the very last record might need to join the very first). And fault tolerance must change: a batch task that ran for a few minutes can restart from the beginning, but a stream job that has been running for several years cannot restart from the beginning after a crash.

11.3.1 — Uses of stream processing

Stream processing has long been used for monitoring — an organization wants alerts when certain things happen: fraud detection systems looking for unexpectedly changed credit-card usage patterns; trading systems examining price changes and executing trades by specified rules; manufacturing systems monitoring factory machines; military and intelligence systems tracking potential aggressors. These require quite sophisticated pattern matching, and the first two styles below grew out of that lineage.

Complex event processing CEP

An approach developed in the 1990s for analyzing event streams, geared toward searching for certain event patterns. Like a regular expression searches for character patterns in a string, CEP lets you specify rules to search for patterns of events in a stream — usually in a high-level declarative query language like SQL or a graphical UI. The queries are submitted to a processing engine that consumes the input streams and internally maintains a state machine performing the matching; when a match is found, it emits a complex event (hence the name) with the details of the detected pattern. Note the reversal from databases: the queries are stored long-term, and the events flow past them — a database stores data and treats queries as transient; CEP engines store queries and treat the data as transient. Implementations: Esper, IBM InfoSphere Streams, Apama, TIBCO StreamBase, SQLstream; Samza has been gaining SQL support too.

Stream analytics aggregations

Less interested in specific event sequences, more in aggregations and statistical metrics over large numbers of events: the rate of some event type (how often it occurs per interval), the rolling average of a value over a period, comparisons of current statistics to previous intervals (trends, alerts on metrics unusually high or low versus the same time last week). Such statistics are usually computed over fixed time intervals — a window. Stream analytics systems sometimes use probabilistic algorithms — Bloom filters for set membership, HyperLogLog for cardinality estimation, percentile-estimation algorithms — which produce approximate results with much less memory. This sometimes leads people to believe stream processing is inherently lossy and inexact, but that is wrong: there is nothing inherently approximate about stream processing; probabilistic algorithms are merely an optimization. Frameworks: Storm, Spark Streaming, Flink, Concord, Samza, Kafka Streams; hosted: Google Cloud Dataflow, Azure Stream Analytics.

Maintaining materialized views derived state

Keeping derived data systems — caches, search indexes, warehouses — up to date with a source database is a specific case of maintaining materialized views: deriving an alternative view onto a dataset so it can be queried efficiently, updated whenever the underlying data changes. Event-sourced application state is also a materialized view. Unlike analytics, this usually requires all events over an arbitrary time period — a window that stretches all the way back to the beginning of time — which runs counter to analytics frameworks that mostly operate on limited windows. Samza and Kafka Streams support it, building on Kafka’s log compaction.

Search on streams percolator

CEP searches for multi-event patterns; there is also sometimes a need to search for individual events by complex criteria, like full-text queries — media monitoring services subscribe to news feeds and search for mentions of companies or products; real-estate sites notify users when a new property matching their criteria appears. The percolator feature of Elasticsearch is one option. Conventional search indexes documents first and runs queries over the index; searching a stream turns it on its head — the queries are stored, and the documents run past the queries, like CEP. In the simplest case you test every document against every query; to optimize, you can index the queries as well as the documents.

Actors are not stream processors (but they rhyme)

Message-passing systems like the actor model (Chapter 4) are also built on messages and events, but three differences matter: actor frameworks are primarily a mechanism for managing concurrency and distributed execution of communicating modules, while stream processing is primarily a data management technique; communication between actors is often ephemeral and one-to-one, whereas event logs are durable and multi-subscriber; and actors communicate in arbitrary ways, including cyclic request/response patterns, while stream processors form acyclic pipelines where every stream is the output of one job derived from well-defined inputs. There is crossover: Apache Storm’s distributed RPC farms user queries out to nodes that also process event streams and interleaves them; and you can process streams with actor frameworks, though many don’t guarantee delivery across crashes, so processing isn’t fault-tolerant without extra retry logic.

11.3.2 — Reasoning about time

Stream processors often need to deal with time — “the average over the last five minutes” sounds unambiguous and is surprisingly tricky. In a batch process, the tasks crunch through a large collection of historical events, and any breakdown by time must use the timestamp embedded in each event; the system clock of the machine running the batch is irrelevant, and using event timestamps keeps the processing deterministic — run it again and get the same result. Many stream processing frameworks, however, use the local system clock of the processing machine (the processing time) to determine windowing. That is simple, and reasonable if the delay between event creation and event processing is negligibly short. It breaks down if there is any significant processing lag.

Event time versus processing time

Processing may be delayed for many reasons: queueing, network faults, contention in the broker or processor, a restart of the stream consumer, or reprocessing of past events while recovering from a fault or fixing a bug. Message delays also lead to unpredictable ordering: a user makes one web request handled by server A, then a second handled by server B; both emit events, but B’s reaches the broker first — the stream processor sees B’s event before A’s, though they occurred in the opposite order.

The Star Wars analogy

Episode IV was released in 1977, V in 1980, VI in 1983, then Episodes I, II, III in 1999, 2002, 2005, and VII in 2015. If you watched the movies in release order, the order in which you processed them is inconsistent with the order of their narrative. The episode number is like the event timestamp; the date you watched it is the processing time. Humans cope with such discontinuities, but stream processing algorithms must be specifically written to accommodate them.

Confusing event time with processing time produces bad data. Suppose a stream processor measures the rate of requests — count per second. If you redeploy the processor, it may be down for a minute and then process the backlog on restart. Measured by processing time, it will look like a sudden anomalous spike of requests while chewing the backlog, when in fact the real request rate was steady. Windowing by processing time introduces artifacts due to variations in processing rate.

11.3.3 — Knowing when you’re ready (stragglers)

Defining windows by event time creates a tricky problem: you can never be sure you have received all the events for a particular window. Grouping into one-minute windows, you have counted events in the 37th minute; time has moved on, and incoming events now fall in the 38th and 39th minutes. When do you declare the 37th-minute window finished and output its counter? You can time out and declare it ready after seeing no new events for a while — but an event may still have been buffered on another machine, delayed by a network interruption. You need to handle such straggler events that arrive after the window was declared complete. Broadly, two options:

1.

Ignore the stragglers

They are probably a small percentage of events in normal circumstances. Track the number of dropped events as a metric, and alert if you start dropping a significant amount of data.

2.

Publish a correction

An updated value for the window with the straggler included — you may also need to retract the previous output.

In some cases a special message can declare “from now on there will be no more messages with a timestamp earlier than t,” which consumers can use to trigger windows — though with several producers on different machines, each with its own minimum-timestamp threshold, consumers must track each producer individually, and adding or removing producers gets trickier. (Modern systems call such markers watermarks, but the underlying bet is the same: a guess that late events are rare.)

11.3.4 — Whose clock are you using, anyway?

Timestamping is even harder when events can be buffered at several points in the system. A mobile app reporting usage metrics may be used while the device is offline, buffering events locally and sending them hours or even days later when a connection returns — to consumers, they appear as extremely delayed stragglers. The timestamp should really be the time the user interaction occurred, according to the device’s clock — but a user-controlled device’s clock often cannot be trusted, being accidentally or deliberately wrong (Chapter 8). The server-received time is more accurate but less meaningful. One adjustment approach logs three timestamps:

  • Event occurred — according to the device clock.
  • Event sent to the server — according to the device clock.
  • Event received by the server — according to the server clock.

Subtracting the second from the third estimates the offset between device and server clocks (assuming network delay is negligible compared to the required accuracy); applying that offset to the event timestamp estimates when the event actually occurred (assuming the offset didn’t change between occurrence and sending). This problem isn’t unique to streaming — batch processing suffers exactly the same issues; it is just more noticeable in a streaming context, where we are more aware of the passage of time.

11.3.5 — Types of windows

Once you know how an event’s timestamp is determined, the next step is deciding how windows over time periods are defined, for aggregations — counting events, averaging values. Four types are in common use:

Figure 11-A (recreated) · Tumbling, hopping, sliding, and session windows on one timeline

One timeline, four ways to slice it. A tumbling window has fixed length and every event belongs to exactly one — a 1-minute tumbling window is just each timestamp rounded down to the nearest minute. A hopping window has fixed length but allows overlap for smoothing — a 5-minute window with a hop of 1 minute contains 10:03:00–10:07:59, then 10:04:00–10:08:59, and so on; implement it by calculating 1-minute tumbling windows and aggregating over several adjacent ones. A sliding window contains all events that occur within some interval of each other — 10:03:39 and 10:08:12 share a 5-minute sliding window even though fixed-boundary windows would separate them; implement with a buffer of events sorted by time, removing old events as they expire. A session window has no fixed duration: group together all events for the same user that occur closely in time, and the window ends after inactivity — say 30 minutes. Sessionization is a common website-analytics requirement, Chapter 10’s friend.

11.3.6 — Stream joins

Batch jobs join datasets by key; since stream processing generalizes data pipelines to unbounded datasets, there is exactly the same need for joins. But new events can appear at any time, which makes stream joins harder. Three types to distinguish:

Figure 11-B (recreated) · The three stream joins

Same skeleton, three join shapes. Stream-stream: both inputs are activity events; the join operator searches for related events within some window of time — a click matched to the search that produced it, keyed by session ID. The click may never come, the delay may be seconds or days, and due to network delays the click may even arrive before the search — you choose a window (say, at most one hour apart) and live with it. Note that embedding the search details in the click event is not a substitute: that would only tell you about clicks, and for accurate click-through rates you also need the searches that went unclicked. Stream-table: one input is activity events, the other a database changelog; the changelog keeps a local copy of the database up to date, and each activity event is enriched by querying it — a local lookup, not a remote query (which would be slow and could overload the database). A stream-table join is very similar to a stream-stream join where the table’s window reaches back to the “beginning of time,” with newer versions overwriting older. Table-table: both inputs are changelogs; every change on one side is joined with the latest state of the other, producing a stream of changes to the materialized view of the join.

The Twitter timeline as a table-table join

Chapter 1’s timeline cache — a per-user “inbox” so reading the timeline is a single lookup — is maintained by exactly four event types: when user u sends a tweet, it is added to the timeline of every follower of u; when a user deletes a tweet, it is removed from all timelines; when u1 starts following u2, u2’s recent tweets are added to u1’s timeline; when u1 unfollows u2, u2’s tweets are removed from u1’s timeline. Implementing this in a stream processor requires event streams for tweets (sending and deleting) and follow relationships (following and unfollowing), plus a database of each user’s follower set so the processor knows which timelines to update. Looked at another way, the processor maintains a materialized view of this query:

SELECT follows.follower_id AS timeline_id, array_agg(tweets.* ORDER BY tweets.timestamp DESC) FROM tweets JOIN follows ON follows.followee_id = tweets.sender_id GROUP BY follows.follower_id

The join of the streams corresponds directly to the join of the tables in that query; the timelines are effectively a cache of the query result, updated every time the underlying tables change. (A neat footnote: if you regard a stream as the derivative of a table, the stream of changes to the materialized join follows the product rule — (u·v)′ = u′v + uv′: any change of tweets is joined with the current followers, and any change of followers is joined with the current tweets.)

11.3.7 — Time-dependence of joins

All three join types have a lot in common: the processor maintains state from one join input and queries it on messages from the other. And in all three, the order of the events that maintain the state is important — it matters whether you first follow and then unfollow, or the other way round. A partitioned log preserves ordering within each partition, but there is typically no ordering guarantee across different streams or partitions. So: if events on different streams happen around a similar time, in which order are they processed? If a user updates their profile, which activity events are joined with the old profile, and which with the new? If state changes over time and you join with some state, what point in time do you use for the join?

This time dependence is everywhere — if you sell things, the right tax rate depends on the country, the product type, and the date of sale, since tax rates change; when joining sales to tax rates you probably want the rate at the time of sale, which may differ from the current rate when reprocessing historical data. If ordering across streams is undetermined, the join becomes nondeterministic: rerun the same job on the same input and you may get a different result, because the input streams interleaved differently. In data warehouses this issue is known as a slowly changing dimension (SCD), often addressed by giving each version of the joined record a unique identifier — every time the tax rate changes, it gets a new ID, and the invoice references the ID of the rate at the time of sale. That makes the join deterministic, at the cost of keeping every version of the record — log compaction becomes impossible.

11.3.8 — Fault tolerance

Chapter 10’s batch frameworks tolerate faults easily: a failed task restarts on another machine, its partial output is discarded, and the result is as if nothing went wrong — input files are immutable, each task writes to a separate file, and output becomes visible only when the task completes successfully. In particular, the output of a batch job is the same as if every input record had been processed exactly once — no records skipped, none processed twice. That principle is known as exactly-once semantics, although effectively-once would be more descriptive, since records may in fact be processed multiple times while the visible effect is as if processed once. The same problem arises in stream processing but is harder: waiting until a task finishes to make output visible is not an option, because a stream is infinite and you can never finish processing it.

Microbatching and checkpoints

One solution: break the stream into small blocks and treat each block like a miniature batch process — microbatching, used by Spark Streaming. The batch size is typically around one second, a performance compromise: smaller batches mean greater scheduling and coordination overhead; larger batches mean longer delay before results become visible. Microbatching also implicitly provides a tumbling window equal to the batch size (windowed by processing time, not event timestamps); jobs needing larger windows must explicitly carry state from one microbatch to the next. A variant used by Apache Flink: periodically generate rolling checkpoints of state and write them to durable storage — if an operator crashes, it restarts from its most recent checkpoint and discards output generated between the checkpoint and the crash. Checkpoints are triggered by barriers in the message stream, like microbatch boundaries but without forcing a particular window size. Within the confines of the framework, both approaches provide the same exactly-once semantics as batch processing. But as soon as output leaves the stream processor — writing to a database, sending messages to an external broker, sending emails — the framework can no longer discard the output of a failed batch: restarting a failed task causes the external side effect to happen twice.

Atomic commit revisited

To give the appearance of exactly-once processing in the presence of faults, all outputs and side effects of processing an event must take effect if and only if the processing is successful: messages sent downstream, database writes, changes to operator state, acknowledgments of input messages — including moving the consumer offset forward. They must all happen atomically, or none of them. If that sounds familiar, it is the atomic commit problem from Chapter 9. The traditional implementations (XA) have problems, but in more restricted environments an atomic commit facility can be implemented efficiently — Google Cloud Dataflow and VoltDB do this, and similar features were planned for Kafka. Unlike XA, these implementations don’t attempt transactions across heterogeneous technologies; they keep everything internal by managing both state changes and messaging within the stream processing framework, and amortize the protocol overhead by processing several input messages per transaction.

11.3.9 — Idempotence and fencing

Distributed transactions are one way to discard the partial output of failed tasks so they can be retried safely; another is to rely on idempotence. An idempotent operation is one you can perform multiple times with the same effect as performing it once: setting a key in a key-value store to a fixed value is idempotent (re-writing the identical value changes nothing); incrementing a counter is not (re-performing it increments twice). Even an operation that is not naturally idempotent can often be made so with a bit of metadata: when consuming from Kafka, every message has a persistent, monotonically increasing offset — when writing to an external database, include the offset of the message that triggered the last write, and you can tell whether an update has already been applied and avoid performing it again. Storm’s Trident state handling is based on a similar idea. Relying on idempotence assumes: restarting a failed task must replay the same messages in the same order (a log-based broker does exactly this), the processing must be deterministic, and no other node may concurrently update the same value. When failing over from one processing node to another, fencing (Chapter 8) may be needed to prevent interference from a node believed dead but actually alive. Despite the caveats, idempotent operations achieve exactly-once semantics with only a small overhead — the recipe of idempotence plus transactional offset commit.

11.3.10 — Rebuilding state after a failure

Any stream process that requires state — windowed aggregations (counters, averages, histograms), tables and indexes for joins — must ensure that state can be recovered after a failure. Options, each with real trade-offs:

1.

Remote datastore, replicated

Keep state in a remote datastore and replicate it. Downside: querying a remote database for each individual message can be slow — the same problem as the naive stream-table join.

2.

Local state, periodically replicated

Keep state local to the stream processor and replicate it periodically; on recovery, the new task reads the replicated state and resumes. Flink periodically captures snapshots of operator state and writes them to durable storage such as HDFS; Samza and Kafka Streams replicate state changes by sending them to a dedicated Kafka topic with log compaction (very like CDC); VoltDB replicates state by redundantly processing each input message on several nodes.

3.

Rebuild from the input streams

Sometimes replication isn’t even necessary: if the state is aggregations over a fairly short window, it may be fast enough to replay the input events for that window; if the state is a CDC-maintained local replica of a database, it can be rebuilt from the log-compacted change stream.

All these trade-offs depend on the performance characteristics of the infrastructure — in some systems network delay is lower than disk access latency, and network bandwidth comparable to disk bandwidth. There is no universally ideal trade-off, and the merits of local versus remote state may shift as storage and networking evolve.

The bridge to Chapter 12

One famous answer to combining stream processing’s low latency with batch processing’s reliability — the lambda architecture, running a stream system for quick approximate results and a batch system that later corrects them over the same events — sits right on the boundary between this chapter and the next, where its promises and its practical problems get the full treatment. The short version: the same benefits are increasingly available from a single system that can do both, and the final chapter explains exactly what that requires.

11.4 · Pulling it together

Summary

Stream processing is very much like the batch processing of Chapter 10, but done continuously on unbounded, never-ending streams rather than a fixed-size input. From that perspective, message brokers and event logs serve as the streaming equivalent of a filesystem. The two broker families, one last time:

AMQP/JMS-style broker asynchronous RPC

The broker assigns individual messages to consumers, who acknowledge individual messages; messages are deleted once acknowledged. Appropriate as an asynchronous form of RPC — task queues, where the exact order of processing is not important and there is no need to go back and read old messages after they have been processed.

Log-based broker derived data

The broker assigns all messages in a partition to the same consumer node and always delivers them in the same order. Parallelism comes from partitioning; consumers track their progress by checkpointing the offset. The broker retains messages on disk, so it is possible to jump back and reread old messages if necessary. Similar to database replication logs and log-structured storage engines — and especially appropriate for stream processing systems that consume input streams and generate derived state or derived output streams.

Where streams come from: user activity events, periodic sensor readings, data feeds — and writes to a database, captured implicitly through change data capture or explicitly through event sourcing. Log compaction allows the stream to retain a full copy of a database’s contents. Representing databases as streams opens powerful integration opportunities: keep derived systems continually up to date by consuming the log of changes, and build fresh views onto existing data by consuming the log from the beginning all the way to the present. Those same facilities — maintaining state as streams, replaying messages — are the basis for stream joins and for fault tolerance via microbatching, checkpointing, transactions, and idempotent writes. And the deep problems that remain — event time versus processing time, stragglers, time-dependent joins — are the ones that make stream processing feel genuinely different from batch: time itself becomes a first-class concern.

Glossary

stream
Data that is incrementally made available over time. Appears as stdin/stdout in Unix, lazy lists, FileInputStream, TCP connections, streaming audio/video — and, in this chapter, event streams as a data management mechanism.
event
A small, self-contained, immutable object containing the details of something that happened at some point in time, usually with a timestamp. May be encoded as text, JSON, or binary; stored by appending to a file or database; or sent over the network.
producer / consumer / topic
Producer (publisher, sender) generates an event once; consumers (subscribers, recipients) may process it; related events are grouped into a topic or stream — the streaming analogue of a filename.
backpressure
Flow control: blocking the producer from sending more messages when it outruns consumers — how Unix pipes and TCP behave, with their small fixed-size buffers. The alternatives are dropping messages or buffering in a queue.
message broker
A server, essentially a database optimized for message streams, that producers write to and consumers read from. Centralizes durability; allows unbounded queueing; consumers are asynchronous — the producer waits only for the broker’s confirmation of buffering.
broker vs database
Brokers delete on successful delivery (databases keep until explicit deletion); assume short queues; offer topic-pattern subscriptions instead of secondary indexes; notify on change instead of answering point-in-time queries. JMS/AMQP tradition: RabbitMQ, ActiveMQ, IBM MQ, and kin.
load balancing (messaging)
Each message delivered to one of a group of consumers, so they share the work — useful for expensive-to-process messages. AMQP: multiple clients on one queue; JMS: shared subscription.
fan-out (messaging)
Each message delivered to all consumers, each independently tuned in without affecting the others — the streaming equivalent of several batch jobs reading the same input file.
acknowledgment / redelivery
A client must explicitly confirm processing so the broker can remove the message; timeout without an ack means redelivery to another consumer. Combined with load balancing, redelivery inevitably reorders messages — the m3/m4 swap.
log-based message broker
A broker whose storage is a partitioned, durable log: producers append, consumers read sequentially and wait at the tail (like tail -f). Kafka, Kinesis Streams, DistributedLog; Google Cloud Pub/Sub is architecturally similar with a JMS-style API. Millions of messages per second via partitioning, fault tolerance via replication.
partitioned log / offset
The broker’s storage split across machines (Chapter 6 partitioning); a topic is a group of partitions. Within a partition, every message gets a monotonically increasing offset — messages in a partition are totally ordered; across partitions, no ordering guarantee.
consumer group
A set of consumer nodes that collectively receive all messages of a topic, with each partition assigned to exactly one node in the group. Load balancing is per-partition, so the number of nodes is at most the number of partitions; fan-out is free because reading doesn’t delete.
consumer offset
A consumer’s position in a partition. All offsets below it are processed, all above unseen — so the broker only periodically records offsets instead of tracking per-message acks. The same idea as the log sequence number that lets a replication follower reconnect and resume. Crash past the recorded offset → messages processed twice.
ring buffer (circular buffer)
What the log effectively is: a bounded-size buffer on disk that discards old messages when full. A 6 TB drive at 150 MB/s holds about 11 hours of writes; deployments typically retain days or weeks. Throughput stays constant regardless of retention, because every message is written to disk anyway.
replay
Reprocessing old messages by resetting a consumer offset — non-destructive because the log is read-only to consumers. Enables experimentation with new code on real history, recovery from bugs by reprocessing with fixed code, and rebuilding derived systems from offset 0.
dual writes
Application code writing to each of several systems directly when data changes. Two fatal problems: a race condition (two clients, two systems, two different write orders → permanent inconsistency with no error) and partial failure (one write succeeds, the other doesn’t → atomic commit problem).
change data capture (CDC)
Observing all data changes written to a database and extracting them in a form that can be replicated to other systems — making one database the leader and the derived systems followers. Implementations: triggers (fragile, overhead) vs parsing the replication log (robust, schema-change challenges): Databus, Wormhole, Sherpa, Bottled Water, Maxwell, Debezium, Mongoriver, GoldenGate. Usually asynchronous — replication lag applies.
initial snapshot
A consistent full copy of the database corresponding to a known offset in the change log, needed when the log doesn’t retain all history — the same mechanism as setting up a new follower.
log compaction (in CDC)
Keeping only the most recent value per key in the log — disk depends on current database contents, not write history. A new derived system can be rebuilt by consuming the compacted topic from offset 0, no snapshot needed. Supported by Kafka.
event sourcing
Storing all changes to application state as a log of application-level events, with the event store append-only and updates/deletes discouraged. State is derived by deterministic replay. Unlike CDC events, later events don’t override earlier ones, so full history is needed — compaction is not possible the same way. From the domain-driven design community.
command vs event
A user request starts as a command that may still fail validation; once validated and accepted it becomes an event — durable, immutable, a fact. Consumers may not reject events (they are already in the log), so validation must happen synchronously before the event exists (or via tentative-then-confirmed event pairs).
state = integral of events
Mutable state and an immutable event log are two sides of the same coin: state is the result of the events that mutated it over time; the changelog is the derivative of state, state the integral of the stream. “The truth is the log; the database is a cache of a subset of the log” (Helland).
compensating transaction
How accountants fix mistakes: never erase the wrong entry — append a correcting entry, and keep the mistake in the ledger forever for audit. The same idea underwrites recovery from buggy code with immutable logs.
CQRS
Command query responsibility segregation: separate the write-optimized form of data (the event log) from one or more read-optimized views derived from it. Normalization debates dissolve — denormalizing read views is fine when the translation process keeps them consistent. Twitter’s fan-out timelines are read-optimized, denormalized state.
excision / shunning
History-rewriting deletion: Datomic’s excision and Fossil’s shunning remove data as if it was never written, for privacy or legal reasons. Truly deleting data is surprisingly hard — copies live in storage engines, filesystems, SSDs, and deliberately immutable backups.
complex event processing (CEP)
Analyzing streams for event patterns with declarative rules, maintained as state machines; matches emit “complex events.” Reverses the database: queries are stored long-term, data flows past them. Esper, IBM InfoSphere Streams, Apama, StreamBase, SQLstream.
stream analytics
Aggregations and statistical metrics over many events — rates, rolling averages, comparisons to previous periods — computed over windows. Sometimes uses probabilistic algorithms (Bloom filters, HyperLogLog) as a memory optimization, but nothing about stream processing is inherently approximate.
percolator / search on streams
Storing the queries and running the documents past them — Elasticsearch’s percolator matches streaming documents against registered searches; media monitoring and real-estate alerts work this way. Index the queries to avoid testing every document against every query.
event time vs processing time
When the event happened vs when the stream processor saw it. They diverge arbitrarily (queueing, network faults, restarts, reprocessing), so processing-time windowing manufactures artifacts — a backlog looks like a spike. The Star Wars release-order analogy: episode number is event time, the date you watched is processing time.
straggler event
An event arriving after its window was declared complete. Handle by ignoring it (track the dropped count as a metric, alert on growth) or by publishing a correction (possibly retracting earlier output).
three timestamps
Device-clock time of occurrence, device-clock time of sending, server-clock time of receipt — subtracting the second from the third estimates the device–server clock offset, which corrects the event timestamp (assuming negligible network delay and a stable offset).
tumbling window
Fixed length, non-overlapping; every event belongs to exactly one. Implement by rounding each event timestamp down to the window boundary.
hopping window
Fixed length, advanced by a step, overlapping for smoothing: 5-minute windows with a 1-minute hop. Implement as aggregations over several adjacent tumbling windows.
sliding window
Contains all events within some interval of each other — no fixed boundaries. Implement with a time-sorted buffer of events, expiring old ones. The only window type that would group 10:03:39 with 10:08:12 in a 5-minute window.
session window
No fixed duration: groups all events for one user closely together in time, ending after an inactivity gap (say, 30 minutes). Sessionization — Chapter 10’s grouping job, made continuous.
stream-stream join
Both inputs are activity events (possibly the same stream — a self-join); the operator keeps windowed state indexed by key and matches related events — a click to its search, within at most some window. Missing counterparts emit their own events (un-clicked searches), which is why embedding one event in the other is not a substitute.
stream-table join (enrichment)
Enrich an activity stream with the latest state of a database, kept current via its CDC changelog and held locally (in-memory hash table or on-disk index) to avoid remote lookups. The table’s window reaches back to the beginning of time; newer versions overwrite older.
table-table join
Both inputs are changelogs; the result is a stream of changes to the materialized view of the join — the Twitter timeline maintenance (tweets ⋈ follows), driven by tweet, delete, follow, and unfollow events.
slowly changing dimension (SCD)
The data-warehouse name for time-dependent joins: join with the version of the record current at the event’s time. Version identifiers make the join deterministic, at the price of retaining all versions — no log compaction.
exactly-once semantics
The output is the same as if no faults had occurred even if faults did occur — more honestly “effectively-once,” since retries may reprocess records while the visible effect is as if processed once. Batch gets it free from immutability and all-or-nothing outputs; streams must work for it.
microbatching
Spark Streaming’s fault tolerance: break the stream into small blocks (typically ~1 second) and treat each like a miniature batch. The batch size trades coordination overhead against latency, and implicitly imposes a processing-time tumbling window equal to the batch size.
checkpointing
Flink’s alternative: rolling checkpoints of operator state written to durable storage, triggered by barriers in the message stream — no fixed window size. A crashed operator restarts from its most recent checkpoint and discards output since.
idempotence
An operation with the same effect executed once or many times: set-value yes, increment no. Make non-idempotent operations idempotent with metadata (e.g., include the Kafka message offset with the write to detect already-applied updates). Assumes same-order replay, deterministic processing, no concurrent writers — and fencing on failover.
rebuilding state
Recovery options for windowed aggregates and join state: remote replicated datastore (slow per message), local state periodically replicated (Flink snapshots to HDFS; Samza/Kafka Streams to a compacted topic; VoltDB redundant processing), or rebuild from the input streams (short windows; compacted changelogs). No universal winner.
