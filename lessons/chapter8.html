8.0 · The setup

Pessimism to the maximum

A recurring theme of this book is how systems handle things going wrong — replica failover, replication lag, weak isolation levels. This chapter turns the pessimism all the way up: anything that can go wrong, will go wrong. Experienced systems operators say that’s a reasonable assumption, and working with distributed systems is fundamentally different from writing software on a single computer — mainly because of lots of new and exciting ways for things to go wrong. The plan: networks first, then clocks, then what a node can actually know about the state of the world. The engineering goal throughout: build systems that do their job — meet the guarantees users expect — in spite of everything going wrong. (One exception is granted up front: faults are assumed to be non-Byzantine — nodes unreliable but honest — until the section on lying.)

8.0.1 — Faults and partial failure

On a single computer, software behaves in a fairly predictable way: it works or it doesn’t. Buggy software may seem to have “a bad day” (often fixed by a reboot), but that’s a consequence of badly written software — when the hardware is working correctly, the same operation always produces the same result: it is deterministic. Hardware problems (memory corruption, a loose connector) usually cause total failure: a kernel panic, a blue screen, a machine that won’t start. An individual computer with good software is usually either fully functional or entirely broken, but not something in between.

That is a deliberate choice in the design of computers: if an internal fault occurs, we prefer a computer to crash completely rather than return a wrong result. The machine hides the fuzzy physical reality and presents an idealized system operating with mathematical perfection — a CPU instruction always does the same thing; data written to memory or disk stays intact. This goal of always-correct computation goes back to the very first digital computer.

Distributed systems break the deal. With software running on several computers connected by a network, there may well be some parts of the system that are broken in some unpredictable way, even though other parts are working fine — a partial failure. Worse, partial failures are nondeterministic: try to do anything involving multiple nodes and the network, and it may sometimes work and sometimes unpredictably fail. You may not even know whether something succeeded — the time a message takes to cross the network is also nondeterministic. This nondeterminism and the possibility of partial failure are what make distributed systems hard to work with.

From the trenches — Coda Hale

“In my limited experience I’ve dealt with long-lived network partitions in a single data center, PDU failures, switch failures, accidental power cycles of whole racks, whole-DC backbone failures, whole-DC power failures, and a hypoglycemic driver smashing his Ford pickup truck into a DC’s HVAC system. And I’m not even an ops guy.”

8.0.2 — Cloud computing and supercomputing

There’s a spectrum of philosophies for building large computers. High-performance computing (HPC): supercomputers with thousands of CPUs for computationally intensive scientific work — weather forecasting, molecular dynamics; the job checkpoints state to durable storage from time to time, and if one node fails, you stop the entire cluster workload, repair the node, and restart from the last checkpoint. A supercomputer is more like a single-node computer than a distributed system: it deals with partial failure by letting it escalate into total failure. Cloud computing (a not-very-well-defined term) is associated with multi-tenant datacenters, commodity computers connected with an IP network (often Ethernet), elastic/on-demand resource allocation, and metered billing. Traditional enterprise datacenters lie somewhere between the two extremes.

Why internet services can’t follow the supercomputer model — six reasons:

1.

Online vs. offline

Internet applications are online — they must serve users with low latency at any time, and stopping the cluster for repair is not acceptable. An offline batch job like a weather simulation can stop and restart with fairly low impact.

2.

Hardware reliability

Supercomputers use specialized, quite-reliable nodes communicating through shared memory and RDMA. Cloud services use commodity machines — equivalent performance at lower cost through economies of scale, but higher failure rates.

3.

Network topology

Large datacenter networks run IP and Ethernet in Clos topologies for high bisection bandwidth. Supercomputers use specialized multi-dimensional meshes and toruses, better for HPC workloads with known communication patterns.

4.

Scale and fault probability

The bigger a system gets, the more likely one of its components is broken. With thousands of nodes, it’s reasonable to assume something is always broken — and if your error handling is “give up,” the system spends more time recovering from faults than doing useful work.

5.

Fault tolerance pays off

If the system tolerates failed nodes and keeps working as a whole, you get rolling upgrades — restart one node at a time while the service continues — and in the cloud, you can kill a poorly-performing VM and request a new one.

6.

Geographic distribution

Geographically distributed deployments communicate over the internet — slow and unreliable compared to local networks. Supercomputers generally assume all nodes are close together.

The conclusion: to make distributed systems work, we must accept the possibility of partial failure and build fault-tolerance mechanisms into the software — a reliable system from unreliable components. Fault handling must be part of the software design, and you as the operator need to know what behavior to expect in the case of a fault. It would be unwise to assume faults are rare and simply hope for the best: consider a wide range of possible faults — even fairly unlikely ones — and artificially create them in your testing environment to see what happens. In distributed systems, suspicion, pessimism, and paranoia pay off.

8.0.3 — Building a reliable system from unreliable components

Intuitively, a system can only be as reliable as its least reliable component — its weakest link. This is not the case, and it’s an old idea in computing (von Neumann, 1956) to construct a more reliable system from a less reliable underlying base:

1.

Error-correcting codes

Let digital data be transmitted accurately across a communication channel that occasionally gets some bits wrong — radio interference on a wireless network, for example.

2.

TCP over IP

IP itself is unreliable — it may drop, delay, duplicate, or reorder packets. TCP provides a more reliable transport layer on top: missing packets retransmitted, duplicates eliminated, packets reassembled in order.

But there are limits to how much more reliable the system can be. Error-correcting codes handle a small number of single-bit errors, not a signal swamped by interference. TCP hides packet loss, duplication, and reordering — but it cannot magically remove delays in the network. The higher-level system isn’t perfect, but it’s still useful: it takes care of the tricky low-level faults, so the remaining faults are usually easier to reason about and deal with.

8.1 · Liar #1

Unreliable networks

The book focuses on shared-nothing systems: a bunch of machines, each with its own memory and disk, connected by a network — the only way those machines can communicate. It’s the dominant approach for building internet services because it’s comparatively cheap (no special hardware), can make use of commoditized cloud computing services, and can achieve high reliability through redundancy across multiple geographically distributed datacenters.

The internet and most internal datacenter networks (often Ethernet) are asynchronous packet networks: one node can send a message to another, but the network gives no guarantees as to when it will arrive, or whether it will arrive at all. So if you send a request and don’t get a response, any of six things may have happened:

8.1.1 — Six ways a request can fail

1.

Request lost

Your request may have been lost — perhaps someone unplugged a network cable.

2.

Request queued

Your request may be waiting in a queue and will be delivered later — perhaps the network or the recipient is overloaded.

3.

Remote node failed

The remote node may have failed — perhaps it crashed or was powered down.

4.

Remote node stalled

The remote node may have temporarily stopped responding — perhaps a long garbage collection pause — but it will start responding again later.

5.

Response lost

The remote node may have processed your request, but the response has been lost on the network — perhaps a switch has been misconfigured.

6.

Response delayed

The remote node may have processed your request, but the response is delayed and will be delivered later — perhaps the network or your own machine is overloaded.

Figure 8-1 (recreated) · Lost, dead, or slow — you can’t tell

The sender can’t even tell whether the packet was delivered: the only option is for the recipient to send a response message, which may in turn be lost or delayed. The usual remedy is a timeout: after some time you give up waiting and assume the response is not going to arrive. But when the timeout fires, you still don’t know whether the remote node got your request — and if it’s still queued somewhere, it may yet be delivered even after you’ve given up on it.

8.1.2 — Network faults in practice

We have been building computer networks for decades — one might hope we’d have figured out reliability by now. We have not:

12 Network faults per month, one medium-sized datacenter study half disconnected a single machine · half disconnected an entire rack
> 1 min Packet delays from one switch software upgrade topology reconfiguration — the network “worked,” just very slowly
1-way A NIC that dropped all inbound packets but sent outbound fine a link working in one direction says nothing about the other direction

Studies measuring top-of-rack switches, aggregation switches, and load balancers found that adding redundant networking gear doesn’t reduce faults as much as you might hope, because it doesn’t guard against human error — misconfigured switches are a major cause of outages. Public cloud services such as EC2 are notorious for frequent transient network glitches; well-managed private datacenter networks can be stabler environments, but nobody is immune from network problems. Sharks have even been known to bite and damage undersea cables.

If the error handling of network faults is not defined and tested

Arbitrarily bad things could happen: a cluster could become deadlocked and permanently unable to serve requests, even when the network recovers — or it could even delete all of your data. If software is put in an unanticipated situation, it may do arbitrary unexpected things.

Handling network faults doesn’t necessarily mean tolerating them — if the network is normally reliable, showing users an error message during a rare outage is a valid response. But you do need to know how your software reacts to network problems, and to ensure the system can recover from them — which is why deliberately triggering network problems and testing the response (the idea behind Chaos Monkey) makes sense. One vocabulary note: when one part of the network is cut off from the rest due to a network fault, that’s a network partition (or netsplit); the book sticks with the more general term network fault to avoid confusion with partitions (shards) of a storage system.

8.1.3 — Detecting faults

Many systems need to automatically detect faulty nodes: a load balancer needs to stop sending requests to a dead node (take it out of rotation), and in a distributed database with single-leader replication, a failed leader means one of the followers needs to be promoted. Unfortunately, the uncertainty about the network makes it difficult to tell whether a node is working. Rapid, explicit feedback exists sometimes — situational, not always available:

1.

The OS refuses the connection

If you can reach the machine but no process is listening on the destination port, the OS closes or refuses the TCP connection (an RST or FIN in reply). But if the node crashed while handling your request, you have no way of knowing how much of the data was actually processed.

2.

Scripted crash notification

If the node process crashed (or was killed by an administrator) but the OS still runs, a script can notify the other nodes about the crash so another can take over quickly, without waiting for a timeout — HBase does this.

3.

Switch management interface

If you have access to the network switches in your datacenter, you can query them to detect link failures at the hardware level (e.g., a remote machine powered down). Ruled out when connecting via the internet, in a shared datacenter, or when the management interface is itself unreachable.

4.

ICMP Destination Unreachable

A router that is sure an IP address is unreachable may reply with an ICMP Destination Unreachable packet. But routers have no magic failure-detection capability — they are subject to the same network limitations as everyone else.

Rapid feedback about a remote node being down is useful, but you can’t count on it. Even if TCP acknowledges that a packet was delivered, the application may have crashed before handling it. If you want to be sure a request was successful, you need a positive response from the application itself; conversely, if something has gone wrong, you may get an error response at some level of the stack, but in general you must assume you’ll get no response at all. In practice: retry a few times (TCP retries transparently, and you may also retry at the application level), wait for a timeout, and eventually declare the node dead if you don’t hear back.

8.1.4 — Timeouts and unbounded delays

If a timeout is the only sure way of detecting a fault, then how long should the timeout be? There is unfortunately no simple answer. A long timeout means a long wait until a node is declared dead — users have to wait, or see error messages. A short timeout detects faults faster, but carries a higher risk of incorrectly declaring a node dead when in fact it has only suffered a temporary slowdown, due to a load spike on the node or the network. And prematurely declaring a node dead is problematic: if the node is actually alive and in the middle of performing some action — sending an email, say — and another node takes over, the action may end up being performed twice.

Worse: when a node is declared dead, its responsibilities are transferred to other nodes, adding load to nodes and network that are already struggling. If a node was merely slow due to overload, transferring its load elsewhere can make everything collapse — in the extreme case, all nodes declare each other dead and everything stops working: a cascading failure.

Imagine a fictitious system whose network guaranteed a maximum delay for packets: every packet is delivered within time d, or it is lost — delivery never takes longer. Assume every non-failed node always handles a request within time r. Then every successful request receives a response within 2d + r, and if you don’t receive a response within that time, you know the network or the node is not working. 2d + r would be a reasonable timeout. Unfortunately, most systems we work with have neither guarantee. Asynchronous networks have unbounded delays — they try to deliver packets as quickly as possible, but there is no upper limit on the time it may take for a packet to arrive — and most server implementations cannot guarantee they handle requests within some maximum time. For failure detection, it’s not sufficient for the system to be fast most of the time: if your timeout is low, it only takes a transient spike in round-trip times to throw the system off balance.

8.1.5 — Network congestion and queueing

The variability of packet delays on computer networks is most often due to queueing — just as travel times on road networks vary mostly due to traffic congestion. Four places your packet waits:

1.

The network switch

If several different nodes simultaneously try to send packets to the same destination, the switch must queue them and feed them into the destination link one by one. On a busy link a packet may wait a while for a slot — and if so much data arrives that the switch queue fills up, the packet is dropped and needs to be resent, even though the network is functioning fine.

2.

The destination OS

When a packet reaches the destination machine and all CPU cores are currently busy, the incoming request is queued by the operating system until the application is ready to handle it — which may take an arbitrary length of time depending on the machine’s load.

3.

The virtual machine monitor

In virtualized environments, a running OS is often paused for tens of milliseconds while another virtual machine uses a CPU core. During that time the VM cannot consume any data from the network, so incoming data is queued (buffered) by the VM monitor, further increasing the variability of delays.

4.

The TCP sender itself

TCP performs flow control (also known as congestion avoidance or backpressure): a node limits its own rate of sending to avoid overloading a network link or the receiving node — meaning additional queueing at the sender, before the data even enters the network.

Figure 8-2 (recreated) · The switch queue fills up

TCP considers a packet lost if it is not acknowledged within some timeout, calculated from observed round-trip times, and retransmits lost packets automatically. The application does not see the packet loss or the retransmission — but it does see the resulting delay (waiting for the timeout to expire, then for the retransmission to be acknowledged). And queueing delays have an especially wide range when a system is close to its maximum capacity: a system with plenty of spare capacity drains queues easily; in a highly utilized system, long queues can build up very quickly.

8.1.6 — TCP versus UDP

Some latency-sensitive applications — videoconferencing, VoIP — use UDP rather than TCP, trading reliability for consistency of delays. UDP does not perform flow control and does not retransmit lost packets, avoiding some reasons for variable network delays (though it is still susceptible to switch queues and scheduling delays). It’s a good choice when delayed data is worthless: in a VoIP phone call there isn’t enough time to retransmit a lost packet before its data is due to be played over the loudspeakers, so the application fills the missing packet’s time slot with silence — a brief interruption — and moves on in the stream. The retry happens at the human layer: “Could you repeat that please? The sound just cut out for a moment.”

8.1.7 — Synchronous versus asynchronous networks

Why can’t we solve this at the hardware level and make the network reliable so the software doesn’t need to worry? The traditional fixed-line telephone network (non-cellular, non-VoIP) is extremely reliable — delayed audio frames and dropped calls are very rare, because a phone call requires constantly low end-to-end latency and enough bandwidth to transfer your voice. When you make a call, the network establishes a circuit: a fixed, guaranteed amount of bandwidth allocated for the call, along the entire route between the two callers, remaining in place until the call ends. An ISDN network runs at a fixed rate of 4,000 frames per second; when a call is established, it is allocated 16 bits of space within each frame in each direction — so for the whole call, each side is guaranteed to send exactly 16 bits of audio every 250 microseconds.

That kind of network is synchronous: even as data passes through several routers, it does not suffer from queueing, because the space for the call has already been reserved at the next hop. No queueing means a fixed maximum end-to-end latency — a bounded delay. A circuit is fundamentally different from a TCP connection: it is a fixed amount of reserved bandwidth that nobody else can use while it is established, whereas packets of a TCP connection opportunistically use whatever bandwidth is available — you can give TCP a variable-sized block of data (an email, a web page) and it will transfer it in the shortest time possible, and while a TCP connection is idle it uses essentially no bandwidth. Ethernet and IP are packet-switched protocols: no concept of a circuit, hence queueing and unbounded delays.

Why did data networks choose packet switching? Because data traffic is bursty. A call needs a constant bits-per-second rate, which suits a circuit. But requesting a web page, sending an email, or transferring a file has no particular bandwidth requirement — you just want it to complete as quickly as possible. Over a circuit you would have to guess a bandwidth allocation: guess too low and the transfer is unnecessarily slow, leaving network capacity unused; guess too high and the circuit cannot be set up at all, because the network cannot guarantee a reservation it can’t fulfill. TCP, by contrast, dynamically adapts the rate of data transfer to the available network capacity. Hybrids exist — ATM (Asynchronous Transfer Mode) tried to support both circuit and packet switching; InfiniBand implements end-to-end flow control at the link layer; quality of service (prioritization and scheduling of packets) and admission control (rate-limiting senders) can emulate circuit switching or provide statistically bounded delay — but such quality of service is currently not enabled in multi-tenant datacenters and public clouds, or when communicating via the internet.

8.1.8 — Latency and resource utilization

Variable delays are a consequence of dynamic resource partitioning. A wire between two telephone switches can carry up to 10,000 simultaneous calls; each circuit occupies one of those call slots, and the resource is divided statically — even if you’re the only call on the wire, with all other 9,999 slots unused, your circuit gets the same fixed bandwidth as when the wire is fully utilized. The internet shares network bandwidth dynamically: senders push and jostle to get their packets over the wire as quickly as possible, and the switches decide moment to moment which packet goes. Downside: queueing. Advantage: maximum utilization of the wire — it has a fixed cost, so better utilization makes each byte cheaper. The same trade-off appears with CPUs: sharing each core dynamically between several threads means a thread sometimes waits in the OS’s run queue while another runs — but it utilizes the hardware better than statically allocated CPU cycles, and it’s also a major motivation for virtual machines.

The economic punchline

Latency guarantees are achievable in certain environments if resources are statically partitioned — dedicated hardware, exclusive bandwidth allocations — but it comes at the cost of reduced utilization, in other words, it is more expensive. Multi-tenancy with dynamic resource partitioning provides better utilization, so it is cheaper, but it has the downside of variable delays. Variable delays in networks are not a law of nature, but simply the result of a cost/benefit trade-off. Most non-safety-critical systems choose cheap and unreliable over expensive and reliable.

The practical conclusion: currently deployed technology gives us no guarantees about network delays or reliability, so we have to assume congestion, queueing, and unbounded delays will happen — and consequently there is no “correct” value for timeouts. They need to be determined experimentally, by measuring the distribution of network round-trip times over an extended period.

8.2 · Liar #2

Unreliable clocks

Clocks and time are important. Applications depend on them for everyday questions: Has this request timed out yet? What’s the 99th percentile response time of this service? How many queries per second did this service handle on average in the last five minutes? How long did the user spend on our site? When was this article published? At what date and time should the reminder email be sent? When does this cache entry expire? What is the timestamp on this error message in the log file? Note the split: the first four measure durations (a time interval, e.g., between a request being sent and its response received); the last four describe points in time (events that occur on a particular date, at a particular time).

In a distributed system, time is tricky because communication is not instantaneous: the time a message is received is always later than the time it was sent, and due to variable network delays we don’t know how much later — which sometimes makes it difficult to determine the order in which things happened across machines. And each machine has its own clock, an actual hardware device — usually a quartz crystal oscillator — that is not perfectly accurate, so every node has its own notion of time, slightly faster or slower than the others.

8.2.1 — Monotonic versus time-of-day clocks

Modern computers have at least two different kinds of clocks, and it’s important to distinguish them since they serve different purposes:

Time-of-day clock wall-clock

Returns the current date and time according to some calendar: clock_gettime(CLOCK_REALTIME) on Linux, System.currentTimeMillis() in Java. The value is the number of seconds or milliseconds since the epoch — midnight UTC on January 1, 1970, Gregorian calendar, leap seconds not counted. Usually synchronized with NTP, so timestamps from one machine (ideally) mean the same as on another.

  • If the local clock is too far ahead of the NTP server, it may be forcibly reset, appearing to jump back to a previous point in time
  • These jumps, and the habit of ignoring leap seconds, make it unsuitable for measuring elapsed time
  • Historically quite coarse-grained (steps of 10 ms on older Windows systems); less of a problem on recent systems

Monotonic clock durations

The right tool for measuring a duration — a timeout, a service’s response time: clock_gettime(CLOCK_MONOTONIC) on Linux, System.nanoTime() in Java. The name comes from the guarantee that it always moves forward (a time-of-day clock may jump back).

  • The absolute value is meaningless — perhaps nanoseconds since the computer started — so it makes no sense to compare monotonic values from two different computers
  • Multi-socket servers may have a separate timer per CPU; the OS compensates, but take the monotonicity guarantee “with a pinch of salt”
  • NTP may slew the rate — speeding it up or slowing it down by up to 0.05% — but can never make it jump; resolution is usually microseconds or better
  • For measuring elapsed time in a distributed system (e.g., timeouts), usually fine: no cross-node synchronization assumed

8.2.2 — Clock synchronization and accuracy

Monotonic clocks don’t need synchronization, but time-of-day clocks must be set according to an NTP server (which gets its time from a more accurate source, such as a GPS receiver) to be useful. Unfortunately, “our methods for getting a clock to tell the correct time aren’t nearly as reliable or accurate as you might hope — hardware clocks and NTP can be fickle beasts.” Eight ways it goes wrong:

1.

Quartz drift

The quartz clock runs faster or slower than it should, varying with the machine’s temperature. Google assumes a drift of 200 ppm (parts per million) for its servers — up to 6 ms for a clock resynchronized every 30 seconds, or 17 seconds for one resynchronized once a day. This limits the best possible accuracy even when everything works correctly.

2.

Refusal and forced resets

If a computer’s clock differs too much from the NTP server, the server may refuse to synchronize, or the local clock will be forcibly reset — applications observing the time before and after may see time go backward or suddenly jump forward.

3.

Firewalled off from NTP

If a node is accidentally firewalled off from its NTP servers, the misconfiguration may go unnoticed for some time — anecdotal evidence says this does happen in practice.

4.

The network is the limit

NTP synchronization can only be as good as the network delay. One experiment showed a minimum error of 35 ms when synchronizing over the internet; occasional spikes in network delay lead to errors of around a second, and large delays can make the client give up entirely.

5.

Wrong NTP servers

Some NTP servers are wrong or misconfigured, reporting time off by hours. Clients are quite robust — they query several servers and ignore outliers — but “it’s somewhat worrying to bet the correctness of your systems on the time that you were told by a stranger on the internet.”

6.

Leap seconds

A minute that is 59 or 61 seconds long messes up timing assumptions and has crashed many large systems. Best fix may be smearing: making NTP servers “lie” by performing the leap second adjustment gradually over the course of a day. Actual server behavior varies in practice.

7.

Virtual machines

The hardware clock is virtualized, and when a CPU core is shared between VMs, each is paused for tens of milliseconds while another runs — from the application’s point of view, the clock suddenly jumps forward.

8.

Devices you don’t fully control

On mobile or embedded devices, you probably can’t trust the hardware clock at all — some users deliberately set it to a wildly incorrect time, for example to circumvent timing limitations in games.

Very good accuracy is possible if you care enough to invest significant resources: the MiFID II draft European regulation requires all high-frequency trading funds to synchronize clocks to within 100 microseconds of UTC — to help debug market anomalies like “flash crashes” and detect manipulation. That can be achieved with GPS receivers, the Precision Time Protocol (PTP), and careful deployment and monitoring, but it requires significant effort and expertise; a misconfigured NTP daemon or a blocking firewall can let drift grow quickly.

8.2.3 — Relying on synchronized clocks

The problem with clocks: while they seem simple and easy to use, they have a surprising number of pitfalls — a day may not have exactly 86,400 seconds, time-of-day clocks may move backward, and the time on one node may be quite different from the time on another. The parallel with networks is exact: even though networks are well behaved most of the time, software must be designed on the assumption that the network will occasionally be faulty — and the same is true of clocks. The nastiest part: incorrect clocks easily go unnoticed. A defective CPU or misconfigured network makes a machine fail loudly and get fixed; a defective quartz or misconfigured NTP client keeps “working fine” while drifting further and further from reality — and software relying on an accurately synchronized clock tends to fail as silent, subtle data loss, not a dramatic crash. If you use software that requires synchronized clocks, it is essential to carefully monitor clock offsets between all the machines, and declare dead and remove any node whose clock drifts too far from the others.

8.2.4 — Timestamps for ordering events: LWW loses data

If two clients write to a distributed database, who got there first — which write is the more recent? Tagging each write with a timestamp from the time-of-day clock of the node where it originated, and keeping the newest value, is called last write wins (LWW) — widely used in multi-leader replication and leaderless databases such as Cassandra and Riak. (Some implementations generate timestamps on the client rather than the server; the fundamental problems don’t change.) Here is the failure:

Figure 8-3 (recreated) · Two clocks disagree, and the increment is lost

When a write is replicated to other nodes, it is tagged with a timestamp according to the originating node’s time-of-day clock. The clock synchronization here is very good — node 1 and node 3 are skewed by less than 3 ms — yet the timestamps fail to order the events correctly: the write x = 1 carries timestamp 42.004 s while the causally-later write x = 2 carries 42.003 s. When node 2 receives both, it concludes that x = 1 is the more recent value and drops the write x = 2. Client B’s increment is silently lost.

Three problems with LWW, beyond the figure:

1.

Writes mysteriously disappear

A node with a lagging clock is unable to overwrite values previously written by a node with a fast clock until the clock skew between the nodes has elapsed. Arbitrary amounts of data can be silently dropped — without any error reported to the application.

2.

Sequential vs. concurrent — can’t tell

LWW cannot distinguish writes that occurred sequentially in quick succession (client B’s increment definitely occurs after client A’s write) from writes that were truly concurrent. Additional causality tracking, such as version vectors, is needed to prevent violations of causality.

3.

Timestamp ties

Two nodes can independently generate writes with the same timestamp — especially when the clock has only millisecond resolution. An arbitrary tiebreaker (which can simply be a large random number) is required, but that approach can also violate causality.

Could NTP synchronization be made accurate enough that such incorrect orderings cannot occur? Probably not. NTP’s accuracy is itself limited by the network round-trip time, in addition to other error sources like quartz drift — and for correct ordering you need the clock source to be significantly more accurate than the thing you are measuring, namely network delay. Even with tightly NTP-synchronized clocks you can send a packet at timestamp 100 ms (by the sender’s clock) and have it arrive at timestamp 99 ms (by the recipient’s clock) — it appears to arrive before it was sent, which is impossible. The safer alternative for ordering events is logical clocks, based on incrementing counters rather than an oscillating quartz crystal: they don’t measure the time of day or the seconds elapsed, only the relative ordering of events. Time-of-day and monotonic clocks, which measure actual elapsed time, are together known as physical clocks.

8.2.5 — Clock readings have a confidence interval

You may be able to read a machine’s time-of-day clock with microsecond or even nanosecond resolution — but that doesn’t mean the value is actually accurate to such precision. Drift in an imprecise quartz clock can easily be several milliseconds, even if synchronized with NTP on the local network every minute. With NTP over the public internet, the best possible accuracy is probably to the tens of milliseconds, and the error may easily spike to over 100 ms with network congestion. A clock reading isn’t a point in time — it is more like a range of times, a confidence interval. A system may be 95% confident that the time now is between 10.3 and 10.5 seconds past the minute, but it doesn’t know any more precisely than that. If you only know the time ±100 ms, the microsecond digits in the timestamp are essentially meaningless. Unfortunately, most systems don’t expose this uncertainty: clock_gettime() returns a value with no expected error, so you don’t know whether its confidence interval is five milliseconds or five years.

8.2.6 — Synchronized clocks for global snapshots: Spanner and TrueTime

Snapshot isolation is a very useful feature for databases that need both small, fast read-write transactions and large, long-running read-only ones (backups, analytics): read-only transactions see the database in a consistent state at a particular point in time. The most common implementation requires a monotonically increasing transaction ID — writes with a greater ID than the snapshot are invisible to it. On a single-node database, a simple counter suffices. But when the database is distributed across many machines, potentially in multiple datacenters, a globally monotonically increasing transaction ID is difficult to generate, because it requires coordination — and the ID must reflect causality (if transaction B reads a value written by transaction A, B must have a higher ID, or the snapshot isn’t consistent). With lots of small, rapid transactions, this becomes an untenable bottleneck. So: can the timestamps from synchronized time-of-day clocks serve as transaction IDs? If the synchronization were good enough, they’d have the right properties — later transactions get higher timestamps. The problem is the uncertainty about clock accuracy.

Google Spanner implements snapshot isolation across datacenters exactly this way, using the clock’s confidence interval as reported by its TrueTime API — which explicitly returns two values, an earliest and a latest possible timestamp, instead of a point. The key observation: if two confidence intervals A = [Aearliest, Alatest] and B = [Bearliest, Blatest] do not overlap, then B definitely happened after A — no doubt about it. Only if the intervals overlap are we unsure of the order. So Spanner deliberately waits for the length of the confidence interval before committing a read-write transaction, ensuring any transaction that may read the data is at a sufficiently later time that the intervals don’t overlap. And to keep that wait short, it keeps the clock uncertainty small:

7 ms Clock uncertainty inside Google datacenters a GPS receiver or atomic clock in each DC — keeps Spanner’s commit wait short
[earliest, latest] What TrueTime returns instead of a point the interval’s width depends on how long since the local quartz was last synced to a better clock

Using clock synchronization for distributed transaction semantics is an area of active research — the ideas are interesting, but they have not yet been implemented in mainstream databases outside of Google.

8.2.7 — Process pauses

One more dangerous use of clocks. Consider a database with a single leader per partition, where only the leader is allowed to accept writes. How does a node know that it still is the leader — that it hasn’t been declared dead by the others — and that it may safely accept writes? One option is for the leader to obtain a lease from the other nodes, similar to a lock with a timeout: only one node can hold the lease at any one time; when a node obtains it, it knows it is the leader for some amount of time, until the lease expires; to remain leader, it must periodically renew the lease before expiry. If the node fails, it stops renewing, and another can take over when the lease expires:

while (true) { request = getIncomingRequest(); // Ensure that the lease always has at least 10 seconds remaining if (lease.expiryTimeMillis - System.currentTimeMillis() < 10000) { lease = lease.renew(); } if (lease.isValid()) { process(request); } }

Two problems with this code. First, it depends on synchronized clocks: the lease’s expiry time is set by a different machine (perhaps calculated there as current time plus 30 seconds) but compared to the local system clock — if the clocks are out of sync by more than a few seconds, this code will start doing strange things. Second, and more fundamentally, process pauses: even switching the protocol to use only the local monotonic clock doesn’t fix it. The code assumes very little time passes between the point it checks the time and the point the request is processed. Normally it runs so quickly that the 10-second buffer is more than enough. But what if there is an unexpected pause — the thread stops for 15 seconds right around the lease.isValid() line before continuing? The lease will likely have expired by the time the request is processed, and another node has already taken over as leader. There is nothing to tell this thread that it was paused for so long — it won’t notice the lease has expired until the next iteration of the loop, by which time it may have already done something unsafe. Six reasons a thread might be paused:

1.

Garbage collection

Stop-the-world GC pauses have sometimes been known to last for several minutes. Even so-called “concurrent” collectors like HotSpot JVM’s CMS cannot fully run in parallel with the application — they, too, must stop the world from time to time. Tuning helps, but for robust guarantees, assume the worst.

2.

Virtual machine suspension

A VM can be suspended (pausing all processes and saving memory to disk) and resumed (restoring memory and continuing execution) — sometimes used for live migration of VMs between hosts without a reboot. The pause can occur at any time and last arbitrarily long.

3.

End-user device suspension

On laptops, execution may be suspended and resumed arbitrarily — when the user closes the lid.

4.

OS context switching

When the OS context-switches to another thread, or the hypervisor switches to a different VM, the running thread can be paused at any arbitrary point in the code. (CPU time spent in other VMs is known as steal time.) Under heavy load, it may take a while before the paused thread runs again.

5.

Synchronous disk access

A thread may pause waiting for slow disk I/O — which can happen surprisingly, e.g., Java classloaders lazily loading class files at any point in execution. If the disk is actually a network filesystem or network block device (such as Amazon’s EBS), the latency is further subject to network variability. I/O pauses and GC pauses may even conspire to combine their delays.

6.

Swapping to disk (paging)

A simple memory access may trigger a page fault requiring a page from disk — possibly evicting another page first. Under memory pressure the OS may spend most of its time swapping pages in and out, getting little done (thrashing) — which is why paging is often disabled on server machines.

And one more: a Unix process can be paused with the SIGSTOP signal (Ctrl-Z in a shell) and gets no CPU again until SIGCONT — even if your environment never uses it deliberately, it might be sent accidentally by an operations engineer. The common thread: all of these occurrences can preempt the running thread at any point and resume it at some later time, without the thread even noticing. It’s like making multi-threaded code on a single machine thread-safe — you can’t assume anything about timing, because arbitrary context switches and parallelism may occur. On a single machine we have decent tools for that (mutexes, semaphores, atomic counters, lock-free data structures, blocking queues), but they don’t translate to distributed systems, which have no shared memory — only messages over an unreliable network. So: a node must assume that its execution can be paused for a significant length of time at any point, even in the middle of a function. During the pause, the rest of the world keeps moving and may even declare the paused node dead because it’s not responding. Eventually it resumes — without even noticing it was asleep, until it checks its clock sometime later.

8.2.8 — Response time guarantees, and limiting GC’s impact

Those reasons for pausing can be eliminated if you try hard enough, and some software runs where failure to respond in time causes serious damage: computers that control aircraft, rockets, robots, cars, and other physical objects. These have a specified deadline by which the software must respond — miss it, and the entire system may fail. These are hard real-time systems: “if your car’s onboard sensors detect that you are currently experiencing a crash, you wouldn’t want the release of the airbag to be delayed due to an inopportune GC pause.” Delivering on that requires:

  • A real-time operating system (RTOS) that allows processes to be scheduled with a guaranteed allocation of CPU time in specified intervals
  • Library functions that document their worst-case execution times
  • Dynamic memory allocation restricted or disallowed entirely (real-time garbage collectors exist, but the application must still ensure it doesn’t give the GC too much to do)
  • An enormous amount of testing and measurement to ensure the guarantees are being met

All of this requires a large amount of additional work and severely restricts the range of languages, libraries, and tools. Developing real-time systems is very expensive; they mostly appear in safety-critical embedded devices. And “real-time” is not “high-performance”: real-time systems may actually have lower throughput, since they must prioritize timely responses above all else. For most server-side data processing, real-time guarantees are simply not economical or appropriate — so those systems must suffer the pauses and clock instability of a non-real-time environment. What you can do is mitigate GC pauses without real-time scheduling:

1.

Treat GC pauses as brief planned outages

Let other nodes handle requests while one node is collecting its garbage. If the runtime can warn that a GC pause is soon required, the node can stop sending new requests, wait for outstanding requests to finish, then perform GC while no requests are in progress — hiding the pause from clients and reducing the high percentiles of response time. Some latency-sensitive financial trading systems use this approach.

2.

GC only short-lived objects, restart periodically

Use GC only for short-lived objects (fast to collect) and restart processes periodically, before they accumulate enough long-lived objects to require a full GC. Restart one node at a time with traffic shifted away first — like a rolling upgrade.

These measures can’t fully prevent garbage collection pauses, but they usefully reduce their impact on the application.

8.3 · Liar #3

Knowledge, truth, and lies

Put the chapter so far together: no shared memory, only message passing over an unreliable network with variable delays, partial failures, unreliable clocks, and processing pauses. It follows that a node in the network cannot know anything for sure — it can only make guesses based on the messages it receives (or doesn’t receive) via the network. A node can only find out what state another node is in by exchanging messages with it; if the remote node doesn’t respond, there is no way of knowing what state it is in, because network problems cannot reliably be distinguished from node problems. The questions border on the philosophical — what do we know to be true or false, how sure can we be if our mechanisms for perception and measurement are unreliable, should software systems obey the laws we expect of the physical world, such as cause and effect? The practical answer is enough: state your assumptions as a system model, and design the system so it meets them. Algorithms can be proved to function correctly within a certain system model — reliable behavior is achievable even when the underlying model provides very few guarantees. It is, however, not straightforward to do so.

8.3.1 — The truth is defined by the majority

Imagine a network with an asymmetric fault: a node is able to receive all messages sent to it, but any outgoing messages from that node are dropped or delayed. The node works perfectly well and is receiving requests from other nodes — but nobody can hear its responses. After a timeout, the other nodes declare it dead. “The semi-disconnected node is dragged to the graveyard, kicking and screaming ‘I’m not dead!’ — but since nobody can hear its screaming, the funeral procession continues with stoic determination.” The node may even notice its messages aren’t being acknowledged and realize there must be a fault in the network — but it is still wrongly declared dead. Or the third scenario: a node experiences a long stop-the-world GC pause — every thread frozen for one minute, no requests processed, no responses sent. The other nodes wait, retry, grow impatient, and declare it dead. Then the GC finishes, and the threads continue as if nothing had happened — “the supposedly dead node suddenly raises its head out of the coffin, in full health, and starts cheerfully chatting with bystanders.” From the GCing node’s perspective, hardly any time has passed since it was last talking to the others.

The moral: a node cannot necessarily trust its own judgment of a situation — and a distributed system cannot exclusively rely on a single node, which may fail at any time and leave the system stuck. So many distributed algorithms rely on a quorum: voting among the nodes, with decisions requiring some minimum number of votes from several nodes — including decisions about declaring nodes dead. If a quorum of nodes declares another node dead, then it must be considered dead, even if that node still very much feels alive — the individual node must abide by the quorum decision and step down. Most commonly, the quorum is an absolute majority of more than half the nodes: with three nodes, one failure can be tolerated; with five nodes, two. And it remains safe, because there can only be one majority in the system — there cannot be two majorities with conflicting decisions at the same time.

8.3.2 — The leader and the lock

Frequently, a system requires there to be only one of some thing: only one node allowed to be the leader for a database partition (avoiding split brain); only one transaction or client allowed to hold the lock for a particular resource or object (preventing concurrent writes from corrupting it); only one user allowed to register a particular username (a username must uniquely identify a user). Implementing this in a distributed system requires care: even if a node believes it is “the chosen one” — the leader, the lock holder, the first to grab the username — that doesn’t necessarily mean a quorum of nodes agrees. The node may have formerly been the leader, but if the others declared it dead in the meantime (a network interruption, a GC pause), it may already have been demoted and a new leader elected. If it keeps acting as the chosen one and other nodes believe it, the system as a whole may do something incorrect:

Figure 8-4 (recreated) · The stale lease that corrupts a file

The client holding the lease is paused for too long, its lease expires, another client obtains a lease for the same file and starts writing — and when the paused client comes back, it still believes it holds a valid lease and proceeds to write as well. The clients’ writes clash and corrupt the file. Not theoretical: HBase used to have exactly this problem.

8.3.3 — Fencing tokens

The fix for a node under a false belief of being “the chosen one” — so it cannot disrupt the rest of the system — is a fairly simple technique called fencing. Every time the lock server grants a lock or lease, it also returns a fencing token: a number that increases every time a lock is granted. Every time a client sends a write request to the storage service, it must include its current fencing token. The storage server remembers the highest token it has already processed and rejects any write with an older one:

Figure 8-5 (recreated) · Writes only in order of increasing fencing tokens

Client 1 acquires the lease with a token of 33, then goes into a long pause and the lease expires. Client 2 acquires the lease with a token of 34 — the number always increases — and sends its write, including the token, which the storage accepts. Later, client 1 comes back to life and sends its write with token 33; the storage server, having already processed a write with token 34, rejects it.

If ZooKeeper is used as the lock service, the transaction ID zxid or the node version cversion can serve as the fencing token, since both are guaranteed to be monotonically increasing. The critical requirement: the resource itself must take an active role in checking tokens, rejecting any writes with an older token than one already processed. It is not sufficient to rely on clients checking their own lock status — the paused client doesn’t know its lease expired; that’s the whole problem. For resources that don’t explicitly support fencing tokens, workarounds exist (e.g., include the token in the filename for a file storage service) — but some kind of check is necessary to avoid processing requests outside the lock’s protection.

Server-side checking is a feature, not a bug

Checking a token on the server side may seem like a downside, but it is arguably a good thing. It is unwise for a service to assume that its clients will always be well behaved — the clients are often run by people whose priorities are very different from those of the service’s operators (at the launch of Halo 4, clients effectively DDoSed the services). Any good service should protect itself from accidentally abusive clients.

8.3.4 — Byzantine faults

Fencing tokens can detect and block a node that is inadvertently acting in error — but a node that deliberately wanted to subvert the system’s guarantees could simply send messages with a fake fencing token. In this book we assume nodes are unreliable but honest: they may be slow or never respond, their state may be outdated — but if a node does respond, it is telling the “truth” as best it knows it, playing by the rules of the protocol. Distributed systems problems become much harder if there is a risk that nodes may “lie” — send arbitrary faulty or corrupted responses, for example claiming to have received a particular message when it didn’t. Such behavior is a Byzantine fault, and the problem of reaching consensus in this untrusting environment is the Byzantine Generals Problem.

The Byzantine Generals Problem generalizes the older Two Generals Problem: two army generals need to agree on a battle plan, communicating only by messenger — and the messengers sometimes get delayed or lost, exactly like packets in a network. The Byzantine version: there are n generals who need to agree, most of them loyal and sending truthful messages — but there are traitors among them, who may try to deceive and confuse the others by sending fake or untrue messages while trying to remain undiscovered. And it is not known in advance who the traitors are.

Why “Byzantine”?

Byzantium was an ancient Greek city that later became Constantinople, on the site of present-day Istanbul — and there’s no historic evidence that the generals of Byzantium were any more prone to intrigue and conspiracy than those elsewhere. The name comes from “Byzantine” in the sense of excessively complicated, bureaucratic, devious — used in politics long before computers. Lamport wanted a nationality that wouldn’t offend any readers, and was advised that calling it “The Albanian Generals Problem” was not such a good idea.

A system is Byzantine fault-tolerant if it continues to operate correctly even if some nodes are malfunctioning and not obeying the protocol, or if malicious attackers are interfering with the network. Where that concern is real:

1.

Aerospace environments

Data in a computer’s memory or CPU registers could become corrupted by radiation, leading a node to respond in arbitrarily unpredictable ways. Since a system failure would be very expensive — an aircraft crashing and killing everyone on board, a rocket colliding with the ISS — flight control systems must tolerate Byzantine faults.

2.

Multi-organization systems

Some participants may attempt to cheat or defraud the others, so it isn’t safe to simply trust another node’s messages. Peer-to-peer networks like Bitcoin and other blockchains can be considered a way of getting mutually untrusting parties to agree whether a transaction happened, without relying on a central authority.

In the kinds of systems this book discusses, we can usually safely assume there are no Byzantine faults: in your datacenter, all nodes are controlled by your organization, and radiation levels are low enough that memory corruption isn’t a major problem. Byzantine protocols are quite complicated; fault-tolerant embedded systems rely on hardware-level support; in most server-side data systems, the cost of deploying Byzantine fault-tolerant solutions makes them impractical. Web applications do need to expect arbitrary and malicious behavior from clients under end-user control — that’s why input validation, sanitization, and output escaping (against SQL injection and cross-site scripting) are so important — but the standard approach is making the server the authority on what client behavior is and isn’t allowed, not Byzantine protocols. Two sobering notes: a software bug could be regarded as a Byzantine fault, but if you deploy the same software to all nodes, a Byzantine fault-tolerant algorithm cannot save you — most such algorithms require a supermajority of more than two-thirds of nodes functioning correctly (with four nodes, at most one may malfunction), so you’d need four independent implementations and hope a bug appears in only one. And a protocol can’t protect you from security compromises either: an attacker who can compromise one node can probably compromise all of them, since they probably run the same software. Traditional mechanisms — authentication, access control, encryption, firewalls — remain the main protection against attackers.

Even without full Byzantine tolerance, guarding against weak forms of lying is worthwhile — simple, pragmatic steps that wouldn’t withstand a determined adversary but improve reliability: application-level checksums (network packets occasionally get corrupted in ways that evade the built-in TCP/UDP checksums), input validation for publicly accessible services (range checks, string size limits to prevent memory-exhaustion DoS; even internal services benefit from sanity checks in protocol parsing), and NTP’s approach — configure multiple server addresses, estimate each server’s error, require a majority to agree on a time range, and exclude outliers, so a single misconfigured server is detected.

8.3.5 — System model and reality

Many algorithms have been designed to solve distributed systems problems — the consensus solutions of Chapter 9 among them — and to be useful, they must tolerate the faults of this chapter while not depending too heavily on the details of particular hardware and software. That requires formalizing the faults we expect: a system model is an abstraction that describes what things an algorithm may assume. Two axes. First, timing:

Synchronous model

Assumes bounded network delay, bounded process pauses, and bounded clock error — not exactly synchronized clocks or zero delay, just known upper bounds that are never exceeded. Not a realistic model of most practical systems: unbounded delays and pauses do occur.

Partially synchronous model

The system behaves like a synchronous system most of the time, but sometimes exceeds the bounds — after which network delay, pauses, and clock error may become arbitrarily large. A realistic model of many systems: networks and processes are mostly well behaved (otherwise we’d never get anything done), but any timing assumption may occasionally be shattered.

Asynchronous model

An algorithm is not allowed to make any timing assumptions — in fact it doesn’t even have a clock, so it cannot use timeouts. Very restrictive, but some algorithms can still be designed for it.

Second, node failures:

Crash-stop faults

An algorithm may assume that a node can fail in only one way — by crashing. The node may suddenly stop responding at any moment, and thereafter it is gone forever: it never comes back.

Crash-recovery faults

Nodes may crash at any moment, and perhaps start responding again after some unknown time. Stable storage (nonvolatile disk) is preserved across crashes; the in-memory state is assumed to be lost.

Byzantine (arbitrary) faults

Nodes may do absolutely anything, including trying to trick and deceive other nodes — as described above.

For modeling real systems, the partially synchronous model with crash-recovery faults is generally the most useful model. How do algorithms cope with it? First we need to say what “correct” means.

8.3.6 — Correctness, safety, and liveness

To define what it means for an algorithm to be correct, we describe its properties — like a sorting algorithm’s output having the property that for any two distinct elements, the one further left is smaller. For a fencing-token generator, three properties:

1.

Uniqueness

No two requests for a fencing token return the same value.

2.

Monotonic sequence

If request x returned token tx, and request y returned token ty, and x completed before y began, then tx < ty.

3.

Availability

A node that requests a fencing token and does not crash eventually receives a response.

An algorithm is correct in some system model if it always satisfies its properties in all situations that we assume may occur in that model. But that seems odd — if all nodes crash, or all network delays become infinitely long, no algorithm gets anything done. The resolution is distinguishing two kinds of properties:

Safety “nothing bad happens”

If a safety property is violated, we can point at a particular point in time at which it was broken — a particular operation that returned a duplicate fencing token — and after the violation, the damage is done; it cannot be undone. Uniqueness and monotonic sequence are safety properties. For distributed algorithms it is common to require that safety properties always hold, in all possible situations — even if all nodes crash or the entire network fails, the algorithm must not return a wrong result.

Liveness “something good eventually happens”

A liveness property may not hold at some point in time — a node may have sent a request and not yet received a response — but there is always hope that it may be satisfied in the future. The giveaway: liveness properties often include the word “eventually” in their definition — and yes, eventual consistency is a liveness property. With liveness we are allowed caveats: a response comes only if a majority of nodes have not crashed, and only if the network eventually recovers — which is exactly what the partially synchronous model promises (any period of interruption lasts only a finite duration).

The distinction helps us deal with difficult system models — and it maps cleanly onto the fencing tokens: safety must hold unconditionally; liveness may carry caveats.

Mapping system models to the real world

Safety, liveness, and system models are very useful for reasoning about correctness — but when you implement an algorithm in practice, the messy facts of reality bite again, and it becomes clear that the system model is a simplified abstraction. Algorithms in the crash-recovery model assume data in stable storage survives crashes — but what if data on disk is corrupted, or wiped out by a hardware error or misconfiguration? What if a server has a firmware bug and fails to recognize its hard drives on reboot, even though the drives are correctly attached? Quorum algorithms rely on a node remembering the data it claims to have stored — if a node suffers amnesia and forgets, the quorum condition, and thus the correctness of the algorithm, breaks; a new model where stable storage mostly survives would be harder to reason about. Theoretical descriptions can declare that certain things are simply assumed not to happen — a real implementation may still need code for the impossible case, which may boil down to printf("Sucks to be you") and exit(666) — letting a human operator clean up the mess. (This is arguably the difference between computer science and software engineering.)

None of which makes the abstract models worthless — quite the opposite. They are incredibly helpful for distilling the complexity of real systems down to a manageable set of faults we can reason about, so we can understand the problem and solve it systematically. We can prove algorithms correct by showing their properties always hold in some system model — but proving an algorithm correct does not mean its implementation on a real system will necessarily always behave correctly. It is a very good first step, because the theoretical analysis can uncover problems that might remain hidden until unusual circumstances defeat your assumptions. Theoretical analysis and empirical testing are equally important.

8.4 · Pulling it together

Summary

The chapter covered three families of problems. Networks: whenever you try to send a packet, it may be lost or arbitrarily delayed — and so may the reply; if you don’t get a reply, you have no idea whether the message got through. Clocks: a node’s clock may be significantly out of sync with other nodes despite your best NTP efforts, and it may suddenly jump forward or back; relying on it is dangerous because you most likely don’t have a good measure of your clock’s error interval. Process pauses: a process may pause for a substantial amount of time at any point in its execution (perhaps a stop-the-world GC), be declared dead by other nodes, and come back to life without realizing it was paused.

The possibility of partial failures is the defining characteristic of distributed systems — so we build tolerance of partial failure into the software, letting the system as a whole continue functioning even when some of its constituent parts are broken. Two hard parts. Detecting faults: most systems have no accurate mechanism for it — timeouts are the tool, but they can’t distinguish network from node failures, and variable delay sometimes causes a node to be falsely suspected of crashing. Worse, a node can be degraded rather than dead — a Gigabit network interface suddenly dropping to 1 Kb/s throughput from a driver bug — a “limping” node can be harder to deal with than a cleanly failed one. Tolerating faults: once detected, there’s no global variable, no shared memory, no common knowledge between the machines — nodes can’t even agree on what time it is, let alone anything more profound. The only way information flows is over the unreliable network, so major decisions cannot be safely made by a single node: we need protocols that enlist other nodes and get a quorum to agree.

A single-computer perspective, for contrast: if you’re used to the idealized mathematical perfection of one machine — the same operation always returning the same result — the messy physical reality of distributed systems is a bit of a shock. Distributed systems engineers often regard a problem as trivial if it can be solved on a single computer, and a single computer can do a lot nowadays. If you can avoid opening Pandora’s box and keep things on one machine, it’s generally worth doing so — but scalability isn’t the only reason to distribute: fault tolerance and low latency (placing data geographically close to users) can’t be achieved with a single node. And the unreliability is not an inevitable law of nature: hard real-time response guarantees and bounded network delays are possible, but expensive, with lower hardware utilization — most non-safety-critical systems choose cheap and unreliable over expensive and reliable. Supercomputers, which assume reliable components, must be stopped and restarted entirely when a component fails; distributed systems can run forever without service-level interruption, handling faults and maintenance at the node level — at least in theory, because in practice a bad configuration change rolled out to all nodes will still bring the whole thing to its knees. This chapter was all problems and a bleak outlook; the next one is finally about solutions: algorithms that cope.

Glossary

partial failure
Some parts of the system broken in unpredictable ways while others work fine. Nondeterministic — may sometimes work and sometimes fail, and you may not even know whether something succeeded. The defining characteristic of distributed systems.
deterministic
On a single, correctly functioning computer: the same operation always produces the same result. A deliberate design choice — computers prefer to crash completely rather than return a wrong result.
shared-nothing
Architecture where each machine has its own memory and disk; the network is the only communication channel. Cheap, commoditized, and the dominant approach for internet services.
asynchronous packet network
One node can send a message to another, but the network gives no guarantees as to when it will arrive, or whether it will arrive at all. The internet and most datacenter networks (Ethernet).
network partition (netsplit)
One part of the network cut off from the rest due to a network fault. The book prefers the general term “network fault” to avoid confusion with storage-system partitions (shards).
timeout
After some time, give up waiting and assume the response is not going to arrive. The only sure way to detect a fault — yet still tells you nothing about whether the request was received.
unbounded delays
No upper limit on the time a packet may take to arrive. Asynchronous networks try to deliver as fast as possible, but promise nothing.
cascading failure
Declaring slow (not dead) nodes dead transfers their load to others, which then also slow down, get declared dead… until everything stops working.
flow control (backpressure)
TCP limits its own rate of sending to avoid overloading a network link or the receiving node — queueing the data before it even enters the network.
circuit switching
A fixed, guaranteed amount of bandwidth allocated along the entire route for the duration of a call. No queueing, bounded delay, static partitioning — good for constant-bit-rate audio, wasteful for bursty data.
packet switching
Packets opportunistically use whatever bandwidth is available; the rate adapts dynamically. Better utilization, but queueing and unbounded delays.
synchronous network
Bounded delay: space is reserved at every hop, so there is no queueing and the maximum end-to-end latency is fixed — like the traditional telephone network.
time-of-day clock
Current date/time according to a calendar, since the epoch (midnight UTC, Jan 1 1970). Usually NTP-synchronized; may jump backward. Good for points in time, unsuitable for durations.
monotonic clock
Always moves forward; the right tool for measuring durations (timeouts, response times). Absolute value meaningless, not comparable across computers. NTP may slew its rate by up to ±0.05% but can never jump it.
slewing
NTP adjusting the frequency (rate) at which the monotonic clock moves forward — speeding it up or slowing it down by up to 0.05% — as opposed to stepping (jumping) the time-of-day clock.
clock drift
The tendency of a quartz crystal oscillator to run faster or slower than it should, varying with temperature. Google assumes 200 ppm: up to 6 ms between 30-second resyncs, or 17 seconds for daily resyncs.
NTP
Network Time Protocol: adjusts the computer clock according to the time reported by a group of servers (which use GPS or similar). Accuracy limited by network delay — 35 ms minimum over the internet; robust clients query several servers and ignore outliers.
leap second
A minute that is 59 or 61 seconds long. Has crashed many large systems. Smearing — spreading the adjustment gradually over a day — is the kinder alternative.
last write wins (LWW)
Conflict resolution that keeps the value with the latest timestamp and discards others. On time-of-day clocks it silently loses data to clock skew, can’t distinguish sequential from concurrent writes, and needs arbitrary tiebreakers.
logical clocks
Based on incrementing counters (Lamport), not quartz. Measure only the relative ordering of events — a safer basis for ordering than timestamps. Physical clocks (time-of-day + monotonic) measure actual time.
confidence interval
A clock reading is not a point but a range of times within which the actual time is believed to lie. If you only know the time ±100 ms, the microsecond digits are meaningless.
TrueTime API
Google Spanner’s clock API that explicitly reports the confidence interval — earliest and latest possible timestamps. Spanner waits out the interval before committing, and GPS receivers/atomic clocks in each datacenter keep it to about 7 ms.
lease
Similar to a lock with a timeout: only one node can hold it, and it must be periodically renewed before expiry. Basis of the “am I still the leader?” mechanism — and breakable by process pauses.
stop-the-world GC pause
All running threads paused by the garbage collector — sometimes for several minutes. Even “concurrent” collectors must occasionally stop the world.
steal time
CPU time spent by the hypervisor running other virtual machines — your thread is paused while it accrues.
thrashing
The OS spending most of its time swapping pages in and out of memory, getting little actual work done. Why paging is often disabled on servers.
hard real-time system
Must respond within a specified deadline or the system fails (aircraft, rockets, airbags). Requires an RTOS, worst-case execution time documentation, restricted allocation — expensive, and not “high-performance” in throughput terms.
quorum / majority
Voting among nodes: decisions require a minimum number of votes. An absolute majority tolerates failures (3 nodes → 1, 5 nodes → 2) and is safe because there can be only one majority. Even “is this node dead?” is a majority decision.
fencing token
A number that increases every time a lock is granted. The resource rejects writes with tokens older than the highest it has processed — so a paused node that wakes up believing it still holds the lease cannot cause damage.
Byzantine fault
A node that “lies” — sends arbitrary faulty or corrupted responses. Nodes in this book are assumed unreliable but honest; Byzantine behavior needs BFT protocols with a supermajority (>2/3) of correct nodes.
Two Generals Problem
Two generals must agree on a battle plan via messengers who may be delayed or lost — like packets. The Byzantine Generals Problem adds traitors and unknown allegiances.
system model
An abstraction describing what an algorithm may assume. Timing: synchronous (bounded), partially synchronous (mostly bounded, occasionally shattered), asynchronous (no clock at all). Failures: crash-stop, crash-recovery, Byzantine. Partially synchronous + crash-recovery is generally the most useful.
safety property
“Nothing bad happens.” If violated, you can point at the moment it broke — and the damage cannot be undone. Must always hold, even if every node crashes.
liveness property
“Something good eventually happens.” May not hold at a given moment, but there is always hope for the future. May carry caveats (majority alive, network eventually recovers). Eventual consistency is one.
