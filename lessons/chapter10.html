10.0 · The setup

Three kinds of systems

A batch processing system takes a large amount of input data, runs a job over it, and produces output data. To see what makes that category distinct, it helps to lay out the three broad kinds of data systems — the book’s taxonomy, worth memorizing because the rest of the book leans on it:

10.0.1 — Online, offline, and near-real-time

Services (online) latency

Waits for a request or instruction from a client, handles it as quickly as possible, and sends a response. The primary performance measure is response time, and availability is often paramount — if the service is unreachable, the client gets an error. Everything from Chapter 1’s “responsive” quality goal to Part II’s replication and consensus machinery exists to serve this world.

Batch processing (offline) throughput

Takes a large, fixed input, runs a job that may last minutes to days, and writes output. Nobody is sitting waiting for it to finish. Jobs typically run on a schedule — say, once a day. The primary performance measure is throughput: time to crunch through a dataset of a given size. This chapter.

Stream processing (near-real-time) in between

Consumes and produces events shortly after they happen rather than responding to requests — lower latency than the equivalent batch job, but not interactive either. Also called nearline. Chapter 11.

10.0.2 — Everything old is new again

MapReduce — published by Google in 2004, and quickly hyped as the algorithm that made Google so massively scalable — has open-source descendants in Hadoop, CouchDB, and MongoDB. It was also, in truth, a fairly low-level step relative to the parallel processing systems that data warehouses had enjoyed for over a decade beforehand. Its importance has since declined, but it remains worth understanding, because the ideas underneath it have outlived the engine.

Batch processing itself is far older than MapReduce: punch-card tabulating machines — the Hollerith machines used in the 1890 US Census — predate programmable digital computers entirely, and MapReduce’s sorted-records pipeline bears an uncanny resemblance to the electromechanical IBM card-sorting machines of the 1940s and 1950s. History repeats. The plan: start with plain Unix tools on a single machine, because the ideas and lessons there carry over exactly to large-scale, heterogeneous distributed systems.

10.1 · The grandfather pipeline

Batch processing with Unix tools

A web server appends a line to a log file every time it serves a request. An nginx default-format line looks like this (it’s one line, folded here for readability):

216.58.210.78 - - [27/Feb/2015:17:55:11 +0000] "GET /css/typography.css HTTP/1.1" 200 3377 "http://martin.kleppmann.com/" "Mozilla/5.0 (Macintosh; Intel Mac OS X 10_9_5) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/40.0.2214.115 Safari/537.36"

Read the fields: February 27, 2015 at 17:55:11 UTC; a request for /css/typography.css; client IP 216.58.210.78; the user not authenticated; response status 200 (success); 3,377 bytes sent; Chrome 40 on macOS; referred from the author’s own site. The task: find the five most popular pages.

10.1.1 — The log pipeline

cat /var/log/nginx/access.log | awk '{print $7}' | sort | uniq -c | sort -r -n | head -n 5
1.

cat — read the file

Pour the log in. (Yes, awk could take the filename as an argument and skip cat — but the linear pipeline is more apparent written this way.)

2.

awk '{print $7}' — extract the URL

Split each line into whitespace-separated fields and print the seventh — the requested URL. Want to ignore CSS files instead? Change the argument to $7 !~ /\.css$/ {print $7}. Want top client IPs? {print $1}. One-word edits repurpose the whole pipeline.

3.

sort — order them

Alphabetically sort the URLs. A URL requested n times now appears n times in a row — grouping by adjacency, not by lookup.

4.

uniq -c — count duplicates

uniq collapses repeated adjacent lines; with -c it prefixes each distinct URL with how many times it occurred.

5.

sort -r -n — rank

Sort numerically (-n) by the count at the start of each line, reversed (-r) so the biggest number comes first.

6.

head -n 5 — take five

Keep the first five lines, discard the rest. Output: the five most popular pages with their counts.

This pipeline chews through gigabytes of logs in seconds, and it’s representative: awk, sed, grep, sort, uniq, and xargs in combination can answer a surprising share of everyday data questions in minutes, and they perform remarkably well.

Figure 10-A (recreated) · Six programs, one pipeline, no temp files

The whole chapter grows out of this picture: MapReduce is the same composition, industrialized across a cluster — and the biggest architectural difference, as we’ll see, is that MapReduce’s chained jobs do write intermediate files, more like a sequence of commands writing temp files than a true pipeline.

10.1.2 — Chain of commands versus a custom program

The same job in Ruby is a hash table counting URLs, sorted descending, top five printed — a few lines, quite readable, and partly a matter of taste. The real difference shows on large files, and it’s about the execution model, not the syntax. Details below.

10.1.3 — Sorting versus in-memory aggregation

The Unix pipeline sorts a list in which each URL appears repeatedly; the Ruby script keeps an in-memory hash table mapping URL → count. The hash table’s footprint is the working set — the memory the job needs random access to — which depends only on the number of distinct URLs: a million hits on one URL still cost one hash entry. If the working set fits in memory, the hash approach is fine, even on a laptop.

Once the working set outgrows memory, sorting wins, because sorting can use disks efficiently — the same principle as Chapter 3’s SSTables and LSM-trees: sort chunks in memory, write them out as sorted segment files, and merge them; mergesort’s sequential access pattern is kind to disks. GNU coreutils’ sort does exactly this — spilling to disk automatically, even parallelizing across CPU cores. So the humble command chain scales to datasets far larger than memory without special effort; the bottleneck becomes the rate you can read the input from disk.

10.1.4 — The Unix philosophy

Doug McIlroy — the inventor of pipes, which he first described back in 1964 — wanted programs to connect like garden hose: screw in another segment whenever data needs another massage. The plumbing metaphor stuck, and by 1978 the philosophy had crystallized into four principles:

1.

Do one thing well

Make each program do one thing well. To do a new job, build afresh rather than complicate old programs by adding new “features.”

2.

Expect composition

Expect the output of every program to become the input to another, as yet unknown, program. Don’t clutter output with extraneous information; avoid rigidly columnar or binary formats; don’t insist on interactive input.

3.

Build and try early

Design and build software, even operating systems, to be tried early — ideally within weeks. Don’t hesitate to throw away the clumsy parts and rebuild.

4.

Prefer tools

Use tools in preference to unskilled help, even if you must detour to build the tools — and expect to throw some of them out after you’re finished using them.

Read those again and notice what they sound like: automation, rapid prototyping, incremental iteration, friendliness to experimentation, big projects broken into manageable chunks. It’s a remarkably close match to today’s Agile and DevOps movements — surprisingly little has changed in four decades.

10.1.5 — A uniform interface

If one program’s output is to become another’s input, they must agree on the data format — and if you want to connect any program to any program, they all need the same interface. Unix’s is the file (more precisely, the file descriptor): an ordered sequence of bytes. It is deliberately over-loaded — an actual file on disk, a communication channel to another process (stdin/stdout, a Unix socket), a device driver, a TCP connection can all be represented the same way, so wildly different things plug together.

By convention, most (not all) Unix programs treat those bytes as ASCII text, with the newline character (\n) as the record separator — our pipeline depended on awk, sort, uniq, and head all agreeing on that. The choice is arbitrary (the ASCII record separator 0x1E was arguably designed for the job), but the agreement is what enables interoperability. Parsing within a line is much vaguer — whitespace, tabs, CSV, pipe-separated all appear, and xargs alone has half a dozen options for how to parse its input. So it mostly works, and it isn’t exactly beautiful: {print $7} is not exactly {print $request_url}.

Still remarkable, decades later

Not much software interoperates and composes as well as Unix tools do. You can’t pipe your email account and your shopping history through a custom analysis tool into a spreadsheet and post the results to a wiki. Even databases sharing the same data model rarely make it easy to move data from one into another — the lack of integration is what Balkanizes data. Uniform interfaces are rare and precious (URLs and HTTP, the foundations of the web, are another example — any site can link to any other, across organizational boundaries). Unix is the exception, not the norm.

10.1.6 — Separation of logic and wiring

The characteristic feature is stdin and stdout. Run a program without redirection and stdin comes from the keyboard, stdout goes to the screen — but files and pipes can be substituted freely. Pipes attach one process’s stdout to another’s stdin through a small in-memory buffer, without writing the intermediate data stream to disk. The design principle: a program can read and write files directly, but the approach works best when the program doesn’t worry about particular paths and just uses stdin/stdout — then the shell user, not the program, decides where input comes from and output goes. The program neither knows nor cares. Call it loose coupling, late binding, or inversion of control — separating the I/O wiring from the program logic is what makes composing small tools into big systems possible. Your own programs join the ecosystem simply by reading stdin and writing stdout: a translator for user-agent strings or IP-address-to-country codes plugs straight into the pipeline, and sort never knows the difference. The limits: multi-input/multi-output programs are awkward, you can’t pipe into a network connection without help (netcat, curl), and a program that opens its own files or sockets has wired up its own I/O, shrinking the shell’s freedom.

10.1.7 — Transparency and experimentation

The last Unix-philosophy advantage is observability, and it comes from three habits:

  • Inputs are immutable — run the commands as often as you like, with whatever options you like, and the input files never change.
  • End the pipeline anywhere — pipe the output into less and look at it: does it have the expected form? Great for debugging.
  • Checkpoint stages to files — write one stage’s output to a file and feed the next stage from it, so you can restart the later stage without rerunning everything.

Unix tools are blunt instruments next to a relational query optimizer — yet amazingly useful, especially for experimentation. Their one hard limitation: they run on a single machine. That’s where Hadoop comes in.

10.2 · The blunt instrument, distributed

MapReduce and distributed filesystems

MapReduce is like Unix tools but spread across potentially thousands of machines — equally blunt, brute-force, and surprisingly effective. A single MapReduce job is the analogue of a single Unix process: it takes one or more inputs and produces one or more outputs. It shares the virtues we just cataloged: running a job does not modify the input, it has no side effects beyond the output, and output files are written once sequentially, never modified after the fact. Where Unix tools use stdin/stdout, MapReduce jobs read and write files on a distributed filesystem — in Hadoop, HDFS.

10.2.1 — HDFS, the shared-nothing filesystem

HDFS is an open-source reimplementation of the Google File System (GFS, published 2003); cousins include GlusterFS, the Quantcast File System, and object stores like Amazon S3, Azure Blob Storage, and OpenStack Swift. The architectural principle is shared-nothing — the opposite of the shared-disk NAS/SAN approach with its centralized storage appliance and special interconnects like Fibre Channel. A distributed filesystem needs no special hardware at all: just every machine in the datacenter and the disks already attached to each.

1.

The daemon on every machine

A daemon process on each node exposes a network service so other nodes can access the files stored on that machine — conceptually one big filesystem using every daemon-running machine’s disks.

2.

The NameNode

A central server tracks which file blocks are stored on which machine — the filesystem’s directory brain.

3.

Replication or erasure coding

Blocks are made fault-tolerant by replication on multiple machines, or by erasure coding such as Reed–Solomon (recoverable with lower storage overhead than full copies) — RAID-like redundancy, but over a conventional datacenter network rather than special hardware.

10,000s Machines in the biggest HDFS deployments combined storage capacity of hundreds of petabytes
commodity Hardware and open-source software much cheaper than the equivalent dedicated storage appliance
locality Compute can be scheduled onto the machine holding the data object stores usually keep storage and computation separate; erasure coding breaks locality too

10.2.2 — How a MapReduce job runs

MapReduce is a programming framework for writing code that processes large datasets in a distributed filesystem. The pattern of data processing has four steps, and if it looks familiar, it should — it is the log-analysis pipeline again:

1.

Break input into records

Read the input files and split them into records — one log line each in the web server example, where \n was the separator. Handled by the input format parser, not by you.

2.

Call the mapper per record

The mapper extracts a key and value from each input record — our awk '{print $7}', with the URL as key and the value empty. Called once per record; may emit any number of key-value pairs (including none); keeps no state between records.

3.

Sort all the pairs by key

The framework sorts — implicitly and always. Mapper output is handed to the reducer pre-sorted. This is the step you don’t write, and it’s the heart of the engine.

4.

Call the reducer per key

Sorting has made all pairs with the same key adjacent, so the reducer — our uniq -c — gets each key with an iterator over its values and combines them without holding much in memory.

Steps 2 and 4 are where your custom code lives. In Hadoop, mapper and reducer are each a Java class implementing an interface; in MongoDB and CouchDB, they’re JavaScript functions (and you can even use standard Unix tools as mappers and reducers). If you need a second sorting stage — ranking URLs by count, like our sort -r -n — you write a second MapReduce job and chain them. Viewed this way, the mapper’s job is to prepare data for sorting, and the reducer’s job is to process sorted data.

10.2.3 — Distributed execution: the shuffle

The key difference from Unix pipelines: MapReduce parallelizes across machines without you writing any parallelism code. Mappers and reducers each handle one record at a time and never need to know where their input comes from or output goes — the framework moves the data. The mechanics:

Figure 10-1 (recreated) · A MapReduce job: three mappers, three reducers

The full lifecycle: the scheduler tries to run each map task on a machine that stores a replica of its input file (assuming spare RAM and CPU), saving a network copy. Each map task partitions its output by reducer — hash of the key — and writes sorted files to its local disk (the same SSTable/LSM-tree technique from Chapter 3). When a mapper finishes, reducers connect to it and download the partition meant for them; each reduce task merges those files (preserving sort order, so same-key records from different mappers become adjacent) and streams your reducer one key at a time — the iterator may hold more data than memory. Partition-by-reducer + sort + copy is the shuffle — a misleadingly named step with no randomness in it.

10.2.4 — Chaining jobs into workflows

One job counts page views per URL, but finding the most popular URLs needs a second sort — so jobs get chained: the output of one becomes the input of the next. Hadoop MapReduce has no first-class workflow support: chaining is done implicitly by directory name — job 1 writes to a designated HDFS directory, job 2 is configured to read that same directory, and as far as the framework is concerned they are two independent jobs. Since a job’s output is only valid when the job has completed successfully (partial output of a failed job is discarded), the next job can only start after the previous one finishes.

This is where workflow schedulers earn their keep — Oozie, Azkaban, Luigi, Airflow, Pinball — managing the dependencies between job executions. And the scale is real:

50–100 MapReduce jobs in a typical recommendation-system workflow in a large organization, many teams run jobs that read each other’s output — tooling matters
temp files What chained jobs really resemble less like Unix pipes (tiny in-memory buffer), more like a sequence of commands each writing to an intermediate file — with consequences, see 10.3.1

Higher-level tools — Pig, Hive, Cascading, Crunch, FlumeJava — assemble multi-stage workflows automatically, and we’ll return to them in 10.3.4.

10.2.5 — Reduce-side joins and grouping

Joins were Chapter 2’s business from the data-model side; now we see how they’re actually executed at scale. Anywhere one record has an association with another — a foreign key, a document reference, an edge in a graph — code that needs both sides of the association needs a join, and denormalization can reduce the need but not remove it. The batch version of a join: resolve every occurrence of an association within the dataset, for all users at once — not a point lookup for one user, which is what indexes are for. And that’s the first big difference from a database: MapReduce has no concept of indexes — given a set of files, it reads all of them. A database would call that a full table scan; outrageous for a few records, entirely reasonable when the query aggregates over millions and can be parallelized across machines.

The running example: activity events joined with user profiles

On one side, the log of activity events (clickstream) — the fact table of a star schema from Chapter 3; on the other, the user database — one of its dimensions. The analytics task: correlate activity with profiles — which pages are popular with which age groups. The events carry only the user ID, not the profile (embedding the profile in every event would be wasteful), so the two datasets must be joined. The naive approach — iterate events, query the user database per user ID — is limited by round-trip time, hostage to cache effectiveness, and parallel queries can overwhelm the database. The batch approach: take a copy of the user database (an ETL extract from a backup, say), put it in the same distributed filesystem as the event log, and let MapReduce bring all relevant records together.

Figure 10-3 (recreated) · A reduce-side sort-merge join on user ID

The mapper’s key is the destination address: emit (user ID, event) from one side, (user ID, date of birth) from the other — and the shuffle delivers every record for a given user ID to one reducer call. MapReduce separates the physical communication (getting data to the right machine) from the application logic (what to do once it’s there), and because the framework handles retries, it also shields your code from worrying about other nodes’ partial failures. If both inputs are partitioned into many files, each side runs many mappers in parallel — the diagram compresses them.

10.2.6 — Grouping and sessionization

“Bring all records with the same key to one place” is bigger than joins — it’s also GROUP BY: set the mappers’ key to the grouping key and partitioning-and-sorting delivers each group to one reducer, which then aggregates — counting records (COUNT(*)), summing a field (SUM(field)), or picking the top k by some ranking. Grouping and joining look nearly identical when implemented on MapReduce.

A common special case is sessionization: collating all activity events for one user session to reconstruct the sequence of actions — the basis of A/B testing (do users shown the new site buy more?) and marketing-effect calculations. Events for one user are scattered across many web servers’ logs; a session cookie or user ID as the grouping key gathers each user’s events into one place while keeping different users apart.

10.2.7 — Handling skew: the celebrity problem

The “bring everything with the same key together” pattern collapses when one key dominates. In a social network most users have a few hundred connections, but a few celebrities have millions of followers — disproportionately active records, known as linchpin objects or hot keys. One reducer gets the celebrity’s entire reply stream while others idle — and since a job is only complete when all its tasks complete, every downstream job waits for the slowest, most bloated reducer. That’s skew (hot spots, Chapter 6’s problem in batch clothing). The defenses:

1.

Pig’s skewed join

First a sampling job determines which keys are hot. In the real join, records for a hot key go to one of several reducers chosen at random (unlike the usual deterministic hash of the key), and the other join input is replicated to all the reducers handling that key. Work spread at the cost of duplication.

2.

Crunch’s sharded join

The same idea, but hot keys must be specified explicitly rather than sampled — very close to Chapter 6’s random-suffix trick for relieving hot spots in a partitioned database.

3.

Hive’s skewed join

Hot keys are declared in table metadata; records for those keys are stored in separate files and joined with a map-side join (below) instead.

4.

Two-stage aggregation

For grouping over a hot key: stage 1 sends records to a random reducer, where each partially aggregates its subset into a compact intermediate; stage 2 combines those intermediates into the final value per key. The hot key’s load is split before the real aggregation.

10.2.8 — Map-side joins

Reduce-side joins make no assumptions about the input — whatever the properties and structure, the mappers can prepare it for joining. The price: all that sorting, copying to reducers, and merging is expensive, and depending on memory buffers the data may hit disk several times on its way through. If you can make assumptions about the inputs, joins get much cheaper: a cut-down job with no reducers and no sorting, where each mapper reads one input file block from the distributed filesystem and writes one output file. That’s all.

Broadcast hash join small + large

The simplest and most common case: one input is small enough to load entirely into memory in each mapper. On startup, a mapper reads the small dataset — the user database, say — into an in-memory hash table, then streams the large input (the activity events) and looks up each user ID in the table. Broadcast: every mapper for a partition of the large input reads the entire small input, so it’s effectively sent to all of them; hash: the lookup structure. Supported as Pig’s “replicated join,” Hive’s MapJoin, and in Cascading, Crunch, and Impala. If the small input doesn’t fit memory, a read-only index on local disk gets random-access lookups nearly as fast via the OS page cache — without requiring the dataset to fit in RAM.

Partitioned hash join same-way partitioned

If the inputs are already partitioned the same way, the hash join runs per partition: activity events and user database each partitioned by, say, the last digit of the user ID; mapper 3 loads users with IDs ending in 3, scans only events for users with IDs ending in 3. Each mapper reads one partition from each input and its hash table is a fraction of the size. The constraint: both inputs must have the same number of partitions, keyed the same way with the same hash function — reasonable when prior MapReduce jobs produced them. Hive calls these bucketed map joins.

Map-side merge join same-way sorted

If the inputs are not only partitioned identically but sorted by the same key, memory size stops mattering: the mapper performs the merging a reducer would normally do, reading both inputs incrementally in ascending key order and matching equal keys. When this is possible, prior jobs probably produced the sorted, partitioned form — so the join could have been done in that prior job’s reduce stage, but running it as a separate map-only job makes sense when those datasets serve other purposes too.

Figure 10-4 (recreated) · Reduce-side vs broadcast map-side join

The trade in one picture: reduce-side pays a full shuffle of both inputs for total generality; broadcast map-side pays nothing per record, in exchange for the assumption that the small input fits in memory everywhere. Note the output difference: reduce-side output is partitioned and sorted by join key, map-side output inherits the large input’s partitioning — which is why knowing the physical layout of datasets (partitions, keys, sort order — tracked in HCatalog and the Hive metastore) becomes part of optimizing joins.

10.2.9 — The output of batch workflows

All these algorithms, one neglected question: what is the result of all that processing for? Batch processing isn’t transaction processing, and it isn’t really analytics either — closer to analytics (scans over large portions of input), but a MapReduce workflow is not an SQL query, and its output is usually not a report. What is it?

Building search indexes

Google’s original use of MapReduce was building search indexes — a workflow of 5 to 10 MapReduce jobs. A full-text search index like Lucene’s is, in simplified form, a term dictionary: look up a keyword, get the postings list of document IDs containing it (real ones add ranking, misspelling handling, synonyms). For a fixed set of documents, batch processing is a very effective way to build one: mappers partition the documents, each reducer builds its partition’s index, index files go to the distributed filesystem — document-partitioned indexes (Chapter 6) parallelize beautifully. Queries are read-only, so the index files are immutable once created; when the document set changes, either rerun the whole indexing workflow periodically and swap in the new index wholesale (computationally wasteful for a few changed documents, but beautifully easy to reason about — documents in, indexes out), or build incrementally the Lucene way (new segment files, background merges). Even after Google moved on, Hadoop MapReduce remained a good way to build Lucene/Solr indexes.

Key-value stores as batch output

The other big category: machine learning systems — classifiers (spam filters, anomaly detection, image recognition) and recommenders (“people you may know,” related products) — whose output is usually a database: queried by user ID for suggested friends, by product ID for related products. That database serves a web application far from the Hadoop cluster. The obvious approach — write to the database server from mappers or reducers via the client library, one record at a time — works, and is a bad idea three ways:

1.

Point writes are slow

A network request per record is orders of magnitude below a batch task’s normal throughput — even with batching in the client library, performance suffers.

2.

It overwhelms the database

MapReduce jobs run many tasks in parallel; if all the mappers or reducers write to one database at batch rates, they can swamp it and degrade its queries — dragging down other parts of the system with it.

3.

It breaks the all-or-nothing guarantee

Normally a job’s result is as if every task ran exactly once, or nothing if the job failed. Writing to an external system from inside a job makes those side effects publicly visible — you inherit partially completed jobs, task retries, and speculative-execution complexities to clean up after.

The better approach: build a brand-new database inside the batch job, written as files to the job’s output directory in the distributed filesystem. The files are immutable once written, then bulk-loaded into read-only serving stores — Voldemort, Terrapin, ElephantDB, and HBase’s bulk load all support it. And MapReduce is well suited to it: extract a key, sort by it — much of building an index is already done. Because the stores are read-only (files written once by a batch job), the data structures are simple — no write-ahead log needed, for instance. The Voldemort loading pattern shows the payoff: the server keeps serving from the old files while the new ones copy across, then atomically switches — and if anything goes wrong, it switches back, because the old immutable files are still there.

The philosophy of batch outputs

Notice what Unix taught, restated at cluster scale. Treat inputs as immutable, replace any previous output completely, avoid side effects like writing to external databases — and you gain three big things. Human fault tolerance: deploy buggy code that corrupts the output, and rolling back the code and rerunning the job fixes the data again (or just switch back to yesterday’s output directory) — impossible with read-write transactions, where buggy writes are already baked in; the ease of recovery speeds up feature development, a minimization of irreversibility. Safe automatic retries: a failed map or reduce task is simply rescheduled on the same input — transient faults are tolerated, buggy code crashes identically and eventually fails the job — which is only safe because inputs are immutable and failed tasks’ outputs are discarded. Reusable outputs: the same files feed other jobs, including monitoring jobs that compare a run’s output with the previous one and measure discrepancies. Plus the same logic/wiring separation as Unix: one team builds a job that does one thing well; other teams decide where and when to run it. One difference from Unix: Hadoop replaces untyped text files with structured formats like Avro and Parquet, killing the low-value {print $7}-style syntactic parsing while keeping schema evolution (Chapter 4).

10.2.10 — Comparing Hadoop to distributed databases

Zoom out: Hadoop is something like a distributed Unix — HDFS is the filesystem, MapReduce a quirky implementation of a Unix process that happens always to run sort between the map and reduce phases. When the MapReduce paper appeared, little in it was new: the processing and parallel join algorithms existed in MPP databases (the Gamma database machine, Teradata, Tandem NonStop SQL) more than a decade earlier. The biggest difference is philosophical: MPP databases are about parallel execution of analytic SQL queries; MapReduce plus a distributed filesystem is a general-purpose operating system that can run arbitrary programs.

Diversity of storage

Databases require data structured by a particular model (relational or document). Distributed filesystems store byte sequences — database records, sure, but equally text, images, video, sensor readings, sparse matrices, feature vectors, genome sequences. This inverts the warehouse discipline: dump data into HDFS indiscriminately first, figure out how to process it later — where an MPP database demands careful up-front modeling in its proprietary format before import. A purist prefers the modeling (better-quality data for users); in practice, making data available quickly — even raw, quirky, and difficult — often beats deciding the ideal model up front, because simply gathering an organization’s data in one place already enables joins across previously disparate datasets. That is the data lake (or enterprise data hub) idea, and it’s schema-on-read from Chapter 2 writ large: interpretation becomes the consumer’s problem, which suits producer/consumer teams with different priorities — there may be no single ideal model, just different views for different purposes. The slogan the chapter attaches to it: “raw data is better.” Hadoop also became the ETL workhorse: dump transactional data raw into HDFS, clean and transform it into relational form with MapReduce jobs, then import into an MPP warehouse — modeling still happens, just decoupled into a separate step.

Diversity of processing models

MPP databases are monolithic and tightly integrated — storage layout, query planning, scheduling, execution all tuned together for excellent SQL performance, and SQL’s declarative semantics serve analysts with graphical tools like Tableau. But not all processing is expressible as SQL: machine-learning and recommendation systems, full-text indexes with relevance ranking models, image analysis — feature engineering, natural-language models, fraud-risk estimators — inevitably require code, not just queries. That was MapReduce’s contribution: engineers running their own code over large datasets. Given HDFS plus MapReduce you can build a SQL engine on top (Hive did) — or any other processing model, and the openness of the platform meant many models flourished on one shared cluster, all reading the same files. No data movement between specialized systems; new processing models are easy to experiment with. The ecosystem agrees: HBase (random-access OLTP) and Impala (MPP-style analytics) both skip MapReduce entirely but share HDFS — very different approaches coexisting in one system.

10.2.11 — Designing for frequent faults

Two more differences from MPP databases: how faults are handled, and how memory and disk are used. Batch jobs tolerate faults well — users aren’t waiting, and jobs can always be rerun. Most MPP databases abort the entire query if a node dies mid-execution (resubmit or rerun automatically) — acceptable for queries of seconds to minutes — and they prefer keeping data in memory (hash joins, for instance) to avoid disk reads. MapReduce instead retries at the granularity of an individual task, and is eager to write to disk — partly for fault tolerance, partly assuming datasets too big for memory anyway. The trade: per-task recovery overhead makes fault-free processing slower, but it wins for large jobs likely to experience at least one task failure — rerunning everything for one failed task would be wasteful.

But in most clusters, machine failures aren’t actually frequent — rare enough that most jobs never see one. Is the overhead worth it? Google’s answer explains the design, and it has nothing to do with unreliable hardware:

~5% Risk that a one-hour MapReduce task is preempted at Google to make room for a higher-priority process — more than an order of magnitude above the rate of actual hardware failures
> 50% Risk that at least one task is terminated in a 100-task job each task running 10 minutes — preemption risk compounds across tasks

Google runs mixed-use datacenters: online production services and offline batch jobs share machines, every task has a container-enforced resource allocation (CPU, RAM, disk) and a priority, and a higher-priority task can preempt lower-priority ones to reclaim resources (with priority also driving pricing). That architecture lets non-production resources be overcommitted — better utilization and efficiency than segregating production and non-production — at the price that MapReduce jobs, running at low priority, effectively pick up the scraps under the table and can be killed at any moment. The freedom to arbitrarily terminate processes is worth more than the fault tolerance it costs. Among open-source schedulers, general priority preemption is (at the time of writing) missing from YARN, Mesos, and Kubernetes — YARN’s CapacityScheduler has preemption only for balancing queue allocations — and in environments where tasks are rarely terminated, MapReduce’s design decisions make much less sense. The next section is about the alternatives that chose differently.

10.3 · Fixing the engine

Beyond MapReduce

MapReduce got enormous hype in the late 2000s, but it’s just one programming model among many — depending on data volume, structure, and processing type, other tools fit better. It remains worth learning as a clear, understandable abstraction over a distributed filesystem… in the sense of being easy to understand, not easy to use: implementing a complex job with the raw APIs is genuinely hard and laborious — you’d implement join algorithms from scratch. Higher-level models (Pig, Hive, Cascading, Crunch) help, but they don’t fix the execution model itself, which shows up as poor performance on some kinds of processing. On one hand MapReduce is astoundingly robust — arbitrarily large data, unreliable multi-tenant clusters, frequent task terminations, and it still finishes (slowly). On the other, other tools are sometimes orders of magnitude faster.

10.3.1 — Materialization of intermediate state

Every MapReduce job is independent; its only contact with the rest of the world is its input and output directories. Chain jobs by pointing job 2’s input at job 1’s output, and let an external scheduler start job 2 when job 1 finishes. That’s reasonable when the first job’s output is a dataset you want to publish widely — referred to by name, reused as input by other teams, loosely coupled just like Unix’s separation of logic and wiring. But in a 50–100 job recommendation workflow, much of what’s on disk is intermediate state: a means of passing data from one job to the next, nothing more. Writing that state out to files is materialization — eagerly computing a result and storing it rather than computing on demand (the same word as Chapter 3’s materialized views). Compared with Unix pipes, which stream through a small in-memory buffer, it has three costs:

1.

Full-stage barriers

A job can only start when all tasks of its input-producing predecessor finish — pipes start processes together and consume output as it’s produced. With skew and varying load, a job typically has a few straggler tasks far slower than the rest, and waiting for them drags the whole workflow.

2.

Redundant mappers

The mapper of a downstream job often just reads back the file the previous reducer wrote and re-prepares it for partitioning and sorting. The mapper code could usually have been folded into the previous reducer — reducers could be chained directly if their output were partitioned and sorted as mappers would have done.

3.

Replicating scratch data

Intermediate state in a distributed filesystem is replicated across several nodes — overkill for temporary data nobody else reads.

10.3.2 — Dataflow engines

Several engines were built to fix these problems — Spark, Tez, and Flink — with one thing in common: they handle an entire workflow as one job, explicitly modeling the flow of data through several processing stages (hence dataflow engines; research ancestors: Dryad and Nephele). Like MapReduce, they repeatedly call user-defined functions, one record at a time on a single thread, parallelizing by partitioning inputs and copying output over the network. Unlike MapReduce, the functions need not alternate in strict map/reduce roles — they’re operators, assembled flexibly, with several ways to wire one operator’s output to another’s input:

1.

Repartition + sort by key

Exactly the MapReduce shuffle — enables sort-merge joins and grouping as before, but only where actually needed.

2.

Repartition, skip the sort

For partitioned hash joins: partitioning matters, order doesn’t — building a hash table randomizes the order anyway.

3.

Broadcast

One operator’s output sent to all partitions of the join operator — the broadcast hash join as a first-class wiring option.

Figure 10-5 (recreated) · MapReduce materialization vs a dataflow engine

The advantages, collected: (1) expensive sorting only where it’s actually required, not by default between every map and reduce; (2) no pointless map tasks — a mapper doesn’t change partitioning, so its work can fold into the preceding reduce operator; (3) with all data dependencies declared, the scheduler sees the whole graph and can co-locate producers and consumers, exchanging data through shared memory buffers instead of the network; (4) intermediate state lives in memory or local disk rather than replicated HDFS files; (5) operators start the moment their input is ready — no waiting for the previous stage to fully finish; (6) operators reuse existing JVM processes instead of starting a new one per task.

In practice these engines run the same computations as MapReduce workflows, usually significantly faster, and because operators generalize map and reduce, the same processing code runs on either — Pig, Hive, and Cascading workflows move from MapReduce to Tez or Spark with a configuration change, no code modification. (Internal differences: Tez is a fairly thin library leaning on YARN’s shuffle service for moving data; Spark and Flink are big frameworks with their own network layers, schedulers, and user-facing APIs.) One unavoidable limit on pipelining: a sort must consume its entire input before emitting anything — the very last record might carry the lowest key and need to be first out — so any operator that sorts accumulates state, at least temporarily. But most of a workflow pipelines just fine; and when the job completes, its output still goes to durable storage — usually the distributed filesystem — so the improvement over MapReduce is precisely that you skip writing the intermediate state to it.

10.3.3 — Fault tolerance in dataflow engines

MapReduce’s full materialization makes fault tolerance easy: a failed task restarts on another machine and rereads the same input from the filesystem. Spark, Tez, and Flink skip that, so they recover differently: if a machine dies and its intermediate state is lost, recompute it from whatever is still available — a prior intermediate stage if possible, otherwise the original HDFS input. The framework therefore tracks the ancestry of every piece of data: which input partitions and which operators produced it. Spark does this with the resilient distributed dataset (RDD) abstraction; Flink checkpoints operator state so a faulted operator can resume. One wrinkle: determinism. If lost data was already sent downstream and the recomputed version differs (nondeterministic operators — hash-table iteration order, random numbers, clock or external-data reads), downstream operators can’t reconcile the contradiction — the usual fix is killing and rerunning them on the new data. Cascading faults are avoided by making operators deterministic (fixed seeds for pseudorandomness, and so on). And recomputation isn’t always right: when intermediate data is much smaller than the source, or the computation is CPU-heavy, materializing the intermediate to files is cheaper than recomputing.

10.3.4 — Graphs and iterative processing: Pregel

Chapter 2 met graphs as data models with OLTP-style traversal queries — find a few vertices matching some criteria. Batch processing has a different graph question: offline analysis or processing of an entire graph — machine learning (recommendation engines), ranking systems, and the most famous of them all, PageRank, which estimates a web page’s popularity from what links to it and feeds the ordering of search results.

First, an important disentangling: dataflow engines arrange a job’s operators as a directed acyclic graph — that is not graph processing. In dataflow, the flow of data is graph-shaped while the data itself is relational-style tuples; in graph processing, the data itself is the graph. Another unfortunate naming collision.

Graph algorithms usually work by traversing one edge at a time — joining a vertex with an adjacent vertex to propagate information, repeating until some condition holds (no more edges to follow, or a metric converges — the locations-in-North-America example from Chapter 2 was a transitive closure computed exactly this way). You can store the graph in the distributed filesystem as files of vertices and edges, but “repeat until done” cannot be expressed in plain MapReduce, which makes exactly one pass. The workaround: an external scheduler runs a batch job per iteration, checks the completion condition when it finishes, and loops. Inefficient — MapReduce re-reads the entire input and produces an entirely new output dataset even when only a small part of the graph changed since the last iteration.

The bulk synchronous parallel model

The fix that became popular for batch graph processing is the bulk synchronous parallel (BSP) model of computation, widely known by the name of the Google paper that popularized it: Pregel. Open-source implementations include Apache Giraph, Spark’s GraphX API, and Flink’s Gelly API. The idea echoes MapReduce’s key-as-address trick: where a mapper “sends a message” to a particular call of the reducer by choosing the key, in Pregel one vertex sends a message to another vertex — typically along an edge. Each iteration (a superstep) calls a function for each vertex, handing it all the messages sent to it — much like a reducer call. The difference from MapReduce: a vertex remembers its state in memory from one iteration to the next, so each superstep only processes new incoming messages. If no messages are sent to some part of the graph, no work happens there.

Figure 10-6 (recreated) · One Pregel superstep

A superstep in one picture. Vertex state persists in memory across supersteps; messages sent in one round are delivered in the next, exactly once, even over a lossy network. Fault tolerance comes from periodically checkpointing every vertex’s state at the end of a superstep — a node loses its in-memory state, and the simplest recovery rolls the whole computation back to the last checkpoint (with deterministic algorithms and logged messages, selective recovery of just the lost partition is possible). The framework partitions the graph and routes messages by vertex ID — the vertex never learns which machine it runs on. Optimal partitioning (co-locating chatty vertices) is hard; in practice, partitioning is often just by arbitrarily assigned vertex ID, so graph algorithms carry heavy cross-machine communication — the intermediate messages can be larger than the graph itself, and the network overhead can dominate. Which suggests a threshold: if the graph fits in one machine’s memory — or even on its disks (single-machine frameworks like GraphChi) — a single-machine, maybe single-threaded, algorithm will likely outperform the distributed version. Only graphs too big for one machine force the distributed route, and efficient parallel graph processing remains open research.

10.3.5 — High-level APIs and declarative languages

As the engines matured — clusters over 10,000 machines processing many petabytes — the problem of physically operating batch jobs at scale was considered more or less solved, and attention shifted to the programming model, processing efficiency, and broadening the problems these tools can solve. Hive, Pig, Cascading, and Crunch arose precisely because hand-written MapReduce is laborious; as Tez emerged, these languages gained the side benefit of moving to the new engine without rewriting job code, and Spark and Flink ship their own high-level dataflow APIs (inspired by FlumeJava).

These APIs use relational-style building blocks — join datasets on a field, group tuples by key, filter, aggregate by count or sum — implemented internally by the join and grouping algorithms from this chapter. Beyond needing less code, the high-level interfaces enable interactive use: write analysis code incrementally in a shell, run it frequently, watch what it does — echoing the Unix philosophy’s experimentation loop — and they improve execution efficiency at the machine level, too.

How so? Because declaring joins relationally lets the framework choose the algorithm. Hive, Spark, and Flink have cost-based query optimizers that analyze the join inputs’ properties, pick the most suitable join algorithm, and even reorder joins to minimize intermediate state — and the choice of join algorithm can make a big difference to a batch job’s performance. It’s Chapter 2’s lesson again: say what, not how, and the optimizer figures out how — so you don’t have to remember everything this chapter taught you. MapReduce and successors differ from fully declarative SQL in a crucial way, though: they’re built around callbacks — a user function free to call arbitrary code over each record — which is what lets batch systems draw on the huge ecosystems of existing libraries for parsing, natural-language analysis, image analysis, and numerical algorithms. Databases have user-defined functions, but they’re cumbersome and poorly integrated with the package managers programmers actually use (Maven, npm, Rubygems). Declarative features creep in from other directions too: a callback that is just a simple filter or field selection can be compiled instead of called — Spark generates JVM bytecode, Impala uses LLVM native code — enabling vectorized execution (Chapter 3) and column layouts that read only required fields. The convergence this drives is worth savoring: batch frameworks with built-in operators and declarative optimizers begin to look like MPP databases with comparable performance, while keeping the freedom to run arbitrary code on arbitrary data. And standard processing patterns keep reappearing — reusable libraries emerged: Mahout (machine learning on MapReduce, Spark, Flink) and MADlib (inside an MPP database, Apache HAWQ) for statistical algorithms; k-nearest-neighbor style similarity search; approximate string matching for genome analysis. In the end they are all just systems for storing and processing data.

10.4 · Pulling it together

Summary

The chapter traced one design philosophy from awk to Spark: inputs are immutable, outputs are meant to become the input to another (as yet unknown) program, and complex problems are solved by composing small tools that do one thing well. The uniform interface that makes composition possible is files and pipes in Unix, a distributed filesystem in MapReduce, and dataflow engines add pipe-like transports for intermediates — while the initial input and final output of a job are still HDFS.

Distributed batch frameworks solve two hard problems. Partitioning: mappers partition by input file blocks, then repartition, sort, and merge into a configurable number of reducer partitions — all to bring related data (the same keys) to the same place; dataflow engines avoid sorting unless required but partition similarly. Fault tolerance: MapReduce’s frequent disk writes make single-task recovery easy but slow the failure-free case; dataflow engines materialize less, keep more in memory, and must recompute more when a node fails — and deterministic operators shrink the recomputation. Join algorithms, one line each: sort-merge — both inputs through key-extracting mappers, partition-sort-merge delivers same-key records to one reducer call; broadcast hash — one input small enough to load entirely into every mapper’s hash table while the large input streams; partitioned hash — both inputs partitioned identically, hash join per partition.

The programming model is deliberately restricted — callbacks assumed stateless with no side effects beyond their designated output — and that restriction is precisely what lets the framework hide the hard distributed-systems problems: tasks retry safely, failed tasks’ output is discarded, several attempts of one partition may succeed but only one’s output becomes visible, and the final result is as if no faults occurred at all — stronger semantics than most online services offer. And the defining characteristic of batch processing: it reads input, produces output, and doesn’t modify the input — the output is derived. Crucially, the input is bounded: known, fixed size (log files at a point in time, a database snapshot), so a job knows when it has read everything, and eventually finishes. In the next chapter the input becomes unbounded — never-ending streams — and a job is never complete, because at any time more work may arrive. Stream and batch processing rhyme, but that one assumption changes everything about how the systems are built.

Glossary

batch processing
Offline jobs that take a large fixed input, run minutes to days, and produce output — nobody waiting. Scheduled periodically; measured by throughput, not response time.
Unix pipe
Connects one process’s stdout to another’s stdin through a small in-memory buffer — no intermediate files. The composition mechanism the entire chapter is named after.
uniform interface
Every program using the same I/O interface (in Unix: the file — an ordered byte sequence), so any output feeds any input. Rare and precious; URLs/HTTP are another example.
stdin / stdout
The conventions separating logic from wiring: programs read standard input and write standard output without knowing where either is attached — the shell decides.
working set
The memory a job needs random access to — for URL counting, only the distinct URLs, not the log size. Fits in memory → hash table; larger → sorting, which uses disks efficiently (sequential mergesort runs, SSTable-style).
MapReduce
Framework for processing large datasets on a distributed filesystem: mapper called per input record (emits key-value pairs), framework sorts by key, reducer called per key over all its values. One job = one Unix process, industrialized.
mapper
Called once per input record; extracts key and value; may emit any number of pairs (or none); stateless between records. Its job: put data into a form suitable for sorting.
reducer
Called with one key and an iterator over all its values (possibly more than memory); may emit any number of output records. Its job: process what sorting grouped.
shuffle
Partition mapper output by reducer (hash of key), sort, and copy each partition from mappers to reducers over the network. No randomness — unlike a deck of cards. MapReduce’s heart.
HDFS
Hadoop Distributed File System — open-source GFS reimplementation. Shared-nothing: a daemon per machine plus a central NameNode tracking which blocks live where; fault tolerance by replication or erasure coding (Reed–Solomon). Biggest deployments: tens of thousands of machines, hundreds of petabytes.
NameNode
HDFS’s central server that records which file blocks are stored on which machine — the filesystem’s directory brain.
speculative execution
Running backup copies of slow (straggler) tasks and taking the first successful result — one reason side-effect-free batch code is essential.
putting computation near the data
Scheduling each map task on a machine storing a replica of its input file, when spare RAM and CPU allow — copy the code, not the data.
secondary sort
Arranging reducer input so that within each key, records arrive in a chosen order — the user profile record before that user’s events, events in timestamp order.
reduce-side (sort-merge) join
Mappers on both inputs emit (join key, record); partition-sort-merge brings all same-key records to one reducer call. No assumptions about inputs; pays a full shuffle of both sides. Output partitioned and sorted by key.
broadcast hash join
Map-side join for a large input plus a small one that fits in every mapper’s memory: load the small side into an in-memory hash table, stream the large side, look up each record. No shuffle, no reducers. Hive “MapJoin,” Pig “replicated join.”
partitioned hash join
Map-side join when both inputs are partitioned identically (same key, same hash function, same partition count): each mapper hash-joins just its partition. Hive “bucketed map join.”
map-side merge join
When inputs are identically partitioned and sorted by the same key, mappers merge directly — like a reducer without the shuffle; size doesn’t matter.
hot key (linchpin object)
A disproportionately active record — the celebrity with millions of followers — that floods one reducer with skew while others idle, stalling every downstream job.
skew handling
Pig’s skewed join (sampling finds hot keys, then random reducer choice plus replicating the other input), Crunch’s sharded join (hot keys declared explicitly), Hive’s skewed join optimization (hot keys in separate files, joined map-side), and two-stage aggregation for grouped counts.
sessionization
Collating all activity events for one user session (session cookie or user ID as grouping key) to reconstruct action sequences — the basis of A/B testing and marketing attribution.
human fault tolerance
What immutable inputs and replaceable outputs buy: buggy code can be rolled back and the output simply regenerated (or yesterday’s output switched back in) — recovery from human error, impossible with read-write transactions.
data lake (enterprise data hub)
Dump data raw into the distributed filesystem first, model later — schema-on-read at organizational scale, decoupling data collection from schema design. “Raw data is better.”
preemption
A cluster scheduler killing lower-priority tasks to free resources for higher-priority ones. Google overcommits resources this way; ~5% of one-hour MapReduce tasks get preempted — an order of magnitude above hardware-failure rates — which is why MapReduce was designed for frequent faults.
materialization
Eagerly computing and writing out intermediate state, rather than streaming it. MapReduce materializes every job’s output to the distributed filesystem; Unix pipes and dataflow engines mostly don’t.
dataflow engine
Spark, Tez, Flink: execute an entire workflow as one job, with operators (generalized map/reduce functions) connected flexibly — sort only where needed, no redundant mappers, locality-aware scheduling, in-memory/local-disk intermediates, pipelined startup, JVM reuse.
DAG (directed acyclic graph)
The shape of operator data dependencies in a dataflow engine — the flow of data is graph-shaped. Not the same thing as graph processing, where the data itself is a graph.
RDD (resilient distributed dataset)
Spark’s abstraction tracking each piece of data’s ancestry — which input partitions and operators produced it — so lost intermediate state can be recomputed after a failure.
Pregel / BSP
Bulk synchronous parallel graph processing: each vertex keeps in-memory state across supersteps, processes messages delivered from the previous superstep, and sends messages delivered in the next. Exactly-once delivery, checkpoints for faults. Implementations: Giraph, GraphX, Gelly.
superstep
One BSP iteration. A barrier separates supersteps: every message of round k is copied over the network before round k+1 begins. Vertices are “actors with a schedule and a checkpoint.”
transitive closure
Repeatedly following edges to find everything reachable — all locations within North America, for example. The natural graph algorithm shape that single-pass MapReduce can’t express.
bounded input
The defining assumption of batch processing: input of known, fixed size, so a job knows when it’s read everything and eventually completes. Chapter 11 removes it.
