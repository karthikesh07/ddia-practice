7.0 · The setup

The slippery concept of a transaction

Everything in this chapter starts from a list of things that go wrong in data systems. The database software or hardware may fail at any time — including in the middle of a write operation. The application may crash at any time — including halfway through a series of operations. Network interruptions can cut off the application from the database, or one node from another. Several clients may write at the same time, overwriting each other’s changes. A client may read data that makes no sense because it was only partially updated. Race conditions produce surprising bugs.

A transaction is the mechanism of choice for simplifying all this: a way for an application to group several reads and writes into a logical unit. Conceptually, all the reads and writes in a transaction are executed as one operation: either the entire transaction succeeds (commit) or it fails (abort, rollback). If it fails, the application can safely retry. Transactions are not a law of nature — they were created to simplify the programming model, so the application can ignore certain error scenarios because the database handles them instead: safety guarantees.

Not every application needs transactions, and sometimes weakening or abandoning them buys performance or availability. The history: almost all relational databases follow the style introduced in 1975 by IBM System R, the first SQL database — the general idea has remained virtually the same for 40 years. Then in the late 2000s, NoSQL databases offered new data models, replication, and partitioning by default, and transactions were the main casualty — many abandoned them entirely or redefined the word to mean much less. The popular belief became “transactions are the antithesis of scalability.” Both viewpoints are pure hyperbole. Transactions have advantages and limitations, like every other design choice.

7.0.1 — The meaning of ACID

The safety guarantees are described by ACID — Atomicity, Consistency, Isolation, Durability — coined in 1983 by Theo Härder and Andreas Reuter. The high-level idea is sound, but the devil is in the details: one database’s implementation of ACID does not equal another’s, the meaning of isolation is especially ambiguous, and today “ACID compliant” is mostly a marketing term. (Systems that don’t meet the criteria are sometimes called BASE — Basically Available, Soft state, Eventual consistency — which is even vaguer; the only sensible definition of BASE is “not ACID.”)

A — Atomicity

Not about concurrency (that’s isolation). It describes what happens when a fault occurs partway through several writes: if the transaction cannot complete, it is aborted and all its writes are discarded. The defining feature is really abortability.

C — Consistency

An application-specific notion of the database being in a “good state” — invariants that must always hold (in accounting, credits and debits balanced). The database can’t stop you from writing bad data, so the C doesn’t really belong in ACID.

I — Isolation

Concurrently executing transactions are isolated from each other — they cannot step on each other’s toes. Formally: serializability, the pretense that each transaction is the only one running.

D — Durability

Once a transaction has committed successfully, its data will not be forgotten, even if there’s a hardware fault or the database crashes — written to nonvolatile storage, or replicated to some number of nodes.

Two of these deserve a closer look. On atomicity: in multi-threaded programming, “atomic” means no other thread can see a half-finished operation — but in ACID, atomicity is not about concurrency at all. It’s about faults during multi-write sequences: a process crashes, the network drops, a disk fills, a constraint is violated. Without atomicity, you don’t know which changes took effect; the application could retry, but that risks doing the same change twice. With atomicity, an aborted transaction is guaranteed to have changed nothing — so it can safely be retried. “Abortability” would have been a better term.

On consistency: the word is terribly overloaded — replica consistency and eventual consistency (Chapter 5), consistent hashing (Chapter 6), linearizability in CAP (Chapter 9), and here, the application’s own invariants. The ACID sense is a property of the application, not the database: atomicity, isolation, and durability are properties of the database, but the application must define its transactions to preserve its own consistency. (Joe Hellerstein’s remark: the C was “tossed in to make the acronym work.”)

On isolation, a first taste of the trouble: serializable isolation is rarely used in practice because of its performance penalty — Oracle 11g doesn’t even implement it, offering an isolation level called “serializable” that actually implements something weaker (snapshot isolation).

Figure 7-1 (recreated) · Two clients concurrently incrementing a counter

Each client reads the current value, adds 1, and writes it back — a read-modify-write cycle. Interleaved, the second write doesn’t include the first modification: the later write clobbers the earlier one. Isolation should make each transaction behave as if it were the only one on the database.

7.0.2 — Sidebar: replication and durability

Durability has been understood as writing to an archive tape, then writing to disk or SSD, and more recently as replication. In a replicated database, durability may mean the data has been copied to some number of nodes — and the database must wait for those replications to complete before reporting a commit. But perfect durability does not exist, and the sidebar’s reality check is worth absorbing:

  • Write to disk and the machine dies — data safe but inaccessible until the machine is fixed or the disk moved; replicated systems stay available.
  • A correlated fault — a power outage or a bug that crashes every node on a particular input — can knock out all replicas at once, losing anything that lived only in memory. Writing to disk still matters, even for in-memory databases.
  • In an asynchronously replicated system, recent writes can be lost when the leader becomes unavailable (Chapter 5’s failover problem, again).
  • When power is suddenly cut, SSDs have been shown to sometimes violate their guarantees — even fsync isn’t guaranteed to work correctly. Disk firmware has bugs like any other software.
  • Subtle interactions between storage engine and filesystem can corrupt files after a crash, and on-disk data can gradually corrupt without detection — if it’s been corrupted for a while, replicas and recent backups may also be bad, forcing a restore from a historical backup.
30–80% Of SSDs develop at least one bad block in the first four years one study’s finding — magnetic drives get fewer bad sectors but fail completely more often
weeks How fast an unpowered SSD can start losing data depending on temperature — power off is not a pause button

The conclusion to carry forward: no one technique provides absolute guarantees — only risk-reduction techniques that should be used together: writing to disk, replicating to remote machines, and backups. Take any theoretical “guarantee” with a healthy grain of salt.

7.0.3 — Single-object and multi-object operations

Atomicity and isolation both describe what the database should do when a client makes several writes in one transaction: atomicity means an error halfway through aborts and discards everything so far (all-or-nothing); isolation means concurrent transactions see either all or none of another transaction’s writes, never a subset.

The book’s running example for what isolation prevents: an email application that stores an unread counter in a separate field (a denormalization). When a message arrives, the transaction inserts the email and increments the counter. If another transaction reads between those two writes, it sees the new message but a stale counter — an inconsistent halfway state caused by reading another transaction’s uncommitted writes: a dirty read.

And for atomicity: if the counter update fails halfway through the transaction, an atomic database aborts and rolls back the already-inserted email — the mailbox and the counter never drift out of sync.

Multi-object transactions need a way to know which operations belong to the same transaction — in relational databases, typically the client’s TCP connection: everything between BEGIN TRANSACTION and COMMIT on one connection is one transaction.

Single-object writes

Atomicity and isolation also apply to a single changing object. Write a 20 KB JSON document and ask: if the connection drops after 10 KB, does the database store an unparseable fragment? If power fails mid-overwrite, do old and new values get spliced together? If another client reads during the write, does it see a half-updated value? Storage engines almost universally prevent this: atomicity via a log for crash recovery, isolation via a lock on each object. Some databases also offer richer atomic single-object operations — an increment (removing the need for a read-modify-write cycle) and compare-and-set (write only if the value hasn’t been concurrently changed). Useful — but marketing that calls these “lightweight transactions” or “ACID” is misleading: a transaction is a mechanism for grouping multiple operations on multiple objects.

The need for multi-object transactions

Many distributed datastores abandoned multi-object transactions because they’re hard to implement across partitions. But nothing fundamentally prevents them (distributed transactions: Chapter 9), and three situations genuinely need them:

1.

Foreign key references

Rows in one table referencing rows in another (or vertices with edges). Inserting several records that refer to one another needs the foreign keys correct and up to date, or the data becomes nonsensical.

2.

Document denormalization

Document models keep related fields in one document — but document databases lacking joins encourage denormalization, and updating denormalized data means updating several documents at once (the email example).

3.

Secondary indexes

Almost everything but pure key-value stores has them, and indexes are separate objects: without isolation, a record can appear in one index but not another mid-update.

All three can be built without transactions — but error handling gets much more complicated without atomicity, and the lack of isolation invites concurrency bugs.

7.0.4 — Handling errors and aborts

A key feature of a transaction is that it can be aborted and safely retried. ACID databases are built on this philosophy: if atomicity, isolation, or durability is in danger, abandon the transaction entirely rather than leave it half-finished. Not everything follows it — leaderless replication datastores work on a best-effort basis: “the database will do as much as it can, and if it runs into an error, it won’t undo what it already did.” The application recovers.

And yet even developers on ACID databases prefer the happy path: popular ORMs like Rails’s ActiveRecord and Django don’t retry aborted transactions — the exception bubbles up, the user’s input is thrown away. A shame, since the whole point of aborts is to enable safe retries. Although — retrying isn’t perfect either:

1.

The transaction actually succeeded

If the network failed while the server tried to acknowledge the successful commit, the client thinks it failed — and retrying performs it twice, unless you have application-level deduplication.

2.

The error is overload

Retrying makes the problem worse. Limit retry counts, use exponential backoff, and handle overload-related errors differently.

3.

Only transient errors are worth retrying

Deadlock, isolation violation, temporary network interruption, failover — yes. A permanent error like a constraint violation will fail every time.

4.

Side effects outside the database

If the transaction sends an email, aborting doesn’t unsend it — and retrying sends it again. For multiple systems committing or aborting together, you need two-phase commit (Chapter 9).

5.

The client process fails while retrying

Whatever data it was trying to write is lost.

7.1 · The partial shields

Weak isolation levels

If two transactions don’t touch the same data, they can run in parallel safely. Concurrency bugs only come into play when one transaction reads data that another is concurrently modifying. Those bugs are hard to find by testing — they trigger only when you get unlucky with the timing, they’re rare, and they’re difficult to reproduce; and in a large application you don’t necessarily know what else is accessing the database. So databases have long tried to hide concurrency from developers with transaction isolation. In theory, isolation should let you pretend no concurrency is happening. In practice, serializable isolation has a performance cost many databases won’t pay, so weaker levels that protect against some race conditions but not all are the norm — harder to understand, prone to subtle bugs.

This is not a theoretical problem

Congestion bugs from weak isolation have caused substantial loss of money, investigations by financial auditors, and customer data corruption. The popular retort — “use an ACID database if you’re handling financial data!” — misses the point: even many popular relational databases (usually considered “ACID”) use weak isolation, so they wouldn’t necessarily have prevented these bugs.

7.1.1 — Read committed

The most basic level, making two guarantees:

No dirty reads

When reading, you only see data that has been committed.

No dirty writes

When writing, you only overwrite data that has been committed.

No dirty reads

A transaction has written data but hasn’t committed or aborted yet. Can another transaction see that uncommitted data? If yes — that’s a dirty read. Under read committed, writes become visible to others only when the transaction commits (and then all its writes become visible at once). Two reasons this matters: a multi-object update would be seen partially (the new email but the old counter — confusing to users and misleading to other transactions), and if the writing transaction aborts, a dirty reader would have seen data that is rolled back — never actually committed at all, which gets mind-bending fast.

Figure 7-4 (recreated) · No dirty reads

The read-visibility half of read committed.

No dirty writes

Two transactions update the same object; if the earlier write belongs to a transaction that hasn’t committed yet, the later write is overwriting an uncommitted value — a dirty write. Read committed prevents this, usually by delaying the second write until the first transaction commits or aborts. The book’s example: a used-car site where Alice and Bob simultaneously buy the same car. Buying requires two writes — update the listing, and send the invoice. With dirty writes interleaved, the sale is awarded to Bob but the invoice goes to Alice.

Figure 7-5 (recreated) · Dirty writes mix up the car sale

But note: read committed does not prevent Figure 7-1’s counter race — the second write there happens after the first transaction commits, so it isn’t dirty. Still wrong, for a different reason (lost updates, below).

Implementing read committed

Very popular — the default in Oracle 11g, PostgreSQL, SQL Server 2012, MemSQL, and many others. Dirty writes are prevented with row-level locks: to modify an object, a transaction must first acquire the lock on it and hold it until commit or abort; only one transaction can hold it. This is automatic in read committed mode and stronger levels. Dirty reads — two options:

1.

Read locks (bad idea)

Require readers to briefly acquire the same lock. It works, but one long-running write transaction forces many read-only transactions to wait — harmful to read response times and operability.

2.

Version tracking (what most do)

For every written object, remember both the old committed value and the new value held by the lock owner. While the write transaction is ongoing, other transactions are simply given the old value; when the write commits, readers switch to the new value. No reads block.

At the time of writing, the only mainstream databases using locks for read committed are IBM DB2 and Microsoft SQL Server with read_committed_snapshot=off.

7.1.2 — Snapshot isolation and repeatable read

Read committed looks sufficient at first glance — it allows aborts, prevents reading incomplete results, prevents intermingled writes. But there are still plenty of ways to get concurrency bugs. The signature example — Alice’s bank accounts:

Figure 7-6 (recreated) · Read skew: $100 vanishes

Alice has $1,000 split across two accounts; a transaction transfers $100 between them. If her read lands between the debit and the credit, she sees an inconsistent state: after the outgoing transfer but before the incoming payment. This is a nonrepeatable read, or read skew — reading the balance again later would return a different value. Read skew is acceptable under read committed: everything Alice saw was committed at the time she read it.

Reloading the page a few seconds later would fix Alice’s view. But some situations can’t tolerate temporary inconsistency: backups — copying a large database takes hours, writes continue meanwhile, and the backup ends up with old parts and new parts; restoring from it makes the inconsistencies permanent. And analytic queries and integrity checks — scans over large parts of the database return nonsense if they observe different points in time.

The solution: snapshot isolation — each transaction reads from a consistent snapshot of the database: all the data committed at the start of the transaction. Even if other transactions change the data afterwards, each transaction keeps seeing the old state. A boon for long-running read-only queries like backups and analytics. Supported by PostgreSQL, MySQL with InnoDB, Oracle, SQL Server, and others.

Implementing snapshot isolation: MVCC

Like read committed, write locks prevent dirty writes — one writing transaction can block another writing the same object. But reads take no locks at all. The key principle: readers never block writers, and writers never block readers — long read queries on a consistent snapshot run alongside normal writes without lock contention. To pull that off, the database keeps several different committed versions of an object side by side, because different in-progress transactions need different points in time: multi-version concurrency control (MVCC).

A typical approach (Figure 7-7, PostgreSQL-flavored): each transaction gets a unique, always-increasing transaction ID (txid) at start; every write is tagged with the writer’s txid. Each row has a created_by field (the txid that inserted it) and a deleted_by field, initially empty. A delete doesn’t remove the row — it marks it by setting deleted_by. Later, when no transaction can still access the deleted data, a garbage collection process removes marked rows. An update is internally a delete + create.

Figure 7-7 (recreated) · MVCC with multi-version objects

Note the footnote-worthy detail: PostgreSQL’s transaction IDs are 32-bit integers that overflow after roughly 4 billion transactions; the vacuum process cleans up so the wraparound doesn’t corrupt data.

Visibility rules for a consistent snapshot

Transaction IDs decide which objects a reader sees. Four rules:

1.

In-progress writes are ignored

At the start of each transaction, the database lists all other transactions in progress; writes by those are ignored — even if they subsequently commit.

2.

Aborted writes are ignored

Permanently.

3.

Later transactions are ignored

Writes by transactions with a later (higher) txid — started after the current one — are invisible, committed or not.

4.

Everything else is visible

All other writes are visible to the application’s queries.

The rules apply to creation and deletion of objects. Simplified to a single condition: an object is visible if (a) the creating transaction had committed when the reader’s transaction started, and (b) the object is not marked for deletion — or if it is, the deleting transaction had not yet committed when the reader started. In Figure 7-7: transaction 12 reads account 2 as $500, because the $500 row’s deletion was performed by transaction 13 (invisible to 12 by rule 3), and 13’s new $400 row is invisible for the same reason.

Read committed vs. snapshot isolation in MVCC terms: a typical approach is that read committed uses a separate snapshot for each query, while snapshot isolation uses the same snapshot for an entire transaction. And long-running transactions keep reading values that other transactions have long overwritten or deleted — that’s fine; never updating in place and always creating a new version is a small overhead for a consistent snapshot.

Indexes and snapshot isolation

How do indexes work in a multi-version database? Option one: the index points to all versions of an object, and an index query filters out versions invisible to the current transaction; as garbage collection removes old versions, the index entries go too. (PostgreSQL has optimizations for skipping index updates when versions of the same object fit on the same page.) Option two, used by CouchDB, Datomic, and LMDB: append-only / copy-on-write B-trees — updating a page doesn’t overwrite it but creates a new copy, with parents copied and repointed up to the root; unaffected pages stay immutable. Every write transaction creates a new B-tree root, and each root is a consistent snapshot of the database as of its creation — no transaction-ID filtering needed, at the cost of a background compaction/GC process.

Repeatable read, and why nobody knows what it means

Snapshot isolation is useful — especially for read-only transactions — but the naming is a mess, because the SQL standard has no concept of snapshot isolation (it’s based on System R’s 1975 isolation levels, and SI hadn’t been invented). The standard instead defines repeatable read, which looks superficially similar. So: PostgreSQL and MySQL call their snapshot isolation “repeatable read” because it satisfies the standard’s requirements — standards compliance. Oracle calls snapshot isolation “serializable.” And IBM DB2 uses “repeatable read” to refer to serializability. The standard’s definition is ambiguous, imprecise, and not implementation-independent; even the formal research definition of repeatable read isn’t met by most implementations. Nobody really knows what repeatable read means.

7.1.3 — Preventing lost updates

Read committed and snapshot isolation have mostly been about what a reader sees amid concurrent writes. The classic write-write conflict beyond dirty writes is the lost update (Figure 7-1): an application reads a value, modifies it, writes it back; two concurrent transactions doing this lose one modification — the later write clobbers the earlier. Three recurring scenarios: incrementing a counter or account balance; making a local change to a complex value like adding an element to a list inside a JSON document; and two users editing a wiki page, each saving the entire page contents. Four lines of defense:

Approach 1 — Atomic write operations

Remove the read-modify-write cycle from application code:

UPDATE counters SET value = value + 1 WHERE key = 'foo';

Concurrency-safe in most relational databases; MongoDB offers atomic operations for local modifications of a JSON document, Redis for its data structures. Implemented by taking an exclusive lock when the object is read (cursor stability) or by forcing atomic operations through a single thread. Usually the best choice — when the write can be expressed that way; wiki-page editing can’t. Watch out: ORMs make it easy to accidentally perform an unsafe read-modify-write instead.

Approach 2 — Explicit locking

When built-ins don’t suffice, the application locks the objects it will update, forcing concurrent read-modify-write cycles to happen sequentially. Example 7-1, a multiplayer game moving a robot:

BEGIN TRANSACTION; SELECT * FROM figures WHERE name = 'robot' AND game_id = 222 FOR UPDATE; -- Check whether move is valid, then update the position -- of the piece that was returned by the previous SELECT. UPDATE figures SET position = 'c4' WHERE id = 1234; COMMIT;

FOR UPDATE tells the database to lock all rows the query returns. It works, but getting it right requires care — forget one necessary lock somewhere and you’ve introduced a race condition.

Approach 3 — Automatically detecting lost updates

Let the read-modify-writes run in parallel; the transaction manager detects a lost update and aborts, forcing a retry. Efficient in conjunction with snapshot isolation: PostgreSQL’s repeatable read, Oracle’s serializable, and SQL Server’s snapshot isolation all detect lost updates and abort automatically. MySQL/InnoDB’s repeatable read doesn’t — some authors argue a database must prevent lost updates to qualify as snapshot isolation, so MySQL doesn’t provide it under that definition. The great advantage: no special database features in your code — you can forget a lock, but you can’t forget automatic detection.

Approach 4 — Compare-and-set

In databases without transactions, an update that only happens if the value hasn’t changed since you last read it:

-- This may or may not be safe, depending on the database implementation UPDATE wiki_pages SET content = 'new content' WHERE id = 1234 AND content = 'old content';

If the content no longer matches, the update affects nothing — check and retry if needed. The caveat: if the database lets the WHERE clause read from an old snapshot, the condition may be true even while a concurrent write is happening — check whether your database’s compare-and-set is safe before relying on it.

Conflict resolution and replication

Replicated databases add another dimension — multiple nodes accepting writes concurrently. Locks and compare-and-set assume a single up-to-date copy of the data, which multi-leader and leaderless replication cannot guarantee — so those techniques don’t apply. Instead (Chapter 5): concurrent writes create several siblings that application code or special data structures resolve and merge. Atomic operations can work well when they’re commutative — order-independent, like incrementing a counter or adding to a set — the idea behind Riak 2.0 datatypes, which merge concurrent updates without losing any. And last write wins, the default in many replicated databases, is prone to lost updates — Chapter 5’s warning, again.

7.1.4 · The subtle one

Write skew and phantoms

Dirty writes and lost updates are conflicts over the same objects. Write skew is subtler: conflicts over a pattern that spans different objects.

The doctors on-call example

A hospital application manages on-call shifts. Several doctors are usually on call at once, but at least one must be on call at all times. Alice and Bob are the two on-call doctors for a shift; both feel unwell and both click “go off call” at roughly the same time:

Figure 7-8 (recreated) · Write skew: no doctor left on call

Each transaction checks that two or more doctors are on call, concludes it’s safe for one to leave, and updates its own record. Both commit; the requirement is violated. Neither a dirty write nor a lost update — the two transactions touched different objects — but definitely a race condition: run one after the other and the second doctor would have been stopped.

Characterizing write skew

Write skew is a generalization of the lost update: two transactions read the same objects, then update some of those objects — possibly different ones. When they update the same object, you get a dirty write or lost update instead. The prevention options are more restricted:

1.

Atomic single-object operations don’t help

Multiple objects are involved.

2.

Automatic detection doesn’t help

The lost-update detection in PostgreSQL’s repeatable read, MySQL/InnoDB’s repeatable read, Oracle’s serializable, and SQL Server’s snapshot isolation does not catch write skew. Preventing it automatically requires true serializable isolation.

3.

Constraints — only sometimes

Uniqueness and foreign keys are enforceable, but “at least one doctor on call” spans multiple objects; most databases can’t express it (triggers or materialized views, maybe).

4.

Explicit locking — the second-best

If you can’t run serializable: lock the rows the transaction depends on. SELECT * FROM doctors WHERE on_call = true AND shift_id = 1234 FOR UPDATE — then the second transaction’s check blocks until the first commits.

More examples of write skew

  • Meeting rooms: check for overlapping bookings; if none, insert yours. Two transactions can both see “no bookings” and both insert overlapping ones — Example 7-2 below.
  • Multiplayer game: Example 7-1’s lock stops two players moving the same figure, but not two figures moving to the same square; a unique constraint may or may not fit the rule being enforced.
  • Claiming a username: two concurrent sign-ups check the name is free and create accounts. The one case with a clean fix: a unique constraint — the second insert aborts.
  • Double spending: insert a tentative spending item, list the account’s items, check the sum is positive — two concurrent spends can both pass the check and drive the balance negative, neither seeing the other.
BEGIN TRANSACTION; -- Check for any existing bookings that overlap with the period of noon-1pm SELECT COUNT(*) FROM bookings WHERE room_id = 123 AND end_time > '2015-01-01 12:00' AND start_time < '2015-01-01 13:00'; -- If the previous query returned zero: INSERT INTO bookings (room_id, start_time, end_time, user_id) VALUES (123, '2015-01-01 12:00', '2015-01-01 13:00', 666); COMMIT;

Example 7-2 — the meeting room booking, not safe under snapshot isolation. (In PostgreSQL you could do this more elegantly with range types, but they aren’t widely supported.)

Phantoms causing write skew

All of those examples share one pattern: (1) a SELECT checks some requirement — two doctors on call, no conflicting bookings, the square is free, the username isn’t taken, the balance is positive; (2) the application decides based on the result; (3) a write changes the precondition of that decision — re-run the SELECT after committing, and it returns a different answer. The steps may even occur in a different order.

In the doctors example, the row being modified was one of the rows the query returned, so SELECT FOR UPDATE could lock it. The other examples are different: they check for the absence of rows matching a condition, and the write adds a row matching that same condition. If the query returns no rows, there’s nothing to attach a lock to.

The phantom, drawn · both bookings see zero, both insert

A phantom: a write in one transaction changes the result of a search query in another. Snapshot isolation avoids phantoms in read-only queries, but in read-write transactions like these, phantoms make write skew particularly tricky.

Materializing conflicts

If the problem is that there’s no object to attach a lock to — artificially introduce one. For meeting rooms: create a table of time slots and rooms, one row per room per 15-minute period, pre-created for (say) the next six months. A transaction wanting to book locks (SELECT FOR UPDATE) the rows for its room and time range, then checks and inserts as before. The extra table stores no booking information — it’s purely a collection of locks, turning a phantom into a lock conflict on concrete rows. This is called materializing conflicts.

A last resort

It’s hard and error-prone to figure out how to materialize conflicts, and ugly to let a concurrency-control mechanism leak into the application’s data model. A serializable isolation level is much preferable in most cases.

7.3 · The real thing

Serializability

The sad situation, restated: isolation levels are hard to understand and inconsistently implemented; looking at application code, it’s difficult to tell whether it’s safe at a particular level — especially in a large application where you don’t know what else runs concurrently; and there are no good tools to help detect race conditions (static analysis hasn’t made it to practice; concurrency testing is hard because problems occur only with unlucky timing). This has been true since weak isolation levels appeared in the 1970s, and the answer from researchers has been simple all along: use serializable isolation.

Serializable isolation is the strongest level: even though transactions execute in parallel, the end result is the same as if they had run one at a time — so if transactions behave correctly individually, they behave correctly concurrently; all race conditions prevented. Most databases providing it today use one of three techniques: literally executing transactions in a serial order, two-phase locking (for decades the only viable option), or optimistic techniques such as serializable snapshot isolation.

7.3.1 — Actual serial execution

The simplest way to avoid concurrency problems: remove the concurrency entirely — execute one transaction at a time, in serial order, on a single thread. No conflict detection or prevention needed; the isolation is serializable by definition. The idea seems obvious, but database designers only considered it feasible around 2007. What changed?

1.

RAM got cheap

The entire active dataset can live in memory for many use cases — transactions that would wait on disk become fast, in-memory operations.

2.

OLTP transactions are short

They make a small number of reads and writes. Long-running analytic queries are typically read-only and run on a consistent snapshot outside the serial loop.

Implemented in VoltDB/H-Store, Redis, and Datomic. A system designed for single-threaded execution can beat a concurrent one by avoiding locking overhead — but throughput is capped at a single CPU core.

Encapsulating transactions in stored procedures

Early database thinking imagined a transaction spanning an entire user activity — booking an airline ticket: search, decide, book seats on each flight, enter details, pay, all atomic. But humans are slow to make up their minds, and a database waiting for user input would have to juggle a huge number of mostly-idle transactions. So OLTP apps keep transactions short: on the web, a transaction commits within a single HTTP request; a new request starts a new transaction.

Even with the human out of the loop, transactions remained interactive: one statement at a time, results shuttling between application and database over the network. On a single-threaded database, that style would be dreadful — the thread would sit idle waiting for each next query. So systems with single-threaded serial processing require the whole transaction as a stored procedure, submitted ahead of time:

Figure 7-9 (recreated) · Interactive transaction vs. stored procedure

Provided all the data a transaction needs is in memory, the stored procedure runs very fast — no waiting for network or disk.

Pros and cons of stored procedures

Stored procedures have been part of the SQL standard since 1999 (SQL/PSM) and carry a bad reputation: every vendor has its own language (PL/SQL, T-SQL, PL/pgSQL) that hasn’t kept up with general-purpose languages; code running in a database is harder to manage — debug, version, deploy, test, monitor; and a database is more performance-sensitive than an app server, shared by many application servers, so a badly written procedure causes more trouble. But these are solvable: modern implementations use general-purpose languages — VoltDB uses Java or Groovy, Datomic Java or Clojure, Redis Lua. VoltDB also uses stored procedures for replication: instead of copying writes to each replica, it executes the same procedure on each — which requires the procedures to be deterministic (same result on every node; the current time via special deterministic APIs, for example).

Partitioning

Serial execution caps throughput at one CPU core. Read-only transactions can run elsewhere under snapshot isolation — but for high write throughput, partition the data (VoltDB supports this): if each transaction only touches one partition, each partition runs its own transaction thread independently, and throughput scales linearly with cores. Any transaction spanning multiple partitions must be coordinated in lock-step across all partitions it touches — and that is vastly slower:

~1,000 Cross-partition writes per second in VoltDB orders of magnitude below single-partition throughput — and not improved by adding more machines

Whether transactions can stay single-partition depends on the data structure: simple key-value data partitions easily; data with multiple secondary indexes likely requires a lot of cross-partition coordination. (If a transaction needs data that isn’t in memory, the best answer may be to abort it, fetch the data into memory asynchronously, and restart it when loaded — anti-caching.)

Summary of serial execution

  • Every transaction must be small and fast — one slow transaction stalls everything.
  • The active dataset must fit in memory; rarely-accessed data on disk would make single-threaded transactions very slow.
  • Write throughput must fit on one CPU core — or transactions must partition cleanly without cross-partition coordination.
  • Cross-partition transactions are possible but hard-limited in how much they can be used.

7.3.2 — Two-phase locking (2PL)

2PL ≠ 2PC

Two-phase locking sounds like two-phase commit, but they are completely different things. 2PC belongs to Chapter 9.

For around 30 years, there was only one widely used algorithm for serializability: 2PL (sometimes “strong strict two-phase locking”, SS2PL). The idea extends the row locks you’ve already seen: several transactions may read the same object concurrently as long as nobody is writing it — but the moment anyone wants to write, exclusive access is required:

1.

Readers block writers

If transaction A has read an object and B wants to write it, B must wait until A commits or aborts — B can’t change the object behind A’s back.

2.

Writers block readers

If A has written an object and B wants to read it, B waits until A commits or aborts — reading an old version mid-write is not acceptable under 2PL.

Compare with snapshot isolation’s mantra — readers never block writers, and writers never block readers — that’s the key difference. Because 2PL is serializable, it protects against everything discussed in this chapter, including lost updates and write skew.

Implementation

Used by the serializable isolation level in MySQL (InnoDB) and SQL Server, and the repeatable read level in DB2. Each object has a lock in either shared mode or exclusive mode:

  • To read an object: acquire the lock in shared mode — several transactions can hold it at once, but an existing exclusive lock means waiting.
  • To write: acquire it in exclusive mode — nobody else may hold it in any mode.
  • Read-then-write upgrades a shared lock to exclusive — same as acquiring exclusive directly.
  • Locks are held until the end of the transaction — that’s the “two phases”: acquire while executing, release all at commit/abort.

With so many locks in play, deadlock is easy: A waits for B’s lock while B waits for A’s. The database detects deadlocks automatically and aborts one of the transactions so the others can proceed — the aborted one is retried by the application.

Performance of two-phase locking

The big downside, and why 2PL isn’t used everywhere: transaction throughput and response times are significantly worse than under weak isolation — partly lock overhead, but mostly reduced concurrency: if two transactions try to do anything that might race, one waits. Traditional databases don’t limit transaction duration, so there’s no limit on how long a wait may last; queues form; latencies become unstable and terrible at high percentiles under contention — one slow or lock-hungry transaction can grind the whole system to a halt. Deadlocks are also much more frequent under 2PL serializable than in lock-based read committed, and every deadlock-aborted transaction has to do all its work again — significant wasted effort.

Predicate locks

A serializable database must also prevent phantoms: if one transaction searched for bookings of room 123 at noon–1pm, no other transaction may concurrently insert a conflicting booking. A predicate lock belongs not to one object but to all objects matching some search condition — e.g., the rows matched by SELECT * FROM bookings WHERE room_id = 123 AND end_time > '2018-01-01 12:00' AND start_time < '2018-01-01 13:00':

1.

Shared predicate lock on reads

Transaction A reading objects matching a condition acquires a shared-mode predicate lock on those conditions; if B holds an exclusive lock on any matching object, A waits.

2.

Exclusive check on writes

Before inserting, updating, or deleting any object, check whether its old or new value matches any existing predicate lock — if so, wait for that transaction to commit or abort.

The key idea: a predicate lock applies even to objects that do not yet exist — the phantoms that might be added in the future. 2PL with predicate locks prevents all write skew and race conditions, and the isolation becomes serializable.

Index-range locks (next-key locking)

Predicate locks perform poorly — checking many locks for matches is time-consuming. So most 2PL databases implement index-range locking, a simplified approximation: it’s safe to simplify a predicate to match a greater set of objects. The room-123-noon-to-1pm predicate can be approximated by locking all bookings of room 123 at any time, or all rooms between noon and 1pm — any write matching the original predicate definitely matches the approximation. In practice the database attaches the lock to an index entry (a room_id index entry, or a range in a time-based index), and a conflicting writer touching that part of the index encounters it and waits. Less precise than predicate locks — it may lock more than strictly necessary — but much cheaper, so a good compromise. With no suitable index to attach to, the fallback is a shared lock on the entire table: safe, but it stops all other transactions writing to that table.

7.3.3 — Serializable snapshot isolation (SSI)

The chapter’s bleak picture: serializability implementations that don’t perform well (2PL) or don’t scale (serial execution), versus weak isolation levels that perform but allow race conditions. Are serializability and good performance fundamentally at odds? Perhaps not. SSI provides full serializability with only a small performance penalty compared to snapshot isolation. It’s young — first described in 2008, the subject of Michael Cahill’s PhD thesis — used in single-node databases (the serializable isolation level in PostgreSQL since 9.1) and distributed ones (FoundationDB uses a similar algorithm).

Pessimistic vs. optimistic concurrency control

Pessimistic — 2PL

If anything might possibly go wrong (a lock held elsewhere), wait until it’s safe. Like mutual exclusion in multi-threaded programming. Serial execution is pessimism to the extreme — one transaction effectively holding an exclusive lock on the entire database, compensated by making each transaction very fast.

Optimistic — SSI

Transactions run anyway, hoping everything turns out fine; at commit, the database checks whether isolation was violated, and only transactions that executed serializably are allowed to commit — the others abort and retry.

Optimistic control is an old idea with known weaknesses: it performs badly under high contention (many transactions abort and retry, and retries add load to an already strained system). With enough spare capacity and moderate contention, it tends to beat pessimistic approaches — and contention can be reduced with commutative atomic operations (concurrent counter increments can all apply without conflict, as long as none of them reads the counter too). SSI is based on snapshot isolation — all reads from a consistent snapshot — and adds an algorithm for detecting serialization conflicts among writes and deciding whom to abort.

Decisions based on an outdated premise

The recurring pattern from write skew: a transaction reads data, decides, and writes based on what it saw. Put another way, the transaction acts on a premise — a fact true at the beginning (“there are two doctors on call”) — which may no longer be true at commit time. The database can’t know how the application uses query results, so it must assume any change in the result means the writes may be invalid: there may be a causal dependency between the queries and the writes, and to provide serializability it must detect when a transaction acted on an outdated premise and abort it. Two cases to detect:

Figure 7-10 (recreated) · Detecting stale MVCC reads

The database tracks when a transaction ignores another’s writes due to MVCC visibility rules; at commit, it checks whether any ignored write has since committed. If so — abort.

Why wait until committing?

Why not abort transaction 43 the moment the stale read is detected? Because at read time the database doesn’t yet know whether 43 will write anything — if it’s read-only, there’s no risk of write skew, and aborting it would be unnecessary. The other transaction may also abort or still be uncommitted at 43’s commit time — in which case the read wasn’t stale after all. Waiting avoids unnecessary aborts and preserves snapshot isolation’s support for long-running reads on a consistent snapshot.

Figure 7-11 (recreated) · Detecting writes that affect prior reads

Like index-range locks, but the locks don’t block: a write into a range other transactions have read acts as a tripwire, notifying them that their read may be outdated. First committer wins; the other transaction aborts when its own commit finds the conflicting write already committed.

In Figure 7-11, transactions 42 and 43 both search for on-call doctors in shift 1234; the index entry records both readers (table level if there’s no index). When 43 writes, it notifies 42 — and vice versa. Transaction 42 commits first and succeeds (43’s write hasn’t taken effect yet, since 43 hasn’t committed). When 43 commits, 42’s already-committed write makes the conflict real — so 43 aborts.

Performance of SSI

Engineering details decide how well it works — notably the granularity of read/write tracking: detailed tracking is precise about who must abort but expensive to maintain; coarse tracking is faster but aborts more transactions than strictly necessary. PostgreSQL uses theory to prove some overwrites are harmless and reduce unnecessary aborts. The advantages over 2PL: no lock waiting — writers don’t block readers and vice versa, so query latency is more predictable, and read-only queries run lock-free on a consistent snapshot (great for read-heavy workloads). The advantages over serial execution: not limited to one CPU core — FoundationDB distributes conflict detection across machines, scaling to high throughput with transactions that touch multiple partitions. The main sensitivity: the abort rate — read-write transactions must be fairly short (long-running read-only transactions are fine), though SSI is probably less sensitive to slow transactions than 2PL or serial execution.

7.4 · Pulling it together

Summary

Transactions are an abstraction that lets an application pretend certain concurrency problems and certain faults don’t exist — a large class of errors collapses into a simple transaction abort, and the application just tries again. The chapter went deep on concurrency control: read committed, snapshot isolation (often called repeatable read), and serializable, characterized by the race conditions each permits. The race conditions, for the record:

1.

Dirty reads

One client reads another client’s writes before they commit. Prevented by read committed and stronger.

2.

Dirty writes

One client overwrites data another has written but not committed. Prevented by almost all transaction implementations.

3.

Read skew (nonrepeatable reads)

A client sees different parts of the database at different points in time. Prevented by snapshot isolation / MVCC.

4.

Lost updates

Two concurrent read-modify-write cycles; one clobbers the other. Some snapshot isolation implementations prevent it automatically; others need a manual SELECT FOR UPDATE.

5.

Write skew

A transaction decides on a premise that is no longer true when it commits. Only serializable isolation prevents it.

6.

Phantom reads

A write changes the result of another transaction’s search. Snapshot isolation handles read-only cases; write-skew phantoms need index-range locks or serializability.

And the three approaches to serializable transactions:

ApproachThe ideaThe catch
Actual serial executionLiterally one transaction at a time on a single thread, transactions as fast stored proceduresGreat if transactions are tiny, data fits in memory, and throughput fits one core — otherwise partitioning, with slow cross-partition coordination
Two-phase lockingShared/exclusive locks with predicate or index-range locks for phantoms; writers block readers and vice versaThe decades-old standard — but poor, unstable performance under contention, and frequent deadlocks
Serializable snapshot isolationOptimistic: run on snapshots, track read-write dependencies, abort at commit if execution wasn’t serializableNeeds spare capacity; aborts hurt under high contention; read-write transactions must be short

The examples used a relational data model, but transactions are valuable with any data model. And this chapter stayed (mostly) on a single machine — distributed transactions open a new set of difficult challenges, in the next two chapters.

Glossary

transaction
Grouping several reads and writes into a logical unit: either all succeed (commit) or all are undone (abort/rollback) and can safely be retried.
ACID
Atomicity, Consistency, Isolation, Durability — coined 1983 by Härder and Reuter; in practice, one database’s ACID ≠ another’s, and the term is mostly marketing now.
BASE
Basically Available, Soft state, Eventual consistency — i.e., “not ACID”; even vaguer than ACID.
atomicity (ACID sense)
Not about concurrency: if a fault occurs partway through a multi-write transaction, it aborts and all its writes are discarded. Really abortability.
consistency (ACID sense)
The application’s own invariants being preserved — an application property, not a database property; the C doesn’t really belong in ACID.
isolation
Concurrent transactions can’t step on each other’s toes; formally, serializability — the result is as if each ran alone.
durability
Once committed, data survives hardware faults and crashes — via disk (WAL) or replication to some number of nodes. Perfect durability does not exist.
read uncommitted
An even weaker level than read committed: prevents dirty writes but allows dirty reads.
dirty read
Reading another transaction’s writes before they commit — you might see data that later gets rolled back.
dirty write
Overwriting a value another transaction has written but not committed — the used-car mix-up.
read committed
The most basic practical level: no dirty reads, no dirty writes. Default in Oracle 11g, PostgreSQL, SQL Server 2012, MemSQL.
read skew / nonrepeatable read
Seeing different parts of the database at different points in time — Alice’s $900.
snapshot isolation
Each transaction reads from a consistent snapshot of the database as of its start; implemented with MVCC.
repeatable read
The SQL standard’s name for a level that looks like snapshot isolation; the definition is so ambiguous that nobody really knows what it means.
MVCC
Multi-version concurrency control — keeping several committed versions of objects side by side so readers never block writers and vice versa.
created_by / deleted_by
Per-row bookkeeping in PostgreSQL-style MVCC: which transaction created the version, and which marked it deleted; updates are a delete + create.
garbage collection (MVCC)
Background cleanup of versions and deleted rows that no transaction can still see.
append-only / copy-on-write B-tree
B-tree variant that copies modified pages up to a new root; each root is a consistent snapshot (CouchDB, Datomic, LMDB).
lost update
Two concurrent read-modify-write cycles; the later write clobbers the earlier without incorporating its change.
cursor stability
Implementing atomic single-object operations by taking an exclusive lock on the object when it’s read.
compare-and-set
An update that applies only if the value hasn’t changed since you last read it — safe only if the WHERE clause doesn’t read an old snapshot.
write skew
Two transactions read the same objects, make decisions on a premise, and write to different objects — the premise breaks. Only serializable prevents it.
phantom
A write in one transaction changes the result of another transaction’s search query — often a row that didn’t exist when the query ran.
materializing conflicts
Introducing artificial lock objects (e.g., a room × 15-minute-slot table) so a phantom becomes a lock conflict on real rows — a last resort.
serializable isolation
The strongest level: the end result is the same as if transactions had run one at a time, whether or not they actually did.
actual serial execution
One transaction at a time on a single thread — serializable by definition (VoltDB/H-Store, Redis, Datomic).
stored procedure
Transaction code submitted to the database ahead of time so it can execute without network round trips — required by single-threaded systems.
deterministic (stored procedures)
Producing the same result on every replica — VoltDB replicates by re-executing the same procedure, so time comes from deterministic APIs.
anti-caching
Aborting a transaction that needs off-disk data, fetching it into memory asynchronously, and restarting the transaction once loaded.
two-phase locking (2PL)
Serializability via shared/exclusive locks held to end of transaction — writers block readers and vice versa. Completely different from 2PC.
shared / exclusive lock
Shared: many simultaneous readers. Exclusive: one writer, nobody else. Read-then-write upgrades shared to exclusive.
deadlock
A waits for B’s lock while B waits for A’s; the database detects it and aborts one transaction for the application to retry.
predicate lock
A lock on all objects matching a search condition — including objects that don’t exist yet (phantoms).
index-range lock / next-key locking
An approximation of a predicate lock attached to an index entry or range — less precise, much cheaper; fallback is a table lock.
pessimistic concurrency control
If something might go wrong, wait until it’s safe — 2PL; serial execution is the extreme case.
optimistic concurrency control
Proceed anyway and check at commit — SSI; performs badly under high contention, well with spare capacity.
serializable snapshot isolation (SSI)
Full serializability on top of snapshot isolation: detect stale MVCC reads and write-after-read dependencies, abort only when necessary (PostgreSQL 9.1+, FoundationDB).
premise
A fact true when a transaction started (“two doctors are on call”) that its decision depends on — possibly outdated by commit time.
tripwire
In SSI, a write into a range others have read notifies them their data may be outdated — instead of blocking them.
