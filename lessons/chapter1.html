1.0 · Before the tools

Thinking about data systems

Most applications today are data-intensive, not compute-intensive. The CPU is rarely the bottleneck — the real problems are the amount of data, its complexity, and the speed at which it changes. When you find yourself choosing which piece of software to trust with that data, you are doing data-system design, whether you call it that or not.

Whatever the application, the same handful of building blocks keep appearing:

Databases

Store data so it can be found again later, after the process that created it is gone.

Caches

Remember the result of an expensive operation, to speed up reads.

Search indexes

Search data by keyword or filter it by various criteria.

Stream processing

Send a message to another process, to be handled asynchronously.

Batch processing

Periodically crunch a large amount of accumulated data.

Why one umbrella — “data systems”

Two trends collapsed these categories into a single subject. First, the boundaries are blurring: Redis is a datastore routinely used as a message queue; Kafka is a message queue with database-like durability guarantees. Second, no single tool meets every requirement anymore — applications stitch together several specialized tools (a cache layer here, a full-text search server there, the main database underneath) and hold them together with application code.

That last point is the quiet thesis of the whole book: when you combine several tools behind one API, you have designed a data system — its guarantees are yours to provide. If a write succeeds but the cache isn’t correctly invalidated, the composite system is broken, no matter how solid each piece was. You are now the database vendor.

The chapter organizes this responsibility into three concerns that matter for almost all software systems:

Reliability § 1.1

Continues to work correctly, even when things go wrong.

Scalability § 1.2

Reasonable ways of growing as load increases.

Maintainability § 1.3

Workable for the people who operate and extend it.

1.1 · Working correctly

Reliability

The colloquial meaning is forgiving: “works reasonably, even when things go wrong.” Concretely, it means:

  • The application performs the function the user expected.
  • It can tolerate the user making mistakes or using the software in unexpected ways.
  • Its performance is good enough for the required use case, under the expected load and data volume.
  • The system prevents any unauthorized access and abuse.

Fault ≠ failure — learn this cold

A fault is one component of the system deviating from its spec. A failure is when the system as a whole stops providing the required service. A dead disk is a fault; the outage it causes (or doesn’t) is the failure. Since it’s impossible to reduce the probability of faults to zero, the design goal is fault-tolerance (resilience): build mechanisms so faults don’t turn into failures. When a fault is hidden from the user entirely, we say it was masked — the standard example is error-correcting memory quietly fixing a flipped bit.

In fault-tolerant systems it even makes sense to deliberately increase the rate of faults: trigger them regularly (in a controlled way) to keep the tolerance machinery exercised and tested. Netflix’s Chaos Monkey — a tool that randomly kills processes in production during working hours — is the famous example: if engineers are used to individual instance failures, they naturally build the service to survive them. And the practice exposes real gaps, because many critical bugs are ultimately poor error handling.

Prevention beats cure

Not all faults can be tolerated once they’ve happened. Security is the clearest case: a compromised system that leaks data can’t be “un-leaked” — there is no tolerance mechanism, only prevention.

1.1.1 — Hardware faults

When you think “reliability”, you picture hardware: hard disks that crash, RAM that flips bits, the power grid going down, someone unplugging the wrong network cable.

10–50 yr Rated MTTF of a hard disk mean time to failure — one disk, on its own, is quite reliable
~1 / day Disks dying in a 10,000-disk cluster 10,000 ÷ (10–50 years × 365 days) ≈ 0.5–2.7 per day. Do the math.

The first line of defense is redundancy: RAID configurations for disks, dual power supplies and hot-swappable CPUs for servers, batteries plus diesel generators for datacenters. Enough redundancy that a single machine’s death is a non-event for the users — a rolling operation rather than an outage.

The shift — from redundancy to fault tolerance

As data volumes and computing demands grew, more machines per application meant proportionally more hardware faults. Meanwhile cloud platforms deliberately traded single-machine reliability for elasticity: an AWS VM can disappear without warning as the platform prioritizes flexibility. The response: software fault-tolerance techniques that tolerate the loss of entire machines — and rolling upgrades, patching one node at a time with no total downtime (an idea we return to in Chapter 4).

1.1.2 — Software errors

The key contrast

Hardware faults are usually random and independent — one disk dies, the others don’t care. Software errors are systematic: the same bug runs on every node, and one bad input can trigger it everywhere at once. Correlated failures — much more dangerous than independent ones.

The canonical examples:

The bad input

A software bug that crashes every application server when given a particular input — the leap second on June 30, 2012 hung many applications simultaneously via a Linux kernel bug: one input, fleet-wide hang.

The runaway process

A process that leaks or hogs some shared resource — CPU, memory, disk space, network bandwidth — until the whole system starves.

The sick dependency

A service the system depends on slows down, stops responding, or starts returning corrupted responses — and every caller degrades with it.

The cascading failure

One small fault in one component triggers a fault in another, which triggers the next — the failure propagates through the system like dominoes.

The root insight: these bugs are usually dormant assumptions — software believes something about its environment that is almost always true, until one day it stops being true (memory never grows this fast; this clock never jumps; that certificate never expires).

No quick fix exists, but the mitigations compound:

  • Careful thinking about assumptions and interactions in the system.
  • Thorough testing — corner cases, failure modes, unusual conditions.
  • Process isolation — let processes crash and restart, so a bad state doesn’t fester.
  • Allowing processes to crash and restart rather than limp along in a corrupted state.
  • Measuring, monitoring, and analyzing production behavior — telemetry.
  • Self-checking systems — e.g. a message queue that verifies incoming message count equals outgoing, and alerts on any discrepancy.

1.1.3 — Human errors

The stat nobody expects

One study of large internet services found that configuration errors were the leading cause of outages, while hardware faults played a role in only 10–25%. Humans — operators and developers — are the largest fault source, and design must assume it.

Six approaches, roughly in order of leverage:

i.

Minimize the opportunities for error

Well-designed abstractions, APIs, and admin interfaces that make “the right thing” the easy thing. But if you make it too restrictive, people will work around it — and the workaround is where the mistakes live.

ii.

Decouple mistake-prone from failure-prone

Provide non-production sandboxes with real (but non-live) data, where people can experiment and make mistakes without affecting real users.

iii.

Test thoroughly, at all levels

Unit tests, whole-system integration tests, manual tests. Automated tests covering rare corner cases are the ones that pay off years later.

iv.

Make recovery quick and easy

Fast rollback for bad configs, gradual code rollout (a bug then hits only a small subset of users), and tools to recompute data after a bad write.

v.

Monitor in detail and clearly

“Telemetry”: performance metrics and error rates that give early warning and make diagnosis possible. (More on this in § 1.3.1.)

vi.

Good management practices and training

Runbooks, blameless postmortems, and not treating people as “plug-and-play components”.

How important is reliability, really?

It’s easy to think reliability only matters for nuclear plants and air traffic control. It doesn’t. A buggy business application means lost productivity and legal risk from wrong data; an e-commerce outage means lost revenue and a reputation hit. Even “noncritical” apps owe their users something — a parent storing all the photos of their children will not care that the service was “just a hobby project”. There are legitimate cases for cutting corners — an unproven prototype, thin margins, a trivial product — but if it’s deliberate, fine; if it’s accidental, that’s just a bug you haven’t noticed yet.

1.2 · Coping with growth

Scalability

Even a system that works reliably today is not reliable if it falls over at twice the load. Scalability is the ability of a system to cope with increased load — but resist using it as a one-dimensional label. “X scales” and “Y doesn’t scale” are meaningless sentences. The real questions are always: if the system grows in a particular way, what are our options for coping? And how do we add computing resources to handle that growth?

Growth doesn’t have to be symmetric: 10,000 → 100,000 concurrent users is one conversation; 1 million → 10 million is a different one, even though both are “×10”.

1.2.1 — Describing load

First describe the load properly. Load parameters are the few numbers that characterize it — and the best choice depends on the architecture: requests per second for a web server, the read/write ratio for a database, the number of simultaneously active users in a chat room, the cache hit rate, and so on. Sometimes the critical parameter is something more exotic — and Twitter is the canonical case.

Case study · Twitter, November 2012

4.6k/s Average rate of post-tweet requests peaking at over 12k/s
12k/s Peak post rate write volume — small in absolute terms
300k/s Home timeline read rate ~65× the write rate — this is the load that matters

Fan-out — the load parameter that decides everything

Borrowed from electronics (the number of logic-gate inputs attached to one output), fan-out here means the number of requests one incoming request triggers. For posting a tweet, the fan-out is the number of followers — and that single number determines which architecture works.

Handling a timeline request is the hard part: 300k/sec of them, each potentially requiring a merge across hundreds of followees.

Approach 1 — fan-out-on-read (pull)

Store all tweets in a single global collection. To render a home timeline, look up everyone you follow, fetch all their tweets, and merge them sorted by time:

SELECT tweets.*, users.* FROM tweets JOIN users ON tweets.sender_id = users.id JOIN follows ON follows.followee_id = users.id WHERE follows.follower_id = current_user

Simple to post (one insert), expensive to read — a heavy query over the follow graph for every timeline view, ×300k per second.

Approach 2 — fan-out-on-write (push)

Maintain a per-user home timeline cache — like a mailbox. When user A posts a tweet, walk A’s follower list and insert the tweet into every follower’s cache. Timeline reads become a trivial lookup: fetch the cache for the requesting user, done.

The history, and why they switched

Twitter started with Approach 1 and struggled as the load grew — then switched to Approach 2. The decisive reasoning: posting is roughly two orders of magnitude rarer than timeline reads (~4.6k/s vs ~300k/s), so it pays to do more work at write time and make the 65×-more-frequent reads cheap.

But push has its own dark side, and the averages hide it:

75 Average followers per tweet 4.6k tweets/s × 75 ≈ 345k writes/s to timeline caches — heavy but survivable
30M+ Followers of the biggest celebrities a single tweet = 30M+ cache writes — a thundering herd for one post
5 s Twitter’s delivery target a tweet should appear in followers’ timelines within five seconds

The hybrid (what Twitter actually runs)

Normal users’ tweets fan out at post time — Approach 2. Celebrities are excepted: their tweets are not pushed to follower caches; instead they’re fetched separately and merged in at read time — Approach 1, applied only to the accounts where push would explode. A nice demonstration that the load parameters pick the architecture — and a design we revisit in Chapter 12.

1.2.2 — Describing performance

Once load is defined, you can ask performance questions — and there are exactly two worth asking:

1.

Load up, resources fixed

Increase the load and keep resources unchanged — how does performance suffer?

2.

Load up, performance fixed

Increase the load — how much do resources need to grow to keep performance unchanged?

How you measure depends on the system type: batch systems care about throughput (records processed per second, or total time to process a fixed job); online systems care about response time — the time between a client sending a request and receiving a response.

Footnote from the book — the ideal vs. reality

The ideal batch time is simply dataset size ÷ throughput. In practice it’s worse: skew (data unevenly distributed) means some steps take far longer, and the job waits on the slowest task to finish. Sound familiar? It will — it’s tail latency, in batch clothing.

Latency vs. response time — not synonyms

Response time is what the client sees: the service’s actual processing (service time) plus network delays plus queueing delays. Latency, strictly, is how long the request waits latent — sitting in a queue, unhandled — before being served. A single slow request inflates its response time; the requests stuck behind it inherit its latency.

Even on an identical workload, response times vary — repeatedly, on the same request:

  • a context switch to a background process,
  • a lost network packet and its TCP retransmission,
  • a garbage-collection pause,
  • a page fault forcing a read from disk,
  • even mechanical vibrations in the server rack.

So you don’t report a number — you report a distribution.

Percentiles — the honest way to talk about response time

Sort your response times and take the middle (median, p50) and tails: p95, p99, p999. If your p95 is 1.5 seconds, then 5 out of 100 requests take 1.5s or more — on purpose, that’s the definition. The median tells the typical story; the tails tell the truth about your worst users’ experience. And the median is per-request: a session making several requests compounds the chance of hitting the slow half well beyond 50%.

The Amazon numbers — why the tail is where the money is

Amazon reported that response-time requirements are set at the 99.9th percentile even though that’s 1 request in 1,000 — because the slowest requests correlate with the customers with the most data on their accounts, i.e. the heaviest and most valuable users. Meanwhile, an increase of 100 ms in response time cost ~1% of sales, and a 1-second slowdown reduced customer satisfaction by ~16%. Optimizing the p99.99 (the absolute worst request in 10,000) was judged too expensive — Amazon drew its own line, and so should you.

SLO / SLA

An SLO (service level objective) is the performance you expect from a service; an SLA (service level agreement) is its contractual twin — the version customers can demand refunds for when it’s missed. Example SLO: the service is considered “up” if the median response time is under 200 ms and the 99th percentile under 1 second and it’s available at least 99.9% of the time.

Head-of-line blocking — why you measure from the client

A server can only process so many things in parallel (CPU cores); if a few slow requests arrive together, they hold up all the requests behind them — head-of-line blocking. Your server-side metrics never show it; your users always feel it. So measure response times on the client side, where the queue is real.

Load-testing gotcha

If your load generator sends a request and waits for each response before sending the next, you have artificially emptied the queue — the test underestimates queueing and, therefore, tail latency. The load generator must keep sending independently of response time.

Response times of requests to a backend service, as they arrived (not sorted). Median and p95 marked. Most requests are fast; a handful of outliers dominate the tail — the arithmetic mean would sit somewhere between, describing almost nothing.

Tail latency amplification

The final indignity: your service can be p99.9-fast and your pages still slow, because an end-user request fans out into multiple backend calls, and the page waits for the slowest one — even when the calls run in parallel. A small percentage of slow calls per service becomes a large percentage of slow pages (Dean & Barroso, “The Tail at Scale”).

Figure 1-5 (recreated) · One page load → 25 backend calls

Say each backend call has a 1-in-100 chance of being slow. The page is slow if any of its 25 calls is slow: P(slow page) = 1 − 0.9925 ≈ 22%. The tail didn’t grow — it multiplied. Small per-call slowness becomes page-level slowness at scale.

Percentiles in practice

Real systems usually compute percentiles over rolling windows — e.g. medians and percentiles calculated every minute over the last 10 minutes — and there are efficient approximation algorithms: forward decay, t-digest, HdrHistogram.

Never average percentiles

The mean of multiple p95 values is mathematically meaningless — you cannot combine quantiles that way. If you need a global p95 across 100 servers, add their histograms together and take the quantile of the sum. (This exact mistake is endemic in dashboards.)

1.2.3 — Approaches for coping with load

People increasingly deal with load by scaling out, but every order-of-magnitude growth should make you rethink the architecture rather than just multiply what you had.

Scaling up (vertical)
A more powerful machine — more CPUs, more RAM. Simple, no distribution to reason about, and it doesn’t scale forever.
Scaling out (horizontal)
More machines, load spread across them — the shared-nothing architecture. Good architectures pragmatically mix both.
Elastic
Automatically adds resources when load increases. Attractive for highly variable load, but operationally surprising; manually-scaled systems are simpler and behave predictably.
Stateful vs. stateless
Stateless services scale out easily; stateful data systems are dramatically harder to distribute — the central tension of Part II. Conventional wisdom: keep your database on one node until the cost or availability requirements force you to shard.

Perspective — same throughput, different universes

Two systems with identical throughput: 100,000 requests/second of 1 kB each, versus 3 requests/minute of 2 GB each. Nothing about the first design informs the second. Numbers alone don’t scale you — which load parameters dominate decides the architecture.

There is no magic scaling sauce

No one-size-fits-all scalable architecture exists. The problem might be read volume, write volume, dataset size, data complexity, latency requirements, access patterns — or a combination. An architecture built on wrong load-parameter assumptions wastes effort or actively backfires. And for early-stage products, iterating on features usually beats engineering for hypothetical load. If it hurts, you’ll know exactly where — and that’s cheaper than guessing.

1.3 · The long game

Maintainability

The majority of a software system’s cost isn’t writing it — it’s ongoing maintenance: fixing bugs, keeping systems operational, investigating failures, adapting to new platforms, shoehorning in new use cases, repaying technical debt, and shipping yet more features. Everyone knows the result: “Every legacy system is unpleasant in its own way.”

Since we can’t opt out of maintenance, we should design systems that minimize it — around three principles:

Operability § 1.3.1

Make life easy for the operations team — keep the system running smoothly.

Simplicity § 1.3.2

Make it easy for new engineers to understand the system — most complexity is accidental, and it can be removed. (Not the same as a simple user interface.)

Evolvability § 1.3.3

Make it easy for engineers to change the system for unanticipated use cases. Also called extensibility, modifiability, or plasticity.

1.3.1 — Operability: making life easy for operations

“Good operations can often work around the limitations of bad software, but good software cannot run reliably with bad operations.”

— an operations truism worth tattooing somewhere

An operations team typically keeps a software system running — the to-do list that never ends:

  • Monitor the health of the system, and quickly restore service when it degrades.
  • Track down the cause of failures (e.g. a network failure, or an application bug).
  • Keep software and platforms patched — including security patches.
  • Watch how systems affect each other, so a risky change doesn’t damage something else.
  • Anticipate future problems before they hit (capacity planning: “will this survive the launch?”).
  • Establish good practices and tooling for deployment, config management, and more.
  • Perform complex maintenance tasks (e.g. platform migrations between servers or datacenters).
  • Maintain the security of the system as configuration and organization change.
  • Define processes that make production predictable — and keep things stable.
  • Preserve the organization’s knowledge about the system as people come and go.

What does good operability look like in a data system itself? The book’s checklist:

  • Visibility into the system’s runtime behavior and internal metrics — monitoring.
  • Automation and standard tools support — integration with the organization’s way of doing things.
  • No dependence on individual machines — take machines down for maintenance while the system runs.
  • Good documentation and an easy-to-understand operational model — “if I do X, Y will happen”.
  • Sensible defaults, but the freedom to override them when needed.
  • Self-healing where appropriate, but with manual control still available for operators.
  • Predictable behavior — minimal surprises.

1.3.2 — Simplicity: managing complexity

Left alone, software rot into a big ball of mud: a sprawling, incomprehensible mess. The symptoms, which you can almost smell:

explosion of state space tight coupling tangled dependencies inconsistent naming performance hacks special-casing workarounds

When a system is hard to understand, the consequences compound: timelines overrun, and every change risks bugs from hidden assumptions, unintended consequences, and missed interactions.

Accidental vs. essential complexity — the crucial split

Moseley & Marks (“Out of the Tar Pit”) separate essential complexity — inherent to the problem itself — from accidental complexity — not inherent to the problem, only to the implementation. Simplifying a system does not mean removing functionality; it means removing its accidental complexity.

The best weapon against accidental complexity is abstraction: hide the implementation details behind a clean façade. A good abstraction can be reused across applications — and reusing a better implementation beats reimplementing it badly, so quality improvements benefit every user of the abstraction. You already live on a tower of them: high-level programming languages hide machine code, registers, and syscalls; SQL hides on-disk and in-memory data structures, concurrent requests, and crash-inconsistency handling. The hard part — still an open research problem, especially in distributed systems — is finding good abstractions.

1.3.3 — Evolvability: making change easy

Requirements never stay fixed — they shift under you: organizational changes, new facts surface, unanticipated use cases appear, business priorities pivot, users ask for the thing they just saw, platforms get deprecated, and legal or regulatory requirements arrive. Growth itself forces architectural change.

Agile working patterns — TDD, refactoring — provide techniques for change at the small scale (a few files of code). This book targets the same agility at the data system level — hence “evolvability”.

Thought experiment

You built a Twitter clone with Approach 1 (fan-out-on-read). It’s now melting under load, and you want Approach 2 (fan-out-on-write with per-user timeline caches). How would you “refactor” that — a live, social, write-heavy system — from pull to push? What do you migrate first? What breaks if both run at once? (Keep this feeling. Chapter 12 returns to it as the kind of problem derived data exists to solve.)

And simplicity is a prerequisite: it’s hard to change a system nobody understands.

1.4 · Pulling it together

Summary

The chapter in one card

Software has functional requirements (what it should do) and nonfunctional requirements — security, reliability, compliance, scalability, compatibility, maintainability — and this chapter is the latter. Reliability: correct behavior under faults (hardware faults are random and independent; software faults are systematic; human error is inevitable — tolerate all three). Scalability: describe load with load parameters, describe performance with percentiles, add capacity to stay reliable under load. Maintainability: build systems with clean abstractions and good operability so engineers and ops can live with them. There are no easy fixes — but the same patterns recur, and the rest of the book is those patterns.

Glossary

data-intensive
The dominant application profile: the challenge is the amount/complexity/velocity of data, not raw CPU cycles.
load parameters
The few numbers that describe current load (req/s, read/write ratio, active users, fan-out…) — architecture-dependent.
fan-out
Number of requests needed to serve one incoming request; for a tweet, the number of followers.
fault
One component deviating from its spec.
failure
The whole system stopping service. Goal: faults don’t become failures.
fault-tolerant / resilient
Designed to keep working correctly, even when faults occur.
MTTF
Mean time to failure — e.g. hard disks rated 10–50 years (per disk; a 10,000-disk fleet loses one a day).
rolling upgrade
Patching one node at a time so the system never fully goes down.
cascading failure
A fault in one component triggering faults in others, propagating through the system.
throughput
Records processed per second (batch), or the time to complete a fixed job.
response time
Client’s view: send request → receive response (service time + network + queueing).
latency / service time
Latency: how long a request waits before being handled. Service time: how long the actual processing takes.
p50 / p95 / p99 / p999
Percentiles of the response-time distribution — median and increasingly harsh tail views.
tail latency
The slowest fraction of requests (p95+). Where your heaviest, most valuable users live.
head-of-line blocking
A few slow requests holding up subsequent ones in a limited-parallelism server.
tail latency amplification
A page needing multiple backend calls waits for the slowest one — small per-call slowness becomes large per-page slowness.
SLO / SLA
Expected performance/availability targets; the SLA is the contractual, refund-triggering version.
scale up / scale out
Bigger machines vs. more machines; “shared-nothing” is the horizontal arrangement.
elastic
A system that automatically adds capacity as load increases (at operational complexity).
accidental complexity
Complexity not inherent to the problem, only to the implementation — the removable kind.
abstraction
A clean façade that hides implementation detail and can be reused — the weapon against accidental complexity.
operability
How easy the system is for ops to run smoothly.
simplicity
How easily new engineers understand the system (≠ a simple UI).
evolvability
How easily engineers can adapt it to unanticipated use cases.
telemetry
Detailed, clear monitoring — performance metrics and error rates that enable early warning and diagnosis.
