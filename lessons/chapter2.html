2.0 · Before the arguments

Every system is a stack of data models

Software is built in layers, and every layer is a data model. Working down from your application to the metal, there are (at least) four:

  1. Application developers look at the real world — people, organizations, goods, actions, money flows, sensors — and model it as objects and data structures specific to their application.
  2. Those structures are expressed in a general-purpose data model: JSON or XML documents, tables in a relational database, or a graph model.
  3. Database engineers take that JSON/relational/graph data and represent it as bytes in memory, on disk, or on the network, in a way that allows querying, searching, manipulation, and processing.
  4. Hardware engineers take those bytes and represent them as electrical currents, pulses of light, or magnetic fields.

Each layer hides the complexity of the layer below it behind a clean data model — that’s how database vendors and application developers can work together at all. And every data model carries assumptions: some operations are easy, some unsupported; some fast, some slow; some transformations natural, some awkward. Mastering even one model takes enormous effort (entire books exist on relational modeling alone), so which model you pick for your application matters enormously.

This chapter compares the three heavyweights — relational, document, and graph — and the query languages that ride on them. Chapter 3 then looks at how those models are actually stored on disk.

2.1 · The main event

Relational model versus document model

A short history of the relational model

The best-known data model today is SQL, based on the relational model proposed by Edgar Codd in 1970: data organized into relations (tables in SQL), each an unordered collection of tuples (rows). It was a theoretical proposal — many doubted it could be implemented efficiently — but by the mid-1980s RDBMS and SQL were the tools of choice, and their dominance lasted ~25–30 years: an eternity in computing.

The relational model’s roots are business data processing on mainframes in the 1960s and ’70s: transaction processing (sales, banking, airline reservations, stock-keeping) and batch processing (invoicing, payroll, reporting). Its goal was radical at the time: hide the internal representation of data behind a clean interface — while competing databases forced developers to think about how the data was stored internally.

EraContenderWhat happened

Every competitor generated hype in its time; none lasted. Meanwhile the relational model generalized far beyond business processing — into online publishing, discussion, social networking, e-commerce, games, and SaaS.

The birth of NoSQL

“NoSQL” started life as a catchy Twitter hashtag for a 2009 meetup on open source, distributed, nonrelational databases — then was retroactively reinterpreted as “Not Only SQL.” The name struck a nerve and spread through the web startup community and beyond. Four forces drove the adoption:

i.

Scalability

Very large datasets or very high write throughput, beyond what relational databases could easily achieve.

ii.

Free & open source

A widespread preference for open source over commercial database products.

iii.

Specialized queries

Operations not well supported by the relational model.

iv.

Schema frustration

Restrictive relational schemas; a desire for a more dynamic, expressive data model.

Notice that relational databases aren’t going anywhere either — the realistic future is polyglot persistence: relational and nonrelational datastores used side by side, each where it fits.

The object-relational mismatch

Impedance mismatch — a term from electronics

Every circuit has an impedance on its inputs and outputs; power transfers best when they match, and a mismatch causes signal reflections and other troubles. In databases, the impedance mismatch is the disconnect between object-oriented application code and the relational model of tables, rows, and columns. ORMs like ActiveRecord and Hibernate reduce the boilerplate but can’t hide the difference between the two models.

Case study: the résumé

Take a LinkedIn profile (Figure 2-1 in the book uses Bill Gates as the example). The profile has first_name and last_name — one value per user, so they become columns on a users table, identified by a unique user_id. But positions, education, and contact information are one-to-many relationships — and SQL gives you three ways to represent them:

  1. Traditional normalized SQL (pre-SQL:1999, still the most common): separate tables — positions, education, contact_info — each with a foreign key to users.
  2. Later SQL standards (SQL:1999+): structured datatypes and XML; multi-valued data within a single row, queryable and indexable. Supported by Oracle, IBM DB2, MS SQL Server, PostgreSQL; JSON datatypes arrived in IBM DB2, MySQL, and PostgreSQL.
  3. Encode as JSON/XML in a text column and let the application interpret it — but the database usually can’t query inside the encoded blob.

Option 3 is basically a hand-rolled document model — so the document databases made it first-class. Example 2-1, the profile as a JSON document:

{ "user_id": 251, "first_name": "Bill", "last_name": "Gates", "summary": "Co-chair of the Bill & Melinda Gates... Active blogger.", "region_id": "us:91", "industry_id": 131, "photo_url": "/p/7/000/253/05b/308dd6e.jpg", "positions": [ {"job_title": "Co-chair", "organization": "Bill & Melinda Gates Foundation"}, {"job_title": "Co-founder, Chairman", "organization": "Microsoft"} ], "education": [ {"school_name": "Harvard University", "start": 1973, "end": 1975}, {"school_name": "Lakeside School, Seattle", "start": null, "end": null} ], "contact_info": { "blog": "http://thegatesnotes.com", "twitter": "http://twitter.com/BillGates" } }

MongoDB, RethinkDB, CouchDB, and Espresso are built around such documents; JSON is much simpler than XML, which is why it won. The structure underneath is a tree of one-to-many relationships — positions, education, and contact info all branch from the profile — and JSON makes that tree explicit:

Figure 2-2 (recreated) · One-to-many relationships form a tree

The one-to-many relationships from a user profile — positions, education, contact info — imply a tree structure (Figure 2-1’s relational schema would shred this tree across four tables). JSON stores the tree as one document.

Locality — the document model’s home advantage

To fetch the profile from the relational schema you need multiple queries (one per table) or a messy multi-way join. In the JSON representation, everything is in one place — one read, one document. We return to locality’s limits a few sections down.

Many-to-one and many-to-many

Notice what Example 2-1 did not do: it stores region_id and industry_id, not the strings “Greater Seattle Area” and “Philanthropy”. The human-readable names live in standardized lists (drop-downs / autocompleters), and for five good reasons:

  • Consistent style and spelling across profiles.
  • Avoiding ambiguity — several cities share a name.
  • Ease of updating — the name lives in one place; rename once, everywhere (a city renamed by political events doesn’t strand a million stale copies).
  • Localization — translate the standardized list, and the region displays in the viewer’s language.
  • Better search — the region list encodes that Seattle is in Washington, so “philanthropists in Washington state” is a real query.

The rule of thumb behind normalization

An ID has no meaning to humans, so it never needs to change — even if the thing it identifies changes its name. Anything meaningful to humans may change, and every duplicated copy is write overhead and a consistency risk. Removing that duplication is the key idea behind normalization. (The literature distinguishes many normal forms of little practical interest; the rule of thumb is: if you’re duplicating values that could be stored in just one place, the schema is not normalized.)

Here’s the rub: normalization requires many-to-one relationships (many people in one region), and those don’t fit the document model — they need joins. Relational databases refer to rows by ID and join freely; document databases historically have weak join support, so the join moves into application code as multiple queries.

And then the features arrive, and data gets more interconnected:

  • Organizations and schools as entities — organization is currently just a string; make it a reference, and each company gets its own page (logo, news feed), and each résumé links to it.
  • Recommendations — one user writes a recommendation shown on another’s résumé, with the recommender’s name and photo. When the recommender updates their photo, the recommendation must reflect it — so it must reference the author’s profile.

Figure 2-4 in the book draws the result: dotted rectangles around the data that still groups nicely into one document, and arrows (references, requiring joins) reaching out to organizations, schools, and other users. The one-to-many tree became a many-to-many web.

Are document databases repeating history?

The most popular business database of the 1970s was IBM’s IMS (born for stock-keeping in the Apollo space program, first commercially released 1968, still running on OS/390 mainframes today). IMS used the hierarchical model: all data as a tree of records nested within records — much like JSON. It worked well for one-to-many, made many-to-many difficult, and had no joins: developers chose between duplicating data or manually resolving references in application code. The problems of the 1960s and ’70s are, recognizably, the problems of document databases today.

Two camps fought the “great debate” of the 1970s over how to fix the hierarchical model:

The network model (CODASYL)

Standardized by the Conference on Data Systems Languages, hence the CODASYL model. It generalized the hierarchy: a record could have multiple parents — one record for the “Greater Seattle Area,” linked from every user living there. But the links weren’t foreign keys; they were more like pointers stored on disk. The only way to reach a record was to start at a root and follow a chain of links — an access path. Querying meant moving a cursor through the database, iterating over lists of records and following access paths; with multiple paths leading to the same record, the programmer had to keep them all in their head. Even CODASYL committee members admitted it felt like navigating an n-dimensional data space.

Manual access-path selection made sense for 1970s hardware (tape drives, extremely slow seeks) — but the code was complicated and inflexible, and if you didn’t have a path to the data you wanted, you were stuck. Changing the data model meant rewriting lots of handwritten query code.

The relational model — and why it won

Codd’s answer laid all the data in the open: a relation is just a collection of tuples, no labyrinthine nested structures, no access paths. You can read any rows matching an arbitrary condition, look up by key, insert into any table without worrying about foreign-key relationships. The access paths didn’t disappear — they moved into the query optimizer, which automatically decides which indexes to use and in which order to execute the query.

The one-time cost that pays forever

You only need to build a query optimizer once, and then every application using the database benefits. Without one, it’s easier to hand-code the access path for a particular query than to write a general-purpose optimizer — but the general-purpose solution wins in the long run: want new query patterns? Declare a new index; existing queries automatically use it. The relational model made adding features to applications dramatically easier.

And document databases? They reverted to the hierarchical model in exactly one respect — nested records stored within their parent — but for many-to-one and many-to-many, they behave like the relational model: the related item is referenced by a unique identifier (a foreign key in relational, a document reference in document), resolved at read time by a join or follow-up queries. To date, document databases have not followed CODASYL down the access-path road.

Relational versus document databases today

The case for documents: schema flexibility, locality, and (for some applications) being closer to the application’s data structures. The case for relational: better joins and better many-to-one / many-to-many support.

Which leads to simpler code? If your data is document-shaped — a tree of one-to-many, typically loaded whole — the document model fits, and the relational technique of shredding it into multiple tables leads to cumbersome schemas. But if your application is full of many-to-many relationships, the document model means denormalizing (and extra code to keep it consistent) or emulating joins in application code — usually slower than a join executed by specialized code inside the database. Highly interconnected data pushes further still: relational is acceptable, but graph models are the most natural.

Schema flexibility: schema-on-read vs. schema-on-write

“Schemaless” is misleading — the reading code still assumes structure; the schema is implicit rather than enforced. The precise terms:

Schema-on-write (relational)Schema-on-read (document)
AnalogyStatic (compile-time) type checkingDynamic (runtime) type checking
EnforcementExplicit schema; DB rejects non-conforming writesImplicit structure; interpreted at read time
Change procedureMigration: ALTER TABLE + UPDATEWrite new-format docs; handle old formats in read code

Concretely — renaming name into first_name/last_name. Document approach: new documents get the new fields, and the application patches old ones on read:

if (user && user.name && !user.first_name) { // Documents written before Dec 8, 2013 don't have first_name user.first_name = user.name.split(" ")[0]; }

Relational approach — a one-time migration:

ALTER TABLE users ADD COLUMN first_name text; UPDATE users SET first_name = split_part(name, ' ', 1); -- PostgreSQL UPDATE users SET first_name = substring_index(name, ' ', 1); -- MySQL

Most databases execute ALTER TABLE in milliseconds; MySQL is the notable exception, copying the entire table — minutes or hours of downtime on a large table (though tools like pt-online-schema-change and gh-ost work around it). The UPDATE is slow everywhere if the table is big; the alternative is leaving first_name NULL and filling it at read time. Schema-on-read shines when items in a collection are heterogeneous — many object types, or structure dictated by external systems you don’t control; when all records share a structure, an enforced schema is a useful document.

Data locality for queries

A document is stored as a single continuous string (JSON, XML, or a binary variant like MongoDB’s BSON). If you usually need the whole document, that’s a performance win over multiple index lookups across tables. The limits:

  • The advantage only applies when you need large parts of the document at once.
  • The DB loads the entire document even when you touch a small part of it — wasteful for big documents.
  • An update rewrites the whole document (only size-neutral edits can happen in place) — hence the advice to keep documents small.

Locality isn’t a document-model monopoly: Google Spanner lets a table’s rows be interleaved within a parent table, Oracle has multi-table index cluster tables, and the Bigtable model (Cassandra, HBase) has column-families for the same purpose.

Convergence

Relational databases added XML (mid-2000s) and JSON (PostgreSQL 9.3, MySQL 5.7, IBM DB2 10.5); RethinkDB added relational-style joins; MongoDB drivers resolve database references client-side. The models are converging — and that’s a good thing: they complement each other, and a hybrid is a good route for the future. (Codd’s original paper even allowed nested relations within a schema — “nonsimple domains” — JSON-in-SQL thirty years early.)

2.2 · How you ask

Query languages for data

Declarative versus imperative

When the relational model arrived, it brought a new way of querying. SQL is declarative; IMS and CODASYL queried with imperative code. The difference, with a marine-biology dataset — find the sharks:

// Imperative: you tell the computer the order of operations function getSharks() { var sharks = []; for (var i = 0; i < animals.length; i++) { if (animals[i].family === "Sharks") { sharks.push(animals[i]); } } return sharks; }

The relational algebra is one line — σfamily="Sharks"(animals) (σ, sigma, is the selection operator) — and SQL follows it closely:

SELECT * FROM animals WHERE family = 'Sharks';

You specify the pattern of the data you want — conditions, sort, grouping, aggregation — not how to achieve it. The query optimizer picks indexes, join order, and execution plan. Three reasons this wins:

i.

Concise

Easier to work with than an imperative API.

ii.

Hides implementation

The engine can improve performance — or reshuffle records — without changing queries. Imperative code might secretly depend on record order, so the DB can never be sure it’s safe to optimize.

iii.

Parallelizable

CPUs get faster by adding cores, not clocks. An imperative program pins operations to an order; a declarative query specifies only the result pattern, leaving the database free to run it in parallel across cores and machines.

The same lesson, in a browser

A web page about ocean animals, with the current section highlighted via class="selected". Declaratively, in CSS:

li.selected > p { background-color: blue; }

Imperatively, in JavaScript DOM manipulation:

var liElements = document.getElementsByTagName("li"); for (var i = 0; i < liElements.length; i++) { if (liElements[i].className === "selected") { var children = liElements[i].childNodes; for (var j = 0; j < children.length; j++) { var child = children[j]; if (child.nodeType === Node.ELEMENT_NODE && child.tagName === "P") { child.setAttribute("style", "background-color: blue"); } } } }

The imperative version has two failure modes the declarative one can’t have: remove the selected class and the manual blue stays stuck until reload (CSS removes it automatically), and you can’t benefit from faster new APIs (getElementsByClassName, document.evaluate) without rewriting (browser vendors can optimize CSS and XPath without breaking anyone). CSS is to the DOM what SQL is to the database.

MapReduce querying

MapReduce (popularized by Google) is a programming model for processing large amounts of data in bulk across many machines — and a limited form is supported by some NoSQL stores (MongoDB, CouchDB) as a read-query mechanism. It sits between declarative and imperative: you supply code snippets that the framework calls repeatedly, based on the map (aka collect) and reduce (aka fold/inject) functions from functional programming.

Count sharks observed per month. In PostgreSQL:

SELECT date_trunc('month', observation_timestamp) AS observation_month, sum(num_animals) AS total_animals FROM observations WHERE family = 'Sharks' GROUP BY observation_month;

In MongoDB’s MapReduce:

db.observations.mapReduce( function map() { var year = this.observationTimestamp.getFullYear(); var month = this.observationTimestamp.getMonth() + 1; emit(year + "-" + month, this.numAnimals); }, function reduce(key, values) { return Array.sum(values); }, { query: { family: "Sharks" }, out: "monthlySharkReport" } );

With two observation documents (Dec 25 1995: 3 great whites; Dec 12 1995: 4 sand tigers), map runs once per document — emit("1995-12", 3), emit("1995-12", 4) — and reduce runs per key: reduce("1995-12", [3, 4]) → 7. The map and reduce functions must be pure: only their inputs, no extra database queries, no side effects — which is what lets the framework run them anywhere, in any order, and rerun them on failure.

The moral: NoSQL reinventing SQL, in disguise

Coordinating two JavaScript functions is harder than writing one query, and the optimizer has less to work with. MongoDB 2.2 accordingly added the aggregation pipeline — a declarative language for the same job:

db.observations.aggregate([ { $match: { family: "Sharks" } }, { $group: { _id: { year: { $year: "$observationTimestamp" }, month: { $month: "$observationTimestamp" } }, totalAnimals: { $sum: "$numAnimals" } } } ]);

Similar expressiveness to a subset of SQL with JSON syntax instead of English-sentence syntax — a matter of taste. The takeaway stands: a NoSQL system may find itself accidentally reinventing SQL, albeit in disguise.

2.3 · When everything relates to everything

Graph-like data models

When many-to-many relationships are very common, model the data as a graph: vertices (nodes, entities) and edges (relationships, arcs). The classics: social graphs (people who know people), the web graph (pages linking to pages), road and rail networks (junctions and the roads between them — shortest-path search). Algorithms like PageRank on the web graph made a search engine a monopoly. Graphs also homogenize heterogeneity — Facebook’s single graph holds people, locations, events, checkins, and comments as vertices, with friendships, checkin-locations, and comment-authorship as edges.

Figure 2-5 (recreated) · Lucy and Alain

Lucy (born in Idaho) and Alain (born in Beaune, France), married and living in London — expressible as a social graph or a genealogical database. Note the graph eating things a rigid relational schema chokes on: France has départements and régions, the US has counties and states; Lucy’s residence is known to city level but her birthplace only to state.

The property graph model

Used by Neo4j, Titan, InfiniteGraph. A vertex has: a unique identifier, a set of outgoing edges, a set of incoming edges, and a collection of properties (key-value pairs). An edge has: a unique identifier, the tail vertex (where it starts), the head vertex (where it ends), a label describing the relationship, and its own properties. In fact you can think of a graph store as two relational tables — Example 2-2:

CREATE TABLE vertices ( vertex_id integer PRIMARY KEY, properties json ); CREATE TABLE edges ( edge_id integer PRIMARY KEY, tail_vertex integer REFERENCES vertices (vertex_id), head_vertex integer REFERENCES vertices (vertex_id), label text, properties json ); CREATE INDEX edges_tails ON edges (tail_vertex); CREATE INDEX edges_heads ON edges (head_vertex);

Three aspects make this model powerful:

  1. Any vertex can have an edge to any other vertex — no schema restricts which kinds of things can be associated.
  2. Given any vertex, you can efficiently find incoming and outgoing edges (hence the two indexes) and traverse chains forward and backward.
  3. Different labels for different relationship kinds — many kinds of information in one graph, clean model intact.

That flexibility is why graphs are good for evolvability: add food allergies later as allergen vertices plus ALLERGIC_TO edges, then query what’s safe for each person to eat — no migration, just more graph.

Cypher

Cypher is a declarative query language for property graphs, created for Neo4j (named after a character in The Matrix; nothing to do with cryptography). The Figure 2-5 data, as a Cypher CREATE:

CREATE (NAmerica:Location {name:'North America', type:'continent'}), (USA:Location {name:'United States', type:'country' }), (Idaho:Location {name:'Idaho', type:'state' }), (Lucy:Person {name:'Lucy' }), (Idaho) -[:WITHIN]-> (USA) -[:WITHIN]-> (NAmerica), (Lucy) -[:BORN_IN]-> (Idaho)

Now the query that defines the model’s value — find people who emigrated from the US to Europe:

MATCH (person) -[:BORN_IN]-> () -[:WITHIN*0..]-> (us:Location {name:'United States'}), (person) -[:LIVES_IN]-> () -[:WITHIN*0..]-> (eu:Location {name:'Europe'}) RETURN person.name

Read it as: find a person whose BORN_IN edge leads (via a chain of zero or more WITHIN edges) to a location named “United States”, and whose LIVES_IN edge leads (via WITHIN*0..) to one named “Europe”. The *0.. is doing enormous work: like the * in a regular expression, it says “this edge, zero or more times” — because LIVES_IN might point at a street, a city, a district, a region, or a state, and we don’t know how many levels up “Europe” sits. You never specify how to execute — scan all people and check, or start from the two Location vertices and work backward through an index on name; the optimizer chooses.

Graph queries in SQL

Can SQL do this? Yes — with difficulty, using WITH RECURSIVE (SQL:1999; PostgreSQL, DB2, Oracle, SQL Server). The same 4-line Cypher query becomes Example 2-5, 29 lines:

WITH RECURSIVE -- in_usa is the set of vertex IDs of all locations within the United States in_usa(vertex_id) AS ( SELECT vertex_id FROM vertices WHERE properties->>'name' = 'United States' UNION SELECT edges.tail_vertex FROM edges JOIN in_usa ON edges.head_vertex = in_usa.vertex_id WHERE edges.label = 'within' ), -- in_europe is the set of vertex IDs of all locations within Europe in_europe(vertex_id) AS ( SELECT vertex_id FROM vertices WHERE properties->>'name' = 'Europe' UNION SELECT edges.tail_vertex FROM edges JOIN in_europe ON edges.head_vertex = in_europe.vertex_id WHERE edges.label = 'within' ), -- born_in_usa is the set of vertex IDs of all people born in the US born_in_usa(vertex_id) AS ( SELECT edges.tail_vertex FROM edges JOIN in_usa ON edges.head_vertex = in_usa.vertex_id WHERE edges.label = 'born_in' ), -- lives_in_europe is the set of vertex IDs of all people living in Europe lives_in_europe(vertex_id) AS ( SELECT edges.tail_vertex FROM edges JOIN in_europe ON edges.head_vertex = in_europe.vertex_id WHERE edges.label = 'lives_in' ) SELECT vertices.properties->>'name' FROM vertices JOIN born_in_usa ON vertices.vertex_id = born_in_usa.vertex_id JOIN lives_in_europe ON vertices.vertex_id = lives_in_europe.vertex_id;

4 lines vs. 29 lines

If the same query takes 4 lines in one language and 29 in another, that just shows that different data models are designed for different use cases. The core mismatch: in SQL you normally know your joins in advance; in a graph query the number of joins is a variable, and recursive CTEs are the sledgehammer that handles it.

Triple-stores and SPARQL

The triple-store is mostly the property graph with different words: all data as three-part statements, (subject, predicate, object) — e.g. (Jim, likes, bananas). If the object is a primitive value, the predicate is a property: (lucy, age, 33) ≡ vertex lucy with {"age":33}. If the object is another vertex, the predicate is an edge: (lucy, marriedTo, alain). Used by Datomic, AllegroGraph and others.

The Figure 2-5 data in Turtle (the human-readable RDF format):

@prefix : <urn:example:>. _:lucy a :Person; :name "Lucy"; :bornIn _:idaho. _:idaho a :Location; :name "Idaho"; :type "state"; :within _:usa. _:usa a :Location; :name "United States"; :type "country"; :within _:namerica. _:namerica a :Location; :name "North America"; :type "continent".

Semicolons let you say several things about one subject — the same data can be written as one triple per line (Example 2-6) or verbose RDF/XML (Example 2-8, best left unvisited). The _: names are just local file-scoped identifiers for vertices.

A word on the semantic web

Triples got famous as RDF, the format for the “semantic web” — the idea that websites should publish machine-readable data, combinable into an internet-wide “database of everything.” It was overhyped in the early 2000s and hasn’t materialized, which made many people cynical; the standards effort also produced a dizzying plethora of acronyms and hubris. But look past the failings and there’s real value: triples are a good internal data model, whether or not you publish RDF. (RDF uses URIs for predicates so different organizations can merge data without collisions: urn:example:within vs. http://other.org/foo#within.)

SPARQL — SPARQL Protocol and RDF Query Language, pronounced “sparkle” — is the triple-store query language, and it predates Cypher (which borrowed its pattern matching). The emigration query:

PREFIX : <urn:example:> SELECT ?personName WHERE { ?person :name ?personName. ?person :bornIn / :within* / :name "United States". ?person :livesIn / :within* / :name "Europe". }

Compare the notations — Cypher (person) -[:BORN_IN]-> () -[:WITHIN*0..]-> (location) versus SPARQL ?person :bornIn / :within* ?location. — and RDF’s simplification of properties: no distinction between properties and edges, just predicates, so {name:'United States'} becomes ?usa :name "United States".. SPARQL is a nice language — even if the semantic web never happens.

Graph databases vs. the network model — aren’t they CODASYL reborn?

Understandable suspicion, wrong in four ways:

i.

Schema

CODASYL fixed which record types could nest within which. In a graph, any vertex can connect to any vertex.

ii.

Access

CODASYL records were reachable only via access paths; graph vertices are addressable directly by unique ID or via any indexed property.

iii.

Ordering

CODASYL children were an ordered set that the database maintained; graph vertices and edges are unordered — sort only at query time.

iv.

Queries

CODASYL queries were imperative and broke on schema changes; graphs have declarative languages like Cypher and SPARQL (though Gremlin stays imperative; Pregel handles bulk graph processing — Chapter 10).

The foundation: Datalog

Datalog is much older — studied extensively by academics in the 1980s — and less known among engineers, but important because it is the foundation later query languages build on. It’s the query language of Datomic, and Cascalog implements it for Hadoop. The data model generalizes triples slightly: write predicate(subject, object). The facts:

name(namerica, 'North America'). type(namerica, continent). name(usa, 'United States'). type(usa, country). within(usa, namerica). name(idaho, 'Idaho'). type(idaho, state). within(idaho, usa). name(lucy, 'Lucy'). born_in(lucy, idaho).

And the emigration query — as rules that define new predicates from existing ones:

within_recursive(Location, Name) :- name(Location, Name). /* Rule 1 */ within_recursive(Location, Name) :- within(Location, Via), /* Rule 2 */ within_recursive(Via, Name). migrated(Name, BornIn, LivingIn) :- name(Person, Name), /* Rule 3 */ born_in(Person, BornLoc), within_recursive(BornLoc, BornIn), lives_in(Person, LivingLoc), within_recursive(LivingLoc, LivingIn). ?- migrated(Who, 'United States', 'Europe'). /* Who = 'Lucy'. */

Uppercase-initial words are variables; a rule fires when all predicates on the right of :- match, and then the left side becomes true with the bound values. Rule 1 applied to name(namerica, 'North America') generates within_recursive(namerica, 'North America'); rule 2 then cascades — within(usa, namerica) plus the previous result generates within_recursive(usa, 'North America'), and so on down to Idaho. Rules can refer to rules, like functions calling functions — build complex queries a piece at a time, and reuse them. A different kind of thinking; less convenient for one-off queries, but powerful when your data is complex.

2.4 · Pulling it together

Summary

The chapter in one card

Data started as one big tree (the hierarchical model). That was bad at many-to-many, so the relational model won. Some applications don’t fit relational either, so NoSQL split in two directions: document databases for self-contained documents with rare cross-links, and graph databases for the opposite — anything potentially related to everything. All three are widely used, each best in its domain; one can emulate another, but awkwardly, which is why we have different systems rather than one size fits all. And all three leave the schema question to you: explicit on write, or implicit on read.

Glossary

impedance mismatch
The disconnect between object-oriented application code and relational tables/rows/columns (term borrowed from electronics, where mismatched circuit impedances cause signal trouble).
normalization
Removing duplication so each piece of information is stored in exactly one place; rule of thumb — if you’re duplicating values that could live in one place, the schema isn’t normalized.
shredding
Splitting a document-like structure into multiple relational tables (positions, education, contact_info…).
schema-on-read
Structure is implicit, interpreted at read time — like dynamic type checking.
schema-on-write
Explicit schema enforced at write time — like static type checking.
document reference
The document-model equivalent of a relational foreign key.
NoSQL
Originally a Twitter hashtag for a 2009 meetup on open-source, distributed, nonrelational databases; retroactively “Not Only SQL”.
polyglot persistence
Relational and nonrelational datastores used side by side, each where it fits.
hierarchical model
IBM IMS’s model (1968): all data as a tree of records nested in records — like JSON, one-to-many friendly, many-to-many hostile.
network model (CODASYL)
Generalization where records can have multiple parents, linked by disk-stored pointers; querying meant following access paths with a cursor.
access path
In CODASYL, the chain of links you had to follow from a root record to reach the data — chosen by the programmer.
query optimizer
The component that chooses indexes, join order, and execution plan — access paths made automatic.
declarative / imperative
Declarative (SQL, CSS, XPath): specify the pattern of results. Imperative (CODASYL, DOM scripting): specify the operations, in order.
MapReduce
Bulk-processing model built on pure map and reduce functions; in-between declarative and imperative.
aggregation pipeline
MongoDB 2.2’s declarative query language — “NoSQL reinventing SQL, in disguise”.
property graph
Vertices + edges, both with unique IDs and property maps; edges have tail, head, and label.
triple-store
Everything as (subject, predicate, object) triples; objects are either primitive values (properties) or other vertices (edges).
RDF / Turtle
Resource Description Framework — machine-readable data for the semantic web; Turtle is its human-readable format.
SPARQL
“Sparkle” — the RDF query language; Cypher’s pattern matching was borrowed from it.
Datalog
1980s logic-programming query language; queries as rules that derive new predicates, composable and reusable.
recursive CTE
SQL:1999’s WITH RECURSIVE — how SQL handles variable-length traversals (29 lines at a time).
